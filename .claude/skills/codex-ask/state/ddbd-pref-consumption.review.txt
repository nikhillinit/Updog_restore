### Semantics

Residual weighting is correct only if you first decide that accrued preference is one fund-level claim consumed serially by deal pools. That is effectively hybrid/whole-fund treatment for preference, conflicting with repo’s stated “no cross-deal subsidy” model.

Order invariance has three different answers:

- Aggregate preferred return, enough proceeds: yes, each partner eventually receives its complete quantized residual.
- Per-pool tier results: no. First pool consumes preference; later pools do not.
- Aggregate catch-up/carry outcomes: not generally invariant, even when aggregate proceeds fully cover preference.

Concrete catch-up counterexample: LP-only preference `100`, post-ROC pool capacities `100` and `200`, catch-up rate `80%`, carry `20%`.

- `100` pool first: preference consumes it completely; second pool goes directly to carry. Aggregate GP profit `40`.
- `200` pool first: it pays preference, catch-up, then carry; second pool also pays carry. Aggregate GP profit `60`.

Total proceeds are identical and sufficient. Difference comes from attaching global preference to whichever per-pool G/L accumulator runs first.

Bounded preference also has micro-unit order dependence from repeated LRM. With residual units `[1,4]` and pool caps `[1,2]`, forward processing allocates `[1,2]`; reversing caps allocates `[0,3]`. Exact proportional arithmetic would be path-independent, but per-pool quantization is not.

Therefore I would fail closed whenever deal-by-deal has multiple positive-proceeds pools plus positive preferred-return entitlement. A deterministic sort merely creates an arbitrary deal priority; it does not restore pool independence. The broader engine also allocates each pool’s ROC and catch-up/carry partner buckets using fund-level `settledCapital`, so this preference map alone cannot certify partner-level deal-by-deal semantics.

### Quantization

Yes: consumption must decrement post-LRM emitted amounts, never raw Decimal shares.

Prefer a `bigint` six-decimal-unit residual map:

- Quantize each eligible partner’s opening preference once.
- Pool target = `min(sum(residualUnits), decimalToCentsFloor(remaining))`.
- LRM using remaining residual units as weights.
- Decrement exact allocated units.
- Return/subtract the summed emitted amount.
- Update per-pool G/L using emitted GP/LP sums, as current code already does.

Current preference allocator returns raw `prefTarget` while partner emissions are quantized. Accrual balances can exceed six-decimal precision, so raw decrement would leave dust or make `allocated`, partner emissions, remaining proceeds, and consumed ledger disagree. Catch-up/carry already follow the stronger emitted-total discipline in [`catch-up-allocation-v2.ts`](/Users/nikhil/code/Updog_restore/shared/lib/internal-economics/v2/catch-up-allocation-v2.ts:23).

Tests should keep pool-order invariance only for zero preference. For nonzero preference, either assert the new refusal, or explicitly acknowledge serial global semantics and test the material catch-up counterexample—not merely aggregate preference conservation.

**Bottom line:** Shared residual consumption fixes the 44k-to-88k conservation bug, but it invents cross-pool preference priority and makes deal-by-deal economics order-dependent. Given the repository’s no-cross-deal-subsidy contract and missing provenance, fail closed for multi-pool preference; when consumption is valid, track and decrement exact post-LRM integer units.
