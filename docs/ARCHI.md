### Path aliases — three separate places, NOT fully aligned

Root `tsconfig.json` defines five aliases: `@/*` → `client/src`, `@/core/*`,
`@/lib/*` → client-scoped, `@shared/*` → `shared/`, `@server/*` → `server/`
(server-only, correctly absent from the client bundle below).

`vite.config.ts`'s own `resolve.alias` array manually hardcodes four of them for
the client bundle (`@`, `@/core`, `@/lib`, `@shared`) — these are not sourced
from any tsconfig at build time.

Separately, `vite.config.ts` also runs the `vite-tsconfig-paths` plugin, but
points it at `client/tsconfig.json` (not root `tsconfig.json`) — and
`client/tsconfig.json` **overrides** (does not merge with/inherit)
`compilerOptions.paths`, defining only `@/*` and `@shared/*`. So `@/core` and
`@/lib` exist **only** as the hardcoded Vite runtime aliases above — they aren't
in the `paths` that `client/tsconfig.json` (the project editors/IDE tooling
actually load for client code) resolves against. They work at build/dev runtime;
they may not type-resolve or IDE-navigate depending on which tsconfig your
tooling loads.

There is no single generated source of truth for aliases — if you add one,
update `tsconfig.json`, `vite.config.ts`'s `resolve.alias`, and (if it needs to
resolve in the client TS project/editor) `client/tsconfig.json`'s `paths`, all
three by hand.

## 3. Server Architecture — Two Deployment Surfaces

Confirmed by reading `server/app.ts`, `server/routes.ts`, `vercel.json`,
`Dockerfile*`, and `scripts/build-vercel-api.mjs` directly — this is not
inferred:

> **v1.5.0 driver switch (ADR-073)**: the Vercel branch of `server/db.ts` now
> builds the Neon WebSocket `Pool` + `drizzle-orm/neon-serverless` (transaction
> capable), no longer neon-http. Both Neon branches pass `ws.default` as
> `neonConfig.webSocketConstructor` (the module namespace silently breaks every
> non-localhost WebSocket) and attach non-fatal pool error listeners. P0
> current-forecast/mode/MOIC and six LP-reporting mutations additionally
> collapsed to single guarded claim-last CTE statements (ledger row inserted
> last, already completed - PostgreSQL CTEs cannot update a row inserted in the
> same statement); pointer advance stays a callback transaction (class b).
> Real-driver proof: `tests/integration/neon-http/` lane (`npm run test:neon`,
> required `neon-lane` job in the CI Gate Status rollup) plus the pg-driver
> lifecycle proof in `tests/integration/current-forecast-reference.pg.test.ts`.

- **Vercel / production** — `vercel.json` rewrites `/api/:slug*` →
  `api/[...slug].ts`, which imports a bundled `_app.generated.mjs` (produced by
  `scripts/build-vercel-api.mjs`, entry point `server/app.ts`) and calls
  **`makeApp()`** (`server/app.ts:28`, sync, returns an Express app, never calls
  `.listen()`, default-exported at line 229). Mount order is **interleaved**,
  not sequential-after: health router → metrics router (+ `/api` mount) → RUM
  ingress guards → metrics-rum router (+ `/api` mount) → auth middleware
  (`requireApiAuth`, public-path exempted) → CSRF middleware →
  `mountCommonRoutes({group: 'pre_runtime'})` → reserves-v1, cashflow,
  calculations, ai, scenario-analysis routers →
  `mountCommonRoutes({group: 'post_runtime'})`. The two `mountCommonRoutes`
  calls bracket the five named routers, not follow all direct mounts as one
  block.
- **Docker / Railway** — `Dockerfile` and `Dockerfile.railway` both run
  `node dist/index.js`, built from entry point `server/bootstrap.ts`
  (`scripts/build-server.mjs`). `bootstrap.ts` calls `createServer()`
  (`server/server.ts`) — a **separate** Express app with DI providers,
  RLS-transaction middleware, idempotency middleware, and static/Vite serving —
  which calls `await registerRoutes(app)` (`server/routes.ts:38`) and returns an
  `http.Server` with WebSocket setup. Local dev (`npm run dev:api` =
  `npx tsx server/main.ts`) uses this same `bootstrap()` chain, **not**
  `makeApp`.

**Routes that exist only on the Docker/Railway surface** (mounted by
`registerRoutes`, no equivalent in `makeApp`) — these **404 on Vercel prod**:
`activities`, `fund-metrics-legacy`, `engine-summaries`, `operations`,
`monte-carlo`, `cache`, `performance-metrics`, `sse-events`, `lp-health`,
`admin/engine`, `portfolio-intelligence` (flag-gated), `error-budget`,
`dev-dashboard` (dev-only).

**`server/services/internal-analysis/analysis-checkpoint-service.ts` (2110
lines): checkpoint creation IS reachable from the Vercel/`makeApp` surface** —
prior `[UNVERIFIED]` tag resolved 2026-08-04 by call-chain trace. Two distinct
entry paths:

- **HTTP path (both surfaces, incl. Vercel)**: `internal-analysis` is the
  terminal element of the common-route manifest, so
  `mountCommonRoutes({surface:'make_app', group:'post_runtime'})`
  (`server/app.ts:210`) mounts `internalAnalysisRouter`
  (`mount-common-routes.ts:110`). Its routes call the service directly:
  `createDraftForPeriod` (route `internal-analysis.ts:437`),
  `refreshDraftWithReceipt` (:535), `saveDraftWithReceipt` (:579, finalizes
  draft into the immutable reference), `startCorrectionDraft` (:664). Gated by
  auth/fund-scope/write-role, no feature flag.
- **Scheduler path (Docker/Railway only)**: `.start()`
  (`analysis-checkpoint-service.ts:1921`, called only at `server/routes.ts:45`)
  is a dual `setInterval` in-process poller — planner enqueues `job_outbox` rows
  (`job_type='quarterly_analysis_draft'`), processor claims
  (`FOR UPDATE SKIP LOCKED`) and runs `createDraftForPeriod`. Gated by
  `ENABLE_QUARTERLY_ANALYSIS !== '0'`. Not BullMQ — `workers/` has zero
  references to this service. An admin route
  (`POST /api/admin/funds/:fundId/internal-analysis/quarterly-draft-run`,
  `internal-analysis.ts:722`) can _enqueue_ from Vercel, but only the
  Railway-resident poller _processes_ — quarterly auto-creation is
  Railway-exclusive.

**Shadow wiring (NEW-A, shipped in v1.4.0)**:
`server/services/current-forecast-shadow-trigger.ts` is invoked at both
production facts-commit call-sites — the `financial-facts` route and the
`analysis-checkpoint-service` `rebuildBasis` port (which fires on the Vercel
HTTP path via `createDraftForPeriod`/`refreshDraft`/
`replaceDraftEconomicsReference`, not just the Railway scheduler) — so shadow
execution reaches both surfaces; only the automatic quarterly cadence is
worker-only. The trigger runs one bounded execution race (mode resolution, facts
lookup, plan resolution, receipt get-or-create, replay) and persists failures
conflict-tolerantly with its own five-second cap. Companion runtime pieces:
`current-forecast-serving-seam.ts` (sole sanctioned facade over
`metricsAggregator` for `dual-forecast`, `fund-metrics`,
`h9-artifact-invalidation-service`), `current-forecast-resume-command.ts`
(idempotency-keyed admin resume/re-arm from `held`), and
`server/lib/transaction-support.ts` (Neon HTTP autocommit fallback with hardened
detection since v1.5.0: exact-match pin on the driver error plus a loud
near-match failure on driver-message drift; usage fenced by the
`guard:transaction-support:check` lint guardrail per ADR-073).

### Route mounting mechanism

`server/routes/mount-common-routes.ts` exports:

```
mountCommonRoutes(app: Express, options:
  | {surface:'make_app', group: keyof COMMON_ROUTE_GROUPS.make_app}
  | {surface:'register_routes', group: keyof COMMON_ROUTE_GROUPS.register_routes}
): void
```

Groups are **contiguous boundary-pair slices** of an ordered route-id list, not
a free list. `COMMON_ROUTE_IMPLEMENTATIONS` (44 entries) `satisfies` a type
derived from `shared/routes/api-route-manifest.ts` (`CommonApiRouteId`), so
TypeScript enforces impl-map completeness against the manifest — but
**group-boundary coverage is hand-maintained, not type-checked**. A
manifest+impl entry inserted between two existing boundary ids without updating
the group boundaries silently drops off that surface. Guarded (currently gapless
on both surfaces) by: `tests/unit/server/route-mount-parity.test.ts`,
`tests/integration/dual-surface-mount-parity.test.ts`,
`tests/integration/common-route-probe-parity.test.ts`.

Per-route auth/governance is separately declared in
`server/route-policy/api-route-policy-registry.ts` (85KB;
`RoutePolicyEntry`/`FinancialSurface`: `apiAuthBoundary`, `fundScopeMode`,
`workflowRequirement`, `exportPolicy`, `provenanceRequired`,
`humanReviewRequired`, `performanceBudgetMs`), validated by
`npm run policy:verify`.

Role authorization is centralized in `shared/auth/effective-roles.ts` (ADR-072):
canonical roles `admin/partner/analyst/service`, legacy aliases
`operator -> partner` and `viewer -> analyst`, and capabilities
(`flag_read`/`flag_admin` -> admin, `reserve_admin` -> partner, admin superset).
Guards in `server/lib/auth/jwt.ts` (`requireRole`, `requireAnyRole`,
`requireWriteRole`, `requireCapability`) read
`req.user?.role ?? req.context?.role`, so they work on both surfaces; role
arrays in route files import `TEAM_WRITE_ROLES`/`PARTNER_WRITE_ROLES` from the
shared module. `/ws/portfolio-metrics` upgrades are authenticated
(callback-style `verifyClient` — never one-arg async, `ws` treats a returned
Promise as truthy) and subscriptions are fund-scope authorized.

**Rule for any new route**: manifest entry
(`shared/routes/api-route-manifest.ts`) + impl-map entry
(`mount-common-routes.ts`) + group-slice on **both** surfaces + a route-policy
entry, or it 404s on whichever surface you forgot, or ships without a declared
auth boundary.

## 9. Guidance for New Work (patterns confirmed above, not aspirational)

**New API endpoint**: add to `shared/routes/api-route-manifest.ts` → impl entry
in `server/routes/mount-common-routes.ts` → group-slice on **both** `make_app`
and `register_routes` surfaces → entry in
`server/route-policy/api-route-policy-registry.ts`. Skipping any one of these
either 404s the route on one surface or ships it with no declared auth boundary.
Idempotency required on mutations (`server/lib/idempotent-command.ts`).

**New DB/schema change**: new domain file under `shared/schema/` (confirm its
re-export path into `shared/schema.ts` first — §4), new additive + replay-safe
migration file under `migrations/`. Read `migrations/meta/_journal.json` fresh
at dispatch time for the real next index — do not trust a plan doc's claimed
tail (§4 caught exactly this). Migration pins must assert their own journal
entry, never `entries.at(-1)`. Avoid `unique()`→`uniqueIndex` FK-target
mismatches (drizzle 42830).

**New UI page/component**: place under `client/src/pages/` or
`client/src/components/<domain>/`; register in
`shared/routes/app-route-definitions.ts` + `client/src/app/app-routes.tsx`;
decide which of the three surfaces (§5) it belongs to and add a
`route-governance-registry.ts` entry; use `presson.*` design tokens only
(`DESIGN.md`), primary accent charcoal `#292929`, never blue.

**New feature flag**: entry in `flags/registry.yaml` → `npm run flags:generate`

zero production reads is dead weight (see `#1299-R` precedent in §8 — it was
deleted, not left inert).

`npm run phoenix:truth`; Decimal.js discipline is enforced by the
