## Overview

The canonical web app (`068430726a`) enqueues reserve scenario calculations
without a `runId` and without creating a `fund_scenario_calculation_runs` row.
The deployed worker (`55c9a6a2b`, 2026-10-01) only executes a delivery that
matches a `queued` run row. For a canonical-web delivery it finds no run, logs
one `info` line, returns a private sentinel, and the BullMQ handler records the
job as a success. The calculation never happens and nothing durable says so.

This plan has two deliverables:

1. An owner-run, read-only reconciliation SQL (appendix) that measures how many
   `calculation_queued` events since 2026-08-09 have no run: a measured lower
   bound on the exposure, and the resubmission list for after the next release.
2. A small pre-release PR that makes an unmatched delivery a visible,
   non-retryable job failure with its own log line, reason-labelled counter, and
   duration outcome label; keeps stale duplicates quiet but counted; leaves
   genuine mid-calculation ownership loss unchanged; adds regression tests;
   records the diagnosis path for the unexplained database-health 503; and
   states how it feeds the next governed two-phase release.

The fix for the drop itself is already on `main`: `acquireReserveCalculationRun`
in `server/services/fund-scenario-calc-queue-service.ts:112-160` creates the
`queued` run before enqueueing and passes `runId` in the job (`:192`). It
reaches production only through a fresh two-phase release. This plan does not
re-plan the producer and does not replace that release.

## Solution Architecture

Three delivery outcomes, separated where they are decided:

| Case                           | Where decided                                                                                                                                                                                                                                                                                                                                              | Today                         | After this PR                                                                                                                               |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Unmatched delivery             | `claimReserveScenarioRun`: no `runId` and the legacy finder returns no `queued` or `running` row (`:713`, `legacy_no_run`); or `runId` set, the claim CAS returns zero rows, the timeout CAS did nothing, and the fenced read-back finds no row (`missing_run`) or a row whose job id or identity fence does not match this delivery (`identity_mismatch`) | `info`, sentinel, job success | `warn` with ids and reason, throw `UnmatchedScenarioDeliveryError`, counter by `reason`, `UnrecoverableError`, outcome `unmatched_delivery` |
| Stale duplicate                | legacy run found `running` (`:713`); or claim CAS zero rows and the row timed out, or reads back with a matching fence in any status (`:722`)                                                                                                                                                                                                              | `info`, sentinel, job success | Same, plus counter `fund_scenario_stale_deliveries_total`                                                                                   |
| Mid-calculation ownership loss | `ScenarioRunOwnershipLostError` (`:821`, `:949`)                                                                                                                                                                                                                                                                                                           | sentinel, job success         | Unchanged                                                                                                                                   |

Why non-retryable: on `origin/main` the producer commits the run row and binds
its job id inside one transaction
(`fund-scenario-calc-queue-service.ts:129-160`) before
`ensureReserveCalculationJob` adds the job (`:162-217`). A job can never precede
its run, so a delivery with no run is a contract violation, not a race. A retry
would only re-log it. `UnrecoverableError` lands the job in the failed set, kept
24 hours by `removeOnFail {age 86400}`.

Where the drop becomes visible, in order of dependability:

1. The worker's own `/metrics` endpoint (`workers/health-server.ts:243`,
   prom-client registry through `getMetrics`):
   `fund_scenario_unmatched_deliveries_total{reason}` and
   `worker_job_duration_seconds{outcome="unmatched_delivery"}`.
2. The two `warn` lines (service and handler) with fund, scenario set, job, and
   correlation ids.
3. The BullMQ failed set itself, for 24 hours, on the workers' Redis.
4. `GET /api/health/queues` (`server/routes/health.ts:462`, counts from
   `:93-98`) is best-effort only: on Vercel the `fund-scenario-calc` producer
   runtime initializes lazily, so an instance that never enqueued reports
   `not_applicable`, and the count is per instance.

Why a zero-row claim is split three ways: with `runId` present, a zero-row claim
CAS (`:721`) today collapses three states. The row may be gone (run rows are
never deleted by application code; only a cascade from `fund_scenario_sets` or
`funds` removes them), which is `missing_run`. The row may match this delivery's
job id and identity fence: another attempt or worker owns or finished it, the
row just expired and the timeout CAS terminalized it, or a failed non-final
attempt's retry requeue (`requeueScenarioCalculationRunIfRunning`, run-service
`:649-671`) moved it from `running` back to `queued` between the claim and the
read-back (Read Committed takes a fresh snapshot per statement). All of these
are stale duplicates, legitimate. Or the row exists but its job id or identity
does not match the delivery, so the fence in
`claimScenarioCalculationRunIfQueued` (run-service `:535-557`) rejected it:
`identity_mismatch`, a contract violation. The read-back therefore classifies by
the fence, never by status: a `queued` row is not evidence of a mismatch. A
fence-matching row past its deadline never reaches the read-back, because the
timeout CAS terminalizes it first. Only the middle state stays quiet, which
keeps the post-release signal exact.

Why a legacy delivery without a `queued` or `running` run fails: only the old
producer sends deliveries without `runId`, and no current code creates a run for
one, so every legacy row is a July-era run, months older than BullMQ's longest
retention (`removeOnFail` one day). A legacy delivery whose identity matches
only a `completed`, `failed`, or `cancelled` legacy row is therefore a new POST
under a reused deterministic job id, not a redelivery, and the finder
(`:559-598`) does not return it. A `failed` or `cancelled` row proves that POST
was not calculated, so counting it stale would trade a visible failure for a
silent drop; it is `legacy_no_run`. A `running` legacy row stays stale because
it can be an in-flight duplicate of a delivery that is executing now. The
`reason` label keeps every `legacy_no_run` failure out of the post-release
defect signal (Release coupling).

Why the runner needs no change: `createReserveScenarioCalculationRunner`'s catch
block (`:948-990`) only persists a failure or requeues when `claimed` is set. An
error thrown from `claimReserveScenarioRun` leaves `claimed` undefined, so the
block rethrows with no run-state write and no event. The claim transaction rolls
back; it only read.

Why the stale counter lives in the service: the handler cannot tell a stale
duplicate from mid-calculation loss (both return the sentinel), and widening the
sentinel into a discriminated outcome would touch every consumer. One `inc()` at
the two stale sites is smaller.

This changes worker delivery semantics, not calculation math. No Phoenix truth
case changes. `scripts/ci/classify-change-paths.mjs:22` treats every
`server/services/` path as financially relevant, so `financial-truth`
(`npm run phoenix:truth`) runs on the PR; it is expected to pass unchanged.

## Implementation Details

### 1. Service: separate unmatched from stale

`server/services/fund-scenario-reserve-calculation-service.ts`

- Export `class UnmatchedScenarioDeliveryError extends Error` beside
  `ScenarioRunOwnershipLostError` (`:196`). Constructor takes
  `reason: 'legacy_no_run' | 'missing_run' | 'identity_mismatch'` plus `fundId`,
  `scenarioSetId`, `jobId`, `correlationId` as readonly fields; the message is
  reason-specific ("Fund scenario delivery has no calculation run" for the first
  two, "Fund scenario delivery was rejected by the run identity fence" for the
  third) so BullMQ's `failedReason` carries it.
- In `claimReserveScenarioRun` replace the combined branch at `:713-719` with
  two:
  1. `deliveryRunId === null` (no `runId`, and the legacy finder returned no
     `queued` or `running` row):
     `logger.warn({fundId, scenarioSetId, jobId: runIdentity.jobId, correlationId: input.correlationId, reason: 'legacy_no_run'}, 'Fund scenario delivery has no calculation run')`
     then `throw new UnmatchedScenarioDeliveryError(...)` with
     `reason: 'legacy_no_run'`. No actor label, no PII.
  2. `input.runId === undefined && legacyDeliveryRun.status !== 'queued'`: keep
     the existing `info` line, call `metrics.fundScenarioStaleDeliveries.inc()`,
     return `null`.
- At the claim-CAS zero-row site (`:722-735`), after the timeout CAS:
  - `timedOut > 0`: the row expired and was terminalized. Existing `info` line,
    `metrics.fundScenarioStaleDeliveries.inc()`, `return null`.
  - Otherwise read the row back with a new
    `readScenarioCalculationRunFence(client, runId, identity)` in
    `server/services/fund-scenario-calculation-run-service.ts`, beside
    `findScenarioCalculationRunForDelivery` (`:559`): one
    `SELECT *, (job_id IS NOT DISTINCT FROM $12${ASYNC_RUN_IDENTITY_FENCE_SQL}) AS fence_matches FROM fund_scenario_calculation_runs WHERE id = $1`
    with `asyncRunFenceParams(runId, identity)` (`:494`; all twelve parameters
    are used, so the 42P18 unused-parameter trap noted at `:564-565` does not
    apply), returning `null` for no row, else
    `{ run: mapRun(row), fenceMatches: row.fence_matches === true }`. Branch on
    the fence, never on status:
    - no row: `warn` and `throw new UnmatchedScenarioDeliveryError(...)` with
      `reason: 'missing_run'`;
    - `fenceMatches === false`: the claim CAS rejected this delivery by job id
      or identity fence (`ASYNC_RUN_IDENTITY_FENCE_SQL`, run-service
      `:523-533`). Contract violation: `warn` with the ids and the row's
      `jobId`, then `throw new UnmatchedScenarioDeliveryError(...)` with
      `reason: 'identity_mismatch'`;
    - `fenceMatches === true`, any status (including `queued` after a retry
      requeue between the claim and the read): stale duplicate. Existing `info`
      line, stale counter, `return null`.
  - No row lock: classification by fence does not depend on status, so the
    interleaving between the claim and the read cannot change the outcome.
  - The handler treats all three reasons the same (fail non-retryably, one
    counter labelled by `reason`) and logs the reason.
- Import `metrics` from `../../lib/metrics` (the module already runs on both
  surfaces through `lib/metrics.ts` consumers).

## Technical Considerations

### Idempotency and duplicates (AGENTS.md mandates)

- Unmatched delivery writes nothing; the claim transaction only reads and rolls
  back on throw. Failing the job is idempotent: a retry of the same job would
  reach the same branch, which is why it is marked unrecoverable.
- Stale duplicate behaviour is unchanged: zero-row claim CAS, timeout CAS no-op
  for unexpired rows, `null` return. Only a fence read-back and a counter are
  added.
- Mid-calculation ownership loss is unchanged.
- Optimistic locking, cursors, and job timeouts are untouched; the hard deadline
  path (`isFundScenarioHardTimeoutError`) keeps precedence over nothing new
  because the unmatched branch runs before any claim.

### Observability

- `warn` log in both service and handler carries fund, scenario set, job, and
  correlation ids plus the `reason`; no actor label, no PII.
- `worker_job_duration_seconds{worker_type="fund-scenario-calc",outcome="unmatched_delivery"}`
  separates drops from `success`, `failure`, `hard_timeout`.
- `fund_scenario_unmatched_deliveries_total{reason}` (three values) and the
  label-free `fund_scenario_stale_deliveries_total`.
- BullMQ failed set retains the job 24 hours. The worker's `/stats` endpoint
  (`workers/health-server.ts:256`) reports `errors` per worker since boot, and
  `GET /api/health/queues` is best-effort only (see Solution Architecture).

### Collecting the worker signal

The Railway workers are private and domainless (ADR-075 in `DECISIONS.md`); the
operator reaches their health server through a local `railway ssh` data-plane
session, which is how the ADR-082 `/health` and `/ready` captures for
`fund-health.json` are made today. In that same session, on the same port,
`GET /metrics` (`workers/health-server.ts:243`) returns the Prometheus text with
`fund_scenario_unmatched_deliveries_total` per `reason`,
`fund_scenario_stale_deliveries_total`, and
`worker_job_duration_seconds_count{worker_type="fund-scenario-calc",outcome="unmatched_delivery"}`;
`GET /stats` returns `errors` per worker. The operator evidence bundle schema
(`scripts/release/operator-evidence-bundle.mjs:52-60`, `.strict()`) is not
widened by this plan; the metric capture is an owner note beside the bundle, not
part of it. Counters reset on worker restart, so every reading is recorded with
the worker deployment it came from.

### Why not retry, requeue, or create the run

Creating a run from the worker would reintroduce the July lazy-create path that
`869dfd3e8` removed on purpose (the run is the command's durable claim). A
canonical-web delivery has no command row either
(`fund_scenario_calculation_commands`, migration 0053), so there is nothing to
recover into. Visibility plus owner resubmission after the release is the
correct scope.

### Release coupling

- Worker code changes, so the next release takes the two-phase route in

- Between phase A and phase B the canonical web still runs the old producer.
  With this PR deployed in phase A, every canonical-web delivery during that
  window fails visibly as `reason="legacy_no_run"` instead of silently; the
  worker `/metrics` counters, the `unmatched_delivery` outcome, and the `warn`
  lines give the owner a live exposure signal for the gap. The owner records the
  counter readings at phase A verification and after phase B, each with the
  worker deployment it came from.
- Reading rule, no baseline needed: only the current producer sends `runId`
  (staged release canaries included), and it commits the run first, so
  `fund_scenario_unmatched_deliveries_total{reason="missing_run"}` or
  `{reason="identity_mismatch"}` above zero at any reading, before or after
  promotion, is a defect. `{reason="legacy_no_run"}` is old-producer exposure,
  not a defect: it keeps rising while canonical web runs the old producer,
  through phase B staging, and for old-producer jobs still queued at promotion.
  Each `legacy_no_run` warn line names a resubmission candidate. After phase B
  the canonical web runs the current producer (`runId` in the job, run committed
  first), so `legacy_no_run` stops once that backlog drains. Phase B reuses the
  phase A worker deployment (exact-SHA reuse path, `PRODUCTION_SCRIPTS.md`
  "Railway worker deploy stage"), so readings across the phases come from one
  process unless it restarted; counters reset on restart.
- The release remains blocked on its own smoke evidence: the 503 (this plan's
  diagnosis step) and canary 1 (#1613, unproven). This PR does not repair the
  release workflow.

### Post-release recovery

Scenario sets the reconciliation classifies as `no_run_drop_candidate` or
`repeat_job_id`, plus those named by `legacy_no_run` warn lines, are resubmitted
by the owner after phase B through the ordinary `calculate-reserve` command. The
dedup index `fund_scenario_calc_runs_active_dedup_idx` (migration 0034) has no
row for a dropped set, so the new producer creates a fresh run with a fresh
`__run__` job id. Resubmission is not part of this PR.

### Canonical post-promotion check (decision D-B)

- Option (a): run a canary-5-equivalent after promotion against the canonical
  host. Cost: a new post-promotion step in `release-production.yml`, a recovery
  handle and residue assertion for the canonical database, and a change to the
  byte-governed residue contract
  (`release-canary-residue-characterization-v2.contract.ts`) or a new v3. It
  mints real residue on production on every release.
- Option (b), recommended: a separate follow-up plan owns that contract and
  workflow change. Interim visibility after this PR: the worker `/metrics`
  counters and `unmatched_delivery` outcome, the `warn` lines, and the failed
  set (`GET /api/health/queues` only best-effort). The reconciliation SQL re-run

### How to run

1. Use a read-capable role for `fund_scenario_set_events`,
   `fund_scenario_calculation_runs`, and `funds`. Record the role name: result
   set 1 prints it. A role restricted by row-level security or by grants would
   under-count; the migrations do not enable RLS on these tables, so the
   expected effect is nil, but the owner states the role either way.
2. Edit only the three constants in the single `params` CTE (window start,
   window end, stuck threshold); there is one copy. The default window start is
   the conservative exposure bound `2026-08-09T00:00:00Z`.
3. Run the whole script as one session (`psql -v ON_ERROR_STOP=1 -f`). It opens
   a `READ ONLY` transaction, sets a 60 second statement timeout, issues two
   `SELECT`s, and ends with `ROLLBACK`. No writes, no temporary objects.
4. Keep the `row_kind = 'event'` rows of result set 2 for the resubmission list.

### How to read the output

Result set 1 is context: role, superuser flag, three column-presence flags,
visible row totals, and the first and last `calculation_queued` timestamps
across all time.

- `has_deadline_at = false`: migration 0050 is not applied; `stuck` then means
  "no update for `stuck_after`" only.
- `has_data_origin = false` or `has_canary_run_id = false`: migration 0051 is
  not applied; `canary_fund` is always false and no canary exclusion is needed
  (canary funds cannot exist without that schema).

- `queued_events_visible_all_time = 0`, or no event in the window: no
  `calculation_queued` event was recorded, which is a lower bound on exposure,
  not proof of none. The old producer inserts the event after `queue.add`
  returns (`068430726a` `:52-102`), so a job whose event insert failed is
  invisible here. If any Redis failed-set or worker log evidence for the window
  exists, read it alongside; absent that, treat zero events as "no measured
  exposure".

Result set 2 `event` row classifications, in precedence order:

| Classification               | Meaning                                                                                                                                                                                                                                           | Action                                                        |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `completed_with_snapshot`    | Run `completed` with a snapshot                                                                                                                                                                                                                   | None                                                          |
| `failed_or_cancelled`        | Run `failed` or `cancelled`; `run_failure_code` shows why                                                                                                                                                                                         | Ordinary failure handling                                     |
| `completed_without_snapshot` | Run `completed` but no snapshot id; should not occur                                                                                                                                                                                              | Investigate                                                   |
| `stuck`                      | Run `queued` or `running` past `deadline_at`, or with no deadline and no update for `stuck_after`                                                                                                                                                 | Deadline sweep should terminalize; investigate if it persists |
| `in_flight`                  | Run `queued` or `running` inside its deadline                                                                                                                                                                                                     | Re-run later                                                  |
| `superseded`                 | No run for this event's correlation id, but a later `completed` run with the same scenario set and input hash                                                                                                                                     | None; the later run covers it                                 |
| `failed_event_only`          | No run, but a later `calculation_failed` event with the same correlation id                                                                                                                                                                       | Treat as failed                                               |
| `calculated_event_only`      | No run, but a later `calculated` event with the same correlation id; should not occur                                                                                                                                                             | Investigate                                                   |
| `repeat_job_id`              | No run and no later evidence for its correlation id, and an earlier event in the window has the same `job_id`. BullMQ deduplicated it into the earlier delivery only if that job was still retained; after removal the same id was a new delivery | Ambiguous: resubmission candidate                             |
| `no_run_drop_candidate`      | No run and no later evidence for its correlation id                                                                                                                                                                                               | Candidate for resubmission after phase B                      |

- A drop candidate is not proof of loss. Before resubmission, confirm the
  scenario set still exists and is not archived, and check the worker failed set
  and logs for the job id if they are still within retention.
- `canary_fund = true` rows belong to release-canary funds
  (`data_origin = 'release_canary'` or `canary_run_id` set). Exclude them from
  resubmission; they are governed by the residue contract.
- Matching is by `correlation_id` only. A `job_id` match alone cannot tell a
  BullMQ-deduplicated repeat POST from a new delivery under a reused id, so the
  SQL never treats it as evidence; an event that shares an earlier event's
  `job_id` and has no evidence of its own lands in `repeat_job_id`. Resubmission
  is per scenario set, so including those rows costs nothing extra.

The `row_kind = 'summary'` rows of result set 2 carry the counts by
classification (`fund_id` NULL means all funds) and the same counts per fund.
Report exposure as a range: the `no_run_drop_candidate` events are the lower
bound, and adding the `repeat_job_id` events gives the upper bound. Job ids are
reused across deliveries, so `distinct_job_ids` does not count deliveries.

### SQL

```sql
-- F_1.21.0 exposure reconciliation: reserve scenario calculations queued by the
-- canonical web app that the deployed worker may have acknowledged without
-- calculating. Owner-run, read-only. Verified against migrations 0011, 0034,
-- 0050, 0051, 0053 and the producer/worker source at origin/main 95b8ea88a and
-- canonical web 068430726a. Columns added after 0044 (the canonical web tail)
-- are read through to_jsonb so the script runs on either schema.
--
-- Run with any Postgres client as a role that can read fund_scenario_set_events,
-- fund_scenario_calculation_runs, and funds. Record which role ran it.
-- Edit only the three constants in the params CTE.

BEGIN TRANSACTION READ ONLY;
SET LOCAL statement_timeout = '60s';
SET LOCAL lock_timeout = '5s';

-- Result set 1: execution context. Lets the owner record the role, confirm
-- that the window and table sizes look plausible, and see which optional
-- columns exist (they postdate canonical web 068430726a, whose migration tail
-- is 0044; ADR-103 records that the 0050-0053 objects were applied to
-- production by manifest catch-up without ledger rows). The query runs either way.
SELECT
  current_user                                                  AS executed_as_role,
  current_setting('is_superuser')                               AS is_superuser,
  now()                                                         AS executed_at,
  EXISTS (SELECT 1 FROM information_schema.columns
           WHERE table_schema = 'public' AND table_name = 'fund_scenario_calculation_runs'
             AND column_name = 'deadline_at')                   AS has_deadline_at,
  EXISTS (SELECT 1 FROM information_schema.columns
           WHERE table_schema = 'public' AND table_name = 'funds'
             AND column_name = 'data_origin')                   AS has_data_origin,
  EXISTS (SELECT 1 FROM information_schema.columns
           WHERE table_schema = 'public' AND table_name = 'funds'
             AND column_name = 'canary_run_id')                 AS has_canary_run_id,
  (SELECT count(*) FROM fund_scenario_set_events)               AS events_visible_total,
  (SELECT count(*) FROM fund_scenario_calculation_runs)         AS runs_visible_total,
  (SELECT count(*) FROM fund_scenario_set_events
     WHERE event_type = 'calculation_queued')                   AS queued_events_visible_all_time,
  (SELECT min(created_at) FROM fund_scenario_set_events
     WHERE event_type = 'calculation_queued')                   AS first_queued_event_at,
  (SELECT max(created_at) FROM fund_scenario_set_events
     WHERE event_type = 'calculation_queued')                   AS last_queued_event_at;

-- Result set 2: one row per calculation_queued event in the window
-- (row_kind = 'event'), followed by the counts by classification
-- (row_kind = 'summary'; fund_id NULL = all funds, otherwise per fund).
WITH params AS (
  SELECT
    TIMESTAMPTZ '2026-08-09T00:00:00Z' AS window_start,  -- exposure lower bound (edit)
    now()                              AS window_end,    -- exclusive upper bound (edit)
    INTERVAL '6 hours'                 AS stuck_after    -- queued/running with no deadline older than this
),
queued AS (
  SELECT
    e.id                                         AS event_id,
    e.fund_id,
    e.scenario_set_id,
    e.created_at                                 AS queued_at,
    e.change_summary_json->>'job_id'             AS job_id,
    e.change_summary_json->>'correlation_id'     AS correlation_id,
    e.change_summary_json->>'input_hash'         AS input_hash,
    COALESCE(e.change_summary_json->>'hash_kind', 'scenario-input-hash-v1') AS hash_kind
  FROM fund_scenario_set_events e
  CROSS JOIN params p
  WHERE e.event_type = 'calculation_queued'
    AND e.created_at >= p.window_start
    AND e.created_at <  p.window_end
),
matched AS (
  SELECT
    q.*,
    r.id          AS run_id,
    r.status      AS run_status,
    r.snapshot_id AS run_snapshot_id,
    r.failure_code AS run_failure_code,
    -- read through jsonb so the query parses when the 0050 column is absent
    (to_jsonb(r)->>'deadline_at')::timestamptz AS run_deadline_at,
    r.updated_at  AS run_updated_at
  FROM queued q
  -- correlation_id only: job ids are reused across deliveries (the old
  -- producer's id is deterministic and BullMQ forgets it once the job is
  -- removed), so a job_id match cannot prove it is the same delivery
  LEFT JOIN LATERAL (
    SELECT r.*
    FROM fund_scenario_calculation_runs r
    WHERE r.scenario_set_id = q.scenario_set_id
      AND r.fund_id = q.fund_id
      AND r.correlation_id = q.correlation_id
    ORDER BY r.created_at DESC
    LIMIT 1
  ) r ON TRUE
),
enriched AS (
  SELECT
    m.*,
    EXISTS (
      SELECT 1 FROM queued q2
      WHERE q2.job_id = m.job_id
        AND q2.event_id <> m.event_id
        AND (q2.queued_at < m.queued_at OR (q2.queued_at = m.queued_at AND q2.event_id < m.event_id))
    ) AS earlier_event_same_job_id,
    EXISTS (
      SELECT 1 FROM fund_scenario_calculation_runs r2
      WHERE r2.scenario_set_id = m.scenario_set_id
        AND r2.fund_id = m.fund_id
        AND r2.input_hash = m.input_hash
        AND COALESCE(r2.hash_kind, 'scenario-input-hash-v1') = m.hash_kind
        AND r2.status = 'completed'
        AND r2.snapshot_id IS NOT NULL
        AND r2.created_at >= m.queued_at
        AND (m.run_id IS NULL OR r2.id <> m.run_id)
    ) AS later_completed_run_same_input,
    EXISTS (
      SELECT 1 FROM fund_scenario_set_events f
      WHERE f.scenario_set_id = m.scenario_set_id
        AND f.event_type = 'calculation_failed'
        AND f.created_at >= m.queued_at
        AND f.change_summary_json->>'correlation_id' = m.correlation_id
    ) AS later_failed_event_same_delivery,
    EXISTS (
      SELECT 1 FROM fund_scenario_set_events c
      WHERE c.scenario_set_id = m.scenario_set_id
        AND c.event_type = 'calculated'
        AND c.created_at >= m.queued_at
        AND c.change_summary_json->>'correlation_id' = m.correlation_id
    ) AS later_calculated_event_same_delivery,
    EXISTS (
      SELECT 1 FROM funds fu
      WHERE fu.id = m.fund_id
        -- jsonb reads: both columns postdate 068430726a (migration 0051)
        AND (to_jsonb(fu)->>'data_origin' = 'release_canary'
             OR to_jsonb(fu)->>'canary_run_id' IS NOT NULL)
    ) AS canary_fund
  FROM matched m
),
classified AS (
  SELECT
    e.*,
    CASE
      WHEN e.run_status = 'completed' AND e.run_snapshot_id IS NOT NULL THEN 'completed_with_snapshot'
      WHEN e.run_status IN ('failed', 'cancelled')                      THEN 'failed_or_cancelled'
      WHEN e.run_status = 'completed' AND e.run_snapshot_id IS NULL     THEN 'completed_without_snapshot'
      WHEN e.run_status IN ('queued', 'running')
           AND ((e.run_deadline_at IS NOT NULL AND e.run_deadline_at < p.window_end)
                OR (e.run_deadline_at IS NULL AND e.run_updated_at < p.window_end - p.stuck_after))
                                                                        THEN 'stuck'
      WHEN e.run_status IN ('queued', 'running')                        THEN 'in_flight'
      WHEN e.later_completed_run_same_input                             THEN 'superseded'
      WHEN e.later_failed_event_same_delivery                           THEN 'failed_event_only'
      WHEN e.later_calculated_event_same_delivery                       THEN 'calculated_event_only'
      WHEN e.earlier_event_same_job_id                                  THEN 'repeat_job_id'
      ELSE 'no_run_drop_candidate'
    END AS classification
  FROM enriched e
  CROSS JOIN params p
)
SELECT
  'event'                          AS row_kind,
  fund_id,
  scenario_set_id,
  queued_at,
  job_id,
  correlation_id,
  classification,
  run_id,
  run_status,
  run_failure_code,
  canary_fund,
  later_failed_event_same_delivery AS later_failed_event,
  NULL::bigint                     AS events,
  NULL::bigint                     AS distinct_job_ids,
  NULL::bigint                     AS distinct_scenario_sets,
  NULL::bigint                     AS events_on_canary_funds
FROM classified
UNION ALL
SELECT
  'summary',
  fund_id,
  NULL, NULL, NULL, NULL,
  classification,
  NULL, NULL, NULL, NULL, NULL,
  count(*),
  count(DISTINCT job_id),
  count(DISTINCT scenario_set_id),
  count(*) FILTER (WHERE canary_fund)
FROM classified
GROUP BY GROUPING SETS ((classification), (fund_id, classification))
ORDER BY row_kind, classification, fund_id NULLS FIRST, queued_at, job_id;

ROLLBACK;
```
