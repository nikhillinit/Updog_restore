Map: Activation Discipline vs Continued Capability Work", delivered as
`PLAN (12).md`) into the plan corpus as the program plan for reaching one
evidence-backed, human-authorized current-forecast activation (#1299). It

advancing through the existing gate chain while unrelated mainline work

PR #1466 plus the tracker staleness that merge left behind. The candidate
baseline is `origin/main @ 12af67a4e` (squash-merge of PR #1466, F_1.10.0

## Problem Statement

The capability the activation program needs is merged, but the program state
around it is stale and three defects/loose ends stand between the merged tree
and a certifiable candidate:

1. **Tracker drift.** Partially discharged by the owner's reconciliation
   pass (2026-09-01 18:39 UTC: #1290/#1293 closed, #1467 filed, #1171
   commented). Residual: the #1171 body still cites the 2026-07-21 baseline
   (`35658654`, migration tail `0035`); #1294's gate statement is unedited
   since 2026-08-17 and names no candidate SHA; #1298 carries the wrong
   runbook reference and a between-window-redeploy allowance. Left as-is,
   gate evidence would reference issues that misdescribe the tree — and the
   same-day drift shows why binding evidence to issues instead of a SHA
   cannot work.
2. **Idempotency defect (#1467).** `POST /funds/:fundId/current-forecast/runs`
   executes `runCurrentForecastV2` with no idempotency key, no command record,
   and no replay semantics — the only reachable mutating current-forecast
   route outside the durable-command pattern. It has zero known client
   callers.
3. **Split wire contract.** The recompute response envelope
   (`{ status, shadowReconciliationId?, failureCode?, replayed }`) is declared
   client-side in `WorkspaceContextRail.tsx` as a local type; the server
   serializes it untyped from the service outcome. Drift would surface only at
   runtime in the rail readback.
4. **No frozen candidate identity.** Gates #1294–#1299 are open with no
   recorded source SHA, so "almost ready" can persist indefinitely — every
   merge silently moves the thing being certified.

## Solution Architecture

Two tracks, one restart rule, one authority rule:

- **Activation train (this plan).** A candidate is an exact `main` SHA,
  recorded in #1294 when Phase 1 completes. Everything after that
  certification binds to the SHA: static gates, deployed identity, end-to-end
  proof, soak windows. The initial candidate is `12af67a4e` + the P0b
  hardening merge (one narrow change; its merge SHA becomes the candidate).
- **Mainline track.** Development continues off-`main` (branches/worktrees)
  throughout the train; what pauses is source admission to `main`, and only
  during the hold window (certification through recorded GO/NO-GO — see
  dispatch fence). Dependency PRs land before candidate selection or queue.
  An exception merge during the hold requires machine-verifiable proof that
  it cannot rebuild, redeploy, promote, or reconfigure any qualifying unit,
  cannot change the target database schema/configuration or accepted source,
  and cannot affect final-action eligibility — recorded durably in #1171.
  Absent that proof the merge queues; default is deny.
- **Restart rule.** Any change to the candidate SHA makes all downstream
  evidence (#1295 onward) ineligible for the current action and restarts
  soak from Window 1 — under the single-candidate-across-all-windows
  contract no completed window survives a candidate change. A
  candidate-critical fix therefore re-runs Phase 1
  certification; nothing "carries over" across SHAs. Ineligible, not false:
  historical exact-SHA receipts stay preserved and immutable (governing
  policy — a new `main` head changes current-action eligibility, not
  historical truth).
- **Dispatch fence.** `release-production.yml` refuses any SHA that is not the
  current `main` HEAD — re-checked fail-closed at four independent points
  across the run (dispatch, staging, and promotion `LIVE_MAIN` resolutions),
  and the canonical production route runs one final source/currentness fence
  immediately before **every** first production mutation — including the
  #1299 activation flip, not just the deployment
  (`docs/workflows/PRODUCTION_SCRIPTS.md`). A frozen candidate is therefore
  only actionable while `main` still points at it. Consequence: the hold
  window runs from Phase 1 certification through the recorded GO/NO-GO
  (#1299) — source admission to `main` queues for the entire interval,
  soak included. If `main` advances anyway, the pre-action fence fails
  closed and the train restarts at Phase 1 on the new HEAD; there is no
  historical-SHA action path (by design, F_1.2.0 WS6). "Mainline work
  continues" therefore means: `main` admission freely before candidate
  selection and after GO/NO-GO; branch development always.
- **Authority rule.** Tests, merges, issue closures, provider observations,
  and operating-decision rows are evidence, never authority. Every production
  action in Phases 3–4 is owner-authorized and action-scoped per the
  governing policy; green evidence authorizes nothing by itself.

Phase order: P0a (tracker reconciliation, no code) and P0b (one narrow
hardening change) may proceed in parallel; Phase 1 (#1294 certification)
requires both; Phases 2–4 follow the existing gate chain #1283/#1287 ->
#1295 -> #1296 -> #1297 -> #1298 -> #1299 already defined by F_1.2.0 WS7 and
the F_1.0.0 plan — this plan sequences and binds them to a candidate identity.
It redefines existing gate acceptance in exactly one place, deliberately
(#1295 additionally gains additive binding fields under P0a, its original
criteria untouched): the live #1298
contract requires an unchanged SHA only **within** each window and permits
redeploys **between** windows; this train requires one candidate SHA across
all four windows (the hold window makes any between-window redeploy a
restart anyway). P0a reconciles #1298 to that tightened contract and the P0b PR amends
the soak runbook to match (the runbook is a tracked file; P0a stays
GitHub-only) — and fixes #1298's runbook reference, which still points at the
marginal-MOIC soak runbook instead of
`docs/runbooks/current-forecast-shadow-soak.md` (the WS-G repair that never
landed).

### 2. P0b item 1 — `/current-forecast/runs` disposition

**Files**: `server/routes/current-forecast.ts` (route at line ~248);
`server/route-policy/api-route-policy-registry.ts`,
`server/lib/database-backed-idempotency-routes.ts`, surface-contract matrix
(regeneration) — subset depending on branch taken.

Registration topology constraint: the manifest id, impl-map entry, and
group-slice cover the **whole current-forecast router module** (recompute,
mode, reference, plan-version, runs endpoints together). Retirement touches
none of those three registration points — the router stays mounted on both
surfaces; only the one endpoint disappears.

Audit first, then exactly one of two dispositions — the "formally excluded
from idempotency" escape hatch is removed either way:

- **Audit**: enumerate consumers of `POST /funds/:fundId/current-forecast/runs`
  across client code, scripts, runbooks, workers, and tests, **plus** a dated
  production-usage observation (provider access logs / route telemetry over a
  stated lookback) where available — the record states the retained interval
  actually queried and any blind spots, and a shorter retained interval is
  never presented as a longer negative; where telemetry is incomplete, an owner
  attestation of no operator or external use, recorded on the issue. An admitted consumer is an intentionally
  supported, owned workflow whose removal would violate a current
  requirement — a stale plan, dead script, exploratory curl, or a test
  that calls the route solely to verify it is not one. Static
  search alone does not prove absence of use. Merge-time observation: zero
  client callers.
- **If no admitted consumer exists (expected): retire the endpoint.** Remove
  the Express handler from `current-forecast.ts`, the endpoint's route-policy
  entry, and its tests; regenerate the surface-contract matrix (its row
  drops); record the retirement in `DECISIONS.md`. Manifest / impl map /
  group slices are untouched (module-level, shared with the surviving
  endpoints). Manual execution needs are already served by the durable
  `/current-forecast/recompute` command.
- **Else: retrofit — semantics fixed here, not at implementation time.** The
  endpoint adopts the recompute command's claim-first pattern wholesale:
  `Idempotency-Key` header required (428 missing / 400 malformed); command
  equivalence = key scoped to fund; request-relevant inputs
  (`currentPlanVersionId`, `financialFactsSnapshotId`, and the request
  `clock`, which becomes required in the body so the hash is deterministic —
  no server-clock default inside the hashed payload) pinned into the command
  record and hashed; same-key different-hash is 409; in-flight duplicate is
  409; completed/failed same-key replay returns the recorded outcome without
  re-execution (fresh attempt needs a fresh key); stale pending claims
  recover after the same 90s takeover window. Register the POST pattern in
  the middleware-exclusion classifier and add real-PostgreSQL
  replay/conflict/concurrency integration tests mirroring the recompute
  suite. **Durable storage is not pre-designed here**: claim state and
  recorded outcomes need either a `command_type` discriminator generalizing
  `current_forecast_recompute_commands` or a sibling command table — both
  are schema changes. Retirement is the expected disposition; if the audit
  finds an admitted consumer, P0b pauses and this plan is amended with the
  storage design and its additive migration before implementation proceeds.

The defect is tracked as #1467 (filed 2026-09-01); either branch records its
disposition there.

  boundaries parse — server before serialization, client after receipt — so
  deployment skew surfaces at whichever side moved. Any residual client
  import of the Drizzle schema file becomes type-only or is re-pointed at

Tests: another fund's command does not block; a command terminal before the
shadow start does not block; pending, completed, failed, and skipped
attempts after the start all block; the pre-transition-command /
post-transition-row edge blocks; a same-key replay of an older terminal
command (which creates no new command or reconciliation row) does not
manufacture contamination; an authorized fresh shadow transition establishes
a new interval; the activation route surfaces the blocker through the
existing blocked-response shape without mutation.

Concurrency: the blocker check alone is check-then-act — a manual command
could claim between the blocker read and the flip, and a CTE shares one
snapshot, so ordering inside one statement does not serialize it. Both
paths therefore take the same per-fund transaction-scoped advisory lock
(`pg_advisory_xact_lock` keyed on the fund): the manual claim and the activation
blocker-check-plus-flip each wrapped in a new transactional critical
section (both are autocommit paths today), with activation re-running the
blocker check under the lock before performing the flip. The real-PG
concurrency case proves both orderings: a claim that commits first blocks
the flip; a flip that commits first leaves the late claim recorded as a
harmless post-flip row.

Scope guard: this is one blocker in the existing taxonomy plus a shared
lock wrapping two new transactional critical sections plus tests — no
provenance filters in runbook or soak queries (deliberately deferred,
still), no schema change, no new service. The runbook amendment in this PR
also adds the zero-pending-command preflight before formal shadow entry (an
unresolved stale pending row blocks entry; one observed during soak blocks
the window and promotes the janitor follow-up from deferred to blocker).

### 9. Phase 4 — Soak + human-gated flip (#1298, #1299)

Four consecutive 7-day windows per
`docs/runbooks/current-forecast-shadow-soak.md`, all four production-side
(Phase 2 constraint), evidence via `evaluateCurrentForecastShadowGreen`,
stable candidate identity throughout, zero unexplained divergences.

**Manual-run contamination control.** The shipped provenance flag
(`created_reconciliation`) marks rows a manual command created, but neither
the soak runbook's queries nor the activation decisive-reference query
filters on provenance today — a manual row could silently enter window
evidence or be the row activation reads. Fail-closed rule for this program:
**manual recompute against any soak-target fund is prohibited from the
production-side shadow deployment (soak start) until the flip.** Two audits
enforce it (the P0b runbook amendment adds both steps): each window's evidence pack
includes a query proving zero manual-provenance reconciliation rows for the
target funds in that window (a manual row voids the window), and #1299's
evidence includes a final pre-flip audit proving (a) zero manual rows for
the target funds over the entire soak-start-to-flip interval — covering the
gaps before window 1 and after window 4 — and (b) that the decisive (latest)
reconciliation row per target fund, the one activation's unfiltered query
will read, is organic. Engineering
provenance filters into the runbook and activation queries is explicitly
deferred — prohibition + audit is the activation-train control; filters can
land post-activation if manual runs on soaked funds ever become desirable. P0b item 4 additionally machine-enforces the
prohibition at the latch itself: the activation eligibility check returns a
typed `manual_recompute_since_shadow_start` blocker (§5), so a violated
prohibition cannot reach the flip even if an audit is missed; the
per-window and pre-flip audits remain the evidence controls.

**Pre-flip fence.** Immediately before #1299 executes, verify in one recorded
check against #1295's binding: `main` HEAD == candidate SHA in #1294; the
active web/API and required worker deployments are the **exact deployment
IDs** #1295 bound — not merely the same SHA, since a same-SHA redeploy or
reconfiguration breaks the binding; the database identity and its
schema/configuration state match the binding; the four-window evidence and
the manual-row audits above are attached. The same identity binding is
re-checked at every window boundary (#1298 evidence), so drift stops a
window, not just the flip. Any mismatch is NO-GO/restart — never an
improvised historical-SHA path.

#1299 is the human-gated activation flip with containment drill; the program
ends in a recorded GO or NO-GO, never indefinite readiness. The pending-row
janitor follow-up stays deferred unless stale-takeover evidence fails during
soak (it is observability, not a blocker).

## Technical Considerations

- **Pattern usage**: route retirement/retrofit follows the ARCHI §3 four-point
  registration rule in reverse/forward; contract placement follows the
  `shared/contracts/*.contract.ts` convention; idempotency via the two
  shipped patterns only (`runIdempotentCommand`, claim-first command table).
- **Two-track coordination cost**: accepted. During the hold window `main`
  admission queues by default — all merges, not only those touching the
  deployment units; the machine-proof exception is the sole bypass and
  defaults to deny. This bookkeeping lives in #1171.
- **Evidence hygiene**: every provider observation dated; every gate record
  names the SHA it certified; soak evidence distinguishes organic vs manual
  provenance (shipped `created_reconciliation` semantics).
- **Governance**: no step in this plan grants production authority. Schema
  apply, release dispatch, and the activation flip are each separately
  owner-authorized actions (prod-ledger precedent: merge authorized nothing).
- **Edge cases**: candidate-critical defect found mid-soak (fix -> new
  candidate -> Phase 1 restart); `/runs` audit finds a consumer in a runbook
  only (treat as non-admitted, update the runbook to the recompute command,
  retire); matrix regeneration after endpoint retirement (row count drops —
  regenerate + G1-style validation, do not hand-edit); `main` advances during
  the certification-to-flip hold (pre-action fence refuses — restart Phase 1
  at new HEAD, do not force); exception merge proposed without machine proof
  (queued — default deny); manual reconciliation row detected in a soak
  window (window voided, re-run).
