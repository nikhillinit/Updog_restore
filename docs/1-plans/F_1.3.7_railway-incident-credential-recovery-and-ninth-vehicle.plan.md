## Decisions fixed by this plan (owner, 2026-11-01)

- **D-1 Rotation timing and method.** The owner first chose "overlap via
  release" for rotation in general, then "reset at release" for the Neon role,
  which supersedes overlap for the database: no second database role is created.
  Rotate inside the release: reset the production Neon role password in place
  after step 4 and immediately before step 5. Neon's password reset invalidates
  the old password at once. Every consumer still holding the old password fails
  from the reset until it is redeployed with the new value; the workers recover
  at phase A and the canonical web at phase B promotion. The owner accepts this
  planned outage. A read-only access-anomaly review comes first; an anomaly
  switches to an immediate emergency reset outside the release (see item 2).
- **D-1a Redis (not separately decided).** This plan applies the same reset at
  release to the production Redis credential. A failed Redis connection returns
  503 on protected routes (#1611), so a Redis reset alone causes the same
  outage. If slice 1 shows that the Redis provider supports a second user or
  credential, the owner may choose overlap for Redis instead (create the new
  credential before the window, disable the old one after step 8); that choice
  is recorded in slice 1 evidence, not by a plan change.
- **D-2 Packaging.** This plan (F_1.3.7) merges first, then gated slices, the
  same pattern as F_1.3.6. The ninth vehicle is a separate docs-only pull
  request.
- **D-3 Governance.** One governance pull request adds ADR-114 for the rotation
  route. If slice 1 finds the original Railway token record absent, the same
  pull request narrowly amends ADR-110's original-token postcondition.
- **D-4 GitHub link.** If the Railway GitHub source connection is broken, the
  owner relinks it in the Railway dashboard for both worker services before the
  ADR-110 preflight snapshot, with automatic deployment off.
- **D-5 Route form.** The ADR-114 route is owner-manual: the owner performs each
  named reset and write in the provider console or CLI and records a receipt per
  write. No helper script. Tension recorded: the policy's Production-action rule
  requires a route to fail closed before its first mutation on a missing or
  stale machine-checkable prerequisite. A script-less route cannot do that by
  itself, so ADR-114 must state, for this route only, that the owner's recorded
  confirmation satisfies that floor, the same form the policy already uses for
  the ADR-103, ADR-105, and ADR-108 routes. Codex or the owner may decide that a
  minimal receipt-only tool is needed instead; that would revise D-5.

## Solution Architecture

Slices run strictly in order. Each slice states who acts. "Agent" means the
executor drafts and verifies locally; the owner pushes, merges, and performs
every provider action.

```
slice 0  F_1.3.7 plan PR (agent drafts; owner merges)
slice 1  read-only recovery readings (owner) ---- stop rules
slice 2  governance PR: ADR-114 (+ conditional ADR-110 amendment) (agent; owner merges)
slice 3  Railway GitHub relink if needed (owner)
slice 4  ADR-110 credential repair (owner or delegated executor)
slice 5  ninth F_1.21.1 vehicle PR (agent drafts; owner freezes and merges in slice 6)
slice 6  release steps 1-4 + merge freeze (owner)
slice 7  rotation window: reset + writes (owner, ADR-114)   <- outage starts
slice 8  release steps 5-8 (owner)                         <- outage ends at promote
slice 9  steps 9-11 and closeout (owner)
```

Why this order:

- The governance pull request moves `main`, so it must merge before the ninth
  vehicle is cut and captured.
- The relink changes Railway service configuration, so it must precede the
  ADR-110 snapshot of protected targets.
- The capture is the first workflow use of the new token; it needs ADR-110 done.
- The reset sits after step 4 because steps 1 to 4 do not use the production
  database credential, and phase A is the first step that does (schema audit and
  certifying proof). The baseline capture binds Railway deployments, not
  variables, so variable writes after the capture are safe only if they create
  no deployment (item 8).

**ADR-114: One-Time Post-Incident Production Credential Rotation** (new ADR in
`DECISIONS.md` after ADR-113):

- Context: Verified state rows 4, 6, 8, and 12; Finding C.
- Decision: for incident QH8L8B3E only, admit an owner-manual reset of exactly
  the credentials that slice 1 found stored in Railway (the production Neon role
  or roles and the production Redis credential), one write of each new value to
  each store in the slice 1 inventory, and the single slice 3 skip-deploy
  rehearsal write of a non-secret Railway variable. The owner performs every
  reset and write; no delegated executor; no helper script.
- Production-action rule floor: for this route only, the owner's recorded
  confirmation of each prerequisite (source identity, target scope, existing
  target identity, readiness gate) satisfies the rule's fail-closed
  machine-checkable floor, in the same form as the ADR-103, ADR-105, and ADR-108
  paragraphs. Every other floor stays in force.
- Optimistic-locking exception: none of the target APIs offers a documented
  conditional write. The owner accepts the concurrent-writer overwrite risk for
  exactly the named writes. Each write records a receipt: target store and name,
  pre-write metadata, write time, post-write metadata readback (no plaintext),
  and outcome. One attempt per write; an unknown outcome stops for
  reconciliation and never triggers a blind rewrite.
- Timing and preconditions, separately per action:
  - the skip-deploy rehearsal write (item 4): after ADR-114 admission and any
    relink, before ADR-110 and before the step 2 capture, with no active release
    run. It does not depend on step 4;
  - the resets and credential writes (item 8): after F_1.21.1 step 4 succeeds
    and immediately before step 5, inside the declared merge freeze, with no
    active release run. Railway variable writes must not create a deployment.
- Planned outage: from the first reset until phase B promotes. Accepted by the
  owner (D-1).
- Rollback restores old credentials: a Railway rollback restores the
  deployment's historical variables, which after the reset are the old, rejected
  credentials. The release workflow's worker recovery prefers rollback
  (`deploy-railway-workers.mjs:1387-1411`). A successful rollback therefore
  proves nothing about connectivity. After any rollback of a worker (by the
  release workflow or otherwise), ADR-114 permits one bounded reapplication: one
  write of each rotated variable on that worker and one deployment from the
  rolled-back deployment's pinned commit with those variables, followed by the
  worker's `/health` and `/ready` checks, which exercise the database and Redis.
  A failed readiness check stops; no further attempt.
- Contingency when a release attempt fails after the reset: the owner chooses
  between a forward release on a new vehicle and a one-time service restore.
  Vercel: a new production deployment of the current canonical deployment's
  exact source, built with the new environment. Railway: a deployment of each
  worker from its current deployment's pinned commit with the rotated variables,
  never a rollback or redeploy of the historical deployment, then `/health` and
  `/ready`. ADR-114 admits the restore as a route; each use still needs explicit
  owner authorization at the time. Railway warned that pre-incident source may
  not deploy until GitHub is relinked, so the Railway restore is not proven
  usable. If Railway refuses, the workers stay down until the forward release.
- Emergency path: an access anomaly found in slice 1 or slice 7 permits an
  immediate reset of the affected credential outside the release window, with
  the same receipts; the release plan is then revised.
- Not authorized: any other credential or Railway token; any deployment or
  promotion other than the bounded post-rollback reapplication and the
  owner-authorized contingency restore named above; any database DDL or data
  change; or a standing rotation exemption.

## Technical Considerations

- **Pattern usage**: docs-only plan and vehicle pull requests, same structure as
  F_1.3.6 and the F_1.21.1 vehicles; owner-run production procedures in
  `docs/workflows/PRODUCTION_SCRIPTS.md` with ADR plus policy section, same as
  ADR-108, ADR-110, ADR-112, and ADR-113.
- **Optimistic locking**: retained everywhere except the ADR-110 write and the
  named ADR-114 writes, each with explicit owner acceptance.
- **Idempotency**: every credential action has a one-attempt budget; unknown
  outcomes stop for reconciliation; no automatic retry.
- **Capture binding**: the capture binds worker deployments
  (`capture-release-recovery-context.mjs:471`); any deployment between capture
  and phase A fails the phase preflight. Railway variable writes must skip
  deployment.
- **Vercel environment changes** apply only to new deployments; the live
  deployment keeps the old values and fails once the old password is reset.
- **Schema audit identity** checks the database name only
  (`reconcile-prod-schema.mjs:2143`). A password reset keeps role and database,
  so the identity check is unaffected.
- **Neon integration on Vercel** stays connected (ADR-112). If it manages the
  Vercel `DATABASE_URL`, the provider documents automatic synchronization and a
  forced resync; whether this project's entry syncs on a role password reset is
  UNVERIFIED. Slice 1 establishes whether the entry is managed; slice 7 item 8
  verifies synchronization before step 5, with one resync and a stop path.
- **Rollback and credentials**: a Railway rollback brings back historical
  variables, so every rollback after the reset needs the item 3 bounded
  reapplication and readiness checks before the worker counts as restored.
- **Edge cases**: original token record absent (slice 2 amendment); relink
  creates a deployment (stop); ADR-110 unknown outcome (stop); access anomaly
  (emergency path); phase A or B failure after reset (contingency, prolonged
  outage); new advisory on the vehicle's merge commit (as #1606 and #1674: stop,
  fix lands before a tenth vehicle); merge during the freeze (restart at a new
  baseline).
