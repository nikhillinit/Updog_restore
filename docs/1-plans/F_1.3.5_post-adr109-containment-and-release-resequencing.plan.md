### Finding A: the F_1.21.1 release needs a sixth vehicle

Rows 8 and 9. The capture at `336729dda` bound PR #1639 and head `272b3acfb`.
Release preflight accepts a primary release only when the release SHA is the
captured PR's merge commit and a single-parent squash onto the captured baseline
(`capture-release-recovery-context.mjs` lines 1392-1406), and `validate-target`
accepts only the live `main` head as `expected_sha`. `c64771fc4` satisfies the
first and fails the second; `42a3ac8a9` fails the first. Capture 38292779127 is
now a historical receipt only. The handoff's "decide which SHA is releasable"
has one answer: none of the existing SHAs; a new docs-only vehicle PR frozen on
live `main`, with its own capture, is required. This repeats the pattern that
F_1.21.1 "Overview" already records for #1625, #1628, #1629, and #1630.

### Finding B: the `42a3ac8a9` bracket is UNDETERMINED by the procedure's own terms

Row 10. The handoff frames the open item as "needs 30 min" (condition (b)).
Waiting repairs (b) only. Condition (a) requires a processed push at most 1 hour
before `PUSHED`, and no such push exists; the gap is 2h01m52s. The table in
`PRODUCTION_SCRIPTS.md` reads "tree covered: yes, bracket not met, 0
deployments" as UNDETERMINED. The 03:21Z reads in row 3 are observations, not a
bracket result, and must not be recorded as one. A later natural push cannot
certify this historical push; it can only produce its own bracket.

### Finding C: new release open risk introduced by ADR-109

ADR-109 "UNDETERMINED" and `PRODUCTION_SCRIPTS.md` Step 1 both state that
whether Release Production's CLI deploy
(`vercel deploy --prebuilt --prod --skip-domain --meta githubDeployment=1 --meta githubCommitRef=main`)
is affected by `git.deploymentEnabled: false` is settled only by the first
dispatch after the merge, and that a refusal fails closed at the deploy step's
URL validation before promote. That step is `stage-production`, which runs only
in `mode=full` (phase B); phase A proves nothing about it. The F_1.21.1 plan
predates ADR-109 and does not carry this risk. The sixth vehicle must add it.

## Decisions (owner, 2026-10-19 discovery)

- **D-1 Queue patch placement.** The patch merges through its own PR, outside
  the sixth vehicle's capture-to-phase-B window: before the fresh capture, or
  after phase B and step 8. The vehicle stays docs-only. Rebase onto current
  `origin/main` first. The local `actionlint` mismatch does not change the
  sequencing; source currentness does.
- **D-2 Dependabot.** All eight open Dependabot PRs are HOLD: no merge from
  capture through phase B; dependency adoption resumes after step 8, one PR at a
  time. Before any push to one of them, rebase locally onto `origin/main` and
  confirm `HEAD:vercel.json` carries the key; no blind bulk rebase or update
  requests. If one becomes a demonstrated release blocker, it lands before a
  fresh successor vehicle's capture. Containment of Dependabot's own branch
  rebases is a separate question: closed auto-merge is not a branch-write
  freeze, and Dependabot may still rebase previously opened PRs. Until effective
  containment is evidenced, an explicit ADR-109 blocker stays on the HOLD list.
- **D-3 Bracket procedure amendment.** This plan's PR amends canonical Step 1,
  the ADR-109 rationale, and the governance tests to distinguish a pending
  observation (conditions (b) to (e) not yet readable) from a missing historical
  control (condition (a) unsatisfiable). The one-hour threshold is preserved.
  The `42a3ac8a9` push is recorded as the out-of-window example, kept separate
  from the two qualifying PR-head observations of 2026-10-19. The unresolved
  outcome retains the coverage gap and blocks any action that requires that
  proof; a future natural push needs its own bracket; no deployment is created
  to obtain a control. This is a classification clarification: it admits no
  mutation authority and relaxes no governing requirement. The amendment lands
  before the fresh capture.

## Problem Statement

1. The release path is stalled on a stale capture that no SHA can consume
   (finding A), and the F_1.21.1 plan still names `336729dda` as live `main`.
2. The first `main` push under ADR-109 cannot be classified by the procedure as
   written (finding B), and the procedure does not say how to record a push
   whose before-control is structurally missing, so an operator could either
   wait forever or misrecord the 03:21Z observation as coverage.
3. A seven-workflow CI change sits on a stale, unpushed, key-less branch; pushed
   as is, it violates the rebase-before-push rule in the governing policy.
4. Eight Dependabot heads lack the key, and any merge between capture and phase
   B restarts the release; nothing on `main` records their disposition.
5. Existing exposure (four production-parented Neon branches, 164 Neon-bound
   Preview snapshots, a possibly shared production role password, and unknown
   old Preview `REDIS_URL` values) is inventoried in ADR-109 Step 3 but has no
   decision record of which actions, if any, the owner will authorize and in
   what order relative to the release.

## Solution Architecture

Four thin slices, each verifiable on its own and each landing on `main` before
the next starts. Slices 0 and 1 are source changes that merge before the fresh
capture. Slice 2 is the release itself, run under F_1.21.1 as revised, with no
other merge from capture through phase B. Slice 3 is owner-gated provider
handling that produces decisions and inventories only; no provider write is part
of this plan.

```
Slice 0 (slice 0 PR, docs + tests) -> merge
Slice 1 (queue patch PR)          -> merge            } both before capture
Slice 2 (sixth vehicle PR)        -> freeze -> capture -> rerun PR CI -> merge
                                   -> phase A -> phase B -> step 8 -> steps 9-11
Slice 3 (owner-gated, no writes)  -> decisions recorded; Dependabot adoption
                                     resumes only after step 8
```

Ordering rationale: slice 0 before slice 1 so the amended Step 1 is on `main`
when the queue PR's own push is read; both before slice 2 so each `main` advance
happens before the baseline is captured, not after (F_1.21.1 "Constraints": a
new `main` head fails the phase B re-fence and restarts the sequence).
