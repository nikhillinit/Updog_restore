# F_1.15.0 Capital-Planning Feasibility Workflow — Revision 3

## Overview

F_1.15.0 adds a deterministic internal workflow for testing whether a
user-entered portfolio-construction plan fits supported lifetime capital under a
callable-as-needed assumption. It reuses the existing Scenario Workspace and
Fund Model Results surfaces, existing scenario-set persistence/CAS/dedupe
machinery, and existing partner/analyst permissions.

Revision 3 supersedes the historical funding wording in
[Plan A source](references/F_1.15.0_plan-A-source.md) and the out-of-repository
Plan C revision 2. Governing cashless-GP treatment comes from
[ADR-070](../adr/ADR-070-cashless-gp-commitments-and-fee-waivers.md): available
construction capital deducts the GP deemed contribution, while
`fundedFromFeesPct` never reduces fee basis or fee amount.

This remains one unimplemented F_1.15.0 feature release with staged
implementation and acceptance gates. No automatic F_1.15.1 split is assumed; a
future split requires an explicit owner choice. Baseline accessibility,
review-before-save provenance, independent verdict axes, and source/refusal
recovery remain F_1.15.0 release requirements.

Historical Plan A/Plan B comparison scores remain A **4.200/5** and B
**2.925/5** under the frozen rubric. Those scores describe the historical
candidate texts; they do not override ADR-070, prove implementation readiness,
or change through this revision.

## Problem Statement

Existing scenario infrastructure can persist, calculate, compare, deduplicate,
and mark source-pinned scenario sets stale, but it has no `capital_plan`
scenario kind. Users cannot yet answer, in one durable workflow:

- how many companies an allocation supports under explicit initial/follow-on
  assumptions;
- how conditional graduation, participation, fixed checks, pro-rata checks, and
  incremental pool dilution build lifetime follow-on demand;
- whether total demand fits supported construction capital;
- whether allocation budgets or designated follow-on earmarks are exceeded
  independently;
- how much modeled demand falls beyond fund term without implying
  current-liquidity failure;
- how saved alternatives differ without silently recalculating historical
  results; or
- what one representative holding might return under summarized preference terms
  without feeding forecast proceeds back into construction capital.

Revision 2 also proposed blanket refusal and tri-state source-presence changes
for cashless GP funding. Repository evidence shows that approach conflicts with
accepted ADR-070 and existing V1 compatibility. Missing `fundedFromFeesPct`
deliberately normalizes to effective zero without materializing a source
default; explicit zeros are intentionally omitted from serialized V1 config to
preserve hashes. F_1.15.0 must use the governing deemed-contribution identity
without changing `FundDraftWriteV1`, client store/adapters, or existing
economics V1 semantics.

## Solution Architecture

### Product boundary

F_1.15.0 is deterministic hypothetical decision support. It does not rank
companies, recommend allocations, approve investments, publish authoritative
state, ingest live actuals, execute capital calls, model current cash, perform
Monte Carlo analysis, or claim probability of shortfall.

Forecast exits, recycling, fee offsets, secondaries, borrowing, subscription
lines, expected receipts, and unrealized value never increase construction
capital or cure an infeasible construction plan. The optional performance
companion remains visually, mathematically, and durably isolated from
construction feasibility.

### Existing platform seams

- Scenario-set routes are already mounted under `/api` through
  `server/routes/fund-scenario-sets.ts`; F_1.15.0 extends those existing routes
  and adds no new router.
- `createFundScenarioSet()` already locks the fund row, resolves optional create
  idempotency replay before source CAS, locks the published config, validates
  expected source ID/version, and inserts the set/variants/event
  transactionally.
- Synchronous `calculateFundScenarioSet()` accepts no idempotency header or
  command receipt. It locks the scenario-set row, reuses a completed exact-input
  run, acquires/fences a run, and writes run/snapshot/event in one transaction;
  an exception rolls that entire calculation transaction back.
- `findCompletedScenarioRun()`, `acquireScenarioCalculationRun()`,
  `markScenarioCalculationRunCompleted()`, and
  `markScenarioCalculationRunFailed()` already provide durable dedupe and fenced
  completion/failure behavior.
- `getFundScenarioComparison()` already reads persisted scenario results;
  capital-plan comparison must not use its authoritative-economics branch.
- Client route `/fund-model-results/:fundId/scenarios` already hosts scenario
  creation/calculation/comparison; `/fund-model-results/:fundId` already hosts
  saved scenario summaries.

### Bounded module design

Use a small capital-planning contract and pure modules rather than calling
`normalizeEconomicsConfig()` or `runEconomicsModel()`. The capital materializer
must reproduce only the selected source semantics needed by F_1.15.0, especially
GP commitment precedence, fee/expense inputs, finite-term facts, allocations,
pipeline stages, and provenance. It must not import economics-engine default
dates, default tiers, recycling, exit, waterfall, or current-plan behavior.

No new database table, queue, worker, feature dependency, generic waterfall
framework, benchmark service, note system, persona model, or product shell is
required.

### Authoritative composite source bundle

Capital planning must not treat ambiguous `FundDraftWriteV1.fundSize` as an
authoritative commitment amount or infer any unit from magnitude. Build one
bounded, server-owned `fund-scenario-capital-source-bundle/1.0.0` from two
persisted sources plus explicit scenario-local unit declarations:

- `funds.id`, `funds.size`, `funds.base_currency`;
- selected `fundconfigs.id`, `version`, `published_at`, and raw JSONB `config`;
- V3 create `unitDeclarations` keyed by exact consumed source path.

Neither `funds.size` nor raw-config `fundSize` persists the unit/write-path
marker needed to prove an existing row's scale. Equality proves source
consistency only after each field has independently resolved unit provenance; it
does not prove dollars. Require `funds.base_currency = 'USD'`; otherwise refuse
`FUND_CURRENCY_UNSUPPORTED` at `baseCurrency`.

For each consumed ambiguous field, require an exact-path declaration such as
`usd` or `usd_millions`, normalize with Decimal arithmetic, and save provenance
as `scenario_declared`. A declaration is a scenario assumption, not an
independently verified source fact. Missing money/rate declaration returns
`UNIT_PROVENANCE_UNRESOLVED` at the exact path before create writes. Never use a
magnitude heuristic, a blanket fund-wide unit assertion, or a global V1 field
repair.

Admission is field-by-field:

| Consumed source                                                                                              | Required unit/provenance treatment                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `funds.size`                                                                                                 | Independent absolute-money declaration; normalize to USD fixed-decimal.                                                                                                            |
| raw config `fundSize`                                                                                        | Independent absolute-money declaration when present; after normalization require equality with `funds.size`, else `FUND_SIZE_SOURCE_MISMATCH`. Absence remains `absent`.           |
| `economicsAssumptions.gpCommitmentModel.commitmentAmount`                                                    | Independent absolute-money declaration when selected.                                                                                                                              |
| top-level `gpCommitment`                                                                                     | Independent absolute-money declaration when selected; do not inherit nested GP or fund-size declaration.                                                                           |
| `economicsAssumptions.gpCommitmentModel.commitmentPct`                                                       | `resolved_ratio` from `RatioSchema`; do not treat as percent points.                                                                                                               |
| `fundedFromFeesPct`                                                                                          | `resolved_ratio` from explicit `[0,1]` contract; absence keeps ADR-070 effective-zero provenance.                                                                                  |
| `capitalPlanAllocations[*].initialCheckAmount`, `followOnAmount`                                             | Independent absolute-money declarations at each consumed allocation path.                                                                                                          |
| `pipelineProfiles[*].stages[*].roundSize`, `valuation`, `exitValuation` when selected                        | Independent absolute-money declarations at each consumed stage path.                                                                                                               |
| `fundExpenses[*].monthlyAmount`                                                                              | Independent absolute-money declaration at each consumed expense path.                                                                                                              |
| `feeProfiles[*].feeTiers[*].percentage`                                                                      | Independent `ratio` or `percent_points` declaration because current persisted contract has no unit marker.                                                                         |
| `funds.management_fee`                                                                                       | Not consumed by F_1.15.0; never a fallback or a cross-source equality requirement.                                                                                                 |

Derived fee amount `F` becomes `resolved_dollars` only after its commitment
basis, rate, periods, applicability, and every absolute expense input are
independently admitted. Different fields may legitimately declare different
units; for example `funds.size = 100` declared `usd_millions`, an initial check
`2_000_000` declared `usd`, and fee tier `2` declared `percent_points`.

Canonicalize the untouched raw JSONB config with existing canonical JSON rules
and hash those UTF-8 bytes as `rawConfigHash`. Materialize only bounded source
facts required by the versioned capital method, including exact source path,
canonical raw value, normalized value, unit class, provenance origin,
raw/effective/default state, and interpretation version.

Compute `sourceBundleHash` as lowercase SHA-256 over canonical UTF-8 JSON of the
versioned raw-source projection without the hash field. Bind the source
projection/bundle schema version, fund ID, locked raw fund facts, config
ID/version, `rawConfigHash`, currency, and persisted source unit/schema tags
when present. A missing persisted tag has a stable absent marker. Fingerprinting
loads and canonicalizes raw source independently of unit-dependent
materialization; unresolved declarations do not prevent a fingerprint.

Exclude scenario-local declarations, derived normalized values, readiness
results, annotations inferred by the current interpreter, materializer and
interpretation/method versions, retrieval timestamps, display-only publication
timestamps, actor/correlation IDs, and unrelated metadata. Changes to a named
raw source fact, persisted source tag, or canonical raw-config content change
the source hash. A new interpreter over the same raw projection does not. Freeze
the raw projection schema independently of interpreter releases; a method
needing additional raw fields must require an explicit compatible
source-envelope refresh rather than silently changing this preimage.

The source GET returns this hash before declarations. Create recomputes it from
locked sources for CAS, then independently verifies declarations and derives
normalized values. Declarations, normalized consequences, and interpretation
versions bind create/calculation identity, never source freshness. The saved
envelope retains the interpretation version and is calculation-complete; raw
fingerprint availability, calculation readiness, and method compatibility are
separate concerns.

The persisted bundle contains these strict bounded fields:

| Bundle area      | Required fields                                                                                                                                                                                               |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity         | Contract version `fund-scenario-capital-source-bundle/1.0.0`, fund ID, source config ID/version, display-only published timestamp, raw-config hash, interpretation version, and bundle hash.                  |
| Fund facts       | Exact `funds.size` source path/raw value, declared unit, normalized USD value, `scenario_declared` provenance, and USD base currency.                                                                         |
| Config fund size | `absent` or `matched`; when present, exact path/raw value, independent declared unit, normalized USD value, and `scenario_declared` provenance.                                                               |
| Rate facts       | Exact path/raw value, source unit `ratio` or `percent_points`, normalized ratio, and provenance origin `contract_resolved` or `scenario_declared`.                                                            |
| Capital facts    | Optional genuine `modelInputsAsOfDate` when present, non-evergreen vehicle fact, fund life, investment period, GP facts, fee/expense facts, construction links, and each field's raw/effective/default state. |

`CapitalGpSourceFactsV1` stores nested commitment amount, nested commitment
percent, top-level commitment amount, `fundedFromFeesPct`, resolved precedence,
raw/effective/default states, and declaration provenance.
`CapitalFeeExpenseSourceFactsV1` stores the selected fee/expense branches in the
decision table below: admitted explicit or legacy tiers, and explicit annual or
legacy monthly expenses. Rate-only fallback candidates remain unsupported, not
admitted tiers. Store raw presence/empty states, selected paths/values, units,
declared month origins, normalized inclusive windows, basis, population, source
labels, effective/default provenance, and shadowed-path annotations. Shadowed

and `pipelineProfiles` with stable IDs and validated links. All three are strict
bounded schemas. If a future method needs a raw field absent from the versioned
bundle, refuse the method/input as unavailable rather than reading live config
during replay.

V3 create receives `expectedSourceConfigId`, `expectedSourceConfigVersion`,
`expectedSourceBundleHash`, `expectedInterpretationVersion`, and bounded
exact-path `unitDeclarations`. The server supplies the interpretation version
with the preview; create binds it in request identity and uses that exact
supported version. A newer installed version cannot silently reinterpret the
reviewed candidate. If the expected version is no longer supported, refuse
`INTERPRETATION_VERSION_UNSUPPORTED` before writes; an exact successful
create-key replay still precedes this check. No generic interpreter registry is
required for the initial single supported version. Inside one transaction,
retain current ordering: lock/read the fund row, resolve exact
create-idempotency replay, then lock/read the published config and compare all
expected source fields. Only expected identities, unit declarations, and
editable plan assumptions appear in client input. Strictly reject any
client-injected `sourceBundle`, `sourceBundleHash`, normalized value, or other
server-owned source field. The server re-reads and recomputes source under
locks, verifies the stable preview source hash, validates each declaration,
derives normalized values, then injects the complete bounded bundle and hash
into every `capital_plan` variant's existing `override_payload`. All variants
must contain byte-equivalent bundles with the same hash. Maximum-five
duplication is included in input-byte capacity measurements. No new source
table/column or event-log repurposing is required. The separate override-type
CHECK migration below is required to persist the new variant.

Calculation reads and verifies the pinned bundle from variant JSONB. Preserve
existing hash-kind lineage resolution: genuine `modelInputsAsOfDate` uses
`scenario-input-hash-v2` with `comparison-lineage-v1`; absence uses
`scenario-input-hash-v1` with null date/lineage. Add conditional capital-only
preimage fields `calculationDomain: 'capital_plan'`,
`calculationMode: 'sync_capital_plan'`, an explicit capital-preimage version,
`sourceBundleHash`, exact unit declarations, normalized values verified from raw
source plus units, and capital method/provenance versions. Reject capital-only
fields for legacy modes and byte-lock existing V1/V2 normalized preimages and
hashes. No hash-kind naming migration or new as-of-date prerequisite is needed.
Timing-origin validation remains a separate financial rule and cannot substitute
establishment or execution time for a missing business as-of date.

Return an exact completed snapshot before historical source-integrity or saved
interpreter-support checks so persisted replay remains readable. For a new
calculation, load the referenced config ID/version, verify its canonical content
hash, and require support for the pinned interpretation version before run
acquisition or writes. Missing or mismatched historical content refuses; an
unsupported saved interpreter returns `INTERPRETATION_VERSION_UNSUPPORTED`. Use
pinned fund facts and declarations, never current replacement values.

Capital read contracts expose three independent, capital-only axes without
widening legacy evidence-state enums:

- `sourceFreshness`: `CURRENT`, `STALE_PUBLISH` for changed published-config
  identity, `STALE_SOURCE` for changed raw fingerprint at the same identity, or
  `STALE_SOURCE_UNAVAILABLE` only when raw source cannot be loaded or
  canonicalized. The last value means freshness is unknown; it is not proof of a
  changed source. Compare identity and raw fingerprint without declarations or
  financial materialization.
- `calculationReadiness`: `READY`, `INPUT_REQUIRED`, or `UNSUPPORTED`, with
  exact typed issues and explicit context `current_preview` or `saved_input`. A
  declaration-free preview may require units while the saved envelope remains
  ready using its pinned declarations. Live preview readiness never overwrites
  saved-input readiness or invalidates a completed result.
- `interpretationCompatibility`: `CURRENT`, `UPGRADE_AVAILABLE` when a newer
  interpretation exists but the saved one is supported, or
  `UNSUPPORTED_SAVED_VERSION` when a new run cannot use it. Upgrading
  interpretation creates a new calculation identity, even if normalized values
  happen to match, and requires an explicit reviewed candidate. It does not mark
  unchanged raw source stale or rewrite a saved result.

An unchanged source fetched without declarations retains `CURRENT` for the saved
scenario. An interpretation-only upgrade also retains `CURRENT`. A later
USD-to-non-USD currency change remains fingerprintable: it yields `STALE_SOURCE`
plus `FUND_CURRENCY_UNSUPPORTED` for the current preview, not source
unavailability. All freshness/readiness/compatibility metadata is
presentation-only with respect to saved snapshot bytes and completed replay.

### Normative construction-capital identity

All money values use explicitly normalized USD fixed-decimal strings and Decimal
arithmetic.

Definitions:

- `C`: committed-capital amount from independently unit-resolved `funds.size`,
  normalized to a USD fixed-decimal string.
- `G`: resolved contractual GP commitment.
- `r`: effective fee-funded fraction, `fundedFromFeesPct ?? 0`.
- `D_gp = G * r`: GP deemed contribution under ADR-070.
- `F`: supported lifetime management fees under the current full-fund
  committed-capital population.
- `E`: supported lifetime fund expenses.
- `A = C - D_gp - F - E`: supported available construction capital.
- `N`: explicit planning budget when supplied, otherwise `A`.

`N` may be lower or higher than `A`. A higher `N` remains a valid saved
comparison but must report over-capacity/infeasible diagnostics; it never
enlarges `A` or bypasses source validation.

Validate explicit `N` as nonnegative. Preserve signed `A` and signed shortfall
when deemed contribution plus supported costs equal or exceed commitments.

- If `A = 0` and explicit `N` is absent, effective `N = 0`, expected company
  count is exactly `0`, and zero-denominator ratios are `null` with a typed
  not-applicable reason. A complete snapshot may save with a visible
  zero-construction-capital qualification; positive entered-count demand may
  save as `over_capacity`.
- If `A < 0` and explicit `N` is absent, do not clamp `A` or invent cash.
  Expected sizing is `null` with `NO_CONSTRUCTION_CAPITAL`; allocation and ratio
  outputs requiring a nonnegative planning budget are unavailable with the same
  reason. Lifetime capacity is known `over_capacity`, signed shortfall remains
  visible, and a complete valid-but-infeasible diagnostic snapshot may save.
- If explicit nonnegative `N` is supplied while `A < 0`, demand/count arithmetic
  may save, but lifetime capacity remains `over_capacity`; `N` never repairs or
  enlarges `A`.

GP cash is already represented within total commitments and is not subtracted
again. Only deemed GP contribution is removed from construction cash capacity.
`r` never reduces `F`, any fee basis, or any fee amount. F_1.15.0 does not
assume waived-fee dollars equal deemed contribution and does not add a
cancellation or addback.

### GP commitment resolution and provenance

Resolve `G` using current economics precedence, with capital-only prevalidation
and no silent clamp:

1. `economicsAssumptions.gpCommitmentModel.commitmentAmount`, when selected and
   valid;
2. otherwise
   `economicsAssumptions.gpCommitmentModel.commitmentPct * admitted C`, when
   selected and valid;
3. otherwise top-level `gpCommitment`, when present and valid;
4. otherwise zero.

A selected source value that is malformed, negative, nonfinite, out of domain,
or incompatible refuses at its actual field path; it does not fall through to a
lower-precedence value. Reject `G > C` as `GP_COMMITMENT_EXCEEDS_COMMITMENTS` at
the selected GP source path rather than clamping. Existing economics V1 clamp
behavior remains unchanged.

`r` comes from top-level `fundedFromFeesPct`; absent means effective zero under
ADR-070. Preserve both source value and effective value/default provenance in
the scenario snapshot:

- source state: explicit value or absent;
- effective value: explicit ratio or default zero;
- default reason: `ADR_070_MISSING_FRACTION_ZERO` when absent;
- resolved GP source path and normalized source value;
- deemed contribution amount and method version.

Do not mutate the pinned source object, materialize the default into
`FundDraftWriteV1`, change the original serialized config/hash, or alter
`client/src/stores/fundStore.ts` and
`client/src/adapters/fund-store-adapters.ts` zero-omission/hydration behavior.

If `r > 0` and every GP amount source is absent, return
`GP_COMMITMENT_UNRESOLVED` at `gpCommitment` before run acquisition or writes. A
supplied selected malformed, negative, nonfinite, or out-of-domain GP amount or
percent is always invalid at its actual source path regardless of `r`; never
label it `GP_COMMITMENT_UNRESOLVED` and never fall through. Explicit `G = 0`
with positive `r` yields zero deemed contribution; it is not a contradiction
under this plan.

### Vehicle, currency, fee, and expense admission

- Read raw pinned source facts, not hydrated client defaults.
- Persisted `isEvergreen === true` returns `FUND_VEHICLE_MODE_UNSUPPORTED` at
  `isEvergreen`.
- Persisted `isEvergreen === false` is an eligible configured fact, subject to
  valid finite fund-life and investment-period inputs.
- Absent `isEvergreen` returns `FUND_VEHICLE_MODE_UNRESOLVED` at `isEvergreen`;
  do not infer false and do not write it back.
- Current schema has no SPV discriminator. A future unsupported vehicle mode
  must refuse at its actual future field path; current inputs cannot claim SPV
  detection.
- Known non-USD basis returns `FUND_CURRENCY_UNSUPPORTED` at `baseCurrency`; no
  FX engine is added.
- Resolve `funds.size` and supplied raw-config `fundSize` independently. After
  declared-unit normalization, require exact Decimal equality; absence is
  recorded, and mismatch returns `FUND_SIZE_SOURCE_MISMATCH` at `fundSize`
  without conversion or fallback.
- Fee adapter supports only the current admitted full-fund committed-capital
  semantics and records population, basis, period, source paths, normalized
  units, and method version.
- F_1.15.0 retains the specifically supported economics V1 full-fund
  committed-capital population. Migrating this adapter to LP-only/class-specific
  semantics would require separate versioned work; internal economics V2 already
  has separate LP-class fee-profile semantics and is not invoked here. Do not
  import default tiers, guess profile applicability, or change economics V1.
- Required expense/fee facts that are missing, ambiguous, malformed, or
  unsupported refuse at their actual source path before durable writes.

### Ordered fee/expense source selection

Validate all supplied fee/expense structures against their persisted schemas
first, including shadowed fields. A persisted-schema failure retains HTTP 409
`scenario_source_config_invalid` with its actual issue paths; it does not become
a capital financial refusal. For schema-valid sources, select from raw presence
and array cardinality before financial normalization.

Rate normalization applies only to admitted Fee 1/Fee 2 tiers. Resolve required
exact-path unit declarations, then require each normalized rate to be finite and
within [0,1]; otherwise return HTTP 422 `FEE_RATE_INVALID` at the selected
`rate` or `percentage` path. Selected Expense 1/Expense 2 amounts must normalize
to finite nonnegative money; otherwise return HTTP 422 `EXPENSE_AMOUNT_INVALID`
at the selected `amount` or `monthlyAmount` path. Missing unit declarations
retain their existing exact-path refusal. Never clamp invalid values or fall
through to another branch.

Fee 3 consumes no rate or basis. After persisted-schema validation, raw fallback
presence always produces `FEE_TIER_SCHEDULE_REQUIRED`, without unit resolution
or rate-domain normalization, even for schema-valid `managementFeeRate = -1` or
`101`. In contrast, an out-of-range nested `defaultRate` fails its persisted
ratio schema first and cannot reach Fee 3. This order is intentional: an
unconsumed fallback cannot produce `FEE_RATE_INVALID`.

This reproduces V1 branch precedence without its magnitude-based unit inference
or broad default generation. Capital-only admission tightens empty selected
legacy tiers, multiple profiles, absent expense coverage, and unsupported
period/policy cases; existing V1 contracts and calculations remain unchanged.
Capital financial errors identify the actual selected path rather than V1's
generic `feeModel` error path. Valid lower-precedence values may disagree
without a value-mismatch refusal: record the winning and shadowed paths, never
merge, average, add, or substitute competing branches. Missing unit declarations
on unconsumed shadowed fields do not block admission.

`economicsAssumptions.feeModel.source` and `expenseModel.source` are retained
descriptive labels, not branch selectors. A valid label naming legacy while
explicit values win (or the reverse) records `SOURCE_LABEL_SELECTION_MISMATCH`
as a visible provenance annotation, not a financial refusal or a branch switch.
`funds.management_fee` is not read for fee calculation, source fingerprinting,
or cross-source equality; disagreement with the selected config rate has no
effect. Raw-config competitors remain bound through the raw-config hash.

Supported fee basis is exactly `committed_capital` over admitted `C`, including
contractual GP commitment. Other selected explicit tier `basis` or legacy tier
`feeBasis` values refuse `FEE_BASIS_UNSUPPORTED` at the exact selected path.
Fallback `defaultBasis` never overrides explicit tiers and does not make a
rate-only schedule admissible. Active selected tiers are additive on that same
full-fund base; overlapping explicit tiers are not alternative profiles. `r` and
`D_gp` never alter this base or the resulting `F`.

Resolve the annual horizon from present
`economicsAssumptions.timeline.fundLifeYears`, otherwise present `fundLife`;
both require valid positive integer years. A differing valid lower-precedence
fund life is shadowed, not combined; record this one admitted fund-life fact for
fees, expenses, and construction timing. Missing both refuses at `fundLife`,
without the V1 ten-year default. Explicit annual starts/ends are positive
integer years with inclusive endpoints; omitted ends run through that horizon.
Reuse the existing `computeFeeBasisTimeline()` committed-capital adapter only
for representable annual fee-tier boundaries; do not modify its broader engine
behavior.

Legacy month-origin provenance must be explicit: persisted contracts do not
distinguish the repository's zero-based engine from one-based wizard windows.
Extend the already-planned V3 strict `unitDeclarations` enum for consumed
`feeProfiles[*].feeTiers[*].startMonth`/`endMonth` and
`fundExpenses[*].startMonth`/`endMonth` to `fund_month_zero_based` or
`fund_month_one_based`. Each supplied boundary requires its own declaration,
both boundaries of one window must agree, and these labels are rejected on
money/rate paths. Declare these exact literals and path-class validation in the
V3 request and bounded source-bundle schemas; no such runtime vocabulary exists
yet, and no additional request field or source column is introduced. Missing or
conflicting origin refuses `TIME_ORIGIN_UNRESOLVED` at the affected boundary.
This remains a reviewed scenario assumption, not a repaired persisted source
fact; bind declarations and normalized month indices to the existing
create/calculation identities. Normalize one-based month 1 to canonical month 0
by the declared convention, never by the observed number. An omitted end is
absence, not month 0, and uses the finite horizon's final month with explicit
effective-value provenance.

After normalization, legacy fee windows must start at a nonnegative multiple of
12 and end at an inclusive month whose successor is a multiple of 12. Reject
other fee boundaries with retained `FEE_PERIOD_NOT_REPRESENTABLE` at the
offending path; do not round a month-6 rate change or alter CP-015's code.
Annual fee year 1 covers canonical months 0 through 11. Valid fee tiers beyond
the horizon remain in provenance but do not accrue inside lifetime `F`.

Legacy expense windows use nonnegative integer canonical fund months with
inclusive start/end and end not before start. `startMonth === endMonth` charges
once, including month 0; recurring months 0–5 charge six times and 0–11 twelve
times. Thus formation and recurring costs remain supported. Intersect each
window with months 0 through `fundLifeYears * 12 - 1`, retaining out-of-horizon
facts in provenance. Do not apply fee-tier annual restrictions, V1's
month-to-year rounding, or a blanket multiply-by-12 to these expenses. Explicit
annual expenses retain their selected annual schedule and do not combine with
shadowed legacy monthly expenses.

Absent or explicit zero `annualExpenses[*].growthRate` is supported with
raw/effective provenance; nonzero growth refuses `EXPENSE_GROWTH_UNSUPPORTED` at
that exact path. Any supplied `expenseModel.orgExpenseCap` or
`orgExpenseCapType` refuses `EXPENSE_CAP_UNSUPPORTED` at each supplied path;
this narrow adapter does not silently ignore expense-cap policy. Tier
`recyclingEligiblePct` / legacy `recyclingPercentage` remains an explicitly
unconsumed recycling annotation and cannot reduce fees or increase `A`. Other
valid economics subtrees stay outside construction funding. A malformed,
unsupported, or unit-unresolved selected branch never falls through; all
required refusals occur before create or calculation-run writes. Save the
selection, normalized `F`/`E`, periods, units, and method version in the bounded
source/result provenance. Historical calculation consumes those pinned facts.

### Allocation, graduation, checks, and ownership

Each allocation has a budget share, positive initial check, deployment period,
optional entered company count, selected source profile/stage, and ordered
follow-on rounds. Each round has stable identity, conditional graduation,
participation, months after the previous round, and exactly one supported
policy: `fixed_check` or linear `pro_rata`.

For simple primary rounds with prior ownership `o`, pre-money valuation `V`,
primary capital `R`, participation `p`, and incremental pre-money pool dilution
`d`:

- `u = o * (1 - d)`;
- fixed conditional check `c = checkUsd`;
- pro-rata conditional check `c = proRataExerciseRatio * u * R`;
- participating ownership `= (u * V + c) / (V + R)`;
- skipped ownership `= u * V / (V + R)`;
- conditional mean ownership `= (u * V + p * c) / (V + R)`.

Full pro-rata preserves `u` against financing dilution; it does not undo pool
expansion. A total option-pool percentage is not incremental dilution.
Missing/ambiguous pool semantics may leave ownership unavailable while
fixed-check construction demand remains complete when ownership is not required
by the selected policy.

Graduation is conditional on reaching the previous stage. Participation does not
change graduation. A skipped check does not imply exit/failure or remove later
financing/dilution. Never force graduation, exit, failure, and remaining to sum
to 100% in this model.

### Expected and entered-count views

- Expected per-company cost
  `E_a = initialCheck + Σ(q_r * participation_r * conditionalCheck_r)`.
- Expected companies `n_a = allocationBudget / E_a`, retained fractionally and
  labeled **Expected companies**.
- Expected follow-on demand
  `F_a = Σ(n_a * q_r * participation_r * conditionalCheck_r)`.
- User-entered integer `plannedCompanyCount = k` produces a separate **Entered
  company count** view with initial demand, follow-on demand, total demand, and
  signed residual.
- Every stress and comparison identifies whether it uses `n` or `k`; no output
  silently swaps count basis.

### Conservation, timing, and verdict axes

- `F_lifetime = F_within_term + F_beyond_term`.
- `initialDemand + F_lifetime + unassignedPlanningBudget = N`, plus one named
  signed rounding residual after output quantization.
- Follow-on reserve is derived demand/earmark, not a fixed target or bank
  balance.
- Allocation gaps and reserve-earmark gaps may coexist with unused fund
  capacity; report each independently without automatic transfer or winner
  selection.
- Monthly entry cohorts and cumulative previous-round lags drive timing. Timing
  changes may move demand beyond term without changing lifetime demand.

Every complete result exposes independent axes:

| Axis              | Values                                                                  |
| ----------------- | ----------------------------------------------------------------------- |
| Input support     | `complete`, `incomplete`, `unsupported`, `invalid`                      |
| Lifetime capacity | `within_capacity`, `over_capacity`, `unavailable`                       |
| Allocation budget | `within_allocation`, `allocation_gap`, `unavailable`                    |
| Reserve earmark   | `within_earmark`, `earmark_gap`, `unavailable`                          |
| Timing            | `within_term`, `includes_beyond_term`, `all_beyond_term`, `unavailable` |
| Staleness         | `current`, `stale_source`, `unknown_current_source`                     |

An umbrella headline must include material qualifiers. Example:
`Within lifetime capacity; includes $X beyond fund term.` Never show unqualified
`Feasible` when beyond-term demand exists. Beyond-term demand is not a
current-liquidity, settlement, capital-call, or funding-date failure.

Ambiguous time origin returns `TIME_ORIGIN_UNRESOLVED` at the exact duration
source path. Because timing is required core result content, this blocks
save/run/snapshot. The UI may show unaffected arithmetic only as an incomplete
unsaved preview.

### Optional representative-issuer performance companion

One optional case represents one named holding or explicitly labeled
representative issuer. It uses Plan A's aggregate preference method and remains
separate from construction:

- required nonempty issuer label, exit equity value/date, effective ownership,
  fund preference, senior/pari/junior other claims, preference type, invested
  cost, and optional participating total-payout cap;
- `totalPreferencesJuniorUsd` means other holders' junior claims; display
  **Preferences Behind Position**;
- manual ownership override changes only this companion;
- manual FMV override changes displayed FMV only and never changes proceeds,
  invested cost, any MOIC, or construction;
- non-participating, participating/capped, and full-conversion routes conserve
  exit equity and select `max(preferredRoute, conversionRoute)` at full
  precision;
- zero invested cost returns null MOIC with `ZERO_COST`.

Unsupported instrument mapping, required companion inputs, or ambiguous
seniority blocks save while the companion is selected. The user must correct it
or explicitly remove/disable the companion. Optional FMV may remain unavailable
without blocking a valid companion. A complete fixed-only construction result
may persist with independent ownership unavailable.

No aggregate preference deduction, secondary proceeds, portfolio TVPI-like
metric, follow-on MOIC, exit-value-to-return-fund solver, partial-sale model, LP
waterfall, or security-level conversion ships in F_1.15.0.

## Technical Considerations

- **Precision:** Decimal/fixed strings throughout; quantize emitted leaves once
  and show signed rounding residual.
- **Idempotency/concurrency:** keep create `Idempotency-Key` request-hash replay
  separate from synchronous calculate V3 input-hash dedupe. Retain fund/config
  locks, composite source CAS, scenario-row serialization, fenced completion,
  and atomic whole-transaction success or rollback.
- **Input trust boundary:** schema validation first; selected malformed source
  facts refuse without lower-precedence fallback.
- **Source compatibility:** absent `fundedFromFeesPct` effective zero is
  scenario provenance only; original config bytes/hash and V1 outputs stay
  stable.
- **Fee semantics:** deemed GP deduction and fee calculation are separate;
  full-fund committed-capital population remains current supported method until
  versioned ADR-070 Decision 3 work.
- **Core/optional boundary:** required core timing/source issues block
  persistence; fixed-only ownership and optional FMV may be unavailable in
  otherwise complete results; selected invalid companion blocks until
  removed/corrected.
- **Accessibility:** baseline completion and recovery behavior is release
  gating.
- **Security/governance:** existing auth/fund access/team-write roles only. No
  production, provider, publication, merge, or activation authority follows from
  this plan.
- **No new dependencies:** existing Zod, Decimal, React/Preact, query, scenario,
  and design-system utilities suffice.

### Application rollback after capital persistence

The first committed capital scenario set/variant is the compatibility boundary;
a calculation snapshot need not exist yet. After that write, recovery is
**forward-fix-only**: retain capital-aware family classification, strict capital
readers, early legacy aggregate filtering, and the expanded CHECK. Do not deploy
the pre-F_1.15.0 application or revert these readers; it cannot parse persisted
capital rows. A targeted application repair may remove faulty write/UI behavior
only while preserving those compatible readers and every saved set/snapshot.
Archiving a set, hiding UI, or disabling client features does not erase this
boundary. No new flag, receipt table, or staged reader-only release is required.

Before the first capital-enabled release, the existing release verification must
demonstrate default legacy and negotiated capital reads on synthetic persisted
legacy plus capital sets, both before and after calculation and while archived.
Verify the proposed recovery artifact against that same persisted-data fixture;
an artifact that removes capital-aware readers is blocked. Before any committed
capital write, ordinary governed application rollback is eligible only with
positive evidence that no capital set/variant/snapshot exists and new writes
have stopped; retain the expanded CHECK. A failed transaction alone is not proof
of global absence, and an ambiguous/lost commit response is not proof of
failure. If absence cannot be established, apply the post-write forward-fix-only
rule.

Follow the existing governed rollback/release route in
`docs/runbooks/rollback.md` and `docs/workflows/PRODUCTION_SCRIPTS.md`; this
plan does not authorize their execution. Preserve data and schema, never run a
down migration or delete capital rows to make an old binary fit. Any later data
or constraint retirement requires separate reviewed work and authority.
