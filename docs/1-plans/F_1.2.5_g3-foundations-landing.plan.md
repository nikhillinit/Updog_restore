### Locked public/API contracts

- `PATCH /api/portfolio-companies/:id?fundId=<id>` — requires
  `Idempotency-Key` header; body `{ expectedVersion, patch }`; writable
  fields exactly `name`, `sector`, `foundedYear`, `description`, `dealTags`;
  omitted fields unchanged, nullable fields clearable with `null`; returns
  updated row with `rowVersion` + `updatedAt`; errors `VERSION_CONFLICT`
  (409), `IDEMPOTENCY_KEY_REUSE` (409), validation (400), fund
  denial/not-found (403/404). No transition endpoint.
- `POST /api/funds` — partner/admin write role; existing request shape;
  fund + initial draft + creation event + creator `user_fund_grants` row
  commit atomically; only the canary principal produces marked canary funds;
  ordinary clients cannot submit `dataOrigin`.
- Fund-scenario hard timeout — run status remains `failed`;
  `failureCode: "HARD_TIMEOUT" | null` surfaced; no internal stack/error
  text exposed; non-retryable via BullMQ `UnrecoverableError`.
- `GET /api/version` — returns application version, exact commit (via
  `getReleaseIdentity()`), and runtime Node version. Control-plane IDs stay
  out of the public response.
- Worker `GET /health` — returns commit, deployment ID, **non-empty**
  registered worker list, per-worker state, counters; zero workers, wrong
  worker name, paused worker, or SHA mismatch => non-ready (503).
- `PUT /api/lp/settings` — stop faking success; return
  `501 LP_SETTINGS_WRITE_NOT_IMPLEMENTED`. Notification preferences continue
  through their existing persisted endpoint.

#### Lane B — Fund-scenario hard timeout + lifecycle fencing

**Files**: `workers/fund-scenario-calc-handler.ts`,
`workers/fund-scenario-calc-worker.ts`,
`server/queues/fund-scenario-calc-worker-init.ts`,
`server/services/fund-scenario-calculation-run-service.ts`,
`server/services/fund-scenario-reserve-calculation-service.ts`,
`server/services/fund-scenario-calculation-status-service.ts`.

1. Require `FUND_SCENARIO_HARD_TIMEOUT_MS` in production (fail fast if
   unset); explicit injected values in tests. The production value is
   measured and release-owner-ratified — not invented.
2. Deadline actor: owned `AbortController` combined with BullMQ
   cancellation (precedent: `server/queues/backtesting-queue.ts:67,164,209`);
   abort checks around claim, calculation boundaries, and before
   persistence.
3. **Fencing (closes a live defect)**: replace the unfenced
   `WHERE id = $1` updates (`fund-scenario-calculation-run-service.ts:254-308`)
   with per-transition CAS predicates (four distinct write paths — ordinary
   failure and deadline timeout are separate transitions with separate
   predicates):
   The deadline is **persisted, not computed at check time**: add a
   **nullable** `deadline_at timestamptz` column to
   `fund_scenario_calculation_runs` (`shared/schema/fund.ts`, additive
   migration via the Lane C schema owner). **Migration is column-only
   DDL — no backfill**: the ratified timeout value lives in
   `FUND_SCENARIO_HARD_TIMEOUT_MS` (runtime env) and is never injected
   into migration SQL; all legacy-row stamping happens in the runtime
   sweep reconciliation step (below), where the configured value already
   exists. Legacy rows therefore sit at `deadline_at IS NULL` (invisible
   to the timeout CAS) until reconciliation grants them a full fresh
   window — genuinely stranded rows are terminalized one window after
   sweep enablement (bounded delay, no insta-kill of healthy in-flight
   work). All sync rows (NULL `job_id`) stay NULL forever.
   **Sweep enablement gate (two-stage, closes the Railway-overlap race)**:
   Railway activates a new deployment before terminating the old one, so
   an old unfenced (`WHERE id = $1`) worker can briefly coexist with the
   new fenced code. The sweep (both steps) ships disabled behind
   `FUND_SCENARIO_SWEEP_ENABLED` (default off). Stage 1 deploy ships
   fenced CAS writes + the deadline column; after the operator confirms
   via Railway deployment list that no previous worker deployment remains
   active, the flag is enabled (stage 2). From then on no unfenced writer
   exists, so a timeout terminalization can never be overwritten.
   Regression coverage: (a) fenced completion after terminalization
   zero-rows (late worker cannot overwrite `HARD_TIMEOUT`); (b) sweep
   disabled => reconciliation and terminalization both no-op. Semantics are **async-only**: the synchronous calculation
   path (`fund-scenario-calculation-service.ts`) sets no deadline and is
   unchanged; NULL means "no deadline", and deadline predicates below are
   written NULL-safe (`deadline_at IS NULL OR ...`) so sync rows never
   zero-row on the deadline term. The async insert sets
   `deadline_at = clock_timestamp() + timeout` (bounds queued-but-never-
   claimed rows); the claim CAS re-arms it for the execution window. All
   comparisons use `clock_timestamp()` (statement-real time), never
   `NOW()` (transaction-start-stable, admits late completion inside a long
   transaction). **Job-identity predicate is NULL-safe**: synchronous
   callers create rows with `job_id = NULL` and call these same transition
   functions, and SQL `NULL = NULL` never matches — every `job_id`
   comparison below is therefore written
   `job_id IS NOT DISTINCT FROM $n`, which keeps strict fencing for async
   rows (non-NULL must match exactly) while letting sync callers (passing
   NULL) transition their own NULL-job rows:
   - claim (`markScenarioCalculationRunRunning`):
     `WHERE id = $1 AND status = 'queued' AND job_id IS NOT DISTINCT FROM $n AND
     (deadline_at IS NULL OR clock_timestamp() < deadline_at)` — an
     expired queued row cannot be re-armed and executed; the rejected
     claimer routes it through the timeout CAS instead. On success:
     `SET status = 'running', started_at = clock_timestamp(),
     deadline_at = clock_timestamp() + $timeout` (async path only);
   - completion (`markScenarioCalculationRunCompleted`):
     `WHERE id = $1 AND status = 'running' AND job_id IS NOT DISTINCT FROM $n AND
     (deadline_at IS NULL OR clock_timestamp() < deadline_at)`;
   - ordinary failure (`markScenarioCalculationRunFailed`, currently never
     called — wire it for caught execution errors before BullMQ retry):
     `WHERE id = $1 AND status = 'running' AND job_id IS NOT DISTINCT FROM $n` — **no**
     deadline predicate, otherwise every transient error would zero-row and
     strand the run `running` while the retry loses ownership. This path
     explicitly excludes timeout-tagged aborts (below);
   - deadline timeout (new `markScenarioCalculationRunTimedOut`, writes
     `status='failed'`, `failure_code='HARD_TIMEOUT'`):
     `WHERE id = $1 AND status IN ('queued','running') AND job_id IS NOT DISTINCT FROM $n AND
     deadline_at IS NOT NULL AND clock_timestamp() >= deadline_at` — one
     expression covers queued rows (never claimed, insert-time deadline)
     and running rows (claim-time deadline), no `started_at IS NULL`
     special case; sync rows (NULL deadline) are untouchable by it.
   **Expired-row sweep (locked)**: the in-flight deadline actor only
   covers jobs whose worker is alive; each sweep run executes two
   idempotent steps in order:
   1. reconciliation — stamp `deadline_at = clock_timestamp() + timeout`
      (a full fresh window, never immediate expiry — same
      no-insta-kill rationale as the migration backfill) on any active
      (`queued`/`running`) row with `job_id IS NOT NULL AND deadline_at
      IS NULL` (closes the schema-first rollout hole where old code
      instances insert async rows without deadlines after the migration
      backfill has already run);
   2. terminalization — expire any `queued`/`running` row past its
      deadline through the same timeout CAS (passing each selected row's
      own `job_id`), covering crashed workers and never-run jobs.
   Scheduling seam: the sweep is a distinct repeatable job named
   `fund-scenario-deadline-sweep` on the existing fund-scenario queue —
   the worker's processor branches on job name (calculation jobs vs sweep
   job; typed job-name/data union), registration is `await
   queue.upsertJobScheduler(...)` (same API the capital-call worker
   already uses) during worker startup in
   `workers/fund-scenario-calc-worker.ts`, fixed 60 s interval
   (queue-mechanics constant), plus one immediate sweep at startup.
   Lifecycle: the startup path owns BOTH handles — the graceful-shutdown
   path awaits `queue.close()` in addition to the existing
   `worker.close()` (closing only the Worker leaks the Queue connection).
   Test: expire a queued row with no worker (deadline set in the past),
   run sweep, assert `failed`/`HARD_TIMEOUT` and that the dedupe slot
   frees for recalculation. Reconciliation test (two sweeps, honest
   sequencing): seed an async active row with NULL deadline; sweep 1
   stamps a full fresh window and the row **stays active** (before its
   deadline); the test then moves `deadline_at` into the past (direct
   update — no wall-clock waiting); sweep 2 terminalizes it.
   **Abort routing (locked)**: the deadline actor performs the timeout CAS
   FIRST, then aborts the controller with a tagged timeout reason
   (`AbortController.abort(reason)`); the handler's catch inspects the
   tag — timeout-tagged aborts skip the ordinary-failure CAS entirely and
   throw `UnrecoverableError`, so ordinary failure can never win the race
   and launder `HARD_TIMEOUT` into a retryable failure.
   Each function returns affected-row count; zero rows = lost the race,
   caller must not proceed to dependent writes.
   The deadline actor terminalizes on an independent transaction.
   `failure_code` column already exists — populate `HARD_TIMEOUT`; no
   schema change needed for it.
4. Completion loses to timeout: late completion rolls back snapshot +
   success event; no late writes after terminalization.
5. Throw BullMQ `UnrecoverableError` after `HARD_TIMEOUT`; transient errors
   keep the existing `attempts: 2` + backoff.
6. Correct every comment claiming `lockDuration` is an execution timeout

  deadline transaction and Lane A's advisory-lock transaction must not rely
  on CTE visibility.

  surface; `transaction-support.ts` fencing applies.

  hashes by design; only the Phase 4 tracked regen re-approves — disposable
  regens never write review state.
