# Railway Production Token Replacement Route Implementation Plan

## Overview

This plan is slice S2 of
`docs/1-plans/F_1.3.8_ninth-vehicle-prerequisites-and-0062-solo-path.plan.md`
(item 3). It admits a standing owner-run route to replace the GitHub environment
`Production` secret `RAILWAY_TOKEN` with a new Railway project token, and adds a
read-only GitHub Actions provider check that shows whether the stored token and
provider identifiers work before any release uses them. One pull request carries
ADR-118, the governing policy section, the procedure, the check workflow, one
exported provider-read entry point, and tests. Execution (S4) is a separate
owner action after merge.

## Owner decisions (2026-11-20, recorded from discovery)

- Q1 Token path: the owner creates the token in the Railway dashboard and pipes
  it into `gh secret set` from the clipboard. No helper script; the plaintext
  never reaches an agent. A token whose plaintext is lost is revoked and
  replaced. The owner accepts the overwrite risk of the unconditional secret
  write.
- Q2 Old tokens: revoke the original Production token (invalidated by Railway on
  2026-10-22) and any token created by the 2026-11-02 ADR-110 attempt, only
  after the new token passes the provider check.
- Q3 Check dispatch: on the owner's explicit instruction, one delegated local
  executor (the agent) may dispatch the read-only check from `main`. The
  `Production` required-reviewer gate still pauses the job; only the owner
  approves it. The executor never approves a deployment or environment review.
- Q4 S1 readings: the token inventory part of S1 folds into this procedure as
  its inventory step, and the F_1.3.7 two-sample CLI inventory rule is retired
  for this route. Scope of that retirement (Verified state row 9): only G2's
  token inventory and original-token record readings. The worker readings and
  the access-anomaly review stay G2 owner readings.
- Q5 Route scope: standing. The procedure stays admitted for later replacements
  of `Production/RAILWAY_TOKEN`; each use needs the owner's explicit instruction
  and acceptance of the overwrite risk for that use's writes (at most three).

## Problem Statement

Every release mode needs a valid `Production` `RAILWAY_TOKEN`. Railway
invalidated all pre-incident tokens on 2026-10-22, the stored secret predates
that, and ADR-110's one-time route ended with an unknown creation outcome and a
consumed budget. No admitted route can replace the secret, so G1 blocks the
ninth vehicle and every release. A token-scope query alone is not enough proof:
a stale service ID passes it and still fails the capture (F_1.3.8 Verified state
row 23).

## Solution Architecture

- **Owner-run replacement (no new executable).** The owner creates one Railway
  project token scoped to the Production environment in the Railway dashboard
  and writes it with `gh secret set` from standard input. GitHub's
  environment-secret write has no conditional-update contract, so ADR-118
  records, per use, the owner's explicit acceptance of the concurrent-writer
  overwrite risk in place of optimistic locking for this one secret, with
  metadata readback.
- **Read-only provider check in GitHub Actions.** A new manual workflow runs the
  capture's own provider read against the stored `Production` secrets and
  variables and prints only `PASS` or one fixed failure class. It creates no
  provider deployment, artifact, or write.
- **Check first, replace second.** The procedure runs the check against the
  stored token before any token is created. A `PASS` ends the use with no
  replacement. The failure class the stored token produces calibrates the
  mapping before the check judges a fresh token.
- **One provider-read entry point.** The provider-read half of
  `captureProviderBaseline` moves into an exported function that both the
  capture and the check call, so the check cannot drift from what the capture
  verifies.
- **Old-token cleanup after proof.** Revocation of the two named old records
  happens only after `PASS`.

Rejected: an ADR-110-style helper (owner Q1; repeats the lost-plaintext trap and
adds code); a token-context query only (misses stale service IDs); reusing
`capture-release-baseline.yml` (it needs a frozen PR and plan binding and writes
an artifact).

## Implementation Details

### 1. Provider-read entry point and check command

**File**: `scripts/release/capture-release-recovery-context.mjs`

**Current state**: `captureProviderBaseline` (:406-531) validates capture
inputs, reads expected identity from the environment (:316-333), then performs
the Vercel and Railway reads and verifications, then builds the capture context.
`responseJson` (:361-379) wraps every request. `main()` (:1496) dispatches
subcommands such as `capture-provider`.

**Modifications**:

- `responseJson` attaches the HTTP status (or none, when the fetch threw) to the
  thrown error as a property. Its messages and `transport` flag stay unchanged.
- Extract the provider read (from the expected-identity read through the Railway
  topology verification and source-by-service map) into an exported
  `readProviderIdentity({ environment, fetchImpl })` that returns the expected
  identity and the provider identity exactly as `captureProviderBaseline` uses
  them today. `captureProviderBaseline` keeps its input validation, calls the
  new function, and builds the same context. Its output, error texts, and
  request order and count stay unchanged.
- Inside `readProviderIdentity`, tag every failure with one fixed class on the
  thrown error, without adding or reordering any request:
  - `CONFIGURATION`: a missing or invalid environment value other than
    `RAILWAY_TOKEN`.
  - `RAILWAY_TOKEN_VALUE`: `RAILWAY_TOKEN` missing, empty, or with surrounding
    whitespace.
  - `PROVIDER_UNREACHABLE`: any provider request whose fetch threw or timed out,
    returned HTTP 429 or 5xx, or returned an unparsable body.
  - `VERCEL_REJECTED`: a Vercel request with any other non-OK status.
  - `VERCEL_IDENTITY`: the unsafe-URL check or `verifyVercelEvidence` refused.
  - `RAILWAY_TOKEN_REJECTED`: the token-context request returned HTTP 401 or
    403, or a GraphQL error whose `extensions.code` is in a fixed
    authentication-denial set (`UNAUTHENTICATED`, `UNAUTHORIZED`, `FORBIDDEN`).
    This is the only class that confirms a token refusal.
  - `RAILWAY_TOKEN_UNCONFIRMED`: the token-context request returned HTTP 200
    with any other GraphQL error, or no project or environment ID. Railway
    reports both server faults and authorization denials as HTTP 200 GraphQL
    errors, so this class never by itself justifies revocation.
  - `RAILWAY_TOKEN_SCOPE`: the token context's project or environment differs
    from the stored variables. This is recorded right after the token read
    (comparison only, no request) and reported when any later Railway step
    refuses, which `verifyRailwayTopology` always does on that mismatch.
  - `RAILWAY_TOPOLOGY`: any other topology request, normalization, service, or
    source-SHA refusal.
- Add an exported `checkProviders({ environment, fetchImpl })` that returns
  `{ ok: true }` or `{ ok: false, failureClass }`, and a `check-providers`
  subcommand in `main()` that prints exactly `PROVIDER_CHECK PASS` and exits 0,
  or `PROVIDER_CHECK FAIL <CLASS>` and exits 1. It never prints an underlying
  error message, response body, identifier, hostname, SHA, or token. An error
  without a class prints `UNEXPECTED`.

### 2. Provider check workflow

**File**: `.github/workflows/production-provider-check.yml` (new)

Modeled on `capture-release-baseline.yml`:

- Trigger: `workflow_dispatch` only, no inputs. Top-level
  `permissions: contents: read`. Job `if: github.ref == 'refs/heads/main'`,
  `environment: Production`, `timeout-minutes: 10`, own concurrency group with
  `cancel-in-progress: false`.
- Steps: checkout of `github.sha` with `persist-credentials: false` (same pinned
  action SHA as the capture); a guard step that requires
  `GITHUB_EVENT_NAME == workflow_dispatch`, `GITHUB_REF == refs/heads/main`, and
  `GITHUB_ACTOR_ID == github.repository_owner_id`; the same Node setup the
  capture uses; one step running
  `node scripts/release/capture-release-recovery-context.mjs check-providers`
  with `timeout-minutes: 4` and exactly the capture's provider environment:
  `VERCEL_TOKEN` and `RAILWAY_TOKEN` from `secrets`, the seven variables in
  Verified state row 3 from `vars`.
- No artifact upload, cache, provider deployment, `GITHUB_TOKEN` write scope, or
  other secret. The step `env` echo shows the seven variables, as in the capture
  (Technical considerations, public repository). GitHub records an environment
  deployment entry for the job, as for the capture (Verified state row 10). The
  workflow header comment states that execution confers no authorization and
  that output is pass or a failure class only.

### 3. ADR-118 (draft text for `DECISIONS.md`)

> **ADR-118: Owner-Run Railway Production Token Replacement**
>
> **Date:** Set on owner ratification. **Status:** Proposed. Takes effect only
> with explicit owner ratification and protected-main admission of the matching
> policy section, procedure, and check workflow.
>
> **Context.** Every release mode needs a valid GitHub `Production`
> `RAILWAY_TOKEN`. Railway invalidated pre-incident tokens on 2026-10-22. The
> ADR-110 route consumed its single action budget on 2026-11-02 with an unknown
> creation outcome and no GitHub write. GitHub's environment-secret write has no
> documented conditional-update contract, so the retained optimistic-locking
> mandate blocks any replacement without an explicit exception.
>
> **Decision.**
>
> 1. Admit a standing owner-run route, "Railway production token replacement
>    (ADR-118)" in `docs/workflows/PRODUCTION_SCRIPTS.md`, for replacing the
>    `Production` secret `RAILWAY_TOKEN` with one Railway project token scoped
>    to the Production environment. Each use is a separate owner action. The
>    owner creates the token in the Railway dashboard and writes it with
>    `gh secret set` from standard input. The token plaintext never enters an
>    agent session, a file, shell history, or the repository.
> 2. For each use, the owner's explicit acceptance of the concurrent-writer
>    overwrite risk replaces optimistic locking for that use's secret writes, at
>    most three. Each write is followed by metadata readback. The exception
>    covers no other secret, variable, or provider setting.
> 3. Each use starts with the read-only check against the stored token; a `PASS`
>    ends the use without a replacement. A created token whose plaintext is
>    lost, or that the check refuses for a confirmed token reason, is revoked
>    before another is created. A use permits at most three secret writes. There
>    is never more than one unrevoked unused token. An ambiguous provider result
>    never leads to revocation. A use that stops after a write, including on a
>    failed revocation, stays open until it resumes at the check and completes
>    every outstanding revocation and its record.
> 4. A use completes only when the read-only workflow
>    `production-provider-check.yml` reports `PASS` against the stored
>    `Production` secrets and variables. On the owner's explicit instruction,
>    one delegated local executor may dispatch that workflow from `main`. Only
>    the owner approves its `Production` environment gate; the executor never
>    approves a deployment or environment review.
> 5. After the first `PASS` under this route, the owner revokes the original
>    Production project token and any token created by the 2026-11-02 ADR-110
>    attempt. This replaces ADR-110's rule to retain those two records. Later
>    uses revoke the token they replace after `PASS`.
> 6. The route's inventory step replaces only the token inventory and
>    original-token record readings of the F_1.3.7 readings (F_1.3.8 G2). The
>    worker readings and the access-anomaly review remain owner readings.
>
> **Consequences.** ADR-110 is superseded for any further Railway Production
> token replacement; its receipt and outcome stay historical evidence. The
> provider check is evidence, not authorization: it does not admit a release,
> close G1 by itself, or replace the release capture. The route authorizes no
> deployment, promotion, variable change, service change, database action, or
> other credential.
>
> **Accepted risks.** Another GitHub writer can overwrite the secret, or be
> overwritten, between the readback and later use; metadata readback cannot
> prove the stored value. GitHub never returns secret plaintext, so only the
> provider check shows the stored value works. Revoked tokens cannot be
> restored.
>
> **Alternatives.** Keep waiting for a conditional-write contract (blocks every
> release). A tracked helper that calls both APIs (more code, same
> lost-plaintext failure mode). A token-scope query as the only check (passes a
> stale service ID). A one-time route (the next token incident would need
> another ADR).

### 5. Procedure

**File**: `docs/workflows/PRODUCTION_SCRIPTS.md`

Add "Railway production token replacement (ADR-118)" after the ADR-110
procedure, with placeholders only:

1. Preconditions: ADR-118 merged; the owner's explicit instruction for this use,
   including acceptance of the overwrite risk; no `release-production`,
   `capture-release-baseline`, or `prod-schema-reconcile` run queued or in
   progress (`gh run list` per workflow).
2. Check the stored token: dispatch `production-provider-check.yml` from `main`
   (the executor may do this on instruction); the owner approves the
   `Production` gate.
   - `PASS`: the stored token works. Stop; no replacement in this use. (An open
     use resumes at step 7 instead; see step 10.)
   - `RAILWAY_TOKEN_REJECTED`, `RAILWAY_TOKEN_SCOPE`, or `RAILWAY_TOKEN_VALUE`:
     continue to step 3.
   - `RAILWAY_TOKEN_UNCONFIRMED`: re-run at least five minutes later; if it
     repeats, continue to step 3 (this replaces the stored token but revokes
     nothing until `PASS`).
   - `PROVIDER_UNREACHABLE`: re-run later; do not continue on this result.
   - Any other class: stop. The check cannot judge a new token until that repair
     is planned and done separately.
3. Inventory: the owner lists every project token on the Railway project's token
   settings page and records privately each name, environment, and creation
   date, marking the token currently used by GitHub and, on the first use, the
   original Production token and any token created on 2026-11-02. Read the
   `Production` secret metadata (names, `created_at`, `updated_at`); the
   executor may perform this read.
4. Create: one project token for the Production environment, named
   `github-production-<YYYYMMDD>` (add a suffix for a later attempt on the same
   day).
5. Write, then clear the clipboard:
   `pbpaste | gh secret set RAILWAY_TOKEN --env Production --repo <owner/name>`
   and `pbcopy < /dev/null`. Never paste the token anywhere else. If the
   plaintext is lost before the write, revoke the new token and return to
   step 4. A use permits at most three secret writes (the first and two
   re-creations); the owner's acceptance of overwrite risk for the use covers
   each of them, and every write is followed by step 6. A failed or unknown
   write counts toward the three.
6. Readback: `RAILWAY_TOKEN` `updated_at` is later than the step 4 time,
   `created_at` is unchanged, and every other `Production` secret's metadata
   equals step 3.
7. Check the new token (as step 2). Outcomes:
   - `PASS`: continue.
   - `RAILWAY_TOKEN_REJECTED`, `RAILWAY_TOKEN_SCOPE`, or `RAILWAY_TOKEN_VALUE`:
     revoke the new token and return to step 4. When the use has no write left
     (step 5), stop instead.
   - `RAILWAY_TOKEN_UNCONFIRMED`: never revoke. Re-run at least five minutes
     later; if it repeats, stop, keep the new token, and leave the use open
     until a re-run gives `PASS` or a confirmed class.
   - `PROVIDER_UNREACHABLE`: re-run the check; never revoke on this result.
   - Any other class: the token is not the cause. Stop, keep the new token,
     leave the use open, and plan the repair separately.
8. Revoke the token this use replaced and, on the first use, the original
   Production token and any 2026-11-02 token. Re-read the token page: the new
   token is the only Production-environment token, apart from tokens the owner
   chose at step 3 to keep, each recorded with a reason.
9. Record privately: times, token labels, the check run IDs and results. Nothing
   goes in the repository. G1 in F_1.3.8 closes only when the S8 capture
   authenticates to Railway. G2's worker readings and access-anomaly review are
   separate owner readings and are not satisfied by this procedure. The use is
   closed only when this step is complete.
10. Open use: a use that stopped after its first write and before step 9 is
    complete stays open, with its step 3 inventory, writes used, and any
    revocations still outstanding recorded privately. This includes a stop on a
    failed revocation in step 8. It resumes, under the same acceptance or a
    renewed one, at step 7 against the stored token, then performs the
    outstanding revocations of step 8 and completes step 9. A new use cannot
    start while one is open.

## Technical Considerations

- **Pattern usage**: governance amendment as one PR carrying policy section,
  ADR, procedure, executable change, and pinned tests (ADR-110, ADR-112,
  ADR-116). Workflow modeled on `capture-release-baseline.yml`.
- **Optimistic locking**: retained everywhere except a use's secret writes (at
  most three), waived only by explicit per-use owner acceptance with readback
  after each write (the ADR-116 Q9 shape).
- **Idempotency**: the check is read-only and safe to re-run. The replacement is
  not idempotent; the procedure bounds it by revoking each unused token before
  another creation, allowing at most three writes per use, and keeping an
  interrupted use open until it resumes at the check.
- **Public repository**: workflow logs are public. The runner echoes a step's
  `env` block before the command runs; secrets show as `***` but `vars` values
  print in full. The seven provider variables are therefore visible in the
  check's log exactly as they already are in every
  `capture-release-baseline.yml` run; F_1.3.8 (Technical considerations, public
  repository) records the Railway and Vercel project identifiers as already
  public and out of scope. Keeping them as `vars` preserves parity with what the
  capture and release read. The check's own output adds nothing: it prints only
  the pass line or a class token, never a response body, identifier, hostname,
  SHA, or token.
- **Approval gate**: `Production` has one required reviewer. Administrator
  bypass stays on and is not used by this route; the executor must not call any
  pending-deployment review API.
- **Classification safety**: an ambiguous provider result (network, 429, 5xx,
  unparsable) maps to `PROVIDER_UNREACHABLE`, and an unclassified GraphQL error
  maps to `RAILWAY_TOKEN_UNCONFIRMED`; neither leads to revocation on its own.
  Only a confirmed refusal (`RAILWAY_TOKEN_REJECTED`), a scope mismatch, or an
  invalid stored value leads to revocation. `RAILWAY_TOKEN_UNCONFIRMED` never
  leads to revocation, even when it repeats: Railway reports an invalid token's
  authorization error and a valid token's server fault under the same HTTP 200
  `INTERNAL_SERVER_ERROR`, and waiting does not tell them apart. At step 2 it
  only allows the use to continue, which replaces but never revokes the stored
  token.
- **Edge cases**: token created for the wrong environment
  (`RAILWAY_TOKEN_SCOPE`, revoke and re-create); a stale service ID with a good
  token (`RAILWAY_TOPOLOGY`, stop, token kept); a release dispatched during the
  window (precondition refuses; if one starts later, stop and re-run the check
  after it); the token page shows no 2026-11-02 token (record its absence);
  revocation fails (stop, record the outstanding revocation, and keep the use
  open; the new token still works); the stored value carries a trailing newline
  from standard input (`RAILWAY_TOKEN_VALUE`, revoke and re-create).
