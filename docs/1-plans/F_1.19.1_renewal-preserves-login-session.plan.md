Parent: F_1.19.0 (fund workspace journey qualification, plan PR

## Overview

A successful fund create or finalize renews the caller's credential so the
creator can use the new fund without signing in again. Today renewal mints a
token with a new `jti` and a new expiry. Logout revokes only the `jti` it
receives, so a renewed token survives the logout of the session it came from. A
create or finalize response that reaches the browser after user A logs out and
user B signs in installs A's live session over B's (defect D-E).

This plan makes renewal a claims refresh inside the presented login session: the
renewed token keeps the presented token's `jti` and `exp` and changes only its
fund grants. The existing logout revocation then kills every token of that
login. The change is server-side, confined to one module, and needs no
migration, route, claim, or client change.

## Problem Statement

- Renewal: `renewCreationCredential` in
  `server/lib/auth/creator-identity.ts:64-104`. The cookie path signs a new
  browser token with `signBrowserSessionToken` (new random `jti` and a fresh 24h
  `exp`, `server/lib/auth/jwt.ts:436-454`) and installs it with
  `setBrowserSessionCookies`. The bearer path returns `renewedAccessToken` from
  `signToken` (new `jti`, fresh 7d `exp`). Under a non-HS256 verifier it returns
  `credentialRenewal: 'reauth_required'` and mints nothing.
- Callers: fund finalize at `server/routes/fund-config.ts:142` and fund create
  at `server/routes/funds.ts:317`. Both renew unconditionally after
  `executeFundWorkflowCommand` returns, including idempotent replays (create
  reads `result.replayed` only for its log line, `funds.ts:308`). The F_1.19.0
  D-E text names only the finalize caller; this plan covers both.
- Logout: `server/routes/auth.ts:161-185` revokes only the presented
  `claims.jti` (with `expires_at` from the presented `exp`) through
  `revokeToken` (`server/lib/auth/revocation.ts:82-89`). The usability check
  (`revocation.ts:40-57`) looks up `revoked_tokens` by `jti`.
- Why renewal exists: token `fundIds` are the access authority
  (`userFromClaims`, `jwt.ts:236-258`, consumed by
  `server/lib/auth/fund-scope.ts` and `provided-fund-scope.ts`). Renewal adds
  the new fund ID from the user's grants so the creator can reach the fund
  without re-login. This plan keeps that property.
- Browser mechanism: the browser applies `Set-Cookie` from any response it
  receives, so a client-side fence (F_1.19.0 case C5a) cannot stop the install.
  The fix has to make the installed token useless.
- Secondary finding, bearer: the client never reads `renewedAccessToken` (only
  the `credentialRenewal` marker, `client/src/services/funds.ts:187`,
  `client/src/pages/ReviewStep.tsx:387`), so nothing installs a bearer token
  automatically and the bearer path is not the D-E mechanism. A renewed bearer
  token still survives logout of the presented bearer `jti`. The same fix closes
  it.

## Decisions (owner, 2026-09-27)

- **D1, design: `jti`-preserving renewal only.** Renewal keeps the presented
  `jti`; logout's existing revocation covers every renewed token.
- **D2, lifetime: keep the presented `exp`.** Renewal no longer extends the
  session. Creating or finalizing a fund does not slide the 24h browser session
  (or the bearer lifetime).
- **D3, sequencing: order-independent.** This plan carries its own tests and
  states how F_1.19.0 case C5b is written in either order (see "Sequencing with
  F_1.19.0").
- **D4, scope: the stale-tab TODO stays separate.** A tab that replays A's
  pending finalize under B's cookie is a client-fence problem; this fix does not
  touch it.

Accepted residual (consequence of D1): when a late response lands after A logs
out and B signs in, the browser still replaces B's session and CSRF cookies with
A's renewed pair. That token is revoked, so B's next request returns 401 and B
signs in again. There is no identity confusion, only a forced sign-in. The
recovery path already exists and runs on every sign-in: the client login request
always bootstraps CSRF through `GET /api/auth/csrf` first
(`client/src/lib/install-auth-fetch.ts:102`), and that endpoint clears an
invalid session cookie and issues a pre-auth token
(`server/routes/auth.ts:65-95`, clear at `:87-90`), so login proceeds as after
any expired session.

Rejected alternatives (recorded so review does not re-raise them):

- Per-user revoke-at-logout epoch (a users column compared with token `iat`):
  revokes every session of the user, and needs a migration, which the F_1.18.0
  migration freeze (ADR-103) blocks.
- Move renewal to a client call after the command fence: the only design that
  keeps B's session, but the post-fence renewal request still carries A's
  cookie, so it narrows the race without closing it unless combined with D1. It
  also adds client work and either a new route or a side effect on
  `GET /api/auth/session`. Not chosen (D1).
- Authorize from `user_fund_grants` on every request and drop renewal: token
  `fundIds` are the access authority across several auth modules, so this is a
  wide change plus a database read per request.
- Session-family revocation (a family claim plus `family:<id>` rows in
  `revoked_tokens`): same semantics as D1 with an extra claim, extra rows, and a
  changed revocation query. D1 dominates it.

## Solution Architecture

A login session is identified by the `jti` minted at sign-in
(`server/routes/auth.ts:118-131`). After this change, renewal produces a token
with:

- the presented `jti` and `exp` (unchanged session identity and lifetime);
- the claims `claimsRenewedForFund` already builds (`sub`, `email`, `role`, org
  IDs, `lpId`, and the refreshed `fundIds`);
- the same algorithm (HS256), secret, issuer, and audience as
  `signTokenWithExpiry` (`jwt.ts:436-446`), and a fresh `iat`.

Logout of any token in the session (the login token or any renewal of it)
revokes that one `jti`, so every token of the session fails `assertTokenUsable`.
The CSRF token is bound to `session:<jti>` (`server/lib/auth/csrf.ts:55-58`), so
a CSRF token issued before renewal stays valid for the renewed cookie; renewal
still re-issues the CSRF cookie through `setBrowserSessionCookies`.

Fail closed: renewal mints only when the presented `jti` is a non-empty string
of at most 64 characters and the presented `exp` is a safe integer later than
the current time and within the JavaScript `Date` range (at most
8,640,000,000,000 seconds). The `jti` bound matches the `revoked_tokens.jti`
column (`varchar(64)`, `shared/schema/user.ts:68`), so a longer `jti` could not
be revoked at logout; the `exp` bound keeps logout's
`new Date((claims.exp ?? 0) * 1000)` valid (`server/routes/auth.ts:174`). The
check runs immediately before signing, after the asynchronous grant lookup, so
an `exp` that passes during the lookup is caught. Otherwise renewal mints
nothing and returns the existing `credentialRenewal: 'reauth_required'` marker.
It never creates a new session identity. Every token the server mints carries
both claims (`jwtid` and `expiresIn` in `signTokenWithExpiry`), so the
fail-closed branch only affects externally minted HS256 tokens without them;
`verifyAccessToken` requires neither claim (`jwt.ts:103-112`). No consumer of
`renewedAccessToken` exists in `client/`, `scripts/`, or `tests/e2e/`, and the
response contract already allows the marker
(`shared/contracts/fund-finalize-v1.contract.ts:154-159`).

Placement: the whole change lives in `server/lib/auth/creator-identity.ts`,
which both callers already route through, so neither route file changes.
`server/lib/auth/jwt.ts`, `server/routes/auth.ts`, `server/routes/funds.ts`,
`server/routes/fund-config.ts`, and `server/lib/auth/revocation.ts` are
source-hash pinned in `audit/surface-contract-matrix/source-inventory.json`
(`tests/unit/audit/surface-contract-matrix.test.ts` compares each pinned file's
sha256); `creator-identity.ts` is not pinned. Measured on 2026-09-27: a one-line
edit to `jwt.ts` followed by the mechanical hash-refresh tool passes all 13
`tests/unit/audit/` suites and `npm run matrix:check`, but only because the tool
rewrites the `jwt.ts` hash in about 390 rows across `matrix.json`, `MATRIX.md`,
and `g1-review.json` (about 2,300 changed lines). `g1-review.json` (lines 50
and 208) is a recorded review basis; restamping it would assert that the G1
review covered a `jwt.ts` it never saw. The refresh tool exists for rebases
(same reviewed content, new hash), not for semantic changes to a reviewed file,
and the precedent for a semantic change to a pinned route file (#1585,
`funds.ts`) was a scoped-review artifact plus full regeneration. Keeping the
pinned files byte-identical avoids both for a change that alters no route
boundary. The cost is that renewal signs through `jsonwebtoken` directly, using
the same config source as `jwt.ts` (`getConfig()` from `server/config`, which is
all `getJwtConfig` returns, `jwt.ts:41-43`). The existing signers cannot be
reused because `jsonwebtoken` rejects a payload that already carries `jti` or
`exp` when the `jwtid` or `expiresIn` option is also set, and
`signTokenWithExpiry` always sets both. Drift between the two signing sites is
caught by tests that verify renewed tokens through the real `requireAuth` and
`verifyAccessToken`.

## Implementation Details

### 1. Renewal keeps the presented session identity

**File**: `server/lib/auth/creator-identity.ts`

**Current state**: `renewCreationCredential` (lines 64-104) checks the
configured algorithm, reads grants, builds claims with `claimsRenewedForFund`,
then signs a new cookie token (and decodes it to read the new `jti` for the CSRF
cookie) or a new bearer token. Any failure restores the prior `Set-Cookie`
header and returns `reauth_required`.

**Modifications**:

- Keep the non-HS256 guard first (around line 78), unchanged.
- Immediately before signing (after the grant lookup and `claimsRenewedForFund`,
  around line 87), read `jti` and `exp` from `credential.claims` and apply the
  fail-closed rule in Solution Architecture. On failure return `reauth_required`
  with the same header handling as the non-HS256 branch
  (`Cache-Control: no-store` for bearer) and sign nothing. One check placed
  after the only `await` covers both invalid claims and an `exp` that passes
  during the lookup.
- Add one module-private signing helper that signs the renewed claims plus the
  presented `jti` and `exp` with HS256 and the configured secret, issuer, and
  audience, without the `jwtid` and `expiresIn` options. Import `getConfig` from
  `../../config` (the same import `jwt.ts` uses).
- Cookie path: sign with the helper and call `setBrowserSessionCookies` with the
  presented `jti`. Remove the post-sign `jwt.decode` check (lines 90-94); the
  `jti` is already known.
- Bearer path: return `renewedAccessToken` from the same helper, keeping
  `Cache-Control: no-store`.
- Remove the `signBrowserSessionToken` and `signToken` imports if nothing else
  in the module uses them. Keep `getConfiguredJwtAlgorithm`.
- Keep the existing catch block and its `Set-Cookie` restoration unchanged.
- Update the function's doc comment: renewal refreshes fund grants inside the
  presented login session; it never creates a new session identity or extends
  the session, so revoking the session's `jti` at logout revokes every renewal.

### 3. Tests

**File**: `tests/unit/auth/creator-identity.test.ts`

- The `bearerRequest` fixture gains a `jti` and a future `exp`, so the existing
  "returns reauth_required when renewal fails after creation" case still fails
  at the grant lookup, not at the new claim check.
- New cases: a presented credential without `jti`, with a `jti` longer than 64
  characters, with a missing or past `exp`, and with an `exp` beyond the `Date`
  range each return `reauth_required` and sign nothing; a presented `exp` that
  passes while the grant lookup is pending (the lookup mock resolves after the
  clock is advanced past `exp`) returns `reauth_required`; a cookie renewal and
  a bearer renewal each produce a token whose decoded `jti` and `exp` equal the
  presented ones and whose `fundIds` include the new fund.

**File**: `tests/unit/routes/fund-creation-credential-renewal.test.ts`

- Replace the constant `assertTokenUsable` mock with a set-backed revocation
  mock (the pattern in
  `tests/integration/cookie-session-auth-runtime.test.ts:7-20`) that also
  provides `revokeToken`, and mount the auth router so the test can call
  `POST /api/auth/logout` and `GET /api/auth/session`.
- The two existing cases keep passing unchanged in intent.
- New denial case, cookie: create with the old cookie, take the renewed cookie,
  log out with the old cookie (204, revocation recorded for the old `jti`). The
  renewed cookie then gets 401 on `GET /api/auth/session` (zero leak: no user

  mutation). A CSRF token issued before renewal is accepted with the renewed
  cookie before logout.
- New denial case, bearer: the same sequence with bearer credentials; the
  renewed bearer token is denied after the old token's logout.
- New replay case: with `executeFundWorkflowCommand` mocked to report
  `replayed: true`, renewal still returns a token carrying the presented `jti`.

**File**: `tests/integration/fund-lifecycle-db.test.ts`

- In the finalize case (around lines 367-495), decode the presented admin bearer
  token (built by `authHeader`, around line 202) and assert that the first
  finalize response (around line 380) and its idempotent replay (around
  line 491) each carry a `renewedAccessToken` whose `jti` and `exp` equal the
  presented token's. This covers the finalize caller and its replay path against
  real Postgres. The suite runs only under `vitest.config.testcontainers.ts`.

These cases satisfy the policy's auth-domain minimum (denial test plus zero
mutation and zero leak assertion).

### 4. Sequencing with F_1.19.0 (case C5b)

The F_1.19.0 C5b rules treat a 401 as "a normal red test, never masked by
`test.fail()`". Under this fix the correct post-fix outcome of C5b's browser
path is exactly that 401, so C5b does not turn into "expected to fail, but
passed"; it has to be rewritten. The post-fix C5b assertion, in either order:

- After A's out-of-band response is released, the browser context's session
  cookie equals the token from A's response (the release installed it).
- `GET /api/auth/session` then returns 401 with no user body (no A identity is
  served).
- B can sign in again (the csrf endpoint clears the revoked cookie), and the
  session then reports B.
- No `test.fail()` annotation.

If C5b used the API-level fallback, its final assertion is already 401; only
`test.fail()` is removed.

Order handling:

- **F_1.19.0 implementation lands first:** this plan's PR rewrites C5b in
  `tests/e2e/fund-workspace-recovery.spec.ts` to the assertion above and
  replaces the TODOS.md "Auth: late finalize response reinstalls a logged-out
  session" entry with a resolved note naming F_1.19.1.
- **This plan lands first:** C5b does not exist yet. This plan's PR adds one
  paragraph to the TODOS.md "Stabilize-and-qualify PR2, PR3a and PR3b" entry
  (which F_1.19.0 section 10 tells its implementer to update): D-E is fixed by
  F_1.19.1, so PR2 writes C5b as a normal test with the post-fix assertion above
  and adds no open D-E entry.

applies exactly one branch.

## Technical Considerations

- **Pattern usage**: the fix sits in the shared function both callers route
  through (one change, all callers). Renewal stays best-effort and never changes
  the command result (the doc comment at `creator-identity.ts:59-63`).
- **Governing policy, auth domain**: minimum proof is a denial test plus a zero
  mutation and zero leak assertion (section 3). No durable-write, schema, or
  financial path changes, so `phoenix:truth` and real-database proof are not
  triggered by this change.
- **Migration freeze**: no change under `migrations/` or
  `scripts/prod-schema-manifests/`; the revocation query and table are
  unchanged.
- **Surface matrix**: pinned files stay byte-identical (Solution Architecture).
  `tests/unit/routes/fund-creation-credential-renewal.test.ts` appears in
  `audit/surface-contract-matrix/matrix.json` only as unconfirmed evidence
  (`assertion_confirmed: false`), which the matrix test does not hash-check, so
  editing it needs no matrix refresh. The implementer confirms with the matrix
  unit test. The signer is deliberately not placed in `jwt.ts`; the measured
  cost of doing so (review-basis restamp in `g1-review.json`) is recorded under
  Solution Architecture, so a proposal to move it should include a scoped
  review.
- **Session lifetime (D2)**: renewal no longer extends the session. The session
  cookie `Max-Age` is a fixed 24h (`csrf.ts:9`, applied at `:78`) and resets on
  renewal, but the token's own `exp` governs, so the cookie can outlive the
  token harmlessly. Keeping `exp` also keeps the logout revocation row's
  `expires_at` equal to the renewed token's expiry, so a future cleanup job on
  `revoked_tokens_expires_at_idx` could not resurrect a renewed token. (No
  cleanup exists today: nothing under `server/` or `scripts/` deletes
  `revoked_tokens` rows.)
- **Idempotent replays**: a replay renews again with the same presented `jti`; a
  replay made with a revoked token never reaches the handler (auth middleware
  rejects it first).
- **Admin and service roles**: `fundIds` stay `[]` (unrestricted), as today;
  they now also keep the presented `jti`.
- **Concurrent commands in one session**: several renewed tokens share one
  `jti`; the last `Set-Cookie` wins. Each carries grants read at its own
  renewal, as today; this plan does not change that ordering.
- **Security review**: two tokens with different claims now share one `jti`. The
  only `jti` consumers are revocation and the CSRF binding (`csrf.ts`,
  `server/routes/auth.ts`); nothing relies on per-token uniqueness. Reviewers
  should confirm the fail-closed branch and that the renewed token cannot
  outlive the presented one.
- **Edge cases**: presented `exp` in the past, missing, beyond the `Date` range,
  or passing during the grant lookup; `jti` missing, empty, or longer than 64
  characters; non-HS256 verifier, signing failure after a partial `Set-Cookie`
  (existing restoration), replay, admin/service, bearer without cookie, and a
  late response after logout (covered by the denial cases).
- **Out of scope**: the stale-tab replay (D4); `revoked_tokens` growth without a
  cleanup job; session sliding as a product feature.

## Backward Compatibility

- Wire contract unchanged: responses carry either `renewedAccessToken` or
  `credentialRenewal: 'reauth_required'`, as today.
- Existing sessions are unaffected until their next renewal. A renewed token
  minted before deploy keeps its own `jti`; logging out of it revokes it as
  today.
- Behavior change 1: renewal no longer extends the session (D2).
- Behavior change 2: an externally minted HS256 token without `jti` or `exp` now
  receives `reauth_required` instead of a renewed token.
- No migration, so rollback is a source revert.
