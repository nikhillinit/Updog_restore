## Problem Statement

1. The step 2 capture, phase A, and phase B cannot authenticate to Railway, and
   no admitted route can create or store a new token.
2. Every release from current `main` must first apply 0062, and the only route
   for it requires an independent approver and key custodian that a solo owner
   cannot supply. A second GitHub account that the owner controls is not
   independence.
3. The route also depends on nine unconfigured variables, one per-apply secret,
   and an environment reviewer rule, with no admitted configuration route.
4. The F_1.21.1 plan text is stale: it still describes the eighth vehicle, the
   0050-0061 schema identity, and the 2026-10-20 Dependabot list.
5. Evidence windows are short and independent: rehearsal 72 hours, restore
   reference 30 minutes, apply evidence 90 days, capture 30 days, G4 probes 120
   minutes. A sequence that ignores them restarts.

## Solution Architecture

Slices run in the order below. "Agent" means the executor drafts and verifies
locally; the owner pushes, ratifies, merges, approves, dispatches, and performs
every provider and environment action.

```
S0  this plan PR + F_1.3.7 corrections (agent drafts; owner merges)    TRIP-2
S1  read-only readings: F_1.3.7 Phase 1 + ADR-110 reconciliation (owner)
S2  Railway successor credential route: separate plan + PR (out of scope)
S3  ADR-116 amendment PR: policy, ADR, script, tests, procedure (agent; owner)
S4  Railway credential execution under the S2 route (owner)
S5  0062 window opens: environment writes, recovery evidence (owner)
S6  exact-SHA hold: rehearsal -> signed admission -> apply -> receipt (owner)
S7  0062 window closes: reviewer rule removed, readback (owner)
S8  ninth vehicle PR: F_1.21.1 edits; capture; merge freeze; steps 1-4
S9  release steps 5-8 (phase A, G4, residue exit gate, phase B)
S10 steps 9-11 and closeout; ADR-103 freeze lift
```

Why this order:

- S2 and S3 move `main`, so both merge before S6; they may be drafted in
  parallel and merge in either order.
- S4 precedes S5 so that a second Railway failure costs nothing on the schema
  side. Applying 0062 starts two clocks: its trigger on an existing table runs
  under old production code (Verified state row 19), and its receipt artifact
  expires after 90 days. The apply should therefore wait until the release can
  follow it promptly.
- S6 needs one exact SHA: the rehearsal head, the apply candidate, and live
  `main` at apply dispatch must be equal (admission script :56-71, :139-140).
  Any merge between rehearsal dispatch and apply invalidates the rehearsal. The
  S6 exact-SHA hold is therefore a separate, short no-merge window (at most 72
  hours), distinct from the ADR-107 merge freeze.
- S7 precedes S8 so that, per Q5, the release's schema audit does not pause on
  the reviewer rule, and so that the vehicle text can cite a closed window.
- S8 follows S6 because the vehicle text cites the apply identity and the
  capture binds the vehicle file's hash. After the apply, a merge breaks the
  release audit only if it touches `migrations/` or
  `scripts/prod-schema-manifests/`, which the ADR-103 freeze already forbids.
- The ADR-107 merge freeze runs from the step 2 capture through step 8. A freeze
  before the capture protects nothing; merges between S7 and the capture only
  move the vehicle's base.

Deadlines that bind the whole sequence: release step 8 must finish before the
0062 apply artifact expires (90 days after upload) and before the step 2 capture
artifact expires (30 days after upload). The 0050-0061 artifact expiry,
2026-12-28T23:01:35Z, matters only if the owner later switches to the revert
fallback (b), which needs that receipt unexpired; path (c) does not consume it.

### 4. Draft ADR text for the selected 0062 path (S3, path (c))

This is draft text for a new `DECISIONS.md` entry after ADR-115. It lands only

> **ADR-116: Solo-Operator Ratification of ADR-115 for Migration 0062**
>
> **Date:** the S3 admission date.
>
> **Status:** Proposed. Takes effect only with explicit owner ratification and
> protected-main admission of the matching policy amendment, procedure,
> admission-script change, and tests in one pull request. No production action
> is authorized by this entry.
>
> **Context.** ADR-115 (Proposed) admits a forward route for the landed 0062 SQL
> and manifest 39 under the full production schema recovery floor. It adds three
> independence requirements: approval of the apply run through
> `production-schema` by a GitHub user other than the dispatching owner
> (`assert0062IndependentApproval`), review of the recovery evidence by an
> independent reviewer, and custody of the Ed25519 signing key by that reviewer.
> This platform has one owner. No second person can serve as reviewer or
> custodian. A second GitHub account controlled by the owner would satisfy the
> code check while defeating its purpose, so it is rejected. Every release from
> current `main` must apply 0062 first: releases dispatch only on exact live
> `main`, and the release schema audit refuses any receipt but the exact 0062
> receipt once manifest 39 exists. Reverting #1708 instead would need its own
> ADR-103 rollback exception, would break the 0062 runner tests that #1710
> added, would need caller analysis for the shared logging, RLS, idempotency,
> and retention code #1708 touched, and would create two source transitions.
>
> **Decision.**
>
> 1. Ratify ADR-115 with only the substitutions in items 2 to 4. All other
>    ADR-115 text and the policy's 0062 section stand.
> 2. Approval. The apply run requires an explicit `approved` environment review
>    for `production-schema`, recorded on that exact run by the repository
>    owner's account ID; the dispatching actor must also be the owner
>    (unchanged). This is a deliberate pause-and-confirm checkpoint that holds
>    the run while the owner binds the admission to its run ID. It is not
>    independent approval. Any other reviewer, state, or environment, or an
>    absent record, refuses.
> 3. Review and key custody. The owner performs the recovery-evidence review
>    that ADR-115 assigns to an independent reviewer, and holds the Ed25519
>    signing key outside the repository, GitHub, and any CI-reachable store. On
>    the owner's explicit instruction for one named apply run, one delegated
>    local executor may run the signing step. The owner remains the sole
>    authority issuer; the executor may not create, rotate, export, or copy the
>    key, and its instruction covers no other run. The signature binds the
>    repository, candidate, apply run, target fingerprint, production and
>    restore targets, recovery-evidence digests, and rehearsal artifact. It does
>    not attest independence. Named custody roles remain required; each may name
>    the owner.
> 4. Named configuration writes, for this route only, each performed by the
>    owner and each followed by a readback:
>    - (a) At each window open: set `production-schema` protection to the owner
>      as the only required reviewer, self-review allowed, the existing
>      protected-branch deployment policy unchanged, and administrator bypass
>      disabled.
>    - (b) At each window close, after the apply's terminal outcome or on
>      abandonment: restore `production-schema` to the protection observed
>      before (a). A later window repeats (a) and (b) as a new pair; it reuses
>      the existing key and variables after a readback shows them unchanged.
>    - (c) Create-only `production-schema` environment variables:
>      `SCHEMA_0062_RECOVERY_PUBLIC_KEY`, `SCHEMA_0062_REHEARSAL_PROJECT_ID`,
>      `SCHEMA_0062_REHEARSAL_PARENT_BRANCH_ID`,
>      `SCHEMA_0062_REHEARSAL_DATABASE_NAME`,
>      `ACTUALS_PREFLIGHT_NEON_PROJECT_ID`, `ACTUALS_PREFLIGHT_NEON_BRANCH_ID`,
>      `ACTUALS_PREFLIGHT_NEON_ENDPOINT_ID`, `PRODUCTION_DATABASE_NAME`, and
>      `ACTUALS_PREFLIGHT_DATABASE_ROLE`. A write stops when the name already
>      exists at environment or repository scope; changing an existing value
>      needs its own decision.
>    - (d) One write of the `SCHEMA_0062_ADMISSION` secret per apply run, while
>      that run waits for approval.
>
>    GitHub's environment and secret APIs establish no conditional-update
>    contract, as ADR-110 found for one secret write. For writes (a), (b), and
>    (d) only, the owner's explicit acceptance of the concurrent-writer
>    overwrite risk replaces the optimistic-locking mandate. A readback that
>    does not show the intended state stops the window. Writes (c) refuse on
>    existence instead. Nothing here extends to any other environment, secret,
>    variable, or provider write.
>
> 5. Unchanged: managed backup/PITR; an isolated restore at most 72 hours old
>    with named custody and preview/restore isolation; an exact-SHA, attempt-1,
>    same-actor isolated rehearsal completed at most 72 hours earlier, in a Neon
>    project distinct from production; a production-parented restore reference
>    and an admission review each at most 30 minutes old; live protected source,
>    provider target, and restore reference revalidated under the reconcile lock
>    before DDL; one execution from the wholly absent state or a zero-write
>    result from the exact complete state; refusal of partial, inconsistent,
>    unknown, or newer states; no rerun. An ADR-103-style owner confirmation
>    alone still does not satisfy these checks.
> 6. The approval check and its refusal texts are renamed so that no surface
>    claims independence.
>
> **Consequences.** One person can dispatch, approve, sign or instruct signing,
> and apply. A compromised owner account, or an agent session that holds the key
> while signing, could complete the route. Exact-SHA binding, run-bound
> signatures, the 30-minute and 72-hour windows, the window-only reviewer rule,
> readbacks, and refusal on ambiguity limit such a compromise to the pinned 0062
> bytes, on the fingerprinted target, once. Delegated signing is weaker evidence
> of personal review than owner signing. Outside the window `production-schema`
> has no reviewer rule, so an `apply-journaled-0062` dispatch then refuses for
> lack of an approval record. Revisit when a second person gains production
> access (governing policy, "Revisit").

## Technical Considerations

- **Pattern usage**: docs-only plan and vehicle pull requests, as in F_1.3.6 and
  F_1.3.7; governance amendments as one pull request carrying the policy
  section, ADR, procedure, executable route, and pinned tests, as for ADR-110,
  ADR-112, and ADR-115.
- **Optimistic locking**: retained everywhere except the ADR-116 writes (a),
  (b), and (d), each with explicit owner acceptance and readback. Writes (c) are
  create-only.
- **Idempotency**: every apply and rehearsal is attempt 1 only; a second apply
  from the exact complete state is a zero-write result; unknown outcomes stop
  for reconciliation; nothing retries automatically.
- **Approval mechanics**: the approval pause is what lets the envelope name the
  live run ID before the job reads `SCHEMA_0062_ADMISSION`. Environment secrets
  reach a job only when it starts, so the envelope must be written while the run
  waits.
- **Window-only reviewer rule (Q5)**: outside the window, `production-schema`
  holds only its branch policy, and the release schema audit runs without a
  pause. Whether an administrator bypass would create an `approved` record is
  UNVERIFIED; write (a) disables bypass for the window so the question does not
  arise.
- **Protection write shape**: a GitHub environment update may replace fields it
  does not carry (UNVERIFIED). Writes (a) and (b) must carry the existing
  protected-branch deployment policy, and their readbacks must show it.
- **Exact-SHA hold vs merge freeze**: two distinct windows. The hold binds
  rehearsal and apply to one SHA (at most 72 hours). The ADR-107 freeze binds
  the capture to the release (capture through step 8).
- **Public repository**: variable values, provider identifiers, the public key
  fingerprint, and envelope contents stay out of tracked text.
- **Right-sizing candidates (not proposed here)**: releases tied to moving
  `main`, expiring evidence artifacts, and recovery steps without a successor
  path are the friction points this lineage keeps hitting. Any later
  proportionality ADR should target them and must not weaken credential,
  recovery, or financial-correctness boundaries.
- **Edge cases**: S1 finds a token from the 2026-11-02 attempt (S2 decides its
  disposition); access anomaly (stop); a merge during the hold (restart S6 with
  a new rehearsal); a 30-minute or 72-hour bound lapses before approval (reject
  the run, close the window, restart per item 8 step 8); apply unknown outcome

  start S8; re-plan); a new advisory on the vehicle merge commit (stop; the fix
  lands before a tenth vehicle); a merge during the freeze (restart at a new
