## Overview

Production release canary now creates a fund through `POST /api/funds`, saves
the draft through `PUT /api/funds/:id/draft`, and publishes through
`POST /api/funds/finalize` before continuing through portfolio, scenario, and
reporting canaries (`tests/smoke/release-canaries.spec.ts:588`,
`tests/smoke/release-canaries.spec.ts:713`,
`tests/smoke/release-canaries.spec.ts:970`,
`tests/smoke/release-canaries.spec.ts:1073`). Release production runs that suite
without whole-suite retries (`.github/workflows/release-production.yml:958`,
`.github/workflows/release-production.yml:988`).

The historical service characterization is intentionally frozen at 40 total,
four fund events, and two mutation receipts
(`server/services/canary-residue-service.ts:10`,
`shared/contracts/release-canary-residue-characterization-v1.contract.ts:46`).
The existing real-HTTP fund lifecycle proves create/save/finalize, replay
zero-growth, and three workflow receipts
(`tests/integration/fund-lifecycle-db.test.ts:512`,
`tests/integration/fund-lifecycle-db.test.ts:590`). **UNVERIFIED until
implementation:** its strengthened sidecar will record the complete observed
ten-group fund-phase residue vector, the run identity read back from
`release_canary_runs`, and zero-growth results. It will not claim that the HTTP
test itself observed the 44/5/5 final vector or assert its own delta.
Release-proof composition must derive the delta by subtracting the service
artifact's `publish` phase from that observed vector, require exactly +1/+3/+4
with zero in every other group, and derive 44/5/5 by adding that validated delta
to the parsed service artifact's 40/4/2 `finalResidue`. Current evidence
builders still construct the frozen v1 vector, so a clean HTTP run can pass
runtime cap accounting but fail evidence construction
(`shared/contracts/release-evidence-fragment-v1.contract.ts:281`,
`shared/contracts/release-evidence-fragment-v1.contract.ts:311`).

Fix: preserve the v1 characterization source byte-for-byte, add one strict
HTTP-v2 contract and reservation identity, make current evidence contracts
HTTP-v2-only, and bind the existing service characterization to a conditional
result from the strengthened HTTP fund proof in release proof. The existing
manifest builder must project and compare the new identity, bound vectors, and
characterization provenance; otherwise the strict manifest cannot be built
(`scripts/release/build-release-evidence-manifest.ts:473`,
`scripts/release/build-release-evidence-manifest.ts:621`,
`scripts/release/build-release-evidence-manifest.ts:637`). No new service,
framework, schema, dependency, or standalone composition script.

## Problem Statement

1. **Runtime reservation and measured evidence disagree.** HTTP creation selects
   a private 44/5/5 reservation through the existing command path
   (`server/services/canary-residue-service.ts:384`,
   `server/services/canary-residue-service.ts:398`), but exact-run assertion
   imports only the v1 reservation
   (`scripts/release/assert-canary-residue.mjs:575`,
   `scripts/release/assert-canary-residue.mjs:782`). The emitted result then
   copies its residue into policy-measurement and canary-result fragments
   (`.github/workflows/release-production.yml:1063`,
   `.github/workflows/release-production.yml:1087`,
   `.github/workflows/release-production.yml:1130`).

2. **Current evidence contracts hard-code v1.** Policy config requires v1 plus
   exactly 3x v1 caps, policy measurement requires v1, and the manifest repeats
   both assumptions
   (`shared/contracts/release-evidence-fragment-v1.contract.ts:281`,
   `shared/contracts/release-evidence-fragment-v1.contract.ts:311`,
   `shared/contracts/release-evidence-manifest-v1.contract.ts:487`,
   `shared/contracts/release-evidence-manifest-v1.contract.ts:648`). Proof
   certification and manifest validation also require a v1 characterization
   artifact name
   (`shared/contracts/release-proof-certification-v1.contract.ts:74`,
   `shared/contracts/release-evidence-manifest-v1.contract.ts:511`). Current
   contracts must switch to one strict HTTP-v2 shape; the untouched v1
   characterization parser remains the historical validator only.

3. **Existing characterization and HTTP proof are not bound together.** The
   current integration test already covers publish, portfolio, scenario, and
   reporting through service calls
   (`tests/integration/release-canary-residue-characterization.test.ts:293`,
   `tests/integration/release-canary-residue-characterization.test.ts:483`,
   `tests/integration/release-canary-residue-characterization.test.ts:589`,
   `tests/integration/release-canary-residue-characterization.test.ts:656`) and
   writes a strict v1 artifact only after matching 40 rows
   (`tests/integration/release-canary-residue-characterization.test.ts:839`,
   `tests/integration/release-canary-residue-characterization.test.ts:1187`). A
   separate real-HTTP fund test proves create/save/finalize, replay zero-growth,
   and three workflow receipts, but its fund-event and delta assertions are
   incomplete (`tests/integration/fund-lifecycle-db.test.ts:512`,
   `tests/integration/fund-lifecycle-db.test.ts:590`). Extend that test and bind
   its small delta proof to the existing characterization; do not duplicate
   downstream portfolio, scenario, or reporting phases.

4. **Configured caps encode the old retained-run budget.** The policy fragment
   reads repository variables and builds `reservedPerRun` from v1
   (`.github/workflows/release-production.yml:255`,
   `.github/workflows/release-production.yml:290`). Three complete HTTP v2 runs
   require component-wise caps `3/3/3/15/0/3/36/15/21/33`, total `132`, from the
   per-run vector `1/1/1/5/0/1/12/5/7/11`, total `44`. Only owner values
   `12 -> 15`, `6 -> 15`, and `120 -> 132` change; retaining the old values no
   longer represents the declared retained-run budget of three
   (`shared/contracts/release-evidence-fragment-v1.contract.ts:285`,
   `shared/contracts/release-evidence-fragment-v1.contract.ts:297`).

## Solution Architecture

Use one explicit new identity: `release-canary-http-workflow-v2`.

- Leave
  `shared/contracts/release-canary-residue-characterization-v1.contract.ts`
  byte-for-byte unchanged. Its exported 40/4/2 vector and parser remain the
  historical validator
  (`shared/contracts/release-canary-residue-characterization-v1.contract.ts:46`,
  `shared/contracts/release-canary-residue-characterization-v1.contract.ts:258`).
- Add `shared/contracts/release-canary-residue-characterization-v2.contract.ts`.
  It owns the identity literal, the strict 44/5/5 vector, and the strict v2
  artifact schema/parser. The same file owns the small strict
  `release-canary-http-fund-proof-v2` result schema/parser used by the existing
  HTTP test plus one pure `composeReleaseCanaryResidueCharacterizationV2`
  function. The function accepts already-parsed service/HTTP results and the
  expected candidate/workflow identity, performs vector addition, phase
  construction, canonical payload hashing, and binding generation, then returns
  the strict parsed v2 artifact. It performs no environment, filesystem,
  network, or clock access. The module accepts only the HTTP-v2 identity; it
  does not select, parse, or characterize v1 artifacts. Do not extract or
  rewrite v1 internals merely to deduplicate schema code.
- Keep the existing `options.command` runtime seam; it already distinguishes
  HTTP command creation from service-only creation
  (`server/services/fund-persistence-service.ts:289`,
  `server/services/fund-persistence-service.ts:324`). Replace only the private
  derived object with the exported v2 vector. No route signature or persistence
  change.
- Require `--reservation-identity release-canary-http-workflow-v2` on the
  current exact-run assertion. The script selects only the v2 vector and emits
  the identity; omission and unknown identities fail closed. `--global-only`
  continues to reject per-run selectors.
- Make current evidence envelopes HTTP-v2-only. New payloads require
  `reservationIdentity`; there is no identity-free branch and no v1/v2 union.
  Never infer a version from counts, artifact name, or total.
- Release proof emits a v2 characterization artifact named
  `release-canary-residue-characterization-v2-<runId>-<runAttempt>-<sourceSha>`.
  The existing HTTP test conditionally writes a second runner-temp result when
  `RELEASE_CANARY_HTTP_RESULT_PATH`, `RELEASE_CANARY_HTTP_SOURCE_SHA`,
  `RELEASE_CANARY_HTTP_WORKFLOW_RUN_ID`, and
  `RELEASE_CANARY_HTTP_WORKFLOW_RUN_ATTEMPT` are all supplied. The test sends
  the existing `Release-Canary-Workflow-Run-Id` and
  `Release-Canary-Workflow-Run-Attempt` headers on canary creation
  (`server/routes/funds.ts:251`) and seeds `COMMIT_REF` with the candidate SHA
  after clearing `VERCEL_GIT_COMMIT_SHA` and `RAILWAY_GIT_COMMIT_SHA`, which
  take precedence over it (`server/version.ts:47-51`); the run row stores the
  resulting commit as `release_sha`
  (`server/services/fund-persistence-service.ts:143-147`). Without the headers
  the row's workflow run/attempt stay null outside production
  (`server/services/fund-persistence-service.ts:157`). Before writing, the test
  reads `release_sha`, `workflow_run_id`, and `workflow_run_attempt` back from
  `release_canary_runs` and fails closed on null or mismatch against the four
  inputs. Its strict result contains that persisted workflow run/attempt and
  source SHA, database canary run ID, reservation identity, the complete
  observed ten-group residue vector at the fund-phase boundary (after finalize,
  from the full counts `transitionReleaseCanaryRun` returns), and true
  replay/over-cap zero-growth checks. It contains no delta, service baseline,
  composed final vector, or phases. Missing result configuration writes nothing,
  matching the existing conditional atomic characterization-record pattern
  (`tests/integration/release-canary-residue-characterization.test.ts:226`).
- The exported pure composition function requires both result source SHAs to
  equal the expected candidate SHA, requires the HTTP workflow run/attempt to
  equal the expected job context, requires the parsed service artifact
  `finalResidue` to equal the frozen 40/4/2 vector, derives the delta
  component-wise as `http.observedFundPhaseResidue` minus the parsed service
  artifact's `publish` phase residue (captured at
  `tests/integration/release-canary-residue-characterization.test.ts:516`),
  rejects unless that delta is exactly fund-event +1, mutation-receipt +3, total
  +4 with zero in every other group, and computes the composed final vector
  component-wise as `service.finalResidue + delta`. The computed result must
  equal reserved 44/5/5; it is never read from the HTTP sidecar. The v2 `phases`
  array copies the parsed service artifact's chronological phases unchanged and
  appends exactly one terminal `http-command-delta` phase whose residue is the
  computed 44/5/5 vector. That phase is an aggregate composition boundary, not a
  reconstruction of chronological HTTP operations; the sidecar emits no phases.
  The function computes SHA-256 over canonical JSON for each parsed result and
  for the ordered binding tuple. That tuple includes candidate SHA, workflow
  run/attempt, reservation identity, both payload hashes, service final residue,
  derived delta, and computed final vector. The emitted v2 provenance records
  `serviceCharacterizationPayloadSha256`, `httpFundProofPayloadSha256`, and
  `bindingSha256`; no timestamp or filesystem path enters a digest. Reuse the
  repository canonical-JSON hashing pattern
  (`shared/contracts/release-evidence-fragment-v1.contract.ts:426`) in the v2
  module. The workflow's existing temporary TypeScript validation step only
  reads and parses both files, calls this function, and atomically writes its
  result. Proof certification and current manifest validation accept only that
  v2 artifact and require identity, bound-vector, and provenance-hash agreement.
- Aggregate policy remains version-neutral row accounting across every unpurged
  SHA (`scripts/release/assert-canary-residue.mjs:7`). Current release policy
  changes to component-wise 3x HTTP v2: 3 portfolio companies, 3 funds, 3 fund
  configs, 15 fund events, 0 notifications, 3 grants, 36 calculation rows, 15
  mutation receipts, 21 scenario rows, 33 reporting rows, total 132.
- Recovery remains aggregate-only. It uses the configured caps and
  `--global-only`, so it must not select or reinterpret a per-run reservation
  (`.github/workflows/release-canary-recovery.yml:147`,
  `.github/workflows/release-canary-recovery.yml:180`).
- Historical immutable manifest consumption is not a cross-version current
  consumer: Current Forecast checks out and re-fences the manifest's exact SHA
  before parsing it
  (`.github/workflows/current-forecast-production-action.yml:37`,
  `scripts/release/current-forecast-production-action.mjs:424`).
