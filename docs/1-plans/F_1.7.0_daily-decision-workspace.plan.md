## Overview

Two independent PRs building daily-use decision workflows on existing
primitives. **S1** adds a source-pinned Base/Upside/Downside allocation scenario
workflow over the existing scenario-set create/calculate/compare/ archive
machinery, with server-enforced pinning. **C1A** persists one deterministic
current-plan/current-facts deployable-capital reconciliation to `fund_snapshots`
and extends the existing "Deployable Capital vs Plan" card. Neither PR depends
on the other **as a product**; they are NOT merge-conflict-independent — both
touch `server/route-policy/api-route-policy-registry.ts`, the generated
surface-contract-matrix artifacts, `docs/ARCHI.md`, and `CHANGELOG.md`.
Sequencing rule: merge one PR, rebase the second, regenerate the matrix
artifacts from the rebased head, re-run the route/matrix gates; never merge
independently generated matrix snapshots from different bases. C1A always
persists `scenarioSetId: null`. No new dependencies or migrations (both use
existing tables).

## Problem Statement

- Scenario sets already record the server-selected published source config
  (create selects the fund's current published row and stores
  `sourceConfigId`/`sourceConfigVersion` —
  `fund-scenario-set-create-service.ts:167-189`, `fund.ts:265-268`). What is
  missing: the client cannot assert the expected source ID/version (so
  publication drift between read and create is undetectable), nothing enforces
  variant-row congruence with that source, and nothing gives users a one-step
  Base/Upside/Downside template.
- The "Deployable Capital vs Plan" card is client-side derived arithmetic
  (`client/src/lib/variance-remaining-capital.ts` — clamped
  committed-minus-deployed from `unifiedMetrics`), not a persisted, reproducible
  reconciliation pinned to a plan version and facts snapshot.

## Solution Architecture

- **S1**: a narrowed source-config read endpoint plus a V2 create contract
  carrying an expected config ID/version pair. The server — not the UI — is the
  pinning authority: it rejects stale pins (409) and variant row-identity drift
  (422) before any write. UI adds one modal that always submits V2.
- **C1A**: one POST-compute-and-persist + one GET-latest route pair. The
  persisted payload is a `CalcResult` envelope (existing calc-substrate
  vocabulary: `basis`, `value`, `reasonCodes`, `resultHash`); the API response
  wraps it in the presentation vocabulary (`structuredWarnings`,
  `DatasetTrustState`) via the existing ADR-042 bridge — the two vocabularies
  stay separate, never merged into one schema. Idempotent, advisory-locked,
  application-serialized writes into `fund_snapshots` with a new non-timeline
  snapshot type.
- **Route registration (per PR, correctly scoped)**: the manifest/mount chain
  registers router _modules_, not endpoints. S1's new endpoint lives inside the
  already-registered `fund-scenario-sets` module — S1 adds **no**
  manifest/impl/group entry, only a
  `server/route-policy/api-route-policy-registry.ts` entry and a matrix row. C1A
  adds a new router module: **one** manifest entry
  (`shared/routes/api-route-manifest.ts`) + impl-map entry
  (`server/routes/mount-common-routes.ts`) + group-slice inclusion on **both**
  surfaces, plus **two** policy entries and two matrix rows (one per endpoint).

### 1. Source-config read endpoint

**File**: `server/routes/fund-scenario-sets.ts` (modify) + registration chain

```http
GET /api/funds/:fundId/scenario-sets/source-config
```

Register `source-config` **before** the existing `/:scenarioSetId` handler in
the router (Express would otherwise route the literal string through UUID

Returns only: `contractVersion: 'fund-scenario-source-config/1.0.0'`,
`sourceConfigId`, `sourceConfigVersion`, `publishedAt`, `allocations`,
`capitalPlanAllocations` (both nullable, shapes from `FundDraftWriteV1`). Never
the full `FundDraftWriteV1`. Source of truth: the fund-owned current published
row in `fundconfigs` (table name has no underscore —
`shared/schema/fund.ts:92-111`; `version`, `isPublished`, `publishedAt` columns;
unique on `(fundId, version)`). The ID/version pinning pattern already exists in
`fund_scenario_sets` (`fund.ts:265-268`) and `current_plan_versions`
(`current-plans.ts:32-33`) — follow it.

### 2. V2 create contract with server-enforced pinning

**File**: `shared/contracts/fund-scenario-sets-v1.contract.ts` (modify)

Preserve `CreateFundScenarioSetV1Schema` unchanged. Add a V2 request derived
from the same base fields plus
`contractVersion: 'fund-scenario-set-create/2.0.0'`, `expectedSourceConfigId`,
`expectedSourceConfigVersion`. V2 requires **exactly three variants in fixed
order**: index 0 = Base, index 1 = Upside, index 2 = Downside — roles are
positional and immutable; display names are decorative and freely editable.
Every V2 variant MUST carry exactly one override with
`overrideType: 'allocation'` — the existing variant override contract is a
five-type discriminated union (`fund-scenario-sets-v1.contract.ts:117-123`), and
without this rule a non-allocation V2 request would pass the row checks
vacuously (no pinned arrays present to compare). Any other override type, extra
overrides, or a missing allocation override → 422, zero writes. (V1 variants
carry no role field, so position is the only server-identifiable role signal; no
new field is added.) The create route accepts legacy V1 or pinned V2; response
remains `FundScenarioSetDetailV1`.

Service order (inside the existing transaction):

1. Validate request; resolve idempotency request/hash and return a matching
   replay immediately — **before** publication-state validation (the existing
   replay-first order at `fund-scenario-set-create-service.ts:88-95` is
   preserved). Hashing stays the existing
   `sha256(JSON.stringify({fundId, input}))` (`:148-150`) — no canonical-hash
   migration, no change to V1 semantics. V1↔V2 key collision: V2 adds
   contract/pin fields, so a key first consumed by V1 and replayed with a V2
   payload (or vice versa) necessarily hashes differently and returns the
   existing 422 `idempotency_key_reused` (`:152-165`); a matching V2 replay
   returns the originally persisted set.
2. Load the current fund-owned published config.
3. V2: require its ID/version to equal the expected pair; on mismatch return
   `409 scenario_source_config_stale` with supplied/current IDs, writing no rows
   or events.
4. **Server-side pinning enforcement** (the UI is not the authority), with an
   executable row-identity definition. Identity is the typed tuple
   `{arrayKind, id}` where `arrayKind` ∈
   `{'allocation', 'capital-plan-allocation'}` — never bare `id`: the draft
   contract enforces id uniqueness per array independently
   (`fund-draft-write-v1.contract.ts:186-193,226-237`), so an `allocations` row
   and a `capitalPlanAllocations` row may legally share an id. Rules, each
   checked per array kind independently:
   - **Array-kind presence** must match the pinned config: a pinned null/absent
     array must be absent on every variant; a pinned present (possibly empty)
     array must be present.
   - **Every variant** (all three indices): each present array must have the
     pinned array's length and the same id sequence in the same order
     (order-sensitive check — covers set equality and duplicates in one pass).
     Rows cannot be added, deleted, reordered, or remapped.
   - **Frozen non-numeric fields on indices 1-2**: `id`, `sectorProfileId` (a
     foreign reference, `fund-draft-write-v1.contract.ts:160`), and the
     calculation-control fields `entryRound`, `initialCheckStrategy`, and
     `followOnStrategy` (they switch plan-derivation branches —
     `derive-current-plan-v1.ts:89,164`) must equal the pinned row's values;
     display/name fields are decorative and freely editable; numeric fields are
     free.
   - **Base (index 0)**: arrays must equal the pinned arrays exactly — deep
     structural equality of the Zod-parsed values, order-sensitive. Wrong
     variant count or any drift → 422 refusal, zero writes. (No "wrong order"
     refusal exists for _variant roles_ — position defines role.) One server
     helper performs all V2 comparisons and is exercised directly by contract
     and service tests.
5. Insert using that exact config; return the existing detail response.

### 3. UI modal

**Files**: `client/src/components/` scenario area alongside the existing
methodology modal (name final files in TRIP-2 against the actual component
tree); existing scenario hooks.

- Always submits V2; creates exactly three variants: Base, Upside, Downside.
- Base copies the pinned arrays; Upside/Downside begin as clones; names and
  existing numeric fields editable; rows cannot be added, deleted, or mapped to
  newer IDs.
- If neither allocation array exists: unavailable state, create disabled.
- No revise/prefill/lineage-reconciliation workflow — users create a new
  distinctly named set and archive the old one with the existing archive flow.
- Existing methodology modal payload stays byte/shape compatible when V2 fields
  are absent.

## Implementation Details — C1A (PR 2)

### 1. Contract

**File**: new contract under `shared/contracts/` (construction-reconciliation)

Request (strict): `contractVersion: 'construction-reconciliation/1.0.0'`,
`fundId` (must equal route param), `currentPlanVersionId`, and optional
`financialFactsSnapshotId` — when absent the server resolves the fund's current
non-superseded facts head inside the locked transaction (the current-forecast
runs route precedent; a client-pinned id goes stale whenever facts advance, so
the UI always omits it). No `asOfDate`, clocks, scenario IDs, free-form
assumptions, or caller hashes.

Persisted value (inside a `CalcResult` built with `createCalcResultSchema`): the
plan/actual/comparison money fields from the superseded proposal (deployable,
planned initial/follow-on/total, planned-over-deployable, actual
initial/follow-on/total-equity, excluded non-equity, remaining deployable,
planned remaining, signed remaining gap), `asOfDate` derived from the facts
snapshot, `currency: 'USD'`.

**CalcBasis is fully specified** — every `CalcBasisSchema` field
(`shared/core/calc-substrate/calc-basis.ts:30-58`, strict object):

- `contractVersion: 'calc-substrate/1.0.0'` (schema literal)
- `calculationKey: 'construction-reconciliation'`
- `configuredMode: 'on'`, `effectiveMode: 'on'`, `killSwitchActive: false` —
  constants: this calculation has no shadow/off rollout or kill switch; the
  schema's mode-rank and kill-switch invariants hold trivially
- `engineVersion: 'construction-rec-v1'` (also stored as the
  `fund_snapshots.calcVersion` column value — `calcVersion` is a snapshot
  column, not a basis field)
- `methodologyVersion: 'construction-reconciliation/1.0.0'` (the contract
  version)
- `inputHash`: canonical-JSON SHA-256 of
  `{fundId, currentPlanVersionId, financialFactsSnapshotId, snapshotInputHash (financial_facts_snapshots.snapshotInputHash)}`
- `assumptionsHash`: `current_plan_versions.assumptionsHash` of the pinned plan
  head (already a sha256 hex digest)

Persisted anchors only, no clock input, so `resultHash` (computed over the
basis-inclusive preimage per `hash-admission.ts`) is deterministic.

API response = presentation envelope: the CalcResult value plus
`structuredWarnings` (`NON_EQUITY_AMOUNT_ONLY` passes through from the facts
contract, which already emits it as a `StructuredWarning`) and a
`DatasetTrustState` derived via the existing `toDatasetTrustState` bridge.
`reasonCodes` (calc side) and `structuredWarnings` (provenance side) are never
merged into one schema (ADR-042 separation).

Formulas (Decimal; clamps intentional):

```text
plannedTotal = Σ(initialCapitalUsd + followOnCapitalUsd)
plannedCapitalOverDeployable = max(plannedTotal - deployableCapitalUsd, 0)
actualEquity = Σ(facts.initialInvestmentAmount + facts.followOnInvestmentAmount)
remainingDeployable = max(deployableCapitalUsd - actualEquity, 0)
plannedRemaining = max(plannedTotal - actualEquity, 0)
remainingDeployableGap = remainingDeployable - plannedRemaining
```

Exclude `amountOnlyNonEquityAmount` from actual equity totals.

**State reducer (exact, first matching rule wins).** Inputs: the current facts
snapshot's `facts[]` per `fund-company-actuals-fact.contract.ts` — specifically
`facts[*].provenance.trustState` (`provenance-envelope.contract.ts:5,59-61`:
LIVE/PARTIAL/UNAVAILABLE/FAILED) and `facts[*].currencyStatus`
(`base_currency | mismatch_blocked | unknown`). `planningFmvStatus` is
explicitly **not** an input: C1A consumes investment amounts only, never
planning FMV fields. Every reason code below is from the existing closed
registry (`shared/core/calc-substrate/reason-codes.ts:11-24`) — no registry
edit:

1. empty `facts[]` → `unavailable`, `reasonCodes: [INPUT_MISSING]`
2. any `trustState` ∈ {`UNAVAILABLE`, `FAILED`} → `unavailable`,
   `[UPSTREAM_UNAVAILABLE]`
3. any `currencyStatus` ∈ {`mismatch_blocked`, `unknown`} → `unavailable`,
   `[INPUT_INVALID]`
4. any `trustState` = `PARTIAL` → `indicative`, `[STALE_SOURCE]` (documented
   mapping: partially-trusted upstream facts)
5. else (all `LIVE`, all `base_currency`) → `available`, `reasonCodes: []`
6. unexpected error anywhere → `failed`, `[ENGINE_ERROR]`

`createCalcResultSchema` requires a nonempty reason-code set for every
non-available result (`calc-result.ts:29-31,50,58,66`) — the reducer satisfies
it by construction. `NON_EQUITY_AMOUNT_ONLY` passes through as a
`StructuredWarning` only and MUST never be inserted into `reasonCodes` (ADR-042
separation).

Persistence: `available`/`indicative` results persist; `unavailable`/`failed`
are **transient POST responses with zero persistence** (see GET-latest contract
below for how the UI observes them).

### 2. Routes and persistence

Expose only (full registration chain + matrix rows for both):

```http
POST /api/funds/:fundId/construction-reconciliation/runs
GET  /api/funds/:fundId/construction-reconciliation/latest
```

POST: auth + fund access + team-write role + `Idempotency-Key`. GET: auth +
fund-scoped, never computes. No list/update/delete/by-ID routes.

**GET-latest contract (deterministic).** Existing snapshot readers disagree on
"latest" (`snapshotTime DESC` in `time-travel-analytics.ts:174`,
`createdAt DESC` in `variance-tracking/calculation-service.ts:580,593`,
composite in `baseline-service.ts:583`), so C1A defines its own exactly: filter
`fundId` + `type = 'CONSTRUCTION_RECONCILIATION'` + `scenarioSetId IS NULL`;
order `snapshotTime DESC, createdAt DESC, id DESC`, limit 1. "Latest" means the
most recently written persisted reconciliation — never "latest attempt"
(failed/unavailable attempts are not persisted). No rows → 200 with an explicit
`no_persisted_reconciliation` state (not 404, not an empty 500). Stored-payload
contract-parse or recomputed-hash failure → structured 5xx fail-closed response
with telemetry; never silently fall back to an older row. GET serves only
persisted `available`/`indicative` snapshots or the explicit none-state;
`unavailable`/`failed` are observable only as the POST response that produced
them.

Execution order (replay check precedes everything mutable-state-dependent —
`runIdempotentCommand` inserts before loading existing state, and a valid replay
must not fail just because sources advanced after the original write):

1. **Before** the transaction/lock/source reads:
   `replayIdempotentCommandIfPresent` (`server/lib/idempotent-command.ts:70`) —
   a matching key + request hash returns the stored response immediately; a
   matching key with a different request hash is a key-reuse conflict.
2. Within one transaction: advisory lock derived via
   `generateLockKey('construction-reconciliation', String(fundId))`
   (`server/lib/locks.ts:25` — SHA-256 of the joined string clamped to a signed
   64-bit key), acquired with `pg_advisory_xact_lock($key::bigint)` **on the
   same transaction-bound client** that performs the source reads, post-lock
   replay re-check, computation, and insert — a transaction-scoped advisory lock
   is useless on any other client. This follows the purpose-namespace precedent
   of the helper's sole production caller
   (`planning-fmv-override-service.ts:145`). Purpose-scoped by design: C1A needs
   same-fund C1A writers serialized; there is no repo-wide fund-lock namespace
   to join (`withFundLock` has zero production callers; existing advisory locks
   are purpose-scoped string keys).
3. **Immediately after acquiring the lock, repeat the key replay check** —
   before any source validation or computation: `runIdempotentCommand` inserts
   before `loadExisting` and `fund_snapshots` has no key uniqueness constraint,
   so two callers that both miss the pre-transaction check and serialize on the
   lock would otherwise insert duplicate same-key rows. The post-lock re-check
   is the race guard. The caller-supplied `loadExisting`
   (`idempotent-command.ts:21`) is defined exactly: select from `fund_snapshots`
   where `fundId` matches, `type = 'CONSTRUCTION_RECONCILIATION'`,
   `scenarioSetId IS NULL`, and `metadata->>'idempotencyKey'` equals the
   supplied key; then validate metadata shape, the stored `requestHash`, a
   contract-parse of the stored payload, and the stored result hash before
   replaying — any mismatch fails closed per `idempotent-command.ts` semantics.
   This is an unindexed JSONB filter — accepted at ~5-user scale; no migration
   or index.
4. Reload and verify fund ownership.
5. Require the requested plan to be the current non-superseded head (partial
   unique index `current_plan_versions_fund_head_unique`).
6. Require the facts snapshot to be current and non-superseded.
7. Derive `asOfDate` from the facts snapshot; compute `CalcBasis`, value,
   `resultHash`; `runIdempotentCommand` performs the insert.
8. **One snapshot per distinct idempotency key.** No cross-key row reuse: a
   different key with identical economic input inserts its own row carrying the
   same `stateHash` value (the key→snapshot binding lives in
   `metadata.idempotencyKey`, which can only record one key — reusing a row
   across keys would orphan the second key's replay binding).

`fund_snapshots` mapping (`shared/schema/fund.ts:175`):
`type = CONSTRUCTION_RECONCILIATION`, `calcVersion = construction-rec-v1`,
`scenarioSetId = null`, `payload =` canonical CalcResult,
`stateHash = resultHash`,
`metadata = {idempotencyKey, requestHash, currentPlanVersionId, financialFactsSnapshotId, requestedFactsSnapshotId, asOfDate, structuredWarnings}`
(`requestedFactsSnapshotId` is null when the server resolved the facts head —
the stored `requestHash` preimage is the request exactly as supplied;
`structuredWarnings` are the compute-time provenance warnings, strict-validated
on read so replays and GET-latest keep serving the original disclosures), **plus
the non-null columns the superseded proposal omitted**: `correlationId` (request
correlation ID per existing snapshot writers) and `snapshotTime` (write-time
timestamp; record-keeping only, never a hash input). Add
`CONSTRUCTION_RECONCILIATION` to `NON_TIMELINE_SNAPSHOT_TYPES` (`fund.ts:169`)
so time-travel readers (`fund-state-read-service.ts`,
`time-travel-analytics.ts`) exclude it.

This is application-serialized idempotency, not a database uniqueness claim.
Integrity comes from validation, not from JSONB: the writer validates the exact
versioned CalcResult before insertion; readers parse the stored payload under
that contract and recompute the canonical `resultHash`, failing closed on any
schema or hash mismatch. Coverage is stated precisely: the recomputed
`resultHash` covers the basis and value only (the preimage excludes
state/reasonCodes — `hash-admission.ts:10-17`); `state` and `reasonCodes` are
guarded by the strict contract parse, not by the hash. No additional
full-envelope hash is introduced. JSONB key-order normalization is a storage
behavior (textual bytes are not preserved), never itself an integrity guarantee.

**Source-of-truth rule**: `current_plan_versions.deployableCapitalUsd` remains
the plan-side authority; a C1A snapshot is a derived reconciliation pinned to
`currentPlanVersionId` + `financialFactsSnapshotId`. The UI labels it with both
IDs and `asOfDate`; it never overwrites or shadows plan-version data.

## Technical Considerations

- **Pattern usage**: source-pinning follows the existing
  `sourceConfigId/Version` columns pattern; idempotency via
  `runIdempotentCommand` (`server/lib/idempotent-command.ts`); locks via
  `server/lib/locks.ts`; calc envelope via calc-substrate (ADR-042).
- **Known schema quirks**: `fund_snapshots.scenarioSetId` is a bare uuid with no
  FK — irrelevant to C1A (`null`), noted for any future S1 linkage;
  `fund_scenario_sets.idempotencyKey` is nullable with a partial unique index —
  S1 keeps the existing create route's idempotency behavior unchanged.
- **Edge cases**: publication advances between GET source-config and create (409
  path); facts snapshot superseded mid-flight (step 4 refusal); empty facts
  (unavailable, zero persistence); concurrent **same-key** writers (advisory
  lock + post-lock replay re-check → one row per key); concurrent
  **different-key** same-input writers (distinct rows sharing the `stateHash`
  value — intentional, per one-snapshot-per-key).
