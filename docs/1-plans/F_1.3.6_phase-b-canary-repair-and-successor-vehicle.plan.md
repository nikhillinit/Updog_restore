## Overview

F_1.3.5 slice 2 merged the sixth F_1.21.1 vehicle at `5c0c0d906` (#1648). Phase
A (run 39237965242, attempt 1) succeeded and both Railway workers run
`5c0c0d906`. Phase B (run 39249160715, attempt 1, `mode=full`) failed in job
`Authenticated Staged Production Smoke`, step `Assert bounded canary residue`,
before `Promote`; promotion and post-promotion smoke were skipped. Canonical web
still serves the `068430726` baseline (deployment
`dpl_5fB4SsnPTmF76xw13nRQhwFf55jb`, v1.3.2). The `stage-production` job created
a READY production-target deployment that was never promoted.

Two defects produced the failure, and a third gap follows from the second:

1. Release canary 1 enters its dollar fund size into a millions field, so the
   deployed app stores 1e12 and the reload assertion expecting 1e6 fails. The
   production conversion is correct; the test caller is wrong.
2. The exact-run residue check counted six `fund_events` rows against the frozen
   reservation of five (`release-canary-http-workflow-v2`), exit 4,
   `exact-run-failure`. The writer of the sixth event is unverified.
3. The reservation assertion threw before the script's terminal readback, so the
   canary run's terminal state and cleanup are unverified from the run log.

Under F_1.21.1 "Release sequence" (stop and re-plan on any refusal; never re-run
a failed attempt) the release needs a repaired source, a cleaned canary residue,
and a seventh docs-only vehicle on a new `main` head. This plan defines five
slices in order: a read-only diagnosis of the six events against the exact
recovery tuple; a source repair PR with regression tests; the governed recovery
and purge of the failed canary run; the seventh F_1.21.1 vehicle with a fresh
ADR-107 capture; and F_1.21.1 steps 8 to 11 on the successor.

### Finding A: the failure is two independent defects, not one

Canary 1's size assertion (row 4) and the residue overflow (row 6) are
independent: the residue step runs after Playwright regardless of outcome
(`PLAYWRIGHT_OUTCOME` only selects `--fail-current-run`). A repaired canary 1
would still have failed the reservation if the sixth event recurs. Both must be
repaired, and the second needs evidence first.

### Finding B: the canary run is terminal by construction; the readback is what is missing

Row 7: the terminal transition committed in its own transaction before the
assertion. The run row should read `failed` with `failed_at` set and its residue
columns populated. Nothing in the log proves it, so slice 0 reads it. The
transition-then-assert order is the documented design (fail closed, with the
exact run already terminal); it is not a defect. The gap is reporting only.

### Finding C: resolved for the tracked CLI path

Row 9. `vercel deploy --prebuilt --prod` under `git.deploymentEnabled: false`
created the staged deployment. This confirms the ADR-109 text that the key does
not cover CLI or API deployments; it changes no policy and amends no ADR. It is
recorded in the F_1.21.1 "Open risk" revision (item 6).

## Problem Statement

- `tests/smoke/release-canaries.spec.ts` canary 1 is the only deployed proof of
  the fund setup journey, and it cannot pass at any SHA: its fund-size input is
  off by 1e6 against the UI's unit conversion.
- The deployed browser journey writes one more `fund_events` row than the frozen
  reservation. Local characterization (service path plus the strict HTTP
  sidecar) did not predict it, so the gap is between the characterized path and
  the real browser path: either the recorded duplicate-PUT scheduling defect
  (row 15) or a legitimate second draft save that the characterized path never
  issues (step 2 writes its stages into the store on mount). Only the saved
  payloads tell them apart (item 1).
- The failed run's residue columns, terminal status, and cleanup are known only
  from the thrown message. The row will expire about 24 hours after creation and
  then fail every later release until purged.
- The release SHA `5c0c0d906` cannot be released again: the attempt failed, and
  a repair changes the candidate. A new vehicle and capture are required.
