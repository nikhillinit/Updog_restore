# V2 Catch-Up Allocation Parity Implementation Plan (F_2.0.4)

## Overview

Unify the duplicated GP catch-up arithmetic in both V2 waterfall engines behind
one pure Decimal leaf, and close the split-conservation gap by quantizing each
tier allocation exactly once and splitting it with a single joint
largest-remainder pass. Add cumulative GP/LP profit accumulators (fund-level in
whole-fund, per-entitlement-pool in deal-by-deal) so later tiers see profit
granted by earlier tiers. No public capability changes: the catch-up tier
remains unreachable on the public derivation path (admission guard accepts only
a single carry-only tier with zero events), so this is engine-internal
correctness work and preparation for later F3+/admission-widening scope.
Classification: **implementation-conformance correction** — the leaf implements
the locked F_2.0.0 catch-up methodology, which both engines currently diverge
from (see Problem Statement). It is not a methodology change; the methodology
authority is `F_2.0.0_v2-core-financial-model.plan.md:365-372` (ratified). This
plan routes under the governing policy
(`docs/governance/solo-internal-change-and-production-policy.md`); it confers no
production authority.

## Problem Statement

- **Methodology divergence**: both engines compute gross catch-up as
  `(c * (openingPreferredPaid + remaining) - G) / g`
  (`waterfall-whole-fund-v2.ts:190-206` —
  `targetGpProfit = cumulativePrefPaid.plus(remaining).mul(gpShareRate)`,
  `grossCatchUp = gpDeficit.div(gpAllocationRate)`; identical shape in
  `waterfall-deal-by-deal-v2.ts:178-193`). The locked methodology
  (`F_2.0.0_v2-core-financial-model.plan.md:365-372`) requires the stopping rule
  `(c * (G + L) - G) / (g - c)`. Three independent divergences: wrong
  denominator (`g` vs `g - c`); profit base substitutes the **opening**
  preferred-paid scalar for cumulative GP+LP profit (preferred paid by the
  current run's own `preferred_return` tier never enters); the base folds in
  undistributed `remaining` proceeds. Dormant only because the catch-up tier is
  unreachable on the public path.
- **Duplication**: catch-up arithmetic is line-for-line identical in
  `shared/lib/internal-economics/v2/waterfall-whole-fund-v2.ts:181-233` (inline)
  and `shared/lib/internal-economics/v2/waterfall-deal-by-deal-v2.ts:165-221`
  (`allocateGpCatchUp`).
- **Conservation gap**: each tier split is quantized three independent times —
  `decimalToCents(gpAmount)` + LRM, `decimalToCents(lpAmount)` + LRM, and
  `toFixed(6)` on the tier total. Nothing forces GP units + LP units to equal
  `decimalToCents(allocated)`. The same pattern exists in the carry tier
  (whole-fund `:248-262`, deal-by-deal `:237-258`).
- **Per-pool re-grant defect**: deal-by-deal re-derives catch-up inside every
  pool from the same unchanged fund-level opening scalars
  (`waterfall-deal-by-deal-v2.ts:333-340`); GP profit granted in earlier pools
  is never seen by later pools.
- **Zero coverage**: neither waterfall test file contains a single catch-up
  arithmetic assertion; only tier-policy validation is tested
  (`normalize-input-v2.test.ts`).

## Solution Architecture

One pure leaf owns the catch-up formula and the quantized joint split. Both
engines call it. Whole-fund feeds one fund-level cumulative-profit accumulator;
deal-by-deal feeds one clean-opening accumulator per entitlement pool. The
pool-independence and order-invariance claims are scoped to pools keyed by
**distinct deals**: the existing pool builder assigns all of a deal's proceeds
to the first matching security pool (`waterfall-deal-by-deal-v2.ts:80`) and
realization state discards row-level proceeds attribution, so same-deal
multi-security attribution is pre-existing behavior explicitly out of scope here
(deferred to the F3 lineage work). The same quantize-once-then-joint-split
mechanism is applied to the carry tier in both engines, since it is the
identical defect at the identical boundary. Accumulators update from emitted,
quantized `gpShare` / `lpShare` after preferred return, catch-up, and carry;
return of capital is excluded.

Empty-cohort invariant: both engines today subtract a positive GP or LP bucket
from `remaining` even when the eligible partner cohort is empty
(`apportionBySettledCapital` returns an empty map at
`waterfall-whole-fund-v2.ts:62`, but `:223` subtracts unconditionally; same
shape at `waterfall-deal-by-deal-v2.ts:195-220,348`), and normalization never
refuses zero-GP or zero-LP cohorts. The engines MUST NOT subtract a positive
bucket unless the full bucket is assigned to eligible partners: a positive
catch-up or carry bucket with an empty eligible cohort raises an internal
defensive error (same pattern as the deal-by-deal opening-history throw —
unreachable on admitted input, where every affected allocation is zero). No new
public refusal family.

Normative calculation (the locked F_2.0.0 methodology — **not** what current
engines execute; the delta is the Methodology-divergence item above):

```text
G = cumulative GP profit distributions
L = cumulative LP profit distributions
c = terminal carry GP share
g = catch-up tier GP allocation rate

grossCatchUpDue = max(0, (c * (G + L) - G) / (g - c))
allocated = min(available, grossCatchUpDue)
```

Quantization discipline: `allocated` is converted to six-decimal integer units
exactly once with the existing `decimalToCents`; those units are split with one
`apportionCentsLrm` call over `[GP, LP]` with GP at bucket index zero (equal
remainders deterministically favor GP); bucket values convert back with
`centsToDecimalString`. Each GP/LP bucket is then apportioned among eligible
partners through the existing largest-remainder helpers. No decimal helper is
renamed or duplicated.

Oracle: `G=0`, `L=100`, `c=.2`, `g=.5` produces total `66.666667`, GP
`33.333334`, LP `33.333333`.

## Implementation Details

### 1. New pure leaf

**File**: `shared/lib/internal-economics/v2/catch-up-allocation-v2.ts` (new)

Exports `computeGpCatchUpAllocationV2(input)` where input carries `available`,
`cumulativeGpProfit`, `cumulativeLpProfit`, `terminalGpShare`,
`catchUpGpAllocationRate` (all Decimal) and the result carries the
jointly-quantized GP and LP bucket amounts (six-decimal strings) **plus the
allocated total reconstructed from the integer units** (GP units + LP units
converted back — never the raw pre-quantization Decimal). Engines use the
reconstructed total for `remaining` / `totalDistributed` updates, so emitted
buckets can never over-distribute relative to what was subtracted (raw
`25.0000005 + 75.0000025` must not emit `100.000004` against a `100.000003`
subtraction). The leaf asserts the normalized preconditions `0 <= c < g <= 1`
defensively (they are already refused upstream with `INVALID_TIER_POLICY` in
`normalize-input-v2.ts:198-261`); it adds no new public refusal contract.

### 2. Whole-fund engine

**File**: `shared/lib/internal-economics/v2/waterfall-whole-fund-v2.ts`

**Current state**: inline catch-up at `:181-233`; carry split at `:248-262`;
three-way independent quantization; reads only the opening GP-profit scalar.

**Modifications**:

- Initialize one fund-level `G/L` accumulator per the locked methodology's
  profit definition (preferred return + catch-up + carry —
  `F_2.0.0_v2-core-financial-model.plan.md:365`): `G` = opening GP profit
  distributions; `L` = opening cumulative preferred paid + opening LP profit
  distributions. This initialization rule is resume-correct only where GP
  preferred participation is `excluded` — under `pari_passu` the aggregate
  opening preferred-paid scalar cannot be split GP/LP (no per-side provenance
  exists in the opening schema), so nonzero-opening resume under `pari_passu` is
  deferred until GP/LP preferred provenance lands. All opening values are zero
  on any admitted input today; the rule and its limit are documented in the leaf
  test.
- Replace the inline catch-up block with a call to the leaf; feed the
  accumulator; update it from the emitted quantized shares.
- Apply the same quantize-once/joint-split mechanism to the carry tier split.
- Preserve the existing `apportionBySettledCapital` per-partner behavior,
  including its empty-map short-circuit on non-positive amounts.

### 3. Deal-by-deal engine

**File**: `shared/lib/internal-economics/v2/waterfall-deal-by-deal-v2.ts`

**Current state**: `allocateGpCatchUp` at `:165-221` re-reads fund-level opening
scalars inside each pool loop iteration (`:333-340`).

**Modifications**:

- Initialize one clean-opening `G/L` accumulator per entitlement pool; update it
  from that pool's emitted quantized shares. Pool order must not affect output
  and pools remain economically independent **for pools keyed by distinct
  deals** (same-deal multi-security attribution is pre-existing builder
  behavior, out of scope — see Solution Architecture).
- Replace `allocateGpCatchUp` internals with the leaf call.
- Apply the joint-split mechanism to the carry tier.
- Nonzero scalar opening profit-decomposition history is already refused at
  normalization with `OPENING_PROVENANCE_REQUIRED`
  (`normalize-input-v2.ts:509-527`) — that remains the sole public refusal. The
  engine adds only an internal defensive throw (unreachable by contract) if it
  ever receives nonzero scalar opening profit history, because current input
  cannot allocate that history across pools. No new public refusal family; do
  not repurpose `OPENING_RECONCILIATION_VIOLATION` (a normalization-stage
  family) for this.
- Do not add per-pool opening fields, public admission, receipts, routes,
  persistence, queues, or UI.

## Technical Considerations

- **Frozen surfaces are a hard stop.** V2-S-0100/V2-S-0101 frozen hashes
  (`tests/unit/truth-cases/internal-economics-v2-opening-state.test.ts`,
  `-first-success.test.ts`, changed-case manifest) and the exact serialized byte
  assertions (`liquidity-receipt-builder-v2.test.ts:221` pins the V2-S-0100
  receipt at 4206 bytes; the 16 MiB padding test derives from it) must remain
  byte-identical. Admitted public inputs are zero-event carry-only, where every
  affected split is zero, so no drift is expected — verify, and stop if any
  frozen hash or byte count moves.
- **Conformance proof obligation.** Because the leaf changes the executed
  equation, implementation MUST prove no admitted or frozen fixture reaches a
  changed nonzero allocation (today: the shared fixture policy has no catch-up
  tier — `tests/helpers/v2-input-builder.ts:64-72` — and the admission guard
  blocks catch-up publicly, so the changed branch is unreachable). If any
  admitted result changes, stop: component/receipt versioning and the
  changed-case manifest must be reconsidered before proceeding.
- **No component-version bump.** The receipt manifest consumes
  `INTERNAL_ECONOMICS_WATERFALL_DEAL_BY_DEAL_V2_VERSION` as
  `componentVersions.selectedWaterfall`; bumping it would move every
  `resultHash` including the frozen fixtures. Public-path behavior is
  byte-identical, so the constant does not change; the leaf is an internal
  helper, not a new manifest component.
- **Receipt-level parity is out of scope.** `liquidity-receipt-builder-v2.ts`
  writes `catchUpPaid`/`carryPaid` ledger fields as hardcoded zero; parity here
  is asserted at the engine boundary only. Receipt-level tier reporting belongs
  to the F3 eventful-receipt scope (see F_2.0.3 remaining-scope list).
- **Test-runner split**: `npm run test:internal-economics-v2` does not include
  the two hash-frozen truth cases; those run under `npm run phoenix:truth`. Both
  commands are required verification.
- **F3 non-conflict**: F3a (merged, `e0ac8ac9d`) touched
  `event-stream-engine-v2.ts` / `derive-composite-v2.ts` only; remaining F3
  scope (`sourceCashLotId` lineage, eventful receipt, event-stream atomicity) is
  disjoint from this change.
- **Parity claim discipline**: cross-engine equality is tested only for an
  economically equivalent, clean-opening single-pool fixture. Do not assert
  universal parity across multi-pool deal-by-deal and whole-fund waterfalls.

## Test Impact

- New leaf suite: exact oracle, six-decimal conservation (GP + LP ==
  reconstructed allocated, every case), already-satisfied catch-up returns zero,
  prior distributions reduce remaining catch-up, insufficient proceeds allocate
  only available value, resume-oriented case proving `L` includes opening
  preferred paid. Plus one **distinguishing fixture**: for the same nonzero
  input, compute both the current-engine equation (`(c*(P+remaining)-G)/g`) and
  the locked equation (`(c*(G+L)-G)/(g-c)`), assert they differ, and assert the
  leaf matches the locked value — proving which formula is authoritative, not
  merely leaf self-consistency.
- Both waterfall suites gain catch-up arithmetic coverage (currently zero):
  multi-tier cumulative updates from emitted amounts; two **distinct-deal**
  pools independent and order-invariant — the pool tests MUST assert the
  executable precondition, not just prose scope: exact entitlement-pool keys,
  distinct deal IDs, proceeds attributed to the expected pools, no same-deal
  multi-security aliasing, and that permutation changes pool order only (not
  pool identity or economics); clean-opening single-pool fixture equal across
  engines; carry-tier conservation; **catch-up and carry tier** totals equal
  per-partner sums equal the amounts subtracted from remaining proceeds (no
  micro-unit over-distribution); explicit no-GP-cohort and no-LP-cohort cases
  proving the defensive empty-cohort error and that no positive bucket is ever
  silently dropped. The conservation invariant is scoped to those two tiers: the
  preferred-return and return-of-capital boundaries quantize partner shares but
  subtract raw Decimal targets today — pre-existing behavior, out of scope for
  this plan.
- Frozen-surface regression: V2-S-0100/0101 hashes and the 4206-byte receipt
  assertion must stay green — these run under `phoenix:truth` and the
  receipt-builder suite, not the v2 npm script alone.
- Full verification: `npm run test:internal-economics-v2`,
  `npm run phoenix:truth`, `npm run calc-gate`, `npm run check`, `npm run lint`,
  `npm test` (all with `TZ=UTC`).
