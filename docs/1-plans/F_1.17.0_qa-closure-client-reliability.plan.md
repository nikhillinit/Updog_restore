mutation safety, merged in this order:

1. **PR 1 - mutation and error-boundary correctness:** C3, C8.
2. **PR 1b - durable create receipts:** C2 (server receipts, one additive
   migration, persisted client intent keys); integrates after the F_1.16.0

3. **PR 2 - query, state, accessibility, and readable-text closure:** C1, C4-C7,
   C9, C10.

`1` for both preview and commit
(`client/src/components/portfolio/tabs/ReallocationTab.tsx:25`, `:65`, `:125`).

`apiRequest` error channel; it adds no service, state manager, retry layer, or
new schema, but does require a narrow cross-stack row-version contract repair
and a canonical lock order inside the existing shared allocation writer. PR 2
stays mostly client-facing. C5 adds one narrow server-side exact-baseline lookup
because the existing client report list is capped at 50; the remaining items
share the same unit/build gates.

## Solution Architecture

### PR 1 - C3, C8

#### C3 row-scoped optimistic-lock repair

Use `allocation_version` per proposed company from `useLatestAllocations`, keyed
by company ID. Do not require one fund-wide version: active writers lock and
increment individual company rows
(`server/services/allocation-write-service.ts:100-145`;
`server/services/fund-moic-input-service.ts:163-197`), new rows start at version
1 (`server/storage.ts:154-184`), and active integration coverage preserves mixed
versions after a partial write
(`tests/integration/allocation-scenario-apply.test.ts:225-245`). The quarantined
all-equal expectation is replaced, not restored
(`tests/unit/reallocation-api.test.ts:495-530`).

Required flow:

1. Load portfolio companies and latest allocations in parallel with existing
   hooks. Build a `company_id -> allocation_version` map from the allocations
   response (`client/src/components/portfolio/tabs/types.ts:12-24`). Enable
   preview only when every selected company has a positive version. Mixed
   versions elsewhere in the fund are valid; do not guess, take a maximum, or
   fall back to `1`.
2. Extend each proposed allocation with `expected_version`. The preview and
   commit payloads carry that value per company; the successful preview freezes
   the exact proposed rows and expected versions that commit will use. Remove
   the scalar `current_version` contract. Reject duplicate `company_id` values
   in the preview and commit request schemas with one Zod `.refine` (400 before
   any transaction); the current schema accepts duplicates
   (`server/routes/reallocation.ts:37-48`), which would break the
   one-update/one-audit-per-company invariant. Reuse the duplicate message shape
   of the shared writer's guard
   (`server/services/allocation-write-service.ts:79-97`).
3. Validate preview conflicts only for proposed company IDs. On conflict, return
   `details.current_versions` as company/version objects from the route, sorted
   by ascending `company_id`: `{ company_id: number, current_version: number }`.
   The existing `ApiError` already preserves non-5xx `details`
   (`client/src/lib/queryClient.ts:130-160`), so map that field in the two
   reallocation hooks without changing `queryClient.ts`.
4. In the commit transaction, select only proposed company IDs with
   `ORDER BY id FOR UPDATE`, then compare each locked row with its
   `expected_version`. Lock order must not follow request order. A stale row
   aborts the transaction before any update. The existing shared writer locks
   rows one at a time in request order (`updateCompanyAllocation` at
   `server/services/allocation-write-service.ts:100-111`, looped at `:226-236`),
   so opposite-order overlapping requests across the two writers can deadlock
   instead of yielding one success and one 409. Sort a copy of `updates` by
   `company_id` for that lock/update loop inside `applyAllocationUpdates`; keep
   the caller's order for the audit payload (`:184`) so both callers
   (`server/routes/allocations.ts:440`;
   `server/services/allocation-scenario-service.ts:1477`) are fixed once. The
   single-row MOIC input writer
   (`server/services/fund-moic-input-service.ts:163-197`) cannot form a lock
   cycle and stays unchanged.
5. Update only proposed rows and increment each row's own version by one. Leave
   all unproposed rows and their versions untouched. Return `new_versions` as an
   ascending-`company_id` array of
   `{ company_id: number, new_version: number }`; preserve `updated_count` as
   the number of changed proposed rows.
6. Write one existing-schema `reallocation_audit` row per proposed company,
   using that row's expected/resulting versions and exact allocation delta in
   `changes_json`. Return `audit_ids` as an ascending-`company_id` array of
   `{ company_id: number, audit_id: string }`, where `audit_id` is the UUID of
   that company's audit row. Do not invent a fund revision or bump every fund
   row; a true fund revision would require a dedicated column and every writer
   to adopt it. The current audit table has scalar version columns and a UUID
   primary key (`migrations/0001_certain_miracleman.sql:311-319`), so
   per-company audit rows keep those columns truthful without a migration.
7. On preview or commit 409: clear stale preview, refetch latest allocations,
   keep selected companies and reason, then require a fresh preview. Display
   refresh/re-preview copy; never retry commit automatically or silently
   overwrite.
8. Fence late preview responses. Today preview resets only when
   `selectedCompanies` changes (`ReallocationTab.tsx:41-44`), and an in-flight
   `onSuccess` still stores its result after an edit, reset, or fund switch. At
   `mutate()`, capture a fingerprint of `fundId` plus the sorted normalized
   proposed rows and expected versions in a ref. `onSuccess` discards the
   response unless the current fingerprint still matches; stored preview keeps
   its fingerprint, and commit stays disabled unless it equals the fingerprint
   of the displayed inputs. Edit, reset, and fund switch therefore always
   require a fresh preview.

This is an intentional cross-stack repair: the PR description must name the
client/server request, transaction, response, and audit contract change. No
schema migration or fund-wide revision is in scope.

Cutover is coordinated in one deployment, not versioned. At `def8b65f5` the only
callers of the two routes are `client/src/hooks/useReallocationPreview.ts:21`
and `client/src/hooks/useReallocationCommit.ts:24`, and one Vercel build
produces both the client bundle and the API function (`vercel.json:7`). Do not
keep scalar `current_version` request or response fields for compatibility: the
request contract itself changes to per-row `expected_version`, and a scalar
version is not truthful once company versions differ. A stale browser tab that
still sends the old body lacks `expected_version`, so the new request schema
rejects it with 400 before any transaction. Pre-code gate: re-run the caller
search at the implementation head and record the owner's confirmation that no
out-of-repository caller uses either route. If one exists, stop; a separately
versioned route is then an owner decision.

### PR 1b - C2 durable create receipts

C2 is a server-side P1, not a client-only fix. Failure window: the business
`COMMIT` succeeds, then the acknowledgment or the Redis cache write is lost; the
same pinned key has no receipt, so the retry repeats the mutation. The generic
middleware caches only 200/201 in Redis with a default 300-second TTL and stores
nothing without a Redis client (`server/middleware/idempotency.ts:211-217`,
`:267`), and its own test proves a same-key retry after a 500 runs the handler
again (`tests/unit/middleware/idempotency-dedupe.test.ts:275-293`). Today
`createDeal` commits the deal before a separate activity insert
(`server/services/deal-pipeline-service.ts:219-233`) and `confirmImport` inserts
row by row with no transaction (`:636-656`). PR 1b persists a completed receipt
in the same PostgreSQL transaction as each mutation.

#### One state machine, two storage adapters

Reuse `runIdempotentCommand` and `replayIdempotentCommandIfPresent`
(`server/lib/idempotent-command.ts:66-102`) as the single state machine: it
already owns the canonical request hash, changed-payload rejection
(`409 IDEMPOTENCY_KEY_REUSE`), replay, and reload after a lost insert race. Its
row type for these routes is the stored `{ responseStatus, responseBody }`, so
replay returns the original status and body. The hashed request binds the parsed
body, `fundId`, the acting user ID, an operation literal (`deal_create`,
`deal_import`, or `company_create`), and a contract-version literal. Each
adapter's `insert(requestHash)` runs one `db.transaction`:

1. Claim the key with `INSERT ... ON CONFLICT DO NOTHING RETURNING`. A
   concurrent same-key request waits on the unique index, then gets no row;
   return `null` so the helper reloads and replays the committed receipt. If the
   first transaction rolled back, the waiting insert succeeds instead.
2. Run the mutation with the transaction handle.
3. Write the completed response status and body into the claimed receipt.
4. Commit. A deferred constraint trigger (`DEFERRABLE INITIALLY DEFERRED`)
   rejects any receipt whose key, hash, and response are not all present or all
   absent at commit, so no pending receipt can ever be visible. A deferred row
   trigger keeps the `NEW` row captured at the INSERT event, so validating `NEW`
   would reject the completed receipt. The trigger function must instead re-read
   the current row by primary key when it fires and validate that; use the same
   function for both adapters.

Adapters:

- **Company create (receipt on the business row).** Add nullable
  `create_idempotency_key varchar(128)`, `create_request_hash char(64)`, and
  `create_response jsonb` to `portfoliocompanies`, with the all-null-or-all-set
  rule above and a partial unique index on
  `(fund_id, create_idempotency_key) WHERE create_idempotency_key IS NOT NULL`.
  The inserted company row claims the key in step 1; step 3 stores its create
  response. Keep the three columns out of the public model: omit them from
  `insertPortfolioCompanySchema` (`shared/schema.ts:561`, which today omits only
  `id` and `createdAt`), and project them out wherever full rows leave the
  server (`server/storage.ts:672`, `server/routes/portfolio-companies.ts:259`).
  The stored `create_response` is that public projection. Types: keep the
  exported `PortfolioCompany` name as the public type,
  `Omit<PortfolioCompanyRow, 'createIdempotencyKey' | 'createRequestHash' | 'createResponse'>`,
  and add `PortfolioCompanyRow` for the full stored row, in both alias sites
  (`shared/schema.ts:669`, `shared/schema/portfolio.ts:205`). `IStorage`
  (`server/storage.ts:99`) and every response path keep returning the public
  `PortfolioCompany`; only the adapter reads `PortfolioCompanyRow`. No unsafe
  casts. Update the inferred stored-company type in
  `server/services/portfolio-time-machine-read.ts:7` so the historical path does
  not carry receipt fields. No new table and no new row, so release-canary
  residue is unchanged (the canary creates a company through this route,
  `tests/smoke/release-canaries.spec.ts:720-735`). Companies have no hard-delete
  route (the four pinned rows are GET, GET by ID, PATCH, and POST); rows leave

- **Deal create and import (command table).** Add `deal_pipeline_commands`

  `request_hash char(64)` hex check, `created_by`, `response_status`,
  `response_body jsonb`, `created_at`; unique

#### C2 client intent keys

Each write keeps its command identity in a record saved outside the component,
following `client/src/components/lp-reporting/actuals-draft-command.ts` (freeze
before POST, recover, clear). Reuse the pattern, not the module: one small
shared module (for example `client/src/lib/pending-create-command.ts`) serves
the three writes.

- **Record.** `{ version, key, operation, fundId, actorId, createdAt, body }`,
  where `body` is the normalized payload exactly as sent and `actorId` is
  `user.id` from `useAuthSession()` (`client/src/lib/auth-session.ts:5-10`,
  `:41-49`). Each command has its own `localStorage` entry,
  `pending-create:v1:<actorId>:<fundId>:<operation>:<key>`, so the record
  survives unmount, route navigation, reload, and tab or browser termination.
  Two tabs never overwrite each other: a submit only creates its own entry and
  settlement removes only its own entry, so no read-modify-write crosses tabs
  and no lock is needed. Parse each entry with a strict Zod schema; a corrupt
  entry, or one whose actor, fund, operation, or key differs from its storage
  key, is never replayed.
- **Save before dispatch.** When a validated submit/confirm begins with no
  record, or after a definite rejection followed by an edit, generate
  `crypto.randomUUID()` and write the record before calling `apiRequest`. If the
  write throws, send nothing and show an inline error.
- **Restore before enabling submission.** On open, wait for the auth session,
  then scan the entries under the current actor, fund, and operation prefix
  before submit is enabled. If any exist, the oldest by `createdAt` opens in the
  unknown-outcome state below; when it settles or is discarded, the next one
  opens. A new command cannot be submitted while any entry remains in scope.
  Another actor's record is not visible because the storage key includes the
  actor, so it is never replayed under a different actor or fund; the server
  also binds the actor into the request hash.
- Pass `{ headers: { 'Idempotency-Key': key } }` as `apiRequest`'s fourth
  argument; no shared wrapper is needed because headers are already supported
  (`client/src/lib/queryClient.ts:105-116`).
- **First attempt.** A received `ApiError` 4xx other than 408 and
  `409 IDEMPOTENCY_RACE_UNRESOLVED`, on an attempt with no earlier unknown
  outcome, is a definite rejection: rate limiting and authorization run before
  the handler (`server/routes/portfolio-companies.ts:289-294`;
  `server/routes/deal-pipeline.ts:153-157`, `:677-681`), and a handler failure
  rolls back without a receipt. Keep the key while the normalized payload is
  unchanged; an edit after a definite rejection rotates the key and rewrites the
  record before the next request.
- **Unknown outcome.** Network failure, timeout, 408,
  `409 IDEMPOTENCY_RACE_UNRESOLVED`, or 5xx means the server may have committed.
  From then on the command is uncertain: fields and reset are read-only, and the
  only send action resends the stored body with the stored key. Authentication,
  authorization, throttling, not-found, and validation failures on later
  attempts do not establish that the original attempt failed, so the command
  stays uncertain. Only two responses settle it: a 2xx (executed now or
  replayed), or `409 IDEMPOTENCY_KEY_REUSE`, which means a receipt for this key
  already exists, so the original committed under a different binding (for
  example a contract-version change after a deploy). Both clear the record and
  invalidate the list query; the reuse case tells the user the item was already
  recorded. `useFundDraftSync`'s `uncertain` status is the precedent
  (`client/src/hooks/useFundDraftSync.ts:169`); do not import the fund-draft
  settlement module.
- **Explicit discard.** An uncertain command that cannot settle (for example
  after lost write access) offers discard only after the list query has been
  refetched, with copy stating that the item may already exist. Discard clears
  the record; it is the only exit that does not come from the server.
- **Close and reset.** Closing or navigating away never clears an unsettled
  record; it invalidates the list query so the user sees any created row. The
  existing reset seams (add-deal success/reset `AddDealModal.tsx:137-148`,
  `:178-183`; add-company close `AddCompanyDialog.tsx:79-85` and success
  `AddCompanyDialog.tsx:97-104`; import close `ImportDealsModal.tsx:221-233`)
  clear the record only after success, a definite rejection, or discard.
- Add the key only to import confirm (`/api/deals/opportunities/import`), not
  read-only preview (`ImportDealsModal.tsx:137-153`).

Stated ceiling: an unsettled record keeps its form body or import rows in
browser storage until settlement or discard.
