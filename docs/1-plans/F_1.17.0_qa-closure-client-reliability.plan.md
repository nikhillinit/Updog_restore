## Overview

Implement C1-C10 in three reviewable PRs, ordered by financial correctness and
mutation safety, merged in this order:

1. **PR 1 - mutation and error-boundary correctness:** C3, C8.
2. **PR 1b - durable create receipts:** C2 (server receipts, one additive
   migration, per-tab persisted client intent keys). #1584 already sends the
   keys and savepoints import rows; PR 1 (#1583) and the F_1.16.0 implementation
   (#1580) are on `main`.
3. **PR 2 - query, state, accessibility, and readable-text closure:** C1, C4-C7,
   C9, C10.

PR 1 goes first because C3 currently sends hard-coded optimistic-lock version
`1` for both preview and commit
(`client/src/components/portfolio/tabs/ReallocationTab.tsx:25`, `:65`, `:125`).
The shortest correct repair reuses the existing allocations query and
`apiRequest` error channel; it adds no service, state manager, retry layer, or
new schema, but does require a narrow cross-stack row-version contract repair
and a canonical lock order inside the existing shared allocation writer. PR 2
stays mostly client-facing. C5 adds one narrow server-side exact-baseline lookup
because the existing client report list is capped at 50; the remaining items
share the same unit/build gates.

Settled decisions remain closed:

- Team access keeps universal safe reads and strict writes through existing
  authorization helpers.
- No rebrand: primary remains charcoal `#292929`; readable muted copy uses
  `text-presson-textMuted` (`#5A5A5A`) (`DESIGN.md:58`, `DESIGN.md:65-70`). Do
  not remap the Tailwind charcoal scale.
- LP portal remains feature-flagged and out of scope.
- `ReallocationTab` is repaired, not removed.
- Internal-tool scale is about five users: no new framework, service, generic
  retry layer, or design abstraction.

## Solution Architecture

### PR 1 - C3, C8

#### C3 row-scoped optimistic-lock repair

Use `allocation_version` per proposed company from `useLatestAllocations`, keyed
by company ID. Do not require one fund-wide version: active writers lock and
increment individual company rows
(`server/services/allocation-write-service.ts:100-145`;
`server/services/fund-moic-input-service.ts:163-197`), new rows start at version
1 (`server/storage.ts:154-184`), and active integration coverage preserves mixed
versions after a partial write
(`tests/integration/allocation-scenario-apply.test.ts:225-245`). The quarantined
all-equal expectation is replaced, not restored
(`tests/unit/reallocation-api.test.ts:495-530`).

Required flow:

1. Load portfolio companies and latest allocations in parallel with existing
   hooks. Build a `company_id -> allocation_version` map from the allocations
   response (`client/src/components/portfolio/tabs/types.ts:12-24`). Enable
   preview only when every selected company has a positive version. Mixed
   versions elsewhere in the fund are valid; do not guess, take a maximum, or
   fall back to `1`.
2. Extend each proposed allocation with `expected_version`. The preview and
   commit payloads carry that value per company; the successful preview freezes
   the exact proposed rows and expected versions that commit will use. Remove
   the scalar `current_version` contract. Reject duplicate `company_id` values
   in the preview and commit request schemas with one Zod `.refine` (400 before
   any transaction); the current schema accepts duplicates
   (`server/routes/reallocation.ts:37-48`), which would break the
   one-update/one-audit-per-company invariant. Reuse the duplicate message shape
   of the shared writer's guard
   (`server/services/allocation-write-service.ts:79-97`).
3. Validate preview conflicts only for proposed company IDs. On conflict, return
   `details.current_versions` as company/version objects from the route, sorted
   by ascending `company_id`: `{ company_id: number, current_version: number }`.
   The existing `ApiError` already preserves non-5xx `details`
   (`client/src/lib/queryClient.ts:130-160`), so map that field in the two
   reallocation hooks without changing `queryClient.ts`.
4. In the commit transaction, select only proposed company IDs with
   `ORDER BY id FOR UPDATE`, then compare each locked row with its
   `expected_version`. Lock order must not follow request order. A stale row
   aborts the transaction before any update. The existing shared writer locks
   rows one at a time in request order (`updateCompanyAllocation` at
   `server/services/allocation-write-service.ts:100-111`, looped at `:226-236`),
   so opposite-order overlapping requests across the two writers can deadlock
   instead of yielding one success and one 409. Sort a copy of `updates` by
   `company_id` for that lock/update loop inside `applyAllocationUpdates`; keep
   the caller's order for the audit payload (`:184`) so both callers
   (`server/routes/allocations.ts:440`;
   `server/services/allocation-scenario-service.ts:1477`) are fixed once. The
   single-row MOIC input writer
   (`server/services/fund-moic-input-service.ts:163-197`) cannot form a lock
   cycle and stays unchanged.
5. Update only proposed rows and increment each row's own version by one. Leave
   all unproposed rows and their versions untouched. Replace the batched `CASE`
   builder (`server/routes/reallocation.ts:509-561`): its cap branch uses the
   zero-based `params.indexOf(company_id)` as a one-based placeholder
   (`:531-533`), so a cap update binds to the wrong parameter, and a company ID
   equal to the fund ID emits `$0`. This defect predates these PRs. After the
   sorted lock and version check, update each proposed row with one
   fixed-placeholder statement,
   `UPDATE portfoliocompanies SET planned_reserves_cents = $1, allocation_cap_cents = COALESCE($2, allocation_cap_cents), allocation_version = allocation_version + 1, last_allocation_at = NOW() WHERE fund_id = $3 AND id = $4`,
   passing `null` for an omitted cap so the stored cap is preserved; the request
   schema cannot carry a null cap (`:37-41`). Return `new_versions` as an
   ascending-`company_id` array of
   `{ company_id: number, new_version: number }`; preserve `updated_count` as
   the number of changed proposed rows.
6. Write one existing-schema `reallocation_audit` row per proposed company,
   using that row's expected/resulting versions and exact allocation delta in
   `changes_json`. Return `audit_ids` as an ascending-`company_id` array of
   `{ company_id: number, audit_id: string }`, where `audit_id` is the UUID of
   that company's audit row. Do not invent a fund revision or bump every fund
   row; a true fund revision would require a dedicated column and every writer
   to adopt it. The current audit table has scalar version columns and a UUID
   primary key (`migrations/0001_certain_miracleman.sql:311-319`), so
   per-company audit rows keep those columns truthful without a migration.
7. On preview or commit 409: clear stale preview, refetch latest allocations,
   keep selected companies and reason, then require a fresh preview. Display
   refresh/re-preview copy; never retry commit automatically or silently
   overwrite.
8. Fence late preview responses. Today preview resets only when
   `selectedCompanies` changes (`ReallocationTab.tsx:41-44`), and an in-flight
   `onSuccess` still stores its result after an edit, reset, or fund switch.
   Fingerprint equality alone is not a fence: reset followed by identical
   re-entry, an edit and revert, or a fund switch A to B to A restores the same
   fingerprint while a pre-change response is still in flight. Keep a
   `previewGeneration` counter in a ref, incremented on every edit, reset, fund
   switch, and preview start. At `mutate()`, capture that generation plus a
   fingerprint of `fundId` and the sorted normalized proposed rows and expected
   versions. `onSuccess` stores the response only when both the captured
   generation and the fingerprint still match; the stored preview keeps both,
   and commit stays enabled only while both equal the current values. The
   fingerprint remains as a second, input-derived check so a missed generation
   bump cannot pass changed inputs. Edit, reset, and fund switch therefore
   always require a fresh preview.

This is an intentional cross-stack repair: the PR description must name the
client/server request, transaction, response, and audit contract change. No
schema migration or fund-wide revision is in scope.

Cutover is coordinated in one deployment, not versioned. At `def8b65f5` the only
callers of the two routes are `client/src/hooks/useReallocationPreview.ts:21`
and `client/src/hooks/useReallocationCommit.ts:24`, and one Vercel build
produces both the client bundle and the API function (`vercel.json:7`). Do not
keep scalar `current_version` request or response fields for compatibility: the
request contract itself changes to per-row `expected_version`, and a scalar
version is not truthful once company versions differ. A stale browser tab that
still sends the old body lacks `expected_version`, so the new request schema
rejects it with 400 before any transaction. Pre-code gate: re-run the caller
search at the implementation head and record the owner's confirmation that no
out-of-repository caller uses either route. If one exists, stop; a separately
versioned route is then an owner decision.

### PR 1b - C2 durable create receipts

C2 is a server-side P1. #1584 (`ecc61bd4e`) already sends a per-intent
`Idempotency-Key` from all three dialogs and runs each import row in its own
savepoint, so UI creates work on `main`. The remaining gap is durability.
Failure window: the business commit succeeds, then the acknowledgment or the
Redis cache write is lost; the pinned key has no durable receipt, so the retry
repeats the mutation. The generic middleware caches only 200/201 in Redis with a
default 300-second TTL and stores nothing without a Redis client
(`server/middleware/idempotency.ts:211-217`, `:267`); its own test proves a
same-key retry after a 500 runs the handler again
(`tests/unit/middleware/idempotency-dedupe.test.ts:275-293`). It also caches the
2xx at `res.json`, before the request commits
(`server/middleware/idempotency.ts:398-431`), so a failed commit can leave a
cached 201 for a row that does not exist. PR 1b persists a completed receipt in
the same PostgreSQL transaction as each mutation and takes the three routes off
the generic middleware.

#### Transaction topology

Since #1484 every protected `/api` request runs in one request-scoped
transaction (`server/app.ts:243`, `server/middleware/with-rls-transaction.ts`).
`db` resolves to that transaction (`server/db.ts:145-147`), so an adapter's
`db.transaction` is a savepoint and the real commit is the request commit. The
middleware holds the response, rolls back when the status is 400 or above, and
commits before it sends the body. A receipt is therefore durable before the
client sees the acknowledgment, and a 500 in the middle of an import rolls back
the whole request, receipt included. Every request transaction inherits
`statement_timeout = '10s'` and `lock_timeout = '2s'`
(`server/db/request-context.ts:51-52`). A same-key request that waits more than
2 s on another request's advisory lock or uncommitted unique-index entry fails
with 55P03; the routes map it (see Route wiring). All regressions run through
the `makeApp` stack, not direct service calls.

#### One state machine, two storage adapters

Reuse `runIdempotentCommand` and `replayIdempotentCommandIfPresent`
(`server/lib/idempotent-command.ts:66-102`) as the single state machine: it owns
the canonical request hash, changed-payload rejection
(`409 IDEMPOTENCY_KEY_REUSE`), replay, and reload after a lost race. The hashed
request binds the parsed body, `fundId`, the acting user ID, an operation
literal (`deal_create`, `deal_import`, or `company_create`), and a
contract-version literal. Replay follows the in-repo precedent
(`server/routes/operating-object-tasks.ts:90`,
`server/routes/fund-moic.ts:220`): status 200 with the replay body and
`Idempotency-Replay: true`. A first execution keeps its current status (201 for
the two creates, 200 for import confirm). No response status is stored.

- **Company create (key and hash on the business row; owner Q1 = option A).**
  Follow task create
  (`server/services/operating-objects/task-service.ts:101-146`). Add nullable
  `create_idempotency_key varchar(128)` and `create_request_hash varchar(64)`
  (the `tasks.request_hash` type) to `portfoliocompanies`, a plain (not
  deferred) CHECK
  `(create_idempotency_key IS NULL) = (create_request_hash IS NULL)`, the hex
  check on the hash, and a partial unique index on
  `(fund_id, create_idempotency_key)`
  `WHERE create_idempotency_key IS NOT NULL`. `insert(requestHash)` inserts the
  company with the key and hash under `ON CONFLICT DO NOTHING` and returns the
  public row or `null`. Target the partial index if drizzle accepts it (the
  comment at `task-service.ts:137-140` says it does not; the red team reports
  0.45.2 does). Unqualified `DO NOTHING` is also safe: the only other unique key
  is `(id, fund_id)` on a serial `id` (`shared/schema/portfolio.ts:67`).
  `loadExisting` reads the current row by `(fund_id, create_idempotency_key)`
  and returns 500 `COMPANY_IDEMPOTENCY_CORRUPT` for a key without a hash, as
  `task-service.ts:114-119` does. Replay returns the **current** public row, not
  the original response body, so a company edited after its create replays its
  edited state. There is no `create_response` column and no deferred trigger.
  Memory mode (`MemStorage`) is not a durability target and keeps its current
  create path. The release canary creates a company through this route
  (`tests/smoke/release-canaries.spec.ts:720-735`); no row or table is added, so
  company create stays `mutationReceipt +0`.
  - **Public model.** Omit both columns from `insertPortfolioCompanySchema`
    (`shared/schema.ts:561`). Keep `PortfolioCompany` as the public type,
    `Omit<PortfolioCompanyRow, 'createIdempotencyKey' | 'createRequestHash'>`,
    and add `PortfolioCompanyRow` for the stored row at both alias sites
    (`shared/schema.ts:669`, `shared/schema/portfolio.ts:205`). The type split
    alone does not stop a leak, because a full `select()` still compiles against
    it. So `storage.getPortfolioCompanies` and `storage.getPortfolioCompany`
    (`server/storage.ts:672-688`) select the public columns explicitly. That one
    change covers the company routes
    (`server/routes/portfolio-companies.ts:259`) and
    `/dashboard-summary/:fundId` (`server/routes/dashboard-summary.ts:53`),
    which returns raw `getPortfolioCompanies` rows. Do not edit
    `dashboard-summary.ts`: it is a pinned matrix source. Update the inferred
    stored-company type in `server/services/portfolio-time-machine-read.ts:7`.
- **Deal create and import (command table, receipt last).** Add
  `deal_pipeline_commands` next to `dealOpportunities` (`shared/schema.ts:440`),
  copying the shape of `migrations/0059_task_update_commands.sql`: `id` serial;
  `fund_id` NOT NULL, FK to `funds` `ON DELETE CASCADE`; `operation` with a
  CHECK for `deal_create` or `deal_import`; `idempotency_key varchar(128)` NOT
  NULL with a non-empty check; `request_hash varchar(64)` NOT NULL with the hex
  check; `response_body jsonb` NOT NULL with an object check; `created_by` FK to
  `users`; `created_at`; unique `(fund_id, operation, idempotency_key)`; and a
  `BEFORE UPDATE` trigger on the existing `internal_economics_forbid_update()`,
  so a receipt is immutable. The receipt is written last, following
  `server/services/fund-workflow-service.ts:127-221`. Inside
  `runIdempotentCommand`'s `insert(requestHash)`:
  1. `SELECT pg_advisory_xact_lock(hashtext(...))` over the contract version,
     fund, operation, and key; the lock is held until the request commits;
  2. read the receipt for `(fund_id, operation, idempotency_key)`; if it exists,
     return `null` so the helper reloads and replays it;
  3. run the mutation: `createDeal`'s deal and activity inserts, or
     `confirmImport`'s savepointed row loop from #1584;
  4. insert the complete receipt and return it.

  Do not set a lock timeout in the adapter; the request transaction already sets
  2 s. Keys are scoped per fund and operation. The same UUID under another
  operation is an independent command, because the helper compares request
  hashes only after it finds a receipt
  (`server/lib/idempotent-command.ts:45-60`, `:80-102`); the client never reuses
  a key across operations. Deal DELETE archives, so no application path removes
  a receipt and no retention rule is needed.
  - **Import receipt content.** The stored and replayed summary carries
    sanitized `failedRows` entries, `{ index, message: 'Insert failed', code }`,
    where `code` is the PostgreSQL SQLSTATE when present. Never store or return
    raw error text: a `DrizzleQueryError` message embeds the SQL and bound
    parameters, including contact email and phone
    (`server/services/deal-pipeline-service.ts:650`). Log the raw error
    server-side. The same rule makes the create route's 500 message generic
    (`server/routes/deal-pipeline.ts:189` echoes `error.message` today).

#### Route wiring

- Add the three POST paths to `server/lib/database-backed-idempotency-routes.ts`
  so the generic middleware bypasses them
  (`server/middleware/idempotency.ts:272`); keep `requireIdempotencyKey`.
- Parse the key with `parseInternalEconomicsIdempotencyKey`
  (`server/lib/internal-economics-idempotency-key.ts:16`): 1-128 token
  characters, otherwise 400. Without it a key over 128 characters reaches
  PostgreSQL and fails with 22001 as a 500. The release canary's 62-character
  key passes.
- The handlers call the adapters and send the returned status and body.
- All three routes map lock and serialization failures: 55P03 to
  `409 REQUEST_IN_PROGRESS`, and 40P01 or 40001 to `503 COMMAND_RETRY_REQUIRED`,
  both with `Retry-After: 2`. Extract the lock-code branch of
  `sendFundWorkflowError` (`server/services/fund-workflow-service.ts:259-270`)
  into one helper in `server/lib/idempotent-command.ts` and call it from both
  places. Fund-workflow responses stay byte-identical
  (`tests/unit/services/fund-workflow-transport.test.ts` pins its message).
- No `Expected-Actor-Id` header and no `409 EXPECTED_ACTOR_MISMATCH` (owner Q2).
  The actor is bound into the request hash, so a same-key request from another
  actor gets `409 IDEMPOTENCY_KEY_REUSE`, never another actor's replay.

#### C2 client intent keys

#1584 gives each dialog a per-intent key through `useIdempotencyKey`
(`client/src/hooks/useIdempotencyKey.ts`; call sites `AddDealModal.tsx:94`,
`:137`, `:148`; `AddCompanyDialog.tsx:79`, `:100`, `:104`;
`ImportDealsModal.tsx:129`, `:166`, `:170`). The key lives in a component ref,
so a reload loses it. PR 1b adds the smallest persistence that survives a reload
(owner Q2): an optional scope argument on the same hook, not a new module. The
hook's other callers (`client/src/hooks/useTasks.ts`,
`client/src/hooks/useDecisions.ts`,
`client/src/components/fund-results/WorkspaceContextRail.tsx`) pass no scope and
keep today's behavior.

- **Record.** One `sessionStorage` entry per fund and operation,
  `pending-create:v1:<fundId>:<operation>`, holding
  `{ actorId, key, fingerprint, createdAt }` and parsed with a strict Zod
  schema; a corrupt entry is removed. `actorId` is `user.id` from
  `useAuthSession()` (`client/src/lib/auth-session.ts:41`). `sessionStorage` is
  per tab, so two tabs never share or overwrite an entry; it survives a reload
  but not a tab close. Precedent:
  `client/src/components/lp-reporting/actuals-draft-command.ts:66-94`.
- **Fingerprint is a digest, never the payload.** Each dialog computes
  `await sha256Hash(payload)` (`client/src/lib/hash.ts:25`) inside its async
  mutation function and passes the hex digest to `keyFor`, which stays
  synchronous. The stored fingerprint is 64 characters even for a 1000-row
  import. If two payloads ever shared a digest, the server's request-hash check
  would return `409 IDEMPOTENCY_KEY_REUSE`; a wrong replay is not possible.
- **Write before dispatch.** `keyFor` writes the entry before `apiRequest` is
  called. If the write throws (quota, private mode), the hook keeps the key in
  memory and the request is still sent; only reload survival is lost.
- **Restore.** On open, once the auth session has loaded, read the entry. Remove
  it when its `actorId` differs from the session's. With no session (a 401, or
  the dev fallback) nothing is read or written, and the key stays in memory
  only. A restored entry does not refill the form: the dialog says an earlier
  attempt may already be recorded and invalidates the list query. Submitting the
  same payload (the same form values, or the same import file and mode) produces
  the same digest and reuses the stored key, so the server replays the receipt.
  Any other payload rotates the key as a new intent.
- **Import after a reload.** No rows are stored. The user re-uploads the file,
  and a digest match reuses the key.
- **Definite rejection.** On an attempt with no earlier unknown outcome, a
  received 4xx other than 408, `409 IDEMPOTENCY_RACE_UNRESOLVED`, and
  `409 REQUEST_IN_PROGRESS` is a definite rejection: authorization and rate
  limiting run before the handler, and a handler failure rolls back with no
  receipt. An edit afterwards rotates the key.
- **Unknown outcome.** A network failure, a timeout, 408,
  `409 IDEMPOTENCY_RACE_UNRESOLVED`, `409 REQUEST_IN_PROGRESS`, or a 5xx means
  the server may have committed. The dialog sets one in-memory `uncertain` flag:
  fields and reset are read-only, and the only send action resends the same body
  with the same key (after `Retry-After` for `REQUEST_IN_PROGRESS`). Later 4xx
  responses do not settle it. Only a 2xx (executed or replayed) or
  `409 IDEMPOTENCY_KEY_REUSE` (a receipt already exists under another binding)
  settles it; both clear the entry and invalidate the list query, and the reuse
  case tells the user the item was already recorded. Explicit discard is offered
  after the list refetch, with copy that the item may already exist, and clears
  the entry. Precedent: `useFundDraftSync`'s `uncertain` status
  (`client/src/hooks/useFundDraftSync.ts:169`); do not import its module.
- **Close and logout.** Closing or navigating away keeps an unsettled entry.
  Success, an edit after a definite rejection, key-reuse settlement, and discard
  clear it. `finishLocalLogout` (`client/src/app/app-layout.tsx:195`) removes
  every `pending-create:v1:` entry.
- **Headers.** `{ headers: { 'Idempotency-Key': key } }` as `apiRequest`'s
  fourth argument, as #1584 already does. Only import confirm sends a key, never
  the read-only preview.

Stated ceilings:

- A tab close loses the entry. A resubmit after an unknown outcome in a new tab
  can then create a duplicate.
- After a reload, a replay needs identical form values or the same import file
  and mode.
- A session switched in another tab is not fenced client-side. If actor A's
  uncertain command committed, actor B's same-key retry gets
  `409 IDEMPOTENCY_KEY_REUSE` (already recorded). If it did not commit, the
  retry runs as actor B.

## Implementation notes (PR 1, 2026-09-25)

Branch `feat/f1170-pr1-mutation-error-boundary` from `origin/main` at
`cc91110b5`. Deviations and additions found during implementation and the
four-round Codex code review:

- The reallocation tab no longer sends `allocation_cap_cents`: it has no cap
  editor, and resending the cap captured at selection time let a refreshed
  `expected_version` overwrite a concurrent cap change. Omitted caps are
  preserved by the server `COALESCE`.
- `CompanySelectionTable` reports blank or invalid raw input to the parent
  through a `SelectedCompany.invalidInput` flag, so a stored preview is
  discarded and preview/commit stay disabled until every amount parses.
- A fund switch resets selections, preview, and reason, remounts the selection
  table, and resets both mutation observers, so the previous fund's in-flight
  request cannot pin `isPending` or fire callbacks into the new fund's draft.
  Commit-success cache invalidation runs inside the mutation closure, bound to
  the fund the request was sent to.
- `fetchCurrentAllocations` coerces bigint cents to numbers (pg returns strings
  and the pool has no int8 parser). This also fixed a pre-existing preview
  `totals` string-concatenation defect; the PostgreSQL suite asserts numeric
  totals and audit deltas.
