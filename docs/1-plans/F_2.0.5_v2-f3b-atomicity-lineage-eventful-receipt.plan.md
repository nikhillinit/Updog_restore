## Overview

F3b closes the remaining F3 scope recorded in
`docs/1-plans/F_2.0.2_v2-f2-completion-state-journal-receipt-spine.plan.md`
section 8 ("processEvents moves to F3"), minus what F3a already delivered. Four
deliverables, all engine-internal under `shared/lib/internal-economics/v2/` +
`shared/contracts/internal-economics/`:

1. **Event-stream atomicity** — whole-stream atomic prepare/apply: any refusal
   anywhere in the stream publishes nothing; success hands the fully applied
   staged state to the caller. Supersedes F3a's per-event granularity. This
   deliverable also wires `processCallableCommitment` into the chronology loop —
   it is exported and unit-tested at the keyed base
   (`event-stream-engine-v2.ts:310`) but never invoked by the loop, so callable
   consumption is currently inert in derivation.
2. **Source-lot lineage: unified registry, retention, disclosure** — the input
   contract already carries explicit per-allocation lot references
   (`CashSourceAllocationSchema { lotId, amount }`,
   `internal-economics-input-v2.contract.ts:284-289`). At the keyed base the
   engine keeps TWO lot stores: `state.cashSourceLots` (initialized empty at
   `event-stream-engine-v2.ts:363`, populated only by same-stream
   `csl:${eventId}` / `proceeds:${eventId}` lots) and `state.openingCashLots`
   (opening provenance, `:392+`). Consequence: deployments referencing an
   opening lot id currently refuse as unknown. F3b (a) seeds the unified
   registry from opening lots — a deliberate, ADR-recorded admission of
   opening-lot-funded deployments; (b) stages explicit per-event consumption
   records; (c) retains each investment slice's funding vector; (d) discloses
   per-lot and per-slice lineage in the receipt. No input schema change; nothing
   is inferred from `sourceRef`, `investmentLotId`, owner, `dealId`, or
   `securityId` (F2 section 6 boundary holds).
3. **Eventful receipt** — receipt contract bump
   (`internal-economics-receipt/2.1.0` → `2.2.0`) disclosing the event-derived
   journal (normative double-entry posting matrix below), lineage, and
   staged-state-derived partner capital figures (fixes `calledCapital` currently
   computed from raw input, ignoring staged trackers —
   `liquidity-receipt-builder-v2.ts:260`).
4. **Certification-lane enablement** — `certifyInternalEconomicsDualLaneV2`
   currently refuses unconditionally (`UNSUPPORTED_V2_WHOLE_FUND_CERTIFICATION`,
   `derive-composite-v2.ts:205-221`). F3b enables it: a shared event-capability
   guard runs first (see below), both lanes run, lane-correct manifest
   components are emitted, and the certification success shape becomes real —
   making the named consumer (ratified below) actual rather than claimed.
   `deriveInternalEconomicsV2`'s admission guard is untouched.

## Problem Statement

- No whole-stream atomicity: a refusal mid-stream leaves earlier events applied
  to the caller-visible state (F3a acceptance 8 codified per-event granularity).
  F2 section 8 assigns "rollback or non-mutation on any refusal" to F3;
  unimplemented.
- Callable consumption never executes: the chronology loop omits
  `processCallableCommitment`, so overrun streams derive without refusal and
  receipt `calledCapital` comes from raw input — a valid settled contribution
  can yield `settledCapital > calledCapital` and fail conservation.
- Lineage is validated then discarded: `validateCashSourceAllocations` +
  `applyCashSourceAllocations` enforce per-lot cumulative consumption, but no
  record survives of WHICH event consumed WHAT — the created investment lot
  records only `{lotId, dealId, securityId, costBasis, relievedAmount}`
  (`event-stream-engine-v2.ts:609-617`), expense-event consumption is retained
  nowhere, and opening lots sit outside the validated registry entirely.
- The 2.1.0 receipt journal covers only the opening position; event effects are
  not journal-derived, and the raw-event cash equation misclassifies
  fee/expense-purpose contributions as outflows.
- The receipt manifest hardcodes
  `selectedWaterfall: 'internal-economics-waterfall-deal-by-deal/2.0.1'`
  (`internal-economics-receipt-v2.contract.ts:194`) even for the whole-fund
  lane; `waterfall-whole-fund-v2.ts` exports no version constant.
- Dual-lane certification refuses unconditionally; and because the
  correction/write-off/conversion refusal lives only in the derive path's
  admission guard (`derive-composite-v2.ts:45` region) while the engine switch
  silently skips unmatched kinds, naively enabling certification would silently
  ignore those events instead of refusing them.

## Solution Architecture

### Atomicity (prepare/apply via staged-state return)

`processEventsV2ForTest` restructures to: value-deep-clone the caller's
`EventStreamState` into a staged working state, run the chronology loop against
the stage, and return either the first refusal (caller state byte-untouched) or
the staged state (fully applied). `runLane` (`derive-composite-v2.ts:169-189`)
consumes the returned staged state for waterfalls and receipt building. Design
choice: staged-return over in-place swap — non-mutation is provable by
deep-equality of the caller's original state, matching F3a's before/after
equality test style.

Inside the staged loop, each event's processing order is: capability check (kind
admitted) → `processCallableCommitment` per the event's `callableEffect`
classification (overrun refusal propagates, F3a first-refusal semantics) →
event-specific validation and application.

The clone helper must cover **every** field of `EventStreamState` — at the keyed
base: `cashSourceLots`, `investmentLots`, `callableTrackers`, `partnerLedgers`,
`derivedEvents`, `endingCash` (a mutable `Decimal` reassigned in place,
`:353,:519`), `openingCashLots`, `openingInvestmentSlices`,
`openingEntitlementPools`, `openingJournal`, plus the new staged records below
and any field present at implementation head. Completeness is enforced
structurally: the clone helper is written as an exhaustive per-key construction
over `EventStreamState` (compile-time error on a new un-cloned field,
`satisfies` style), plus a runtime deep-equality/independence test. Shallow
clones of `Map` values are forbidden — tracker/ledger/lot objects clone by
value.

### Unified lot registry + staged event-effect records

`initializeEventStreamState` seeds `cashSourceLots` from
`input.openingState.openingProvenance.cashLots` (id, classification, and
remaining balance carried over; `openingCashLots` retained unchanged for
opening-journal/receipt-opening purposes). This admits opening-lot-funded
deployments that today refuse as unknown — deliberate, tested, ADR-recorded.
Opening lot ids are arbitrary non-empty strings, so collisions with
event-created `csl:`/`proceeds:`/`inv:` ids are possible. Every lot insertion
refuses on id collision — at seeding AND at each event-created lot (replacing
today's unconditional `Map.set` in the processors) — tested for both event
prefixes.

Seeding also forces a waterfall-selection change: both engines currently
identify realization proceeds by `lotId.startsWith('proceeds:')`
(`waterfall-deal-by-deal-v2.ts:82-86`, `waterfall-whole-fund-v2.ts:42-46`), and
deal-by-deal distributes `originalAmount`, ignoring later same-stream
consumption. With arbitrary opening ids in the unified registry, prefix matching
misselects any `proceeds:`-shaped opening id, and `originalAmount`
over-distributes a proceeds lot partially consumed by a later deployment. F3b
switches both engines to select realization lots by the explicit discriminator
pair **`origin === 'event' && sourceKind === 'realization_proceeds'`** (origin
alone is insufficient — `csl:` contribution lots are also event-origin) and
distribute `remainingBalance`. Both waterfall version constants reflect the
behavior change (see version table).

Every allocation application and partner-affecting effect appends a staged
record — consumption records `{eventId, lotId, amountUsd}` (deployment AND
fund-expense consumption) and event-origin partner-effect records
`{origin: 'event', eventId, instant, partnerId, field, amountUsd}` (the
origin-discriminated union in Type Definitions; the distribution arm is appended
at derivation stage) — so the receipt derives per-lot consuming-event lists,
per-slice funding vectors, journal rows, and per-partner vectors entirely from
staged records, never by re-reading raw events. `processDeployment` additionally
stores the validated `cashSourceAllocations` vector on the created investment
lot.

### Eventful receipt (2.2.0) — normative double-entry posting matrix

The balance-forward journal extends from opening-only to event-derived entries,
produced from staged effect records. Accounts: existing `cash`,
`invested_basis`, `opening_unreturned_capital`; new `contributed_capital`,
`realized_gain_loss`, `fund_expenses`, `distributions`. Sign convention: asset
accounts (`cash`, `invested_basis`) carry natural signs; capital/income accounts
(`contributed_capital`, `realized_gain_loss`) are credit-negative;
`fund_expenses` and `distributions` are debit-positive. Every applied event
posts a balanced (zero-sum) entry set, in chronology order, each row carrying
the originating `eventId`:

| Event kind (admitted)                 | Postings (each row sums to zero)                                                                                                                                                                                                                         |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `contribution` (settled, any purpose) | `cash` +amount; `contributed_capital` −amount. Contributions are always cash inflows — including fee/expense-purpose rows (fixes the raw-event cash equation). Callable consumption tracks in `callableTrackers`/partner ledgers, not a journal account. |
| `deployment`                          | `cash` −amount; `invested_basis` +amount. Funding vector recorded on the slice; consumption records staged per allocation.                                                                                                                               |
| `realization`                         | `cash` +proceeds; `invested_basis` −reliefTotal; `realized_gain_loss` +(reliefTotal − proceeds) (credit-negative for a gain; positive for a loss).                                                                                                       |
| `fund_expense_payment`                | `cash` −amount; `fund_expenses` +amount. Consumption records staged per allocation.                                                                                                                                                                      |

**Distribution postings (derivation stage):** the receipt-facing
`TierAllocationV2[]` carries totals only, and `runLane`'s `dealToTier` /
`wholeToTier` conversions (`derive-composite-v2.ts:177-189`) discard
`perPartner` — so F3b defines an internal typed tier-partner vector
(`TierPartnerAllocation { lane, tierKind: V2TierKind, tierOrdinal, partnerId, amountUsd }`),
produced from raw waterfall results **before** tier conversion and passed to
`buildReceipt` alongside (not replacing) the receipt `TierAllocationV2[]`.
Deal-by-deal merges its per-pool results deterministically: pool input order,
then tier ordinal, then `partnerId` lexicographic. This vector drives
distribution postings and derivation-origin partner-effect records; the engines'
aggregate `partnerDistributions` / `totalDistributed` returns serve as
cross-checks only. After the event postings, distribution postings follow: per
tier-partner allocation, `cash` −amount; `distributions` +amount — ordered by
tier then partner, carrying lane/tier/partner provenance in place of `eventId`.
Tier→partner-vector mapping (normative; tier kinds enumerated from
`TierAllocationV2` at implementation head): every tier allocation adds to the
partner's `cumulativeDistributions`; return-of-capital tiers additionally reduce
`unreturnedSettledCashCapital`; preferred-return tiers additionally consume
`accruedPreference`; catch-up and carry tiers post GP-attributed distributions
with no capital/preference effect. Tier totals must reconcile to the receipt's
`fundCashEquation.distributions`.

**ROC overdraw is fail-closed:** both waterfalls apportion return-of-capital
pro-rata by `settledCapital`, not by remaining unreturned capital
(`waterfall-deal-by-deal-v2.ts:99-110`, `waterfall-whole-fund-v2.ts:174-175`),
so a valid opening ledger with unequal settled/unreturned ratios can allocate a
partner more ROC than their `unreturnedSettledCashCapital`. F3b does NOT change
waterfall apportionment (a distribution-economics decision needing its own
consumer-backed authority — recorded as a parked follow-up in the ADR); instead
the partner-vector stage refuses when an ROC effect would drive
`unreturnedSettledCashCapital` negative (reuse
`RECEIPT_CONSERVATION_VIOLATION` + stage `receipt`; AGENT-SAFETY: fail closed,
never invent a priority order). A truth case with unequal opening
settled/unreturned ratios proves the refusal.

**Distribution cash-flow entries:** `CashFlowEntryV2` currently requires
`instant` and `eventId` (`internal-economics-receipt-v2.contract.ts:13-18`) —
unrepresentable for derivation-stage distributions without synthetic ids. The
2.2.0 contract makes cash-flow entries source-discriminated (event arm:
`eventId` + event instant; distribution arm: lane/tierKind/tierOrdinal/ partner
provenance). Normative distribution instant: the maximum event instant in the
stream, or the opening-state instant for an eventless stream — deterministic, no
wall clock; distribution entries order after all event entries.

Invariants: every posting set (event or distribution) sums to zero across all
seven accounts; ending `cash` account balance equals staged `endingCash` minus
distributions; the receipt cash-flow equation and per-partner vectors derive
from staged records plus waterfall distribution results (partner attribution via
partner-effect records), replacing raw-event recomputation. Partner figures
(`calledCapital` and siblings) project from staged
`callableTrackers`/`partnerLedgers` — never from raw input. Conservation checks
reuse `RECEIPT_CONSERVATION_VIOLATION` + stage `receipt` (existing union members
— reuse, don't add).

Receipt mechanics preserved: closed field set, all fields readonly, typed
result-hash preimage = receipt without `resultHash`, canonical-json-sha256,
output-row (100,000) and serialized-byte (16 MiB) limits re-asserted against
journal growth.

### Certification enablement + shared capability guard + lane-correct manifest

The correction/write-off/conversion refusal currently implemented inside the
derive path's admission-guard region (`derive-composite-v2.ts:45`) is extracted
into a shared event-capability guard. `deriveInternalEconomicsV2` keeps
byte-identical behavior (guard called from the same position);
`certifyInternalEconomicsDualLaneV2` becomes: normalize → management-fee guard
(kept) → shared event-capability guard (all three unsupported kinds refuse,
tested) → run **both** lanes via `runLane` → on both-success, return the
certification success shape binding both receipts (existing
`V2DualLaneCertificationResult` success arm); any lane refusal propagates. The
engine loop's own capability check (Solution Architecture, atomicity section)
backstops the same invariant at the loop layer.

The manifest's `selectedWaterfall` becomes lane-correct: new exported
`INTERNAL_ECONOMICS_WATERFALL_WHOLE_FUND_V2_VERSION` minted at 2.2.0 (its
selection behavior changes in F3b), manifest type widened to the two-literal
union, builder selects by lane.

## Technical Considerations

- **Pattern usage**: refusal-first, 6-level precedence, literal byte-exact
  diagnostics, deep-sealed input, closed receipt field set, changed-case
  manifest, before/after mutable-state equality proofs (F1–F3a patterns, ARCHI
  section 8.6).
- **Decimal discipline**: six-decimal strings, Decimal.js only, quantize-once
  (`guard:decimal-string-laundering:check`; AGENT-SAFETY financial invariants).
  `realized_gain_loss` posts are computed from already-quantized staged amounts
  — no independent re-rounding.
- **Refusal taxonomy**: no new refusal families expected — capability and
  callable-overrun refusals already exist; journal/receipt failures reuse
  `RECEIPT_CONSERVATION_VIOLATION` + stage `receipt`. Removing the certification
  refusal deletes one always-on refusal path (deliberate, ADR-recorded). Any
  genuinely new code discovered at RED is a stop-and-plan moment.
- **Behavioral admissions (deliberate, tested, ADR-recorded)**: (a)
  opening-lot-funded deployments become valid (previously refused unknown); (b)
  callable-overrun streams now refuse (previously derived unrefused — callable
  check was inert); (c) certification succeeds for conformant inputs; (d)
  waterfall proceeds selection becomes origin-based and distributes
  `remainingBalance` (fixes latent over-distribution of proceeds lots partially
  consumed by later deployments, and immunizes selection against
  `proceeds:`-shaped opening ids). All change engine-internal/test-only
  behavior; public derivation stays guarded.
- **Classifier**: `financial_calc_relevant=true` → `financial-truth`
  (`npm run phoenix:truth`) feeds CI Gate Status; run `npm run calc-gate`.
- **Edge cases**: empty event stream (staged state equals clone of opening
  state; journal = opening rows only); refusal on first vs last event (both
  prove caller-state deep-equality); opening lot consumed exactly to zero;
  opening-lot overdraw refusal; callable overrun mid-stream (atomic
  non-mutation); multiple events drawing the same lot; same-stream
  `csl:`/`proceeds:` lots consumed by later deployments; opening lot id
  colliding with a later `csl:`/`proceeds:` id (refused at insertion); loss
  realization (positive `realized_gain_loss` post); zero-distribution stream (no
  distribution postings, tier totals zero); receipt limits under maximal journal
  growth.
- **Risk — deferred correction policy**: 2.2.0 journal stays
  correction-agnostic; later admitting policy may force another bump (accepted
  at discovery).
- **Risk — clone cost**: one value-deep state clone per lane per derivation;
  bounded by input limits; `benchmark-v2.test.ts` guards regression.
- **Risk — fixture/hash churn**: regenerated receipt fixtures are byte-pinned;
  prove byte-equivalence with repo-config prettier run inside the repo (F_1.3.4
  gotcha applies to any pinned `.md` artifacts).
