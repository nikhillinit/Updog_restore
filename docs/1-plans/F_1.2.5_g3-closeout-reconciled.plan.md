### 3.1 Queue policy

Add a side-effect-free core in `server/config/queue-runtime-policy.ts`, then
compose/re-export it from `server/config/features.ts`:

```ts
export interface QueueRuntimePolicyEnv {
  NODE_ENV?: 'development' | 'test' | 'staging' | 'production';
  VERCEL?: string;
  VERCEL_ENV?: string;
  ENABLE_QUEUES?: string;
  ENABLE_IN_PROCESS_QUEUE_WORKERS?: string;
  REDIS_URL?: string;
  QUEUE_REDIS_URL?: string;
}

export interface QueueProcessPolicy {
  legacyProviderProducersEnabled: boolean;
  inProcessConsumersEnabled: boolean;
}

export function resolveQueueProcessPolicy(
  cfg: QueueRuntimePolicyEnv
): QueueProcessPolicy;

export function assertQueueRuntimePolicy(cfg: QueueRuntimePolicyEnv): void;

// server/config/features.ts
export interface QueueRuntimePolicy
  extends QueueSystemConfig, QueueProcessPolicy {}

export function getQueueRuntimePolicy(
  cfg?: QueueRuntimePolicyEnv
): QueueRuntimePolicy;
```

Contract:

- `ENABLE_QUEUES=1` controls Redis-backed queue capability, including supported
  route-owned producers.
- `ENABLE_IN_PROCESS_QUEUE_WORKERS=1` requests legacy in-process consumers.
- Only `NODE_ENV=development|test` may enable in-process consumers.
- `legacyProviderProducersEnabled` is true only in local/test. G3 maps no
  simulation, report, backtesting, reserve, pacing, or cohort consumer to
  Railway.
- `NODE_ENV=staging|production` or any Vercel runtime with the flag set throws
  before cache, queue Redis, `Queue`, `QueueEvents`, or `Worker` construction.
- Vercel detection is explicit: `VERCEL=1` or nonempty `VERCEL_ENV`; it never
  relies on `NODE_ENV` alone.
- A missing flag is `0`.
- The core module reads only its argument. It does not import canonical config
  or evaluate `process.env` at module load, preventing dotenv-order and circular
  import bugs.

Add one deep queue-runtime seam in `server/queues/provider-queue-runtime.ts`:

```ts
export interface ProviderQueueRuntime {
  producersEnabled: boolean;
  consumersEnabled: boolean;
  close(): Promise<void>;
}

export async function createProviderQueueRuntime(input: {
  queueRedisUrl: string;
  startConsumers: boolean;
}): Promise<ProviderQueueRuntime>;
```

Callers see one lifecycle object. They do not receive per-queue consumer
toggles.

Each provider-owned queue initializer receives an explicit, non-defaulted
option:

```ts
interface QueueInitializerOptions {
  startConsumer: boolean;
}
```

Extend existing `QUEUE_CATALOG` metadata; do not create a parallel inventory
document:

```ts
export type QueueProductionDisposition =
  | {
      mode: 'railway-worker';

        | 'railway-worker-fund-scenario-calc'

    }
```

Every catalog entry receives one disposition. Generator tests, route-boundary

Local/test producer-only mode creates provider-owned `Queue` resources.

provider queues unavailable. The route-owned fund-scenario producer remains

consumer mode.

```ts
export type ProductionWorkerType = 'fund-scenario-calc' | 'capital-call-status';
```

Production resolution requires:

- `WORKER_TYPE` exactly equals the entrypoint’s expected type.
- `RAILWAY_GIT_COMMIT_SHA` is a 40-character lowercase hexadecimal SHA.
- `RAILWAY_DEPLOYMENT_ID` is non-empty.
- `NODE_ENV=production`.

Local/test code supplies a test identity explicitly to
`createWorkerHealthApp()`; it does not fabricate Railway variables or reuse a
production resolver fallback.

The health app also verifies `getReleaseIdentity().commit === identity.commit`;
a Vercel/generic environment variable contaminating Railway identity therefore
fails closed. The final workflow independently compares returned commit to the
candidate SHA.

## 8. Stop conditions

Stop without improvising when any condition holds:

- refreshed `main` changes a locked boundary
- PR 1 or merged-main CI remains red
- producer-only mode cannot enqueue without constructing a worker
- a production API route can enqueue work for an unowned production consumer
- worker identity resolves to local, missing, malformed, or wrong SHA
- production schema audit reports required unapplied migrations
- timeout/canary/retention values lack adequate measurement or written approval
- Railway inventory differs before mutation
- Vercel or either Railway service cannot prove the exact candidate SHA
- private worker runtime evidence is missing, stale, or replaced by
  control-plane-only workflow output
- a production secret appears in output or evidence
- source changes after matrix freeze
- disposable and tracked matrix output differ
- `vercel_function` or either worker proof is failed/unproven
- any G3-due matrix obligation remains
- Planning-FMV has neither completed repair approval nor explicit re-deferral
- rollback deployment IDs are unavailable
- any step would promote Vercel, dispatch `release-production.yml`, apply
  schema, purge canaries, enable the fund sweep, or begin G5
