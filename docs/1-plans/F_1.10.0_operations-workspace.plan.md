## Overview

Close the Wave H remainder: serve the decision lifecycle and evidence-link
routes (#1290) on the spine F_1.8.0 shipped, add the operations page for
decisions and tasks (#1293) that enlivens the dead `operations` nav entry
F_1.9.0 shipped, and land the idempotency-keyed recompute command that F_1.9.0's
context rail defers to "#1290 or a named follow-on". Both issues are labeled
`activation-blocker`; #1296 (sanitized decision-spine dogfood run) cannot start
until this lands.

## Problem Statement

- `operating_decisions` / `decision_evidence_links` tables, contracts, and
  services shipped in F_1.8.0 (`a972a5f76`), but no HTTP surface exists:
  `server/routes/operating-object-decisions.ts` is missing, and the manifest has
  no decisions entry. Decisions are unreachable from any client.
- F_1.9.0 shipped a permanently disabled `Operations` nav entry
  (`client/src/pages/fund-model-results/workspace-nav.tsx:91-96`,
  `disabledReason: 'Operations workspace not yet available'`) and a
  `QuarterlyReviewPanel` capability gate that reports operating-decision links
  "unavailable until the operating-decision dependency lands". No page renders
  decisions or tasks; `client/src/hooks/useTasks.ts` exists with zero consumers.
- The workspace context rail's "Recompute from latest accepted facts" control is
  disabled with reason `'Recompute requires an idempotency-keyed command'`
  (`client/src/components/fund-results/workspace-context-rail-view-model.ts:401-403`)
  because no such command exists.

## Solution Architecture

Three sequential phases, each independently shippable and gated:

1. **Decisions HTTP surface (#1290)** — one new route module mirroring the
   `operating-object-tasks.ts` idioms, registered through the standard triad
   (manifest + mount impl + policy registry) adjacent to
   `operating-object-tasks` so it lands inside the existing `post_runtime` group
   slices on both surfaces with **no group-boundary edits**. All lifecycle
   writes use `If-Match`/`xmin` (428 missing / 412 stale, minted at the route
   layer); creates and supersessions use `Idempotency-Key` through the shipped
   `runIdempotentCommand` wiring. Every new database-idempotent POST is
   registered in the Railway middleware-exclusion classifier
   (`server/lib/database-backed-idempotency-routes.ts`) so both surfaces apply
   identical request-hash replay semantics.
2. **Operations page (#1293)** — one new flat-file page
   (`fund-model-results-operations.tsx`) adopting the
   `fund-model-results-analysis.tsx` workspace-shell pattern
   (`FundWorkspaceProvider` + `WorkspaceNav` + `WorkspaceContextRail`), new
   decision/evidence hooks beside the existing unused `useTasks.ts`, route
   registration on all three client surfaces (app-route-definitions, app-routes,
   derived governance as `internal-live`), and the one-line nav flip from
   `href: null` to `fundScoped(...)`.
3. **Recompute command** — one idempotency-keyed, team-write-gated POST backed
   by a **durable command record** (one small additive migration): a
   `current_forecast_recompute_commands` table claims the key **before**
   execution (`pending` status, CAS finalization), stores the typed outcome and
   the produced shadow-reconciliation reference plus whether the command
   **created** that row, so same-key replay returns the recorded outcome,
   concurrent duplicates cannot double-execute, and manual runs are
   distinguishable from organic facts-commit runs without misclassifying
   deduplicated organic evidence (#1298 soak floors stay clean). The command
   calls the bounded execution core directly with typed outcomes — **not** the
   fire-and-forget `maybeTriggerCurrentForecastShadow` wrapper, which returns
   `void` and suppresses failures. The rail's recompute control enlivens per
   F_1.9.0 Open Question 3 (role-gated, 403-as-disabled fallback). The
   bridge-amounts read contract is **excluded** (bridge panel keeps its
   disabled-with-reason).

Schema impact: Phases 1-2 need **no migration** —
`0054_operating_decisions_spine.sql` already ships every column, constraint, and
trigger they consume. Phase 3 adds **one additive migration** (next free prefix
`0055_` at plan time — journal tail is idx 55 / tag
`0054_operating_decisions_spine`; re-read `migrations/meta/_journal.json` at
dispatch time regardless, ARCHI §4 rule).

#### 2. `server/services/operating-objects/decision-service.ts` (modify — one behavior)

**Current state**: `recordOutcome` (line 373) checks the `xmin` precondition
first, then rejects any re-record with a 409-class conflict. #1290 AC 5 requires
outcome recording to be "a distinct idempotent operation".

**Modification** — explicit precedence order, natural idempotency, no schema
change:

1. Load the row. If an outcome is already recorded **and** the requested payload
   matches it exactly (`outcome` text and recording actor), return the current
   row as a replay success (route maps to 200) — **before** the `xmin`
   comparison, since a stale ETag on an identical terminal state is still an
   idempotent replay.
2. If an outcome is already recorded and the payload differs, return 409
   (immutability holds; changing an outcome requires a superseding decision, AC
   5 sentence 2). Also independent of `xmin`.
3. If no outcome is recorded, enforce `If-Match`/`xmin` as today: stale -> 412
   `PRECONDITION_FAILED`; fresh -> conditional UPDATE.

Log this semantics adjustment in `DECISIONS.md` (it alters shipped service
behavior).

**Deviations recorded, not implemented** (surface on #1290 at release):

- Amendment text allows outcome on "accepted (or deferred-conditional)"; shipped
  service and the DB CHECK (`operating_decisions_outcome_status_check`) allow
  `accepted|rejected` and reject `deferred`. Keeping shipped+DB semantics —
  honoring the amendment would need a migration and contradicts the CHECK.
  Recorded as a deviation for owner sign-off, not silently changed.
- `listDecisionsForFund` stays unpaginated (internal ~5-user tool; evidence
  links already cap at 100). Ceiling noted in code comment; pagination is a
  follow-on if lists grow.

### Phase 3 — Idempotency-keyed recompute command

#### 8. Migration `0055_current_forecast_recompute_commands.sql` (new, additive)

One durable command table — the claim/replay/provenance store the
fire-and-forget trigger path lacks (`maybeTriggerCurrentForecastShadow` returns
`void`, suppresses failures, and skips silently outside shadow mode;
`substrate_shadow_reconciliations` carries neither idempotency key nor trigger
source):

`current_forecast_recompute_commands`:

- `id` serial PK; `fund_id` FK -> `funds.id`;
  `idempotency_key varchar(128) NOT NULL`; `request_hash varchar(64) NOT NULL`;
- `status varchar(16) NOT NULL` CHECK in (`pending`, `completed`, `failed`,
  `skipped`) — **`pending` is the claim state**, inserted before execution (see
  item 9 for the claim protocol);
- `failure_code varchar(64) NULL` — **sanitized stable public code only**
  (`execution_timeout`, `execution_error`, `mode_ineligible`, `stale_pending`);
  raw exception text never persists here and never reaches the browser — it goes
  to server logs with the command id;
- `shadow_reconciliation_id` nullable FK -> the shadow-reconciliation ledger row
  the run resolved to;
- `created_reconciliation boolean NOT NULL DEFAULT false` — whether this
  command's execution **inserted** the reconciliation row, as opposed to
  deduplicating onto one that already existed (the shadow writer inserts with
  `ON CONFLICT DO NOTHING`, so a manual run can resolve to a pre-existing
  organic row — that row stays organic);
- `started_at timestamptz NOT NULL DEFAULT now()`;
  `finalized_at timestamptz NULL`; `created_by integer NULL` FK -> `users.id`.
- Unique `(fund_id, idempotency_key)`.
- **Terminal-state coupling CHECKs**: `completed` requires
  `shadow_reconciliation_id IS NOT NULL AND failure_code IS NULL`; `failed`
  requires `failure_code IS NOT NULL AND shadow_reconciliation_id IS NULL`;
  `skipped` and `pending` require both NULL; every non-`pending` status requires
  `finalized_at IS NOT NULL`, `pending` requires it NULL; and
  `NOT created_reconciliation OR (status = 'completed' AND shadow_reconciliation_id IS NOT NULL)`
  — the created flag is legal only on a completed row that names its
  reconciliation.

Additive and replay-safe, idempotent preflight per house style. Drizzle table in
a new sibling schema file with the `unique()`-not-`uniqueIndex()` FK-target rule
observed.

**Provenance model**: organic facts-commit runs create no command row. Soak
tooling (#1298 organic floor) excludes a reconciliation row **only when a
command row references it with `created_reconciliation = true`** — a manual run
that deduplicated onto an existing organic observation leaves that row counted
as organic. No column change to the existing ledger.

#### 9. Recompute service + route (one new service function, one route)

`server/services/current-forecast-shadow-trigger.ts` (modify): export a new
`runManualCurrentForecastRecompute({ fundId, idempotencyKey, actorId })` that
reuses the bounded execution core (mode resolution, facts lookup, plan
resolution, receipt get-or-create, replay) but with **claim-first command
semantics** (the generic `runIdempotentCommand` primitive treats row insertion
as completed work, so it cannot represent in-flight execution — this command
manages its own row lifecycle):

1. **Claim**:
   `INSERT ... (status='pending') ON CONFLICT (fund_id, idempotency_key) DO NOTHING`.
   If the insert won, this request owns execution. If not, read the existing
   row: request-hash mismatch -> 409 `IDEMPOTENCY_KEY_REUSE` (same contract as
   `runIdempotentCommand`); terminal status -> return it as a replay; `pending`
   -> see stale check.
2. **In-flight duplicate**: a `pending` row younger than the staleness bound
   returns 409 `RECOMPUTE_IN_FLIGHT` — no waiting. (Deviation from "bounded
   duplicate waiting": a 1-click internal UI with ~5 users retries trivially,
   and the rail disables its button while awaiting the readback; a wait loop
   buys nothing but complexity.)
3. **Stale-pending recovery**: a `pending` row older than **90s** (3x the
   execution deadline) is presumed crashed; CAS it to `failed` / `stale_pending`
   (`UPDATE ... WHERE id = ? AND status = 'pending'`) and return that outcome. A
   fresh attempt needs a fresh key.
4. **Execute** with the deadline **pinned at 30s** — the trigger's existing
   default (`current-forecast-shadow-trigger.ts:31`); the separate 5s
   failure-persistence deadline is unchanged. Typed outcomes, no suppression:
   `completed`, `failed` (sanitized `failure_code`; raw error to server logs),
   `skipped` (fund mode ineligible — explicit, never a silent no-op). **Writer
   change (owning file: `server/services/current-forecast-shadow-service.ts`,
   persist path around line 221)**: the reconciliation writer currently returns
   `Promise<void>` and inserts with `ON CONFLICT DO NOTHING`, so neither the
   inserted id nor the dedup target is observable. Change it to
   `INSERT ... ON CONFLICT DO NOTHING RETURNING id`; when no row returns,
   `SELECT` the conflicting row by the applicable unique key; return
   `{ id, created }`. Existing organic callers may ignore the return value
   (backward compatible); the manual path consumes it for
   `shadow_reconciliation_id` + `created_reconciliation`.
5. **Finalize atomically under an ownership fence covering every execution
   write**: the manual path threads **one transaction** through the entire
   execution — `runCurrentForecastV2` (whose fund-snapshot insert at
   `current-forecast-v2-service.ts:302` must ride the same transaction; it takes
   a database handle per the house DI pattern — if it cannot on inspection, the
   manual path constructs a transaction-scoped service), the reconciliation
   writer above, and command finalization — with the CAS finalize
   (`UPDATE ... SET status/.../finalized_at WHERE id = ? AND status = 'pending'`)
   as the **final statement** (claim-last analog of the house guarded-CTE
   pattern). A lost CAS (0 rows: the timeout handler or stale-recovery already
   finalized `failed`) **aborts the whole transaction**, so a revoked owner
   persists nothing — no snapshot, no reconciliation row, no provenance flag.
   The `Promise.race` timeout (`current-forecast-shadow-trigger.ts:247-266`)
   leaving work running is thereby harmless: whichever CAS wins defines the
   recorded outcome, and the loser's writes roll back. **Candidate-reference
   creation is suppressed for manual runs** — the post-reconciliation reference
   write (`current-forecast-shadow-service.ts:313`, default writer on the global
   DB) belongs to the organic activation-evidence pipeline; a manual recompute
   is an observation refresh and must not mint candidate references (this also
   removes the one write the fence could not otherwise capture). Receipt
   get-or-create is idempotent shared state used identically by the organic path
   and carries no provenance — benign if it lands before revocation. Crash after
   execution but before finalization is bounded by the same stale-pending
   recovery.

A real concurrent PostgreSQL test (testcontainers) drives two same-key requests
through the claim path and asserts exactly one execution.

`server/routes/current-forecast.ts` (modify): add

## Technical Considerations

- **Pattern usage**: tasks-family route idioms (ARCHI §3 + shipped
  `operating-object-tasks.ts`); workspace shell pattern from
  `fund-model-results-analysis.tsx`; kpi-observations policy-entry shape.
- **Mount-group integrity**: both insertions are adjacent to existing ids inside
  `post_runtime` slices; `sliceRouteOrder` throws on order violations and the
  impl record is `satisfies`-checked, so a missed entry is a compile or test
  failure, not a silent 404.
- **Idempotency + locking**: creates/supersessions/evidence-links via
  `runIdempotentCommand` (shipped); transitions via `If-Match`/xmin (shipped);
  outcome replay precedence per Phase 1 item 2; recompute via the claim-first
  command table (own lifecycle — `runIdempotentCommand` cannot represent
  in-flight state). All four database-idempotent POST patterns registered in the
  middleware-exclusion classifier so Railway and Vercel replay identically by
  request hash.
- **Soak-evidence hygiene**: manual provenance excludes only reconciliation rows
  a command **created** (`created_reconciliation = true`) — dedup onto a
  pre-existing organic row leaves organic evidence intact. Hard requirement, not
  a nicety.
- **Failure sanitization**: `failure_code` is a closed public vocabulary; raw
  exceptions live only in server logs keyed by command id.
- **No financial mutation**: decision acceptance changes no ledger, plan,
  forecast, reserve, or economics state (AC 3). The recompute command runs a
  shadow execution — it writes shadow/receipt/command state only, same class as
  the existing facts-commit trigger, and cannot touch served results
  pre-activation (one-way latch untouched).
- **Edge cases**: superseding an already-superseded decision (409 via partial
  unique index); transition on superseded predecessor (blocked by lifecycle
  trigger); outcome on deferred (409 + DB CHECK); cross-fund evidence target
  (404, unrepresentable at DB); null actor on outcome (403); stale xmin after
  concurrent edit (412 + client refresh prompt); fund-scope mismatch on page
  entry (StateCard, no data render); recompute on shadow-ineligible fund (typed
  `skipped`); recompute execution timeout at 30s (typed `failed`, command row
  finalized); timed-out execution completing late (fenced transaction loses the
  CAS and rolls back — no orphan snapshot, reconciliation row, or provenance
  flag); manual run never creates a candidate reference (suppressed — organic
  pipeline only); concurrent same-key recompute (one executes, other 409
  in-flight); crashed pending command (stale-recovery to
  `failed`/`stale_pending` after 90s); same-key replay after failure (returns
  recorded `failed`, does not re-execute — fresh attempt needs a fresh key);
  manual run deduplicating onto an existing organic reconciliation row
  (`created_reconciliation = false`, row stays organic).
- **Preact prod bundle**: page + hooks use existing React APIs already proven
  preact/compat-safe on sibling pages; no new React-specific libraries.
