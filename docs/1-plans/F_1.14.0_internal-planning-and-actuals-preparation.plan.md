# Internal Planning and Actuals Preparation Implementation Plan

## Overview

Governing policy:
`docs/governance/solo-internal-change-and-production-policy.md`, resolved from
protected `origin/main` before any governed action. This plan does not replace
its authority or evidence requirements.

Deliver a usable internal workflow while Fund I records remain incomplete: prove
existing actuals behavior with isolated synthetic inputs, explain missing
evidence without losing preparation work, and exercise supported hypothetical
scenario comparisons. Reuse existing imports, revisions, publication,
restatement, consumer contracts, and scenario services. Recovery requirements
and C-series specifications proceed in parallel without becoming prerequisites
for this internal milestone.

The owner selected this bounded scope on September 9, 2026. Proposed plan
version **F_1.14.0** is an additive minor continuation of F_1.13.0; it does not
change package version `1.6.0` or announce a release. This plan records the
authorized bounded local implementation; it does not approve C specifications,
change sequencing policy, or authorize release or production actions.

## Problem Statement

The attached guidance separates software correctness, assumption-based planning,
and verified fund reporting. Source inspection supports that separation, but
reveals narrower engineering gaps than a new end-to-end product would imply:

- Correction, ambiguous commit, duplicate submission, stale basis, disabled
  publication, and incomplete drafts already have substantial tests. The main
  browser lifecycle stubs HTTP responses; a real connected predecessor exists on
  an unmerged branch and needs integration with the newer draft/restatement
  behavior.
- Actuals readback displays raw unavailable codes and aggregate actionability,
  but omits existing per-consumer acceptance/refusal explanations.
- Source-pinned allocation scenarios preserve inputs, but some displayed knobs
  are not consumed by the economics engine. Saving different assumptions is not
  proof of different modeled economic outcomes.
- PR #1493 already added recovery collectors. Remaining work concerns producer
  contracts, authenticated evidence binding, retention definitions, and final
  admission; rebuilding collectors would duplicate work.

## Verification lifecycle repair amendment

The connected verification reproduced a referenced WebSocket heartbeat remaining
alive after its HTTP server closed. This amendment includes the bounded runtime
repair in F_1.14.0: `server/websocket/index.ts` captures each HTTP server's own
WebSocket pair and disposes that pair on its close event. Explicit cleanup remains
idempotent; closing one server must not dispose another server's pair. Existing
WebSocket constructors, authorization, subscriptions, and financial behavior do
not change. The source inventory must fingerprint the repaired implementation.

The four additional core files are `server/websocket/index.ts`,
`tests/unit/websocket/portfolio-metrics.test.ts`,
`tests/unit/websocket/websocket-index.test.ts`, and
`tests/unit/server/connected-actuals-demo-cleanup.test.ts`. The existing connected
helper also closes a created server when listen fails, preserves the primary
failure together with cleanup failures, and restores the caller's environment.

Acceptance requires a destroyed heartbeat after normal and never-listened HTTP
closure, per-server ownership and repeated-cleanup assertions, plus a focused
connected-helper failure test proving cleanup attempts, combined error reporting,
and environment restoration. The connected browser stories must still pass after
the helper repair. These assertions do not certify forced process termination,
startup rejection before a server handle is returned, or shutdown with active
clients. This is not a general shutdown manager or production readiness evidence.
