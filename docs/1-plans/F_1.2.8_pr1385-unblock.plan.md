## Solution Architecture

### Integration strategy: merge `main` into the branch (not rebase)

`scripts/release/verify-plan-approval.mjs` (on the branch) enforces that the
approved base head is an **ancestor** of the live PR head. A merge commit of
`origin/main` into `feat/child-f-g4-readiness` preserves that ancestry, so the
existing PLAN-APPROVAL-V2 record can remain valid. A rebase rewrites all 73
commits, invalidates V2 by design, and replays 9 conflicting files across the
history. The PR will terminally land as a squash merge, so branch-internal merge
commits do not pollute `main` history.

**Stated deviation:** the hardening plan's Task 0 Step 4 anticipated "Task 5
rebase requires new approval". Choosing merge-over-rebase is a deliberate
deviation whose purpose is continuity of the approval chain, not bypassing it —
the release owner ratifies this deviation by approving this plan (TRIP Step 4).
The check is empirical either way:

- Run the verifier at the **current** head before integrating (full command,
  from `.worktrees/child-f`; requires `GH_TOKEN` or `GITHUB_TOKEN`):

  ```bash
  GH_TOKEN="$(gh auth token)" node scripts/release/verify-plan-approval.mjs \
    --repo nikhillinit/Updog_restore \
    --pr 1385 \
    --plan-path docs/superpowers/plans/2026-08-11-pr-1385-release-gate-hardening.md \
    --approver-login nikhillinit
  ```

  If V2 is already invalid (e.g. a plan-file edit since `089bfbdb`), the merge
  premise collapses; fall back to **rebase + approval refresh** (below).

- Run the same command again after the merge push. If the verifier rejects the
  merged head for any reason, perform the same approval refresh.

**Approval-refresh protocol (FAIL path only):** an ordinary merge commit
descends from the approved base, so the merge path itself requires no refresh.
If refresh is required (rebase fallback, or verifier FAIL for another reason), a
comment swap alone cannot pass: the verifier also binds approval to a matching
PR review and check-run at the new head (`verify-plan-approval.mjs:1041-1059`)
and requires `CI Gate Status` success there (`:289-297`), and it accepts only
the literal `PLAN-APPROVAL-V2` marker with exactly one applicable, unedited
record. Use the hardening plan's owner-audited **gate-refresh protocol
verbatim**
(`docs/superpowers/plans/2026-08-11-pr-1385-release-gate-hardening.md:581-599`):

1. run current verifier, record why refresh is required;
2. remove `requires-plan-approval` label before the invalidating push;
3. push the exact new head; require `CI Gate Status` success with
   `plan-approval` skipped (label absent);
4. repeat Task 0 Steps 5-7, binding new review/request/approval to that exact
   bootstrap check-run ID;
5. reapply `requires-plan-approval`; the `labeled` trigger reruns CI at the same
   head requiring `plan-approval=success`;
6. require a second exact-head `CI Gate Status` success, then rerun the verifier
   with `--require-exact-head` before any implementation edit.

If the head changes mid-protocol, restart it. Never remove the label to merge.

**Digest safety:** the digest-bound plan file
`docs/superpowers/plans/2026-08-11-pr-1385-release-gate-hardening.md` is tracked
on the branch and absent from `origin/main`'s tree, so the merge cannot alter it
and the recorded `plan_sha256` survives.

## Technical Considerations

- **Pattern usage:** integration-only change — no app code, no route/schema
  changes, so the makeApp/registerRoutes dual-surface and manifest rules of
  ARCHI.md §3 are untouched. Parity suites still run as regression insurance.
- **Approval integrity:** the only file whose bytes matter to the approval
  digest is the hardening plan doc; it is untouchable in every phase.
- **Workflow YAML fragility:** actionlint after every `ci-unified.yml` edit;
  zero-jobs failure mode is silent in review and fatal in CI.
- **Worktree discipline:** all branch work in `.worktrees/child-f`; its
  `node_modules` state should be checked before running suites (managed
  worktrees can ship empty `node_modules`; `npm ci` ~10s).
- **Edge cases:** if `main` advances again mid-integration, re-run the
  merge-tree conflict scan before resolving — the 9-file list is point-in-time.
  If the PR head moves (another actor), stop and re-verify approval ancestry
  first.
