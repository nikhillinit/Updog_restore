**Governing policy:**
`docs/governance/solo-internal-change-and-production-policy.md` (resolve from
`origin/main`). This plan grants no merge, production, or release authority.
Merge, the baseline capture, each release dispatch, every production SQL
session, and every resubmission remain separate owner actions.

## Overview

Canonical web still serves `068430726` (last successful full release,
2026-07-30). Both workers run `55c9a6a2b` (#1611 phase A, run 36842321386). The
two phase B runs at `55c9a6a2b` failed at
`Authenticated Staged Production Smoke` before promotion (Completed before this
plan, items 2 and 3). Production therefore still drops canonical-web reserve
deliveries silently (F_1.21.0 "Problem Statement").

`main` has moved eight commits past `55c9a6a2b`, including worker code (#1623,
F_1.21.0 Phase 1), so the release takes the two-phase route in
`docs/workflows/PRODUCTION_SCRIPTS.md` ("Railway worker deploy stage").

A preflight on 2026-10-08 found that every push run of `CI Unified` since
`95b8ea88a` (#1617) failed `Secret Scan / Blocking Gitleaks Scan`, and with it
`CI Gate Status`. #1625 fixed the allowlist (item 6) and carried the first
revision of this plan as the release vehicle, but it merged without a successful
baseline capture, as #1602 did in F_1.18.1. A primary release needs
`baseline_evidence_b64` from a `capture-release-baseline.yml` run that binds the
vehicle PR's frozen head and refuses unless live `main` still equals the
pre-merge SHA. So neither `fd1e94090` (#1625) nor `b398d316b` (#1626) can be
released in primary mode.

This PR is the release vehicle instead. It changes only this plan and one
`CHANGELOG.md` note: no runtime code, dependencies, schema, provider
configuration, or workflows. The owner captures a new baseline against this PR's
frozen head and this plan's hash before merge, then releases its merge commit.

## Release sequence

Each numbered step is a separate owner action. On any refusal, stop and re-plan;
never re-run a failed release attempt (`GITHUB_RUN_ATTEMPT` must be 1).

Optional (F_1.21.0 Phase 0): before step 5, the owner may run the F_1.21.0
appendix SQL for an early measure of the exposure. Step 10 is authoritative: it
covers the same window from `2026-08-09T00:00:00Z` through phase B, its rows
form the resubmission list, and its check reads each event's queue time, so it
needs no pre-release baseline. Skipping the early run loses no data; the query
is read-only and the tables keep their rows. The owner chose on 2026-10-08 to
skip it.

1. Freeze this PR's head once `CI Gate Status` is green. Any later push
   invalidates the baseline. The PR stays in draft until step 2 succeeds, so it
   cannot merge early.
2. Dispatch `capture-release-baseline.yml` on `main` with `baseline_main_sha`
   equal to live `main` (`b398d316be1b813eb636f5edc7200d6591899386` when this
   plan was written), the frozen PR head, this PR's number, `plan_path` equal to
   this file's path, and `plan_sha256` equal to this file's SHA-256 at the
   frozen head. The workflow refuses unless its own commit, live `main`, and
   `baseline_main_sha` are equal. If `main` moves first, rebase (branch
   protection requires an up-to-date branch), re-freeze, and recompute
   `plan_sha256`. `main` must not move between this step and the merge.
3. Only after step 2 succeeds, merge this PR (squash). The merge commit becomes
   the release SHA.
4. Wait for the push run of `CI Unified` on the merge commit to conclude
   `success`, including `Secret Scan / Blocking Gitleaks Scan` (full history)
   and `CI Gate Status`. If the secret scan fails, stop: the merge commit cannot
   release. Then dispatch full CI on `main` at the merge commit:
   `ci-unified.yml` with `run_full_suite=true` and `enable_security=true`, and
   `testcontainers-ci.yml`, which now includes
   `tests/integration/reserve-delivery-exposure.pg.test.ts`. G3 requires every
   locked context in `scripts/release/verify-exact-sha-checks.mjs` to succeed on
   the exact release SHA; a push run skips path-filtered lanes, and a failed run
   taints its contexts. Wait for both runs to succeed, then replay the G3
   aggregate step read-only.
5. Phase A: dispatch `release-production.yml` with `mode=railway-workers-only`,
   `release_mode=primary`, `expected_sha` equal to the merge commit, `pr_number`
   equal to this PR's number, the baseline binding from step 2, and the schema
   apply identity from item 1 (`schema_precursor_sha` is
   `7ee0210faeeb8074c53bfb821b2dd49c899b55be`). `scripts/deploy-production.ps1`
   builds `baseline_evidence_b64` in both modes and `operator_evidence_b64` only
   in `full` mode (step 7). Before dispatch, replay the preflight checks
   read-only in a fresh clone of the release commit with full history, matching
   the workflow checkout (`fetch-depth: 0`), not in a development worktree. The
   last `baseline-policy-preflight` step prints the F_1.22.0 exposure counts
   (item 7). Read them; they cannot fail the run, and step 10 stays
   authoritative.
6. After phase A verifies, in the operator's ADR-082 `railway ssh` data-plane
   session:
   - capture `/health` and `/ready` from both workers and encode them with
     `node scripts/release/operator-evidence-bundle.mjs encode`;
   - from the `fund-scenario-calc` worker only, capture `GET /metrics` and
     `GET /stats` on the same port, and record each reading with the worker
     deployment ID it came from (counters reset on restart). This capture is an
     owner note beside the bundle, not part of it (F_1.21.0 "Collecting the
     worker signal").

   Apply the reading rule (ADR-106; F_1.21.0 "Release coupling"):
   `fund_scenario_unmatched_deliveries_total{reason="missing_run"}` or
   `{reason="identity_mismatch"}` above zero is a new defect, so stop and open
   it before phase B. `{reason="legacy_no_run"}` is old-producer exposure; copy
   the job IDs from its `warn` lines to the resubmission list. Capture the
   probes only when ready to dispatch step 7 and approve its gates promptly: G4
   accepts probes at most 120 minutes old and within 15 minutes of each other,
   and the check before `Promote` applies the same age limit.

7. Phase B: dispatch `release-production.yml` with `mode=full`, the same inputs,
   and `operator_evidence_b64`. The deploy job takes the exact-SHA reuse path.
8. Confirm the step 7 run concluded `success` on attempt 1, including
   `post-promotion-smoke` and `evidence-finalizer`, and uploaded the release
   evidence manifest. Then read `/api/version` and confirm the promoted SHA
   equals the merge commit. Only then lift the ADR-103 migration freeze, which
   is still in force because F_1.18.1 never completed its step 8.
9. Capture `GET /metrics` and `GET /stats` from the `fund-scenario-calc` worker
   again with its deployment ID and apply the step 6 reading rule. Phase B
   reuses the phase A deployment, so both readings come from one process unless
   it restarted. `legacy_no_run` keeps rising until old-producer jobs queued
   before promotion drain, then stops.
10. Run the F_1.21.0 appendix SQL ("Appendix: Exposure reconciliation") as a
    role that can read both tables. Expect no `no_run_drop_candidate` or
    `repeat_job_id` row queued after the step 7 promotion time. Merge its
    candidate rows into the resubmission list.
11. Resubmit each listed scenario set through the ordinary `calculate-reserve`
    command. Confirm that the run each resubmission returns reaches `completed`
    with a snapshot; a resubmission can reuse another command's `queued` or
    `running` run (F_1.21.0 "Post-release recovery").

The release is done only when all four hold: the canonical host serves the
release SHA, both workers run it and pass `/health` and `/ready`, the
post-promotion checks passed, and the release evidence manifest was built and
uploaded on attempt 1. The F_1.21.0 incident is closed only when steps 9 to 11
also hold. Anything short of that is partial progress.

If phase B promotes and a later job fails, production already runs the merge
commit. Keep the freeze on and stop; the owner chooses between a rollback-mode
release and a forward fix.
