# Governance Right-Sizing Implementation Plan

## Overview

Right-size the governance infrastructure for a solo-developer internal tool
serving ~5 users. The existing governance surface accumulated enterprise-grade
ceremony (plan-approval jobs, ratification fragments, multi-step manifest
versioning) that adds friction without proportional safety for this scale.
Consolidate into 2 PRs: one for CI/classifier improvements and release-proof
fixes, one for ceremony retirement and workflow hardening.

## Problem Statement

1. **Release Proof secret scoping**: `VERCEL_*` secrets are Production-env-only,
   so standalone `release-proof.yml` diagnostic dispatch structurally fails.
   Owner waived this precondition for PR #1385 — the workaround must become a
   fix.
2. **Missing financial-truth CI gate**: changes touching calculation paths have
   no dedicated `phoenix:truth` CI job; the gate relies on the developer
   remembering to run it locally.
3. **Dead ceremony overhead**: plan-approval verification (embedded step in
   evidence-finalizer at release-production.yml:2257-2296) and
   `policy-ratification` (release-production.yml:1316+), their verifier scripts
   (1,409 + 307 lines), approval templates, fragment builders, and manifest
   consumers add ~400 lines of workflow YAML and ~1,700 lines of scripts for a
   solo-owner repo where the approval authority is always the same person
   dispatching the workflow.
4. **Binary classifier gap**: the current classifier
   (`scripts/ci/classify-change-paths.mjs`) outputs only `autoDocsOnly` /
   `heavyCiRelevant`. Financial calculation changes get the same CI treatment as
   a CSS tweak — no `phoenix:truth` trigger.
5. **Manifest format coupling**: the manifest builder carries plan-approval and
   ratification fields that will become dead branches after ceremony retirement.

## Solution Architecture

**Two PRs instead of five.** The original 5-PR sequence existed to manage
rollback dependencies between ceremony replacement and ceremony removal. For a
solo-dev internal tool, the remaining controls (exact-SHA verification via
`verify-exact-sha-checks.mjs`, CI Gate Status as sole merge gate) are sufficient
— the ceremonies can be removed directly. One actor check remains after ceremony
retirement: `capture-release-recovery-context.mjs:687`
(`if (run?.actor?.login !== owner) fail(...)`) validates baseline-run ownership
and is retained. All other actor checks (plan-approval, ratification) are
removed; dispatch permission serves as authorization for a sole-owner repo.
NOTE: the `environment: Production` required-reviewer click in
`release-proof.yml` (lines 111, 220) is the same sole-owner tautology. Deferred
to a future PR pending deterministic preflight as replacement — this plan does
not remove it.

- **PR1 — CI Hardening**: financial risk predicate in classifier,
  `financial-truth` CI job, release-proof secret fix, fail-closed preflight.
- **PR2 — Ceremony Retirement + Workflow Tightening**: remove plan-approval and
  ratification jobs/scripts/consumers, simplify manifest to single version,
  tighten schema-reconcile routing, harden canary recovery validation.

## Evidence Gate (between PR1 and PR2)

After PR1 merges:

1. Refresh exact `origin/main`.
2. Owner separately authorizes and dispatches `prod-schema-reconcile` in audit
   mode using the six pinned historical inputs (see catch-up evidence above).
3. Require exact checkout, historical receipt/artifact verification, every
   current manifest `SKIP`, and catch-up-aware schema fragment output.
4. Record audit run, attempt, source SHA, result, and fragment artifact
   identity.
5. Cut PR2 from that exact audited SHA. If `main` advances before PR2 merges,
   re-audit at the new SHA before merge.

## Pre-Mortem

1. **Token exists but lacks endpoint scope** — first certifying run fails;
   verify every exact branch-protection/workflow/run/job/check-run endpoint
   before acceptance.
2. **Fragment/manifest retains legacy artifact assumption** — catch-up fixture
   must pass receipt-to-manifest integration before PR1 merge.
3. **Audit becomes stale before PR2** — require audited-base equality and
   re-audit on any main advancement between PR1 merge and PR2 merge.

## Technical Considerations

- **Pattern Usage**: classifier extension follows existing `classify()` pure-
  function pattern. CI job follows existing conditional-job-with-gate pattern
  used by `neon-lane`, `security-tests`, etc.
- **Backward Compatibility**: classifier adds new output fields only — no
  existing consumer breaks. Manifest removes fields that had one internal
  consumer (the release-production workflow itself).
- **Rollback**: PR1 whole-revert safe. PR2 whole-revert restores ceremony jobs
  and success invariants; any manifests produced with null approval/ratification
  during the PR2 window would fail the restored success validator. Mitigation: a
  revert also restores the builder producing non-null values, so the NEXT
  release manifest passes. Previously-emitted null manifests are diagnostic
  artifacts only (not consumed by downstream gates). PRs are independent — PR2
  does not depend on PR1 being merged first.
- **Edge Cases**: classifier uses exclusion-based approach for mixed roots
  (`server/services/**`, `client/src/lib/**`, `shared/schemas/**`) — new files
  trigger the gate by default. Non-financial directories must be explicitly
  excluded and justified. Tripwire regression test catches financial files that
  named-path roots miss.
