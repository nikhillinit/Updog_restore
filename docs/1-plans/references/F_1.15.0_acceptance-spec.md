# F_1.15.0 Capital-Planning Feasibility Acceptance Specification — Revision 3

## Purpose and evidence boundary

This companion defines implementation acceptance for
[F_1.15.0 Capital-Planning Feasibility Workflow](../F_1.15.0_capital-planning-feasibility-workflow.plan.md).
It contains expected behavior and fixtures, not test code or proof that
implementation exists.

Synthetic non-production fixtures may prove isolated functionality. They do not
prove real-config readiness, benchmark validity, production deployment, actuals
admission, or activation. Record those claims separately as `PASS`, `PARTIAL`,
`BLOCKED`, `DEFERRED`, `NOT_COLLECTED`, or `NOT_MEASURED`.

## Normative sources and precedence

1. Revision 3 main plan governs F_1.15.0 implementation.
2. [ADR-070](../../adr/ADR-070-cashless-gp-commitments-and-fee-waivers.md)
   governs cashless GP commitments and fee-basis separation.
3. [Plan A source](F_1.15.0_plan-A-source.md) supplies CP-001–CP-054 fixtures
   and original formulas unless revision 3 explicitly supersedes GP/capacity
   wording.
4. Current repository contracts/services determine actual integration seams.

Plan A CP-001–CP-054 remain required. Revision-3 GP cases below supersede
conflicting historical assumptions in CP-035 and any text treating total
commitments as entirely cash-funded without the ADR-070 deemed deduction.
CP-032/CP-035-style zero-deemed cases remain valid when resolved `G * r = 0`.

## Test rules

1. Run financial tests with `TZ=UTC`.
2. Use Decimal/fixed-string money and ratio values. Never route money through
   JavaScript `Number` after input normalization.
3. Freeze source/config IDs, versions, method versions, clocks, UUIDs, and
   hashes in deterministic fixtures.
4. Record expected values before implementation and compare full precision
   before display rounding.
5. Invalid/unsupported/incomplete cases assert exact reason, exact field path,
   dependent unavailable outputs, and zero run/snapshot writes where specified.
6. Expected-count and entered-count outputs always carry distinct labels and
   count-basis metadata.
7. Visible and copied output share a canonical structured model; compare all
   values/labels/statuses/disclosures after allowed whitespace normalization.

## Exact disclosures

The first three blocks must remain byte-for-byte equal to the Plan A source:

> This schedule assumes capital can be called as needed. It does not model
> current cash availability or capital-call execution.

> Available construction capital excludes recycling and exit proceeds; fee
> offsets are not modeled. Feasibility is evaluated under these assumptions.

> Aggregate preference forecast based on entered ownership and summarized
> preference terms. It does not reproduce a security-level cap table or legal
> distribution waterfall.

Revision 3 adds this exact fourth block:

> Available construction capital deducts the GP deemed contribution under
> ADR-070. An omitted funded-from-fees fraction is treated as zero for this
> calculation without changing the saved source. The fraction does not reduce
> the management-fee basis or fee amount.

Snapshot, visible UI, comparison, and copied memo tests must use these exact
bytes where applicable.

## Revision-3 GP deemed-contribution fixtures

All monetary inputs in GP-R3 fixtures use one explicit normalized synthetic
unit. Unless overridden:

- total commitments `C = 100`;
- resolved contractual GP commitment `G = 10`;
- effective fee-funded fraction `r = 0.4`;
- supported lifetime management fees `F = 10`;
- supported expenses `E = 2`;
- GP deemed contribution `D_gp = 4`;
- available construction capital `A = 84`;
- committed-capital fee population/basis = `100`.

The fee amount stays `10`; it is not reduced to `6` and its basis is not reduced
to `96` or `90` by `r` or `D_gp`.

### Valid identity and boundary cases

- **GP-R3-001 Base deemed contribution.** Inputs above produce `D_gp = 4`,
  `A = 84`, fee basis `100`, fee amount `10`, expenses `2`, and exact fourth
  disclosure.
- **GP-R3-002 Explicit zero fraction.** `G = 10`, explicit `r = 0` produces
  deemed `0` and `A = 88`; provenance says source explicit zero/effective zero.
- **GP-R3-003 Omitted fraction.** `G = 10`, `fundedFromFeesPct` absent produces
  deemed `0` and `A = 88`; provenance says source absent/effective zero/default
  `ADR_070_MISSING_FRACTION_ZERO`. Parsed source and source hash remain
  byte-stable; no default is written back.
- **GP-R3-004 Fully deemed.** `G = 10`, `r = 1` produces deemed `10` and
  `A = 78`; fee basis remains `100` and fee amount remains `10`.
- **GP-R3-005 Zero GP, positive fraction.** Explicit `G = 0`, `r = 0.5` produces
  deemed `0` and `A = 88`; no invented contradiction or unsupported result.
- **GP-R3-006 No GP amount and zero/default fraction.** All GP amount sources
  absent with explicit or default `r = 0` resolves `G = 0`, deemed `0`, and
  `A = 88`; provenance records zero fallback without claiming observed all-cash
  GP treatment.
- **GP-R3-007 Positive fraction unresolved GP.** All GP amount sources are
  absent and `r > 0` returns `GP_COMMITMENT_UNRESOLVED` at `gpCommitment` before
  run acquisition/write. A supplied selected malformed, negative, nonfinite, or
  out-of-domain GP amount or percent instead refuses at its actual source path
  regardless of `r`; it is never labeled `GP_COMMITMENT_UNRESOLVED` and never
  falls through.
- **GP-R3-008 GP cash counted once.** `C` includes contractual GP commitment.
  Assert calculation subtracts only `D_gp`, never subtracts `G`, `G * (1-r)`, or
  GP cash a second time.
- **GP-R3-009 No fee cancellation/addback.** Changing `r` changes only deemed
  deduction. Fee basis and fee amount remain the supported fee adapter outputs;
  no assumed waived-fee equality offsets `D_gp`.

### GP source precedence

- **GP-R3-010 Nested amount wins.**
  `economicsAssumptions.gpCommitmentModel.commitmentAmount = 10`, nested
  percent/top-level GP also supplied with different valid values. Resolve
  `G = 10` from nested amount and preserve all source/effective provenance
  without using lower precedence.
- **GP-R3-011 Nested percent wins when amount absent.** `commitmentPct = 0.10`,
  normalized `fundSize = 100`, top-level `gpCommitment = 20`; resolve `G = 10`
  from nested percent.
- **GP-R3-012 Top-level fallback.** Nested amount/percent absent, top-level
  `gpCommitment = 10`; resolve `G = 10`.
- **GP-R3-013 Zero fallback.** All amount sources absent, `r = 0`; resolve
  `G = 0` with explicit zero-fallback provenance.
- **GP-R3-014 Selected invalid amount does not fall through.** Nested amount is
  negative/nonfinite/malformed while lower-precedence values are valid. Refuse
  at `economicsAssumptions.gpCommitmentModel.commitmentAmount`; do not use
  nested percent/top-level fallback.
- **GP-R3-015 Selected invalid percent does not fall through.** Amount absent;
  nested percent is negative/nonfinite/out of domain. Refuse at
  `economicsAssumptions.gpCommitmentModel.commitmentPct`; do not use top-level
  fallback.
- **GP-R3-016 GP exceeds commitments.** Any selected valid source resolves
  `G > C`; return `GP_COMMITMENT_EXCEEDS_COMMITMENTS` at the selected GP source
  path. Do not clamp as economics V1 does.
- **GP-R3-017 Fraction domain.** Negative/nonfinite or `r > 1` fails
  schema/prevalidation at `fundedFromFeesPct` before arithmetic/run/write.
- **GP-R3-018 Unit normalization.** Equivalent nested amount, nested percent,
  and top-level values expressed through documented source units normalize once
  to the same USD amount; ambiguous units refuse at their actual source path.

### Source/hash compatibility

- **GP-R3-019 Omitted fraction byte stability.** Calculate using copied scenario
  provenance with effective zero; assert pinned source JSON bytes and source
  hash are unchanged.
- **GP-R3-020 Explicit zero compatibility.** Existing V1 serializer may omit
  explicit zero. F_1.15.0 reads raw pinned source and applies ADR-070 default;
  no store/adapter modification, presence tracking, or source rewrite occurs.
- **GP-R3-021 Economics V1 isolation.** Existing `normalizeEconomicsConfig()`
  clamp/defaults, `runEconomicsModel()` outputs, and retained hashes remain
  unchanged. Capital materializer parity cases test precedence but do not call
  or modify the full normalizer.
- **GP-R3-022 Fee population provenance.** Result records current supported V1
  full-fund committed-capital population, method/version, period, units, and
  source fields. Do not label this a universal platform population; internal
  economics V2 remains separate.

### Nonpositive available construction capital

- **GP-R3-023 Zero capacity.** Example `C = 100`, deemed `80`, fees `18`,
  expenses `2` gives `A = 0`. With no explicit `N`, effective `N = 0` and
  expected count is exactly `0`; zero-denominator ratios are `null` with a typed
  not-applicable reason. A complete snapshot may save with a visible
  zero-construction-capital qualification. Positive entered-count demand may
  save as `over_capacity`. Preserve signed `A` and signed shortfall.
- **GP-R3-024 Negative capacity.** Example `C = 100`, deemed `80`, fees `20`,
  expenses `5` gives `A = -5`. With no explicit `N`, do not clamp or invent
  cash: expected sizing is `null` with `NO_CONSTRUCTION_CAPITAL`; allocation and
  ratio outputs requiring a nonnegative planning budget are unavailable with the
  same reason. Lifetime capacity is known `over_capacity`, signed shortfall is
  visible, and a complete valid-but-infeasible diagnostic snapshot may save.
- **GP-R3-025 Explicit nonnegative N with A < 0.** A user may save a nonnegative
  explicit planning budget/demand comparison. Demand/count arithmetic may be
  shown from `N`, but lifetime capacity remains `over_capacity` and shortfall
  uses signed `A`; `N` never repairs or enlarges `A`.
- **GP-R3-026 Invalid N.** Negative/nonfinite `N` refuses at
  `netInvestableCapitalUsd`; no negative-count path.

## Vehicle, fee, expense, and time admission

- **SRC-R3-001 Evergreen true.** Raw persisted `isEvergreen = true` returns
  `FUND_VEHICLE_MODE_UNSUPPORTED` at `isEvergreen`, zero run/snapshot writes.
- **SRC-R3-002 Evergreen absent.** Raw pinned absence returns
  `FUND_VEHICLE_MODE_UNRESOLVED` at `isEvergreen`; no hydrated false inference
  or writeback.
- **SRC-R3-003 Evergreen false.** Raw persisted false is eligible subject to
  explicit valid fund life and investment period. Do not infer how earlier UI
  produced it.
- **SRC-R3-004 No current SPV detection.** Current schema-valid source cannot
  claim SPV classification. A future unsupported mode refuses at its future
  actual path.
- **SRC-R3-005 Currency.** Known non-USD returns `FUND_CURRENCY_UNSUPPORTED` at
  `baseCurrency`; ambiguous/missing required currency returns typed issue. No FX
  conversion.
- **SRC-R3-006 Fee basis.** Current supported full-fund committed-capital
  profile with representable periods passes. Unsupported bases/ambiguous
  applicability/periods refuse at exact paths; no default tiers or profile
  guessing.
- **SRC-R3-007 Time origin.** Entry cohort month 3 plus previous-round lags 12
  and 18 produces months 15 and 33. Ambiguous fund/cohort/stage/previous-round
  origin returns `TIME_ORIGIN_UNRESOLVED`, blocks save/run/snapshot, and may
  show only incomplete unsaved unaffected arithmetic.

- **FEE-R3-001 Explicit tiers win.** Nonempty
  `economicsAssumptions.feeModel.tiers` conflicts with valid legacy
  profiles/defaults. Only explicit tiers feed `F`; all active tiers are additive
  on full-fund `C`. Record selected and shadowed paths, without requiring
  declarations for unconsumed legacy rates.
- **FEE-R3-002 Empty tiers/profile branch.** Missing or empty explicit tiers
  plus nonempty `feeProfiles` selects profiles even when a positive nested
  default rate is present. A selected empty `feeTiers` refuses
  `FEE_MODEL_UNRESOLVED` at `feeProfiles[0].feeTiers` instead of falling
  through.
- **FEE-R3-003 Rate-only fallback is refused.** After persisted-schema
  validation, when both supported tier/profile branches are absent/empty, nested
  `defaultRate` presence wins over raw `managementFeeRate`; return HTTP 422
  `FEE_TIER_SCHEDULE_REQUIRED` at that path without numeric or unit
  normalization. With no nested default, schema-valid raw `managementFeeRate`
  values `-1`, `0`, `0.02`, and `101` all produce this same code; missing
  rate-unit declarations cannot change it. With neither fallback, return the
  same refusal at `economicsAssumptions.feeModel.tiers`. No fallback rate or
  `defaultBasis` synthesizes a schedule; explicit zero-rate tiers remain
  supported. A nested `defaultRate = -1` or `1.01` instead fails its persisted
  ratio schema first with HTTP 409 `scenario_source_config_invalid`; a valid raw
  fallback cannot rescue it. All refusals leave create/run/snapshot/event writes
  absent.

- **FEE-R3-004 Basis provenance.** Only selected `committed_capital` passes.
  Unsupported explicit tier `basis` or legacy `feeBasis` refuses
  `FEE_BASIS_UNSUPPORTED` at its actual path. Fallback `defaultBasis` never
  overrides a selected tier or repairs a rate-only schedule. Changing `r` leaves
  `F` and its full-fund basis unchanged.

- **FEE-R3-005 Source labels and fund row.** Both valid
  source-label/selected-branch mismatches record
  `SOURCE_LABEL_SELECTION_MISMATCH` without branch changes. Changing unconsumed
  `funds.management_fee` changes neither `F` nor source fingerprint; raw-config
  changes still alter `rawConfigHash` even when shadowed.
- **FEE-R3-006 Annual expense precedence.** Present explicit annual expenses
  beat conflicting legacy monthly expenses. Explicit annual `[]` selects `E = 0`
  even when legacy expenses are nonempty; absent annual array falls through to
  present legacy array. Legacy `[]` means zero; both arrays absent refuses
  `EXPENSE_MODEL_UNRESOLVED` at `fundExpenses`.
- **FEE-R3-007 Per-field units.** Selected explicit tier rates are
  contract-resolved ratios; legacy tier rates require exact declarations.
  Fallback rates are not consumed for fees. Explicit
  `annualExpenses[0].amount = 2` declared `usd_millions` normalizes
  independently of a legacy monthly field declared `usd`; only the winning
  branch contributes to `E`. Missing selected amount/rate declaration refuses
  its exact path; no magnitude heuristic or inherited unit runs.

- **FEE-R3-008 Invalid input cannot fall through.** Persisted-schema validation
  precedes fee/expense selection, including supplied shadowed structures.
  Schema-invalid fields retain HTTP 409 `scenario_source_config_invalid` with
  actual issue paths, never a capital financial code. After that boundary,
  invalid consumed tier rates use `FEE_RATE_INVALID` and invalid consumed
  expense amounts use `EXPENSE_AMOUNT_INVALID` (HTTP 422); unsupported or
  unit-unresolved selected facts retain their named refusals. All refuse before
  create/run writes without trying a lower-precedence branch. Valid shadowed
  disagreement alone does not refuse; unconsumed Fee 3 rates never receive
  normalized-rate domain checks.

- **FEE-R3-009 Fee periods and horizon.** Nested `timeline.fundLifeYears` wins
  over differing valid raw `fundLife`, otherwise raw life is used; no
  absent-life default. Explicit annual periods retain inclusive endpoints.
  Declared zero-based legacy fee months 0–11 and declared one-based months 1–12
  normalize to the same first year. A month-6 fee change returns retained
  `FEE_PERIOD_NOT_REPRESENTABLE`, as CP-015 requires. Missing/conflicting origin
  declarations return `TIME_ORIGIN_UNRESOLVED`; do not infer origin from
  startMonth. Retain out-of-horizon facts without accruing beyond the selected
  horizon.

- **FEE-R3-010 Unsupported expense policies.** Absent/zero annual `growthRate`
  is supported with provenance; nonzero growth refuses
  `EXPENSE_GROWTH_UNSUPPORTED`. Any supplied `orgExpenseCap` or
  `orgExpenseCapType` refuses `EXPENSE_CAP_UNSUPPORTED` at the supplied path.
  Recycling annotations never alter `F`, `E`, or `A`.
- **FEE-R3-011 Profile applicability.** Multiple selected legacy profiles refuse
  `FEE_PROFILE_APPLICABILITY_UNSUPPORTED` at `feeProfiles`; do not pick the
  first, average profiles, or infer LP-class population. Nonselected valid
  profiles do not override explicit tiers.
- **FEE-R3-012 Amount/provenance replay.** In normalized synthetic units,
  `C = 100`, `D_gp = 4`, life 2 years, selected explicit annual fee rate `0.02`
  and annual expense `1` produce `F = 4`, `E = 2`, `A = 90`. Conflicting legacy
  fees/expenses do not add to these amounts. Explicit annual `[]` changes only
  `E` to `0` and `A` to `92`. Save selected raw facts, units, periods, and
  provenance; changing current config cannot change historical replay.

- **FEE-R3-013 Monthly formation/recurring expenses.** With normalized monthly
  amount 10 and declared zero-based windows, month 0–0 charges 10, 0–5 charges
  60, 6–11 charges 60, and 0–11 charges 120. Declared one-based 1–1 charges 10
  and 1–12 charges 120. Preserve explicit end 0 rather than treating it as
  omitted; an absent end uses the final horizon month with provenance. A window
  spanning the horizon charges only in-horizon months and retains excluded
  facts. No annual fee-boundary restriction or blanket annualization may reject
  or inflate these amounts.
- **FEE-R3-014 Month-origin identity.** Use exact-path `unitDeclarations` on
  each consumed legacy fee/expense boundary; both boundaries of one window must
  agree. Missing/conflicting declarations return `TIME_ORIGIN_UNRESOLVED`, while
  a month-origin label on a money/rate path fails strict validation. Equivalent
  declared one-based and zero-based sources normalize to matching periods; same
  raw month value with different declarations keeps raw source hash unchanged
  but changes normalized period and create/calculation identity. Saved replay
  retains pinned origin and periods.

- **FEE-R3-015 Invalid admitted tier rates.** Use otherwise supported single
  legacy profiles with explicit units and valid periods/basis. Selected
  `feeProfiles[0].feeTiers[0].percentage = -1` declared `percent_points`, `101`
  declared `percent_points`, or `1.01` declared `ratio` each returns HTTP 422
  `FEE_RATE_INVALID` at that exact path. No clamping, default-rate fallback,
  create, run, snapshot, or event write occurs. A nonfinite selected rate that
  passes the persisted number schema receives the same materializer refusal;
  values rejected by that schema retain HTTP 409
  `scenario_source_config_invalid`. Valid boundary rates `0` and `100` percent
  points normalize to `0` and `1`. An explicit tier `rate = -1` fails its
  stricter persisted ratio schema before materialization.

- **FEE-R3-016 Invalid admitted expense amounts.** With explicit annual expenses
  absent and all required money/period declarations present, selected
  `fundExpenses[0].monthlyAmount = -1` returns HTTP 422 `EXPENSE_AMOUNT_INVALID`
  at that exact path. A nonfinite selected amount that passes the persisted
  number schema receives the same materializer refusal; schema-rejected values
  retain HTTP 409 `scenario_source_config_invalid`. Never clamp, omit an invalid
  selected expense, or substitute another branch. A selected zero monthly amount
  remains valid. An explicit annual `amount = -1` fails its persisted
  nonnegative schema first. Every refusal leaves create/run/snapshot/event
  writes absent.

## Core calculation counterexamples

  never becomes 12% incremental dilution. Ownership remains unavailable/refused
  as appropriate.

  demand while financing dilution and later-stage progression continue under
  entered assumptions.
- **CALC-R3-005 Fixed-only ownership unavailable.** Complete fixed-check
  construction saves successfully with ownership unavailable when ownership is
  not required by selected output.
- **CALC-R3-006 Earmark and allocation coexist.** Allocation gap and
  reserve-earmark gap both persist independently; neither overwrites lifetime
  capacity or assumes transfer.
- **CALC-R3-007 Beyond-term qualifier.** Lifetime capacity fits but some demand
  is beyond term. Headline includes amount; bare `Feasible` is absent.
- **CALC-R3-008 Timing-only stress.** Lifetime demand/capacity/count remain
  unchanged while within/beyond-term partition changes.
- **CALC-R3-009 Multi-input comparison.** Exact changed inputs/output deltas
  appear without additive causal allocation.
- **CALC-R3-010 Invalid generated stress.** Invalid +25% transformation returns
  typed invalid-stress result while valid base remains readable.

## Composite source and wire-contract acceptance

- **SRCB-R3-001 Existing commitment unit unresolved.** A legacy fund with
  `funds.size = 100` and raw-config `fundSize = 100` but no persisted
  unit/write-path marker returns `UNIT_PROVENANCE_UNRESOLVED` at both exact
  paths until each consumed field has an admissible declaration. Raw equality
  does not establish scale.
- **SRCB-R3-002 Independent mixed-unit commitments.** `funds.size = 100`
  declared `usd_millions` and raw-config `fundSize = 100000000` declared `usd`
  both normalize to `100000000.00`; source state is `matched`. Declarations
  remain labeled scenario assumptions.
- **SRCB-R3-003 Normalized commitment mismatch.** Equal or unequal raw values
  whose independent declarations normalize differently return
  `FUND_SIZE_SOURCE_MISMATCH` at `fundSize`; no field inherits the other's unit
  and no magnitude heuristic runs.
- **SRCB-R3-004 GP absolute source isolation.** Selected nested
  `commitmentAmount` and selected top-level `gpCommitment` each require their
  own exact-path money declaration. A fund-size declaration does not resolve
  either field. Missing selected-source provenance returns
  `UNIT_PROVENANCE_UNRESOLVED`; malformed selected value returns its typed
  value-domain refusal and never falls through.
- **SRCB-R3-005 Checks and valuations.** Each consumed `initialCheckAmount`,
  `followOnAmount`, stage `roundSize`, `valuation`, and `exitValuation` resolves
  independently. Initial check `2` declared `usd_millions`, follow-on `500000`
  declared `usd`, and valuation `20` declared `usd_millions` prove mixed units
  normalize separately. Removing one declaration refuses that exact path before
  create writes.
- **SRCB-R3-006 Fees and expenses.** Each selected
  `fundExpenses[*].monthlyAmount` or explicit annual expense `amount` requires
  exact-path money provenance. Consumed legacy fee-tier `percentage` requires
  independent ratio/percent-point provenance; explicit tier rates have ratio
  contracts. Default rates are refused as incomplete schedules, not consumed.
  `F`/`E`/`A` remain unavailable until selected bases, period origins,
  applicability, rates, commitment base, and expense coverage resolve.

- **SRCB-R3-007 Ratio path separation.** Nested GP `commitmentPct`,
  `fundedFromFeesPct`, and explicit fee-tier `rate` have explicit ratio
  contracts. Legacy tier `percentage` requires an independent declaration.
  `funds.management_fee`, raw-config `managementFeeRate`, and nested
  `defaultRate` do not supply a capital fee schedule. Explicit tier rate `0.02`,
  selected legacy `2` declared percent points, and selected legacy `0.02`
  declared ratio normalize to `0.02` in their respective supported branches.

- **SRCB-R3-008 Currency.** Non-USD `funds.base_currency` returns
  `FUND_CURRENCY_UNSUPPORTED` at `baseCurrency`. No source projection or new V3
  scenario persists.
- **SRCB-R3-009 Stable raw-source hash.** `rawConfigHash` is SHA-256 over
  canonical raw config. `sourceBundleHash` binds only the versioned raw
  projection, fund/config identity, locked raw facts, currency, and persisted
  source unit/schema tags or stable absence. Raw fingerprinting requires no
  scenario declarations or unit-dependent financial materialization. Derived
  annotations, normalized values, readiness, and interpretation/method versions
  are excluded and bind calculation identity separately.
- **SRCB-R3-010 Source-hash counterexamples.** Repeated retrieval,
  actor/correlation changes, display-only timestamps, unrelated metadata,
  declaration changes, readiness changes, and interpretation upgrades leave the
  raw fingerprint unchanged. Changed named raw facts, persisted tags, or
  raw-config content change it. Method upgrades cannot silently change the
  frozen raw projection schema.
- **SRCB-R3-011 Declaration identity counterexample.** Same raw source plus
  `funds.size` declared `usd` versus `usd_millions` has the same
  `sourceBundleHash` and freshness state but different create request hash and
  calculation input hash. Server recomputes normalized values from raw values
  plus units; client normalized values and stored hash labels are never trusted
  alone.
- **SRCB-R3-012 Client/server boundary.** V3 create contains expected source
  identities/hash, `expectedInterpretationVersion`, bounded exact-path
  `unitDeclarations`, and editable plan assumptions only. Any client
  `sourceBundle`, `sourceBundleHash`, normalized value, or other server-owned
  source field fails strict validation. Server re-reads source, verifies stable
  hash, validates declarations, and recomputes normalized values under locks.
- **SRCB-R3-013 Physical pin.** Successful create injects one complete bounded
  capital source envelope into every capital variant's existing
  `override_payload`. All one-to-five variants contain byte-equivalent raw
  facts, source hash, declarations, normalized facts, and provenance. Raw config
  is referenced by ID/version and canonical hash rather than copied. Event
  summary remains non-authoritative; no new source table/column is required. The
  separate override-type CHECK prerequisite is covered by DUR-R3-020.
- **SRCB-R3-014 Self-contained source facts.** Current fund/config edits never
  mutate stored envelopes. Calculation uses pinned normalized
  facts/declarations. A future method requiring an omitted raw field refuses
  rather than reading a current replacement value.
- **SRCB-R3-015 Capacity accounting.** Maximum-input measurement includes one
  server-owned envelope copy in each of five variant payloads and tests limit
  and limit-plus-one behavior without partial writes.

- **SRCB-R3-016 Declaration-free unchanged refetch.** Save a scenario with valid
  declarations, then fetch unchanged source without declarations. The raw
  fingerprint matches and saved `sourceFreshness` stays `CURRENT`. The new
  preview reports `INPUT_REQUIRED` with unit issues; saved-input readiness stays
  `READY`. Completed replay bytes/hash are unchanged, and source unavailable or
  source changed is not emitted merely because the refetch lacks units.
- **SRCB-R3-017 Interpretation-only upgrade.** On unchanged raw source,
  interpreter v2 retains the same fingerprint. Saved v1 remains source-current
  with `UPGRADE_AVAILABLE` if v1 is supported. An explicitly reviewed v2
  candidate gets a different calculation input hash even if normalized values
  match. No automatic source-change verdict, saved-input rewrite, or upgrade.
- **SRCB-R3-018 Preview/create interpretation pin.** Preview supplies an
  interpretation version; create includes `expectedInterpretationVersion`
  separately from the source hash and binds it in request identity. Installing
  v2 between preview and create cannot silently replace reviewed v1. If v1
  remains supported, create uses it; otherwise it refuses
  `INTERPRETATION_VERSION_UNSUPPORTED` before writes. Successful exact
  create-key replay precedes current interpreter-support checks. A changed
  expected interpretation on the same create key is a changed-body conflict.

- **WIRE-R3-001 Default source response.** GET source-config without
  `representation` returns unchanged strict `fund-scenario-source-config/1.0.0`
  response.
- **WIRE-R3-002 Capital source response.** GET source-config with exactly
  `representation=capital-plan-v1` returns `fund-scenario-capital-source/1.0.0`,
  representation, source IDs/version, locked raw facts, stable hashes, bounded
  facts, per-field provenance/declaration requirements, and typed refusal state.
- **WIRE-R3-003 Invalid representation.** Unknown, empty, repeated, array, or
  non-string `representation` returns HTTP 400 `invalid_representation` with
  parameter, supplied value, and allowed values; it never silently falls back.
- **WIRE-R3-004 Family-filtered collections.** Default lists contain legacy sets
  only; capital opt-in lists contain one-to-five-variant capital sets only.
  Classify/filter families before counts, empty/pending status, or strict
  mapping; apply `includeArchived` within the selected family. Mixed-family
  variants in one set are refused and never mapped into either schema; retain
  existing legacy validity checks. There is no mixed wire collection.
- **WIRE-R3-005 Direct-read representation.** Default capital detail, results,
  or comparison returns HTTP 406 `scenario_representation_required` before
  strict V1 parsing, naming `capital-plan-v1`. Capital opt-in direct reads of
  legacy sets return HTTP 406 `scenario_representation_not_applicable`. Capital
  status has the separate unsupported-operation rule in WIRE-R3-010.
- **WIRE-R3-006 Strict capital discriminators.** Successful negotiated
  source/list/detail/results/comparison responses carry
  `representation: capital-plan-v1` plus their respective `contractVersion`:
  `fund-scenario-capital-source/1.0.0`, `fund-scenario-capital-list/1.0.0`,
  `fund-scenario-capital-detail/1.0.0`, `fund-scenario-capital-results/1.0.0`,
  and `fund-scenario-capital-comparison/1.0.0`. Lists contain capital summaries
  only, and capital detail/result variants admit only `capital_plan`. Aggregate
  and calculation-status reads do not gain capital response contracts.
- **WIRE-R3-007 Old-reader and combined-display fixtures.** Existing strict
  parsers consume default source/list/detail/status/results/comparison/aggregate
  fixtures and never see a capital discriminator. Capital parsers accept only
  the negotiated family. The workspace independently fetches/parses both lists,
  tags rows by representation, merges by set ID with deterministic display
  ordering, and selects matching detail/results/comparison APIs. Cover
  legacy-only, capital-only, mixed-family collections, archived, and
  uncalculated sets. A family fetch failure remains visible rather than being
  treated as an empty successful collection.

## Durable-state integration

- **WIRE-R3-008 Legacy-only aggregate selection.** The fund-results aggregate
  filters capital before row/count/status/snapshot selection or mapping. Active
  capital only gives `SCENARIOS_NONE_EXIST`; uncalculated legacy plus calculated
  capital gives `SCENARIOS_NONE_CALCULATED`; calculated legacy plus any capital
  state returns only legacy snapshots/counts. Both calculated families still
  return legacy only. Archived legacy plus active capital gives
  `SCENARIOS_NONE_EXIST`; active legacy plus archived capital retains legacy
  behavior. Each list's `includeArchived` expands only its selected family.
  Capital representation on the aggregate returns HTTP 406
  `scenario_representation_not_applicable`; malformed selector returns HTTP 400.
- **WIRE-R3-009 Cache representation and invalidation.** With one QueryClient
  and no cache clear/reset, load legacy then capital and reverse that order for
  the same fund/set across source/list/detail/results/comparison. Each read
  remains under the correct strict parser and response-specific key. Preserve
  legacy keys exactly; capital keys include `capital-plan-v1`, read kind,
  IDs/options under `workspaceQueryKey(fundId)`. Test active-only versus
  include-archived capital lists, and a shared-prefix mutation invalidating both
  families. No capital status key or new key module is introduced.
- **WIRE-R3-010 Synchronous capital without status polling.** Capital
  calculation renders mutation pending/success/error and reloads saved results
  through negotiated scenario reads. Assert no capital status GET or polling
  timer. A direct capital status request with absent or valid representation
  returns HTTP 409 `capital_plan_calculation_status_not_applicable` before
  reserve-identity/run queries; malformed representation returns HTTP 400.
  Existing reserve status responses, keys, and polling remain unchanged.

- **WIRE-R3-011 Capital create acknowledgement/replay.** Valid V3 body
  `fund-scenario-set-create/3.0.0` with absent or capital selector returns HTTP
  201 and strict `FundScenarioCapitalCreateResponseV1Schema`: only
  `contractVersion: fund-scenario-capital-create/1.0.0`,
  `representation: capital-plan-v1`, and persisted UUID `scenarioSetId`. Exact
  create-key replay returns the same HTTP status/body even after source or
  interpreter changes, archiving, or calculation; it precedes new-command source
  checks. Changed valid body keeps HTTP 422 `idempotency_key_reused`. No new
  receipt store or replay flag.
- **WIRE-R3-012 Capital calculate snapshot response.** Capital target requires
  the capital selector before calculation. Fresh completion and exact-input
  dedupe both return HTTP 200 and strict
  `FundScenarioCapitalCalculateResponseV1Schema` with
  `fund-scenario-capital-calculate/1.0.0`, representation, saved `snapshotId`,
  saved `correlationId`, `source: fund_snapshots`, and strict capital snapshot
  `payload`. The same saved snapshot produces byte-identical bodies despite
  current source/interpreter changes. No calculation key, queued receipt,
  polling status, or current freshness field is added.
- **WIRE-R3-013 Mutation selector compatibility.** Default legacy create/replay
  remains HTTP 201 and legacy calculate HTTP 200 through original strict
  parsers. A capital selector on legacy create/calculate returns HTTP 406
  `scenario_representation_not_applicable`; missing selector on capital
  calculate returns HTTP 406 `scenario_representation_required`.
  Unknown/empty/repeated/array/non-string selectors return HTTP 400
  `invalid_representation`, including replay. Assert zero writes in all refusals
  and no capital mutation body enters a legacy parser.
- **WIRE-R3-014 Mutation failure boundary.** Invalid V3 input is HTTP 422
  `invalid_scenario_set_v3_payload`; financial/support refusals are HTTP 422
  with exact code/path in the existing error envelope. Source CAS and
  active-run/fence conflicts retain specified HTTP 409 codes. Unexpected
  calculation, persistence, or capital response validation failure returns
  HTTP 500. Validate success body before commit and inject response-contract
  failure to prove no new set/run/snapshot/event survives. After a successful
  commit with lost response, same optional create-key or calculate input
  identity recovers the saved acknowledgement/snapshot; it must not create a
  duplicate or be mislabeled rollback.

- **DUR-R3-001 V3 only.** `capital_plan` is accepted through V3 and rejected
  through V1/V2 create contracts; existing contract snapshots remain unchanged.
- **DUR-R3-002 Separated fingerprint and materializer.** Source GET, create CAS,
  and freshness use the same versioned raw projection/fingerprint function
  without declarations. Preview/create/calculation readiness separately uses raw
  facts, exact declarations, and the selected supported interpretation. Reading
  freshness never implicitly rematerializes saved inputs with the current
  interpreter.
- **DUR-R3-003 Lock composite CAS.** New V3 create locks/reads fund row,
  resolves create-idempotency replay, then locks/reads published config.
  Mismatched expected config ID/version or stable `expectedSourceBundleHash`
  returns HTTP 409 `scenario_source_config_stale` with supplied/current IDs,
  versions, and hashes; no scenario/snapshot write occurs.
- **DUR-R3-004 Create replay ordering.** Same optional `Idempotency-Key` and
  request hash returns stored scenario before live-source CAS, even after source
  changes. Same key with changed body returns HTTP 422 `idempotency_key_reused`.
  Create replay never implies calculate idempotency.
- **DUR-R3-005 Unit/refusal before writes.** Required unresolved money/rate
  path, source/core issue, or selected-companion issue returns typed exact-path
  refusal before scenario creation or calculation run acquisition. No run,
  snapshot, partial output, or calculated event is written.
- **DUR-R3-006 Completed calculate dedupe.** Synchronous calculate has no
  idempotency header or command receipt. Scenario-row `FOR UPDATE` serializes
  ordinary calls; a waiter reuses the exact completed capital hash result and
  returns HTTP 200 with the same snapshot.
- **DUR-R3-007 In-progress fence conflicts.** Exact queued/running row returns
  HTTP 409 `scenario_calculation_in_progress`. Failed running/completion
  transition remains HTTP 409 `scenario_calculation_ownership_lost`. Neither
  response creates a second snapshot or async receipt.
- **DUR-R3-008 Synchronous failure rollback.** Failures after acquisition, after
  running transition, during calculation, during snapshot insert, and before
  event insert roll back the whole transaction. No new run/snapshot/event or
  durable failed row survives; synchronous path does not call
  `markScenarioCalculationRunFailed()`.
- **DUR-R3-009 Prior-result isolation.** Failed later calculation leaves prior
  completed snapshot byte-identical and readable. Partial output never replaces
  it; retry may perform a fresh transaction.
- **DUR-R3-010 Existing hash-kind, capital domain.** Existing lineage rules
  remain: genuine `modelInputsAsOfDate` uses `scenario-input-hash-v2` plus
  `comparison-lineage-v1`; absence uses `scenario-input-hash-v1` with null
  date/lineage. Capital normalization conditionally binds domain `capital_plan`,
  mode `sync_capital_plan`, explicit capital-preimage version, stable source
  hash, exact unit declarations, server-verified normalized values,
  scenario/variant inputs, and method versions. Legacy V1/V2 preimages/hashes
  remain byte-identical and reject capital-only fields. Timing-origin validation
  remains separate; establishment or execution time never substitutes for an
  absent business as-of date.
- **DUR-R3-011 Completed replay before integrity load.** Exact completed
  snapshot replay returns before loading historical config. Missing or mutated
  referenced config cannot make stored completed result unreadable or change its
  bytes.
- **DUR-R3-012 New-run historical integrity.** Without exact completed snapshot,
  calculation loads referenced config ID/version and recomputes canonical
  content hash. Missing row or mismatch with pinned `rawConfigHash` returns
  `HISTORICAL_SOURCE_INTEGRITY_FAILED` before run/write. FK protection alone is
  not content immutability.
- **DUR-R3-013 Independent read-state axes.** Live changes never rewrite stored
  inputs/results. Changed published identity gives `STALE_PUBLISH`; changed raw
  fingerprint at the same identity gives `STALE_SOURCE`.
  Unloadable/uncanonicalizable raw source alone gives `STALE_SOURCE_UNAVAILABLE`
  (unknown freshness). Missing declarations affect context-labeled preview
  readiness only. Declaration-only and interpretation- only changes leave
  unchanged-source freshness `CURRENT`; calculation identity still binds
  declarations and method versions. Legacy evidence enums remain untouched.
- **DUR-R3-014 Duplicate stale scenario.** Duplicate copies stored source
  envelope and assumptions but cannot calculate as current. Refresh/review
  creates a new server-owned envelope under current CAS; client bundle
  substitution is rejected.
- **DUR-R3-015 Capital comparison isolation.** Capital comparison reads
  persisted capital results only; it never queries or promotes authoritative
  economics/actuals state.
- **DUR-R3-016 Source/default provenance.** Saved scenario includes exact
  paths/raw values, unit declarations, declared-versus-contract provenance,
  server-verified normalized values, identities/hashes, GP effective/default
  state, deemed amount, and materializer version without mutating original
  config.
- **DUR-R3-017 Complete detail.** Persisted monthly detail is bounded and
  untruncated. Summary/copy may omit rows only when labeled summary and never
  claims complete export.

- **DUR-R3-018 Saved interpretation support.** Completed replay succeeds even
  when its saved interpreter is unavailable. A new run using that version
  refuses `INTERPRETATION_VERSION_UNSUPPORTED` before run acquisition/write,
  with `UNSUPPORTED_SAVED_VERSION` compatibility. A still-supported saved
  version may calculate/reuse its exact identity; no implicit upgrade occurs.
- **DUR-R3-019 Fingerprintable unsupported currency.** A later USD-to-EUR change
  at the same config identity changes the raw fingerprint and gives
  `STALE_SOURCE` plus `FUND_CURRENCY_UNSUPPORTED` for current-preview readiness.
  It is not source-unavailable; the saved USD snapshot and replay stay intact.

- **DUR-R3-020 Override-type migration compatibility.** On an isolated synthetic
  database, exercise both the canonical migration chain and the existing legacy
  CHECK state. The forward registered migration admits `capital_plan`, preserves
  `fee_profile`, `reserve_allocation`, `allocation`, `sector_profile`, and
  runtime-supported `methodology`, and rejects arbitrary types. Existing valid
  rows stay byte-identical; malformed existing types fail validation without
  deletion/rewrites. Verify schema/contract allowlist alignment and create/read
  a capital set through the service after migration. No production database is
  required for this future acceptance case.

- **ROLL-R3-001 Before first committed capital write.** Expanded CHECK plus
  legacy-only data permits governed application rollback only after writes stop
  and positive absence evidence covers capital sets/variants/snapshots. Retain
  the expanded CHECK and all legacy rows. Failed-transaction evidence alone does
  not establish global absence.
- **ROLL-R3-002 First write and mixed persisted data.** Persist a capital set
  with no snapshot, then repeat with a completed snapshot, archived capital
  data, and mixed legacy/capital data. Default legacy
  list/detail/results/comparison/aggregate paths filter or return their typed
  family refusal before V1 parsing; negotiated capital reads remain valid.
  Proposed recovery artifact must retain these readers and CHECK. Pre-capital
  binary or removal of compatible readers is blocked; hiding UI/archiving does
  not permit it. No set or snapshot is deleted or rewritten for recovery.
- **ROLL-R3-003 Ambiguous commit and forward repair.** A lost successful-create
  response still establishes the first-write boundary. If capital absence is
  unknown, use forward-fix-only recovery. A targeted write/UI repair is eligible
  only while retained readers pass ROLL-R3-002 against existing data; no down
  migration or old-binary deployment. This is future synthetic acceptance, not
  authorization for production recovery.

## Real-input compatibility census

No production query is authorized by this acceptance specification.

When an authorized sanitized export is supplied, record:

1. export path/identity, SHA-256, export timestamp, source environment label,
   exact Git HEAD, materializer/method version, and operator;
2. raw row count, deduplicated count, duplicate count, and deterministic
   key/rule using fund identity plus selected published config ID/version;
3. GP source precedence counts: nested amount, nested percent, top-level amount,
   zero fallback;
4. `fundedFromFeesPct`: absent, explicit zero, `(0,1)`, explicit one, invalid;
5. resolved GP/deemed min/max and `G > C` refusals;
6. `isEvergreen` true/false/absent, currency, fund-life, investment-period;
7. fee basis/profile/period applicability and expense coverage;
8. allocation/profile/stage linkage and pool-dilution availability;
9. pass/refusal counts by typed reason and exact field path, noting overlapping
   reasons;
10. redaction/sanitization statement and any omitted population/field.

Without that export, status is `NOT_COLLECTED`. No observed non-cash cases does
not waive GP method correctness or source precedence.

## Release blockers

- Fee/expense branch selection, unit/provenance admission, supported-period
  policy, or `F`/`E`/`A` differs from FEE-R3-001–FEE-R3-016.
- Capital create/calculate responses, selectors, statuses, or replay bodies
  differ from WIRE-R3-011–WIRE-R3-014, or capital data reaches legacy mutation
  parsers.
- A post-write recovery artifact removes compatible readers, narrows the CHECK,
  deletes capital data, or treats unknown capital absence as permission to
  deploy an old binary.

- Any retained CP fixture or revision-3 financial fixture fails.
- Deemed contribution reduces fee basis/fee amount, GP cash is
  double-subtracted, or absent fraction mutates source/hash.
- GP precedence differs from current engine semantics or selected invalid source
  falls through.
- Negative/zero `A` produces negative expected counts or hides signed
  capacity/shortfall.
- Required source/core issue or selected invalid companion acquires a run or
  writes a snapshot.
- Capital source uses raw-config `fundSize` as authority, applies a scaling
  heuristic, accepts size mismatch, or calculates non-USD without refusal.
- Client source fields enter stored payload, stored variant bundles differ, a
  bundle/hash is missing or inconsistent, or calculation reconstructs historical
  source from live rows.
- Default/selected source wire discriminants differ from specification, or an
  invalid `representation` silently falls back instead of HTTP 400.
- Create replay is subjected to changed live-source CAS, create key/body
  conflict differs from 422 `idempotency_key_reused`, or calculate is described
  as a receipt/idempotency-key workflow.
- Synchronous failure leaves a new run, snapshot, event, or durable failed row;
  exact active-run and fence conflicts differ from specified 409 codes.
- Failed rerun replaces prior complete snapshot or comparison recalculates
  historical results.
- Any exact disclosure or visible/copy parity fails.
- Baseline keyboard/screen-reader/error-recovery path cannot be demonstrated.
- Deferred B/D feature appears as dormant contract/UI scaffolding.
- Benchmark source is not revalidated before shipped preset selection.
- Supported capacity caps remain unmeasured or limit+1 writes.

## Stop condition

F_1.15.0 is implementation-ready only when the plan receives required external
TRIP review and user approval. It is release-ready only when every applicable
required case passes against the exact final head, hosted CI is green, and
unresolved readiness claims remain explicitly separated.
