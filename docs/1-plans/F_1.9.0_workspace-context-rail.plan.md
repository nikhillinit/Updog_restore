# Workspace Context Rail Implementation Plan (F_1.9.0)

**Status:** PROPOSED **Baseline:**
`origin/main @ aa355aaf75a2f9f1be99783f9633dba6575d97f9` **Production
dispatch:** HOLD — this plan grants no release, schema, or provider authority.
Client-only scope; no production action is authorized by admission of this
document.

**Plan ID note:** `F_1.9.0` was free at authoring time (`docs/1-plans/` tail in
the `F_1.x` series is `F_1.7.0`; no `F_1.8.x` or `F_1.9.x` exists). `F_1.8.x` is

## Overview

One client-only PR that gives every fund workspace surface a shared, explicit
operating context and a rail that displays it. Three new client artifacts (none
exist today; verified zero hits in `client/src` and `tests/`):

- `client/src/contexts/FundWorkspaceContext.tsx` — provider carrying
  `{ fundId, vehicleId | null, asOfDate, currentPlanVersionId | null, viewPreset }`.
- `client/src/hooks/useFundWorkspaceContext.ts` — the consumer hook.
- `client/src/components/fund-results/WorkspaceContextRail.tsx` — the rail,
  mounted beside the existing `WorkspaceNav` on every page component that
  renders it (eight on this baseline, enumerated under Files to Modify).

Everything else is reuse: the rail composes the existing `context-rail/`
primitives (`ContextRailSection`/`ContextRailItem` rendering, the Sheet-based
trigger pattern), reads only existing API endpoints, and extends
`workspace-nav.tsx` link generation so the context survives navigation. No new
backend routes, no schema changes, no new dependencies, no new client routes.
This first slice is strictly read-only: the uncalled-capital bridge panel and
the recompute control ship disabled-with-reason (see the deviations section
immediately below).

## Scope Deviations Requiring Owner Ratification

This plan deviates from issue #1288's original acceptance list in five places.
Each is forced by a verified backend gap, stays inside this plan's client-only /
no-new-backend-routes boundary by shipping the affected control
disabled-with-reason, and **requires explicit owner sign-off at plan approval**:

1. **Uncalled-capital bridge panel ships disabled.** #1288 AC: "Rail renders the
   uncalled-capital bridge from CurrentForecastV2." The dual-forecast response's
   `currentForecastV2` block (`DualForecastCurrentForecastV2Schema`,
   `shared/contracts/dual-forecast/dual-forecast-response.contract.ts:240-258`)
   exposes only status/engineStatus/asOfDate/plan+snapshot ids/hashes/
   versions/unavailableReasons/held — no bridge amounts. The bridge fields
   (`committedCapitalUsd` ... `uncalledCapitalUsd`) exist only in the full
   `CurrentForecastV2` contract
   (`shared/contracts/current-forecast-v2.contract.ts:62-66`), which no
   authorized read serves to the client. Exposing them requires an authorized
   read-contract addition — out of this plan's boundary; it lands with #1290 or
   a named follow-on. The panel renders disabled with reason "bridge amounts not
   yet exposed by an authorized read contract".
2. **Recompute control ships disabled.** #1288 AC: rail "hosts 'Recompute from
   latest accepted facts'". The existing
   `POST /funds/:fundId/current-forecast/runs`
   (`server/routes/current-forecast.ts:246-251`) requires no Idempotency-Key and
   `runCurrentForecastV2` performs an unconditional
   `database.insert(fundSnapshots)` with a `randomUUID()` correlationId
   (`server/services/current-forecast-v2-service.ts:302-314`) — a retried
   invocation duplicates snapshots, violating the repo-wide
   mandatory-idempotency rule. The control renders disabled with reason
   "recompute requires an idempotency-keyed command" until an idempotency-keyed
   backend command with replay semantics exists (backend work excluded here). A
   client-side-only mitigation (debounce, in-flight lock) does not satisfy
   idempotency and is not planned as if it did.
3. **No fabricated as-of date.** #1288 AC default: "as-of = latest accepted
   facts snapshot date else current UTC date." The facts route 404s on absence
   (`server/routes/financial-facts.ts:105-116`); the rail mirrors that absence
   as an explicit "unavailable" state and never substitutes today's date. The
   context field accordingly becomes `asOfDate: string | null`, and no as-of
   override or stickiness ships (see section 4 and closed question 4).
4. **Evidence navigation ships fully disabled-with-reason.** #1288 AC names
   four evidence kinds; on this baseline none has a live, basis-correlated
   client destination. Snapshot identity renders as a short-hash display of the
   served forecast block's own hashes (deviation 5); observation, resolved-term,
   and reconciliation navigation all ship disabled-with-reason (section 3). The
   reconciliation kind's future destination is the C1A persisted construction
   reconciliation card on `client/src/pages/variance-tracking.tsx`
   (`useConstructionReconciliation`, :284) once a basis-correlated read exists;
   the `/moic-analysis` "Latest reconciliation" card renders the MOIC
   reconciliation (`FundMoicRankingsResponseV2.latestReconciliation`), a
   different record, and is not a valid destination.
5. **Active-basis snapshot short-hash display is deferred.** #1284's approved
   rail content includes the active-basis snapshot short-hash. The served
   forecast block's `financialFactsSnapshotId`/`inputHash` may identify the
   facts snapshot that fed the served result, but no correlated read contract
   exists today: the facts-latest response exposes no snapshot row ID
   (`server/routes/financial-facts.ts:76-103`), so the client cannot correlate
   the served basis to a facts read. Until such a contract lands, the rail
   shows the served-forecast hashes themselves as the basis identity when the
   block is present, and "basis unavailable" otherwise; the latest-facts
   `snapshotInputHash` is labeled only as facts freshness, never as
   active-basis snapshot identity.

## Problem Statement

- The workspace nav row
  (`client/src/pages/fund-model-results/workspace-nav.tsx`) carries only
  `fundId`. Vehicle, as-of date, plan version, and view preset are not part of
  workspace state, so nothing preserves them across the seven workspace
  destinations and nothing displays the basis a result was computed from.
- The existing `context-rail/` shell (four files under
  `client/src/components/context-rail/`) is dashboard-scoped and its view model
  accepts only `asOfDate` (`context-rail-view-model.ts`,
  `ContextRailInput = { asOfDate?: string | null }`). It cannot express the
  approved rail content: active basis, snapshot identity, the uncalled-capital
  bridge, the recompute action, or evidence navigation.
- Defect D21: the mark-arrives-to-refreshed-picture loop has no operator
  surface. The approved prototype bounds it to at most two operator actions
  (review, then recompute from latest accepted facts).

## Design Basis (issue #1284, approved 2026-08-11)

The stakeholder-approved prototype fixes the interaction and information
architecture. The following are binding on implementation:

1. **Rail content:** fund / vehicle / as-of / plan context; active basis (as-of
   date plus snapshot short-hash); the "Recompute from latest accepted facts"
   action; the uncalled-capital bridge (committed / called / projected fees
   remaining / recallable / uncalled); evidence navigation from a displayed
   result to snapshot, observation, reconciliation, and resolved-term
   references. This remains the approved end-state design record; the first
   slice ships the bridge, the recompute action, and part of evidence navigation
   as disabled-with-reason per the "Scope Deviations Requiring Owner
   Ratification" section.
2. **Presets:** `gp | analyst | operations` are presentation filters only — they
   alter emphasis, never queries, actions, or authorization (also a DESIGN.md
   interaction-contract rule).
3. **Disabled-with-reason:** every disabled control states its missing
   dependency and, where one exists, a recovery action. `vehicleId: null` on a
   multi-main-blocked fund (R35) renders the vehicle slot disabled with reason,
   never hidden.
4. **Responsive contract:** at 1024-1279px the rail is a closed-by-default,
   focus-managed slide-over with an explicit "Review context" trigger,
   backdrop/Escape close, opener-focus restoration, and preserved rail state.
   Below 1024px the same content opens from a 44px command-bar info button; the
   rail never sits in normal page flow at these widths. At >= 1280px the rail
   may be pinned per the DESIGN.md shell contract (hidden / peek / pinned).
5. **Focus, targets, motion:** 44px minimum touch targets on rail triggers and
   preset controls; visible high-contrast focus treatment; reduced-motion
   honored. Focus treatment is **solid charcoal `#292929`** (~12-14:1 on
   white/mist), per the recorded exception in the review packet
   (`docs/reviews/2026-08-08-issue-1284-prototype-review.md:79-91`): the
   translucent token value `focus.ring: rgba(41,41,41,0.25)` composites to
   ~1.5:1 on white and FAILED the WCAG 2.4.11/1.4.11 3:1 requirement, so the
   prototype replaced it with the solid accent — do not reuse the translucent
   token value as-is. `#2563EB` is reserved exclusively for Info status, never
   focus or accent (DESIGN.md "never blue").
6. **Shared-screen rubric (GR2-1 amendment):** the primary view surfaces the
   operating question, current state and as-of, next recommended action, and
   output basis without opening a secondary panel; "Reviewed with no change"
   (rendered as "Picture refreshed - no change") is a first-class completion
   state distinct from "not reviewed".
7. **Loop bound:** mark-arrives to refreshed-picture in at most two operator
   actions, with the completion state persisting visibly.

Visual language: DESIGN.md is mandatory. `presson.*` tokens only; primary accent
charcoal `#292929`, never blue; paper/sand/ink surfaces; charcoal/beige numeric
scales as already used by `workspace-nav.tsx` and `ContextRail.tsx`;
`tabular-nums` on all bridge figures; 8px spacing grid.

## Solution Architecture

### 1. Context contract

```ts
// client/src/contexts/FundWorkspaceContext.tsx
export type WorkspaceViewPreset = 'gp' | 'analyst' | 'operations';

export interface FundWorkspaceContextValue {
  fundId: number; // from FundContext (number | null there; provider renders children only when resolved, else pass-through defaults)
  vehicleId: string | null; // sole main_fund entry of facts vehicleRoster; null => disabled-with-reason (R35)
  asOfDate: string | null; // served basis date only (section 2); null => explicit "unavailable" state, never a fabricated date
  currentPlanVersionId: string | null; // served basis only (currentForecastV2.currentPlanVersionId); null with "basis unavailable" reason when the block is absent — never the current-plan head
  viewPreset: WorkspaceViewPreset; // default 'gp'; presentation-only
  setViewPreset: (preset: WorkspaceViewPreset) => void;
}
```

Defaults: vehicle = the sole `main_fund` entry of `payload.vehicleRoster` on the
`GET /api/funds/:fundId/financial-facts/latest` response
(`FinancialFactsVehicleRosterEntrySchema`,
`shared/contracts/financial-facts-snapshot-v1.contract.ts:162-170`; present in
every persisted payload version) — this closes open question 1;
`vehicleId: null` with disabled-with-reason when the roster has zero or multiple
`main_fund` entries (R35) or when no facts snapshot exists. As-of = the served
basis only: `currentForecastV2?.asOfDate ?? null` — when the block is absent
the context `asOfDate` is `null` rendered as an explicit "Basis unavailable"
state, with NO fallback to the facts-latest date. The facts-latest `asOfDate`
is exposed separately as accepted-facts freshness metadata (its own display
slot, never the context basis date) — the facts route 404s on absence
(`server/routes/financial-facts.ts:105-116`) and the client mirrors that absence
rather than substituting today's date (UTC formatting exactly as
`context-rail-view-model.ts` already does). Plan =
`currentForecastV2.currentPlanVersionId` from the same dual-forecast read when
that block is present — the served basis is the sole source; when the block is
absent, `currentPlanVersionId` is `null` with an explicit "basis unavailable"
reason, never defaulted to the current-plan head. The existing
`GET /api/funds/:fundId/current-plan-versions` read supplies display metadata
only (labeling the served version); preset = `gp`.

The provider nests inside the existing `FundProvider` on the mounting surfaces
only (not app-wide): it derives `fundId` from `useFundContext()`, reads the
`viewPreset` override from URL search params (wouter `useSearch`, the same
pattern `FundContext` uses via `extractRouteScopedFundId`), and holds preset
changes in state mirrored to the URL so links can carry them. There is NO
`asOfDate` URL override: current-only reads cannot honor a basis override, so
the rail displays the served basis exclusively until basis-selecting reads exist
(closes open question 4 — no stickiness). No persistence beyond the URL; no
writes of any kind.

Basis-identity short-hash: first 8-12 hex chars of the served forecast block's
own `inputHash`/`resultHash`/`assumptionsHash` — rendered in mono per the
DESIGN.md compact-label rule with the full identifier available (title/copy
affordance) — shown only when the `currentForecastV2` block is present;
otherwise the identity slot renders "basis unavailable". The facts
`snapshotInputHash` renders solely under the facts-freshness label and is never
presented as active-basis identity; the correlated active-basis snapshot
short-hash is deferred (deviation 5). Never render the numeric
`financialFactsSnapshotId` as identity: it is a stringified row id, not content
identity. Never fabricate identity the payload does not carry. A present `held` block is a
SERVED golden state, not an unavailable one: the rail renders the held block's
pinned basis identity (its `asOfDate`, `currentPlanVersionId`, hashes) plus the
`held` disclosure content. Basis-unavailable/disabled-with-reason states are
reserved for an ABSENT `currentForecastV2` block or `engineStatus` of
`unavailable`/`failed`, where the rail renders the contract's
`unavailableReasons` (or the absence itself); it
must not synthesize basis or bridge figures (DESIGN.md: render missing data as
unavailable, never invent audit metadata).

### 3. Rail component

`WorkspaceContextRail.tsx` lives in `client/src/components/fund-results/` (issue
AC placement, beside `ForecastBasisControl` which `workspace-nav.tsx` already
imports). It reuses:

- `ContextRailSection`/`ContextRailItem` types and the `ContextRail` section
  renderer for list-shaped content (freshness). Correction to an earlier draft:
  `ContextRailObjectLink` exists in `context-rail-types.ts` (:16-19, item field
  :26) but `ContextRail.tsx` renders only `label`/`detail`
  (`client/src/components/context-rail/ContextRail.tsx:20-27`) — `objectLink` is
  never rendered, so the existing renderer provides NO deep-link behavior.
  Evidence navigation is therefore rendered directly by `WorkspaceContextRail`
  (below), leaving the dashboard renderer untouched.
- The `ContextRailTrigger` Sheet pattern (shadcn `Sheet`, `PanelRight` trigger)
  for the slide-over and sub-1024px modes, extended to meet the approved
  focus-management and 44px-target requirements.

Content that is not list-shaped — the identity block (fund / vehicle / as-of /
plan), the disabled bridge panel, the preset radiogroup, the disabled recompute
control, and the evidence block — is rendered directly by `WorkspaceContextRail`
rather than forced through `ContextRailItem`.

Evidence navigation, per kind (concrete source field and destination; anything
without a real destination on this baseline ships disabled-with-reason,
deviation 4):

- **snapshot** — source: the served forecast block's own hashes
  (`inputHash`/`resultHash`/`assumptionsHash`) when the `currentForecastV2`
  block is present, rendered as the mono short-hash identity with full-hash
  title/copy affordance; "basis unavailable" when the block is absent. The
  correlated active-basis facts-snapshot display is deferred (deviation 5). No
  snapshot-viewer client route exists, so this is an identity display; any
  navigation affordance is disabled with reason "snapshot viewer not yet
  available".
- **observation** — source: `payload.sourceObservationIds` from the same read;
  no observation destination route exists in
  `shared/routes/app-route-definitions.ts` — disabled with reason "observation
  viewer not yet available".
- **reconciliation** — disabled with reason "basis-matched reconciliation not
  yet identifiable". Correction to an earlier draft: the `/moic-analysis`
  "Latest reconciliation" card renders the MOIC reconciliation
  (`FundMoicRankingsResponseV2.latestReconciliation`,
  `client/src/pages/fund-model-results-moic-analysis.tsx:27`, :257-269, :363),
  NOT the C1A persisted construction reconciliation — that renders on
  `client/src/pages/variance-tracking.tsx` (`useConstructionReconciliation`,
  :284). No payload the rail reads identifies a basis-matching reconciliation
  record, so no link ships in this slice; the future destination is the
  variance-tracking C1A card once a basis-correlated read exists (deviation 4).
- **resolved-term** — source: `payload.participationTermRefs` from the same
  read; no destination surface exists — disabled with reason "resolved terms
  view not yet available".

A new pure view-model module `workspace-context-rail-view-model.ts` (colocated
with the component) maps the optional `DualForecastCurrentForecastV2` block
(status/basis IDs/hashes only — never the full `CurrentForecastV2`) +
facts-latest + workspace context into the rail's display model; the existing dashboard
`context-rail-view-model.ts` and its consumer (`dashboard-modern.tsx`) are not
modified. Pure functions first, thin component on top — mirrors the existing
`workspace-nav.tsx` split and keeps the tests DOM-light.

Accessibility carried over from the approved prototype: preset control is a
radiogroup with arrow-key navigation; every disabled control (recompute, bridge,
evidence links) is associated with its reason via `aria-describedby`; preset
changes announce through a status/live region. The recompute live region and the
"Picture refreshed - no change" persistent completion state remain specified as
the approved end-state behavior but are unreachable in this slice (the control
is disabled, deviation 2); tests assert the disabled reason, and the completion
behavior lands with the idempotency-keyed command.

### 4. Context preservation across workspace links

`workspaceNavItems(fundId)` in `workspace-nav.tsx` grows to
`workspaceNavItems(context)` (or an equivalent second parameter — keep the
change minimal and mechanical): links append `viewPreset` as a query param only.
Fund survives via the existing `fundId` params; vehicle, as-of, and plan are
re-derived on every surface from the same served reads, which yields identical
values without link state; and no `asOfDate`/plan params ship at all —
current-only reads cannot honor a basis override, so the displayed basis is
always the served basis (closes open question 4: no stickiness). The resulting
navigation is **seven live destinations plus one disabled Operations
placeholder**. Wave 9B1 contracts are preserved exactly: item order (Portfolio
Actuals before Reserves), the `fundScoped()` disabled-with-reason pattern, ink
active state, at most one primary action, existing `data-testid` values. The
`analysis` key already exists (label "Economics"); the `operations` key is added
because issue #1288's AC explicitly requires it ("`workspace-nav.tsx` extended
(`analysis`, `operations` keys ...)") — closing open question 2 — but, because
no operations page or route exists on this baseline (issue #1293 owns it), it
renders disabled with reason "Operations workspace not yet available" until that
route lands — never a dead link (D-C).

Consumers that read the query params already exist for `fundId`
(`extractRouteScopedFundId`, PortfolioTabs URL sync); the new `viewPreset` param
is additive and ignored by pages that do not consume it. Presets never reach a
query or authorization decision — they gate only emphasis classes in the rail
and, where a workspace page opts in, section ordering.

### 5. Routing and registration

No new client routes. The rail mounts on the existing page components that
already render `WorkspaceNav` (all eight, enumerated under Files to Modify).
Therefore no `app-route-definitions.ts`, `app-routes.tsx`, or
`route-governance-registry.ts` changes are expected. If implementation discovers
a genuine need for a new route (it should not), it follows ARCHI section 9
exactly: definition + `app-routes.tsx` + governance-registry entry, one of the
three routing surfaces declared.

## Technical Considerations

- **Preact compat (ARCHI section 1):** the production bundle ships Preact via
  `vite build --mode preact`; dev runs real React. Everything here must be
  preact/compat-safe: `createContext`/`useContext`/`useState`/`useMemo`,
  TanStack Query, wouter, and the existing shadcn `Sheet` are all already in the
  shipped bundle. Do not introduce React-18-only APIs (`useSyncExternalStore`
  direct use, `useTransition`, `flushSync` dependencies) or any new library.
  `npm run build:web` is the only gate that catches a compat break — run it
  before push.
- **Strict TS:** `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess` are
  on; the context value uses explicit `| null` (not optional properties) exactly
  as the required shape states.
- **Decimal strings:** no money figures arrive in this slice — the served
  `currentForecastV2` block carries status/IDs/hashes only, and the bridge
  panel is disabled (deviation 1). When the authorized bridge read lands,
  figures arrive as `MoneyDecimalStringSchema` strings: display formatting only
  — no client arithmetic beyond formatting; never parse to float for math (repo
  precision discipline).
- **e2e fidelity spec behavior:**
  `tests/e2e/route-fund-context-fidelity.spec.ts` installs an API interceptor
  that returns 500 for any request not in its fixture map and asserts
  `unexpectedRequests`, `failedResponses`, and console errors are all empty
  across its nine-route slice (which includes `/fund-model-results/:id`). Any
  fetch the rail adds on those routes must gain a fixture in the spec.
  `makeDualForecastResponse` (`tests/e2e/fixtures/qa-audit-api.ts:706`) builds
  a response with NO `currentForecastV2` block (the block is optional in the
  contract), so as it stands the spec exercises only the unavailable-basis
  path. Extend the builder to also emit a valid `live` block and a `held`
  variant, plus matching facts-latest and current-plan-versions fixtures whose
  IDs/hashes cohere with the block; the e2e gate must cover both golden paths
  (live and held) and the unavailable-basis path. Budget for this in the diff —
  it is part of the feature, not test noise.
- **Existing header contract:** the spec's `expectHeaderFacts` assertions on the
  fund header must keep passing; the rail adds context, it does not restyle the
  header.
- **UTC:** all date formatting via the existing UTC-pinned pattern
  (`timeZone: 'UTC'`); all test runs `TZ=UTC` (repo rule).
- **No emoji** anywhere in code, copy, or docs (repo rule).
