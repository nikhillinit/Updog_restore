# F1 Publication, Release Admission, and Restatement Implementation Plan

## Overview

Governing policy:
`docs/governance/solo-internal-change-and-production-policy.md`, resolved from
protected `origin/main` before any governed action. This plan does not replace
its authority or evidence requirements.

Complete the release path for persisted actuals drafts, keep canonical
publication disabled until separately admitted, reconcile Fund One from exact
evidence, and then add explicit correction of published actuals without
rewriting history. The owner selected the full roadmap, including later
published-actual restatement, on September 8, 2026. These are sequential
delivery slices with separate acceptance criteria; missing exact F1 actuals do
not block synthetic feature testing or source admission of the draft feature.

Proposed feature-plan version: **F_1.13.0**, an additive minor continuation of
[F_1.12.0](F_1.12.0_fixed-template-financial-facts-publication.plan.md). This is
a plan identifier, not a package-version change or a release claim. Owner
authorized implementation of this full roadmap on September 8, 2026; execute
local phases in bounded batches, preserving separate external-action gates. Plan
approval and independent review do not authorize push, merge, schema/data
application, provider changes, deployment, pilot enablement, shadow, or
activation.

## Problem Statement

The existing candidate already implements immutable draft revisions, restore,
fresh-preview requirements, and bounded legacy migration recovery. Do not
rebuild those features. Four remaining gaps require work:

1. `ACTUALS_PILOT_FUND_ID` jointly registers draft, preview, publication, and
   readback routes. There is no independent runtime control for new publication.
   The private overlay's `canonicalPublicationAllowed: false` is documentary.
2. Migration `0056_actuals_draft_revisions.sql` has no production manifest or
   bounded application procedure. Existing manifest coverage fails for that
   file. The older recovery runner deliberately refuses unknown post-0055
   history.
3. Exact F1 source facts and application identity are incomplete. An earlier
   selected-database read found no F1 row; the existing integration fund is not
   F1. A fresh identity lookup must precede any proposal to create missing
   records.
4. Ordinary publication permanently binds external references to content.
   Correcting a draft works; changing a published reference correctly refuses.
   Appending replacement rows alone would break historical receipt membership,
   double-count capital, or omit replacement cash flows.

## Technical Considerations

- **Identity and authority**: runtime configuration, source facts, reviewed
  code, current-head CI, and production dispatch are different predicates.
  Unknowns fail closed for the action they govern; they do not block independent
  testing.
- **Money and dates**: existing Decimal/string precision, row-count/byte limits,
  UTC dates, fund scope, and complete-coverage contracts remain enforced.
  Replacement tests verify no double count and exact conservation where the
  financial invariant applies. No approximate-to-exact conversion is permitted.
- **Durability**: all mutations retain idempotency and optimistic concurrency.
  Raw historical records remain unchanged by application commands; this plan
  does not claim existing tables universally reject administrative SQL edits.
  New command metadata and lineage enforce their own database constraints.
- **Compatibility**: source admission of default-deny control changes configured
  pilot behavior intentionally; operators must explicitly admit enablement.
  Draft and preview routes stay usable. New-policy facts use explicit codec
  branches; old stored facts/reports and error contracts remain readable.
- **Edge cases**: committed replay after disable, revoked actor during recovery,
  missing F1 identity, sparse genuine migration history, partial DDL,
  replacement of a replacement, concurrency, and dependent-plan staleness are
  acceptance cases, not reasons to introduce generic infrastructure.

## Type Definitions

Phase 1 adds one refusal code and one server configuration reader; no persisted
flag model. Phase 2 uses existing manifest types plus a bounded migration
receipt. Phase 5 adds strict restatement preview/command/item/receipt contracts,
dedicated Drizzle command/item tables, an effective-record projection, and
explicit policy-1.5/payload-6 contract variants. Financial references retain
every field of `FinancialFactsBasisRef`; no snapshot-ID-only shorthand is
accepted.

## Performance and Cost Impact

The publication gate is constant-time. Migration audits use existing catalog
queries with bounded timeouts. Restatement extends the existing per-fund
serialized publication transaction and ancestry validation; query historical
rows/receipts once and build indexed maps, avoiding per-row database queries.
Retain existing byte/row/statement limits and add no new service or dependency.

The existing shared 256 KB JSON transport ceiling also applies to restatement
requests. Contract item and CSV limits are upper bounds; the combined request
must fit the common HTTP body limit. The panel submits one replacement per
correction.

## Backward Compatibility

Phases 1-3 preserve draft/preview routes and introduce intentional default-deny
publication plus prerequisite schema sequencing. Phase 5 adds a new facts policy
and command version; old artifacts remain immutable and readable. No destructive
down migration: recovery uses containment and a reviewed forward action.
Restored application versions must support already-admitted facts/schema before
traffic returns; a pre-payload-6 reader is not an acceptable rollback after
restatement.
