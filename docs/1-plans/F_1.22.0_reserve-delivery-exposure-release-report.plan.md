## Overview

Every `release-production` dispatch gains one read-only, report-only step that
runs the F_1.21.0 exposure reconciliation against the production database for
the window since the last canonical promotion and prints per-classification
counts. It answers, at release cadence and without minting residue, the question
D-B raised: did reserve calculations queued on production complete, or did some
get dropped? The step never blocks a release and never publishes an identifier.

## Problem Statement

F_1.21.0 found that canonical web `068430726a` enqueued reserve calculations the
deployed worker acknowledged without calculating, and that nothing durable
recorded it. Phase 1 (`7b21f953b`, ADR-106) makes each such delivery a visible
worker failure. D-B asked for a check that calculations complete on canonical
production after a release.

The F_1.21.0 option (a), a canary-5-equivalent against the canonical host after
promotion, adds almost no coverage and has real cost:

- `stage-production` creates the staged deployment with
  `vercel deploy --prod --skip-domain`
  (`.github/workflows/release-production.yml`, job `stage-production`), and
  `promote` runs `vercel promote` on that same deployment URL;
  `scripts/release/verify-vercel-promotion.mjs` then proves the canonical alias
  resolves to the expected deployment ID. The canonical host serves the
  deployment that staged canary 5 (`tests/smoke/release-canaries.spec.ts`,
  "canary 5 verifies durable scenario calculation start and success") already
  exercised against the production database (`DATABASE_URL` is
  `PRODUCTION_DATABASE_URL` in `staged-smoke`) and the production workers
  (`staged-smoke` needs `railway-workers-verify`).
- The incident class is skew between the canonical web producer and the workers.
  It happens between phase A and phase B, or between releases, where a
  post-promotion check never runs. From 2026-10-01 to this plan, workers ran
  `55c9a6a2b` while canonical web ran `068430726a`, and no promotion happened.
- A canonical canary would need a new residue reservation identity beside
  `release-canary-http-workflow-v2`
  (`shared/contracts/release-canary-residue-characterization-v2.contract.ts`),
  owner re-certification of the eleven caps and TTL in both the GitHub and
  Vercel `Production` environments (aggregate caps count every unpurged run), a
  second recovery handle, a new evidence fragment, and production residue on
  every release. `preflightCanaryCreation`
  (`server/services/canary-residue-service.ts`) also allows one active canary
  run at a time.

The appendix SQL of F_1.21.0 already classifies every `calculation_queued` event
in a window by what its run and later events show, read-only, and was validated
on a disposable local PostgreSQL 16 database. It is not tracked as code, and it
runs only when the owner remembers to run it.

## Decisions (owner, settled 2026-10-08)

| Id  | Question               | Decision                                                                                     |
| --- | ---------------------- | -------------------------------------------------------------------------------------------- |
| E-1 | Shape of the D-B check | Read-only reconciliation, not a mutating canonical canary. No residue contract change.       |
| E-2 | Where it runs          | Inside `release-production`, window = previous successful canonical promotion to now.        |
| E-3 | Effect of a finding    | Report only. A finding never fails the step or the release.                                  |
| E-4 | What it may publish    | Counts only. No fund, scenario set, job, correlation, or run identifiers, and no role names. |

E-3 rationale: blocking would block the release that repairs the drops (the
F_1.21.1 release is that case). E-4 rationale: Actions logs, step summaries, and
artifacts of a public repository are public.

## Solution Architecture

1. A tracked Node script,
   `scripts/release/report-reserve-delivery-exposure.mjs`, holds the
   reconciliation query as an exported constant. The query keeps the appendix
   classification CTE chain unchanged, takes the window start, window end, and
   stuck threshold as bind parameters, and ends in an aggregate projection: one
   row per (classification, canary fund flag) with a `count(*)::int`, so `pg`
   returns a number, not the bigint string. No identifier column leaves the
   database.
2. The script resolves the window start from the GitHub Actions API: the
   `run_started_at` of the newest completed `release-production.yml` run, other
   than the current one, whose `Promote Staged Vercel Deployment` job contains a
   step named `Promote verified deployment` that concluded `success`. That step
   runs `vercel promote`; once it succeeds, production serves the new release
   even if a later step of the job (canonical proof, evidence upload) or a later
   job fails, so neither the job conclusion nor the run conclusion is used. The
   window starts at that run's start, not at the promotion: the previous phase B
   report ended at its own preflight, before promotion, so starting at the run
   start leaves no gap between consecutive reports. Consecutive windows overlap
   by the length of that run, which a report-only count tolerates. If no such
   run exists, the window starts at the F_1.21.0 exposure bound
   `2026-08-09T00:00:00Z`, and the output says so.
3. The script holds one total deadline of 120 seconds for the whole run,
   computed once at start. Every GitHub request carries an abort signal for the
   remaining budget, the database connect timeout is 5 seconds, and the
   statement timeout is the smaller of 60 seconds and the remaining budget. On
   expiry it exits nonzero with a timeout message. It opens one connection,
   starts a `READ ONLY` transaction, sets a local statement timeout and lock
   timeout, runs the query, and rolls back. It prints the window, how the window
   start was found, the column-presence flags, and the counts, as plain lines
   and as a Markdown table appended to `GITHUB_STEP_SUMMARY`. When any
   non-canary row is classified `no_run_drop_candidate`, `repeat_job_id`,
   `stuck`, `completed_without_snapshot`, or `calculated_event_only`, it also
   emits one `::warning::` annotation with those counts and a pointer to the
   owner-run appendix SQL for the rows.
4. Exit codes separate a valid report from an execution failure: 0 for any
   completed report (findings included), nonzero for invalid arguments, GitHub
   API failure, or database failure.
5. `release-production.yml` job `baseline-policy-preflight` gains one final step
   that runs the script with `DATABASE_URL` from `PRODUCTION_DATABASE_URL` and
   `GH_TOKEN` from `github.token`, scoped to that step's `env`, with
   `continue-on-error: true` and `timeout-minutes: 3`. The step timeout bounds
   the step well inside the job's 15-minute `timeout-minutes` (the existing
   steps took about 70 seconds in runs 36842321386, 36847475505, and
   36856717915), so the report can never cancel the gate job. The job already
   runs in both modes, already uses the `Production` environment, already holds
   `actions: read`, and performs no mutation, so the step adds no approval gate,
   permission, or job. It runs after every existing step, so its outcome cannot
   change the job's outputs.
6. The owner keeps using the appendix SQL locally for the identifiers of the
   rows to resubmit.

## Implementation Details

### 1. Report script

**File**: `scripts/release/report-reserve-delivery-exposure.mjs` (new)

Follow the structure of `scripts/release/assert-canary-residue.mjs`: exported
query constants, exported pure functions, injectable `pg` pool factory and
`fetch`, exit-code constants, and a `main` guarded by the `pathToFileURL`
entry-point check.

- `RESERVE_DELIVERY_EXPOSURE_CONTEXT_QUERY`: the appendix result set 1 minus
  `current_user` and `is_superuser` (E-4). It keeps the three column-presence
  flags, the visible row totals, and the first and last `calculation_queued`
  timestamps.
- `RESERVE_DELIVERY_EXPOSURE_QUERY`: the appendix result set 2 CTE chain,
  unchanged from
  `docs/1-plans/F_1.21.0_reserve-delivery-contract-visibility.plan.md` "SQL",
  except that the `params` CTE reads `$1` (window start), `$2` (window end), and
  `$3` (stuck threshold) with explicit casts, and the final projection groups by
  classification and canary fund flag and returns only the count. The `to_jsonb`
  reads of `deadline_at`, `data_origin`, and `canary_run_id` stay, so the query
  still runs on a schema without those columns.
- `resolvePreviousPromotion({ fetch, repository, token, currentRunId })`: lists
  `release-production.yml` runs with `status=completed`, newest first, 100 per
  page, at most 2 pages (27 completed runs exist on 2026-10-08; each candidate
  run costs one jobs request against the shared `github.token` rate limit), all
  inside the total deadline. For each run other than `currentRunId`, reads its
  jobs; a match is a job named exactly `Promote Staged Vercel Deployment` with a
  step named exactly `Promote verified deployment` whose conclusion is
  `success`, whatever the job and run conclusions. Returns
  `{ source: 'promotion', windowStart: run_started_at, runId }` for the newest
  match, or `{ source: 'fallback', windowStart: '2026-08-09T00:00:00Z' }` after
  the runs are exhausted. A non-2xx response, malformed JSON, or an invalid
  timestamp throws.
- `summarizeExposure(rows)`: validates every row (known classification, boolean
  canary flag, count that is a safe non-negative integer; a string count is
  rejected, which catches a lost `::int` cast) and returns non-canary counts per
  classification, a canary total, and the warning-class total. An unknown
  classification throws, so a drifted query cannot produce a silent report.
- `formatExposureReport(...)`: builds the log lines and the step-summary table
  from the window, its source, the presence flags, and the summary. Its output
  contains numbers, timestamps, classification names, and the promotion run ID
  (a public Actions identifier) only.
- `main(argv, env)`: requires `DATABASE_URL`, `GH_TOKEN`, `GITHUB_REPOSITORY`,
  and `GITHUB_RUN_ID`; accepts `--stuck-after-hours` (default 6, bounded 1 to
  168), `--statement-timeout-seconds` (default 60, bounded 5 to 60), and
  `--deadline-seconds` (default 120, bounded 30 to 150). It runs
  `BEGIN TRANSACTION READ ONLY`, `SET LOCAL statement_timeout`,
  `SET LOCAL lock_timeout = '5s'`, the context query, the exposure query, then
  `ROLLBACK`, and releases the client and ends the pool in `finally`. Window end
  is the database `now()` read inside the same transaction. It never logs the
  connection string or a database error's detail fields; it logs the error class
  and SQLSTATE only.

## Technical Considerations

- **Read-only by construction**: one `READ ONLY` transaction ending in
  `ROLLBACK`, `SELECT` statements only, statement and lock timeouts. The query
  takes no advisory lock and creates no object.
- **Reporting, not authority**: the step follows the repository's split between
  gate steps and reporting steps (`continue-on-error: true` on reporting). A
  database or API failure shows as a failed step with a warning on a successful
  job; it never changes the release outcome. Its absence of findings is not
  evidence of no exposure (F_1.21.0 appendix: the old producer inserted the
  event after `queue.add`).
- **Public output (E-4)**: identifiers stay in the database. The aggregate
  projection removes them before they reach the client, and
  `formatExposureReport` has no identifier input.
- **Window**: a promotion counts once its `Promote verified deployment` step
  succeeds, even if the canonical proof, an evidence upload, or a later job then
  fails, because production serves it. Rollback-mode releases also run that
  step, so they count. Each window starts at the previous promoted run's start,
  so events queued between a phase B preflight and its promotion fall in the
  next report; overlapping windows can count an event twice across two reports,
  never zero times. Phase A dispatches (`railway-workers-only`) never promote,
  so they never move the window. Both phase A and phase B report, so the drops
  between them (`legacy_no_run` deliveries, which the worker fails without
  writing a `calculation_failed` event) show up as `no_run_drop_candidate` in
  phase B.
- **Canary funds**: rows for canary funds are counted separately and never
  warned about; staged canary 5 queues one calculation per release.
- **Resubmitted drops self-heal**: a resubmission that completes creates a
  completed run with the same scenario set and input hash, which reclassifies
  the earlier event as `covered_by_completed_run`.
- **Automation surfaces**: `collectAutomationSurfaces` in
  `tests/regressions/ci-fail-closed.test.ts` collects scripts under `scripts/`
  as `operator:` surfaces at test time (no generated inventory). The new script
  makes GitHub API `GET` requests only and must pass the existing branch-policy
  scans (no workflow dispatch, no mutation request).
- **Pattern usage**: script shape and `pg` pool factory from
  `scripts/release/assert-canary-residue.mjs`; GitHub API JSON fetch with a
  bearer token as in `scripts/release/capture-release-recovery-context.mjs`.
- **First live window**: the job name `Promote Staged Vercel Deployment` and its
  step name `Promote verified deployment` appear unchanged in runs from
  2026-07-12 to 2026-09-30. The newest run whose promote step succeeded is run
  30567774563 (started 2026-07-30T17:50:43Z), so the first report covers
  everything since the `068430726` release run, a wider window than the F_1.21.0
  bound.
- **Edge cases**: no promoted run ever (fallback bound); more than 200 completed
  runs before a match (fallback, reported as such); a matching run with a null
  or invalid `run_started_at` (throws); the total deadline expiring during the
  run scan (nonzero exit, step fails, job continues); an empty window (all
  counts zero, context totals still printed); a schema without the 0050/0051
  columns (presence flags false, query still runs).
- **AGENTS.md mandates** (idempotency, optimistic locking, cursor validation,
  queue job timeouts) apply to mutations, cursors, and queue jobs. This change
  has none.

## Constraints

- Sequencing: this change edits `release-production.yml`, and the F_1.21.1
  release vehicle (#1625) forbids any merge between its baseline capture and
  phase B. Merge this plan's implementation only after F_1.21.1 step 8
  completes, or after the owner explicitly restarts F_1.21.1 at a new baseline.
  The step therefore first runs on the release after F_1.21.1; F_1.21.1 step 10
  (the owner-run appendix SQL) covers that release's own drops.
- The job comment rewrite must not contain a `${{ }}` expression (one in a
  workflow comment breaks the whole file); run `actionlint` after the edit.
- The new integration test is collected only by the Testcontainers config, so
  its own pull request does not run it in CI. Its gate is a local Testcontainers
  run before push.
