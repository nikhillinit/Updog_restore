## Problem Statement

Six BUG findings (report sections quoted therein; line refs keyed to the dirty
baseline):

1. **Run-level deadline resets** — `preflight`, `deployService`, and
   `recoverService` each mint a fresh `config.now() + config.timeoutMs` budget
   (`scripts/release/deploy-railway-workers.mjs:368,725,810,1014`). A
   two-service failure path can consume ~50 minutes of 10-minute phase budgets
   inside a 45-minute job, so the runner can kill the job after a provider
   mutation but before containment evidence is emitted.
2. **Unbounded live-main fence** — the `git ls-remote` subprocess
   (`deploy-railway-workers.mjs:102,327,1017`) has no timeout; a hung
   second-service fence after service A mutated leaves no containment result.
3. **Unreconciled ambiguous rollback** — `deploymentRollback` is Boolean; on
   transport/GraphQL failure or unconfirmed Boolean the code throws without
   discovering whether the rollback was actually accepted
   (`deploy-railway-workers.mjs:835`).
4. **Unreconciled ambiguous redeploy** — a lost redeploy response or missing ID
   returns BLOCKED without discovering the recovery deployment it may have
   created (`deploy-railway-workers.mjs:862`).
5. **Verification poll can outlive its deadline** — `pollRailwayWorkers` checks
   its deadline only between `fetchEvidence()` calls, and the two GraphQL
   requests omit `deadlineAt`
   (`scripts/release/wait-railway-workers.mjs:252,262,310,325`).
6. **Ambiguous deploy can bind a pre-existing exact-SHA deployment** —
   reconciliation does not snapshot deployment IDs before mutation, so a
   historical ready deployment with the expected SHA can satisfy it while the
   actually-created deployment stays unidentified
   (`deploy-railway-workers.mjs:533,725,754`).

## Solution Architecture

Follow the two in-repo reference implementations named by the report — no new
abstraction, dependency, or provider-agnostic framework:

- `scripts/release/verify-vercel-promotion.mjs:192` — one overall deadline
  carried through request aborts, response reads, and clipped sleeps.
- `scripts/release/railway-graphql-transport.mjs:31` — absolute `deadlineAt`
  converted to remaining request time; abort signal covers fetch and body read
  (already landed in the baseline).

Design pillars (fixed decisions inherited from the reviewed executor plan):

1. **Single run budget.** `timeoutMs` becomes the whole-`deployRailwayWorkers`
   run budget. Default **35 minutes**; the workflow job cap stays **45 minutes**
   (`release-production.yml:614-624`, unedited). The 10-minute difference is
   gross reserve shared by pre-helper checkout/setup and post-helper JSON
   emission — tests must word it as gross reserve, not guaranteed finalization
   headroom. Compute `runDeadlineAt` once after argument/environment validation,
   before the first `checkMainReference` call; delete the three phase-local
   resets. Recovery no longer gets a fresh budget (supersedes the baseline's
   per-phase design).
2. **Bounded subprocess.** `fetchLiveMainSha` derives an `execFile` timeout from
   remaining run time and rejects before spawning when none remains, preserving
   typed sanitized failure data.
3. **Pre-mutation identity snapshots.** Immediately before every deploy and
   redeploy mutation, snapshot the complete bounded deployment-ID set (reuse
   `listRecentDeployments`; add a hard ceiling of **100 pages / 500
   deployments** with a `ponytail:` comment naming the ceiling and upgrade
   condition; ceiling exhaustion is typed BLOCKED, never truncated success).
   Immediately before rollback, additionally snapshot the intended prior
   deployment ID and its readiness state.
4. **Novel-identity reconciliation.** A returned deploy or redeploy ID that
   already exists in the pre-mutation snapshot is rejected (typed BLOCKED) — the
   novelty check applies to the initial deploy mutation, not only redeploy. A
   lost/missing deploy or redeploy ID reconciles against the **entire novel-ID
   set** (all discovered IDs absent from the snapshot, not merely the exact-SHA
   subset): resolution requires that set to contain exactly one candidate, and
   that candidate to fully verify (nonempty ID, correct service/environment,
   expected SHA, `deploymentStopped === false`, terminal SUCCESS, at least one
   running instance). Zero novel IDs, multiple novel IDs (even if only one
   matches the expected SHA), disappearing, malformed, wrong-target, wrong-SHA,
   stopped, or non-running candidates stay UNRESOLVED/BLOCKED with every
   observed handle recorded. Novelty is never inferred from ordering, timestamp,
   or SHA alone.
5. **Rollback transition proof.** A confirmed `deploymentRollback === true`
   keeps the existing bounded `waitForRollbackRecovery` path (WATCH #4 stays
   Open). Transport/GraphQL failure, missing Boolean, or false/unconfirmed
   Boolean enters exhaustive bounded reconciliation that accepts exactly one of:
   (a) the same intended prior deployment transitioning non-ready to fully
   ready, or (b) exactly one novel fully verified prior-commit deployment. In
   **both** cases resolution additionally requires the attempted deployment (the
   service's `newDeploymentId`) to be read back as **terminally inactive**:
   `deploymentStopped === true` or a terminal failure/removal status, **and**
   zero running instances. Zero running instances alone is not proof — a
   non-stopped `DEPLOYING`/restarting deployment can transiently show zero
   instances and later serve traffic; such a state is polled under the run
   deadline and otherwise stays UNRESOLVED. Railway models multiple
   simultaneously active deployments, so recovery-target readiness alone does
   not prove the bad deployment stopped serving; if the attempted deployment is
   still active or unreadable, the rollback stays UNRESOLVED. An already-ready
   historical deployment is not proof; commit-hash-only match is insufficient.
6. **Mutation ordering fence.** No later provider mutation (including service A
   recovery) starts while a preceding mutation's identity remains unresolved —
   extends the baseline's `canRecoverPreviousService` gate to the new
   reconciliation outcomes.
7. **Deadline-threaded poll and collectors.** `pollRailwayWorkers` passes one
   absolute poll deadline into `fetchEvidence(deadlineAt)` and on to both
   `postRailwayGraphql` calls. `collect-provider-evidence.mjs` gets one absolute
   collection deadline clipping its Vercel fetches (AbortSignal) and forwarded
   to both Railway requests. `capture-release-recovery-context.mjs` network
   `git fetch` calls get an `execFile` timeout derived from one verification
   deadline (local git commands unchanged).

## Technical Considerations

- **Pattern usage**: mirror `verify-vercel-promotion.mjs` deadline carriage and
  the baseline transport's `deadlineAt` contract; reuse `postRailwayGraphql` and
  `listRecentDeployments` — no new deadline class/module, dependency, or
  cross-release abstraction.
- **Fail-closed evidence**: BLOCKED, malformed JSON, missing exact deployment
  IDs, or nonzero helper exit must never publish successful Railway outputs. Git
  subprocess failures (fence timeout, fetch timeout) emit **fixed typed
  messages** — command class, exit/signal, timing only; raw git stderr and
  remote URLs are never embedded in machine-readable output or nested causes,
  because the existing sanitizer redacts only the supplied Railway token
  (`railway-graphql-transport.mjs:3`) and cannot be trusted to catch
  credential-bearing git URLs. Nested-cause leak tests cover the git paths.
- **Authority boundary**: source admission stays separate from production
  authority (`docs/governance/solo-internal-change-and-production-policy.md`
  resolved from `origin/main`). No push, PR, merge, GitHub reply, or provider
  action without separate explicit authorization. Dispatch HOLD.
- **Edge cases**: deadline exhausted before first mutation (zero
  deploy/rollback/redeploy calls); exhausted after ambiguous mutation (bounded
  reconciliation only, no later mutation); fast infinite pagination (ceiling +
  repeated-cursor rejection); two novel candidates (fail closed, both handles
  recorded); already-ready historical prior deployment (cannot resolve ambiguous
  rollback).
- **Stop conditions** (executor stops and reports rather than guesses):
  unexplained HEAD/diff drift; provider evidence conflicting with assumptions;
  rollback transition unprovable by exact identity + pre-state; more than one
  novel candidate; a fix requiring new dependency, schema change, provider
  mutation, or foreign path; independent review returning fix-first/rethink.

## Performance & Cost Impact

Happy path adds one snapshot listing per mutation (typically one 5-item page
given current per-service deployment counts). The 100-page/500-deployment
ceiling is **per listing attempt**, and reconciliation calls the listing inside
its retry loop, so total read volume is (pages per attempt, up to 100) x
(attempts, paced by `intervalMs` and cut off by the run deadline) — the run
deadline is the binding cumulative bound, not the per-attempt ceiling. A
regression test exercises deadline expiry mid-ceiling-scan. Failure paths get
strictly shorter wall-clock (35-minute helper cap inside the 45-minute job
instead of stacking 10-minute phase budgets past it).
