# Governed Production Release Path Implementation Plan (F_1.3.2)

## Overview

Enable one exact-SHA, owner-dispatched Vercel/Railway release path in
`.github/workflows/release-production.yml` by adding a fixed-purpose Railway
deploy helper and removing the mechanical mutation blocks. Replace the prior
proposal's indefinite "official machine-readable autodeploy readback" blocker
with a layered, policy-consistent autodeploy gate: use an official API readback
if introspection proves one exists, otherwise a per-dispatch operator
attestation input modeled on the existing ADR-082 `operator_evidence_b64`
pattern, corroborated by behavioral observation. Completing this plan
establishes merge eligibility only; production dispatch remains a separate
owner-authorized action under the governing policy.

## Problem Statement

- The release workflow is mechanically blocked: `production-mutation-block` job
  (`release-production.yml:64-71`, `validate-target` needs it at `:75`),
  `if: ${{ false }}` on `stage-production` (`:379`) and `promote` (`:1304`). No
  tracked code can deploy Railway workers at an exact SHA; every Railway call in
  the repo is a read-only GraphQL query.
- Railway autodeploy for the two Git-connected worker services would race an
  owner-dispatched exact-SHA deploy; it must be gated off before the workflow
  mutates providers — by authenticated API readback where one exists, otherwise
  by an owner-attested manual precondition with explicitly accepted residual
  risk (attestation is evidence, not machine proof).
- The superseded proposal gated all mutation on an official machine-readable
  autodeploy readback that current Railway documentation does not provide (UI
  control only) — an indefinite self-block, and stricter than the governing
  policy, which requires exact returned-target-identity verification after
  mutation but nowhere requires machine-readable pre-mutation readback and
  already accepts operator-attested evidence as a dispatch input (ADR-082).

## Solution Architecture

Keep `release-production.yml` as the only tracked provider-mutating caller. One
fixed-purpose helper deploys exactly the two Railway worker services
(`capital-call-status`, `fund-scenario-calc` — ADR-075) serially at the exact
candidate SHA via GraphQL mutations, with re-fencing between steps and
compensating rollback/redeploy recovery. Vercel staging/promotion logic is
unchanged.

Job DAG (matches the existing workflow topology, where
`staged-provider-identity` verifies Railway state and already depends on
`railway-workers-verify` at `release-production.yml:1063`):

```text
validate-deployment (fences: main SHA, topology, token scope, autodeploy gate)
  -> Railway deploy job (new; serial two-service mutation)
  -> railway-workers-verify (exact returned deployment IDs)
  -> staged-provider-identity -> g4 --\
  -> staged-smoke (parallel branch) ----> promote
```

(`staged-smoke` runs parallel to the identity → g4 branch and joins at
promotion, preserving the existing workflow's parallelism — do not serialize it
behind g4.)

Both returned Railway deployment IDs are exposed as job outputs and flow into
`railway-workers-verify` as the expected IDs. **No evidence-manifest change**:
the release-evidence fragment kinds are a closed, strict discriminated union
with an exhaustive producer map
(`shared/contracts/release-evidence-fragment-v1.contract.ts:10-38`), and the
existing `release-provider` fragment (produced by `promote`) already carries
per-service Railway identity — `serviceId`, `deploymentId`, `sourceSha`
(`RailwayIdentitySchema`, `:143-152`). The deploy job's returned IDs are
therefore evidenced through job outputs, `railway-workers-verify`, and the
existing `release-provider` fragment; no new fragment kind, no payload widening.
The finalizer **job wiring** does change: `evidence-finalizer` has a fixed
`needs` list, per-job result env vars, and an ordered failure-stage list
(`release-production.yml:1662-1734`), pinned by
`tests/regressions/ci-fail-closed.test.ts:6198-6211` — the deploy job is added
to all three (needs, result env, stage list, positioned before
`railway-workers-verify`) and the test pin is updated in the same lockstep
commit, so a deploy failure reports its true stage instead of a skipped
`railway-workers-verify`.

### Autodeploy gate (layered, replaces the readback blocker)

1. Owner disables autodeploy for both services in the Railway UI (one-time
   manual precondition).
2. One-time introspection probe (railway.com/graphiql or equivalent) during
   implementation: if the public API exposes a stable autodeploy-state field on
   the service/service-instance, wire it as the authenticated preflight readback
   and prefer it permanently. The same probe is widened into a **blocking
   provider-contract validation phase**: before the mutating helper is written
   or any workflow guard is removed, record authoritative provider documentation
   or a non-mutating authenticated introspection result for every operation,
   argument, response field, status value, and recovery capability the helper
   uses (`serviceInstanceDeployV2`, `deployment`, `deploymentRollback`,
   `deploymentRedeploy`, `canRollback`, `canRedeploy`, `meta.commitHash`,
   terminal statuses). Ambiguous or unavailable schema evidence leaves
   production mutation mechanically blocked — these operation names are
   currently plan text only; nothing in the repository can validate them.
3. Otherwise, the workflow requires a per-dispatch operator attestation input
   (`railway_autodeploy_attestation`) following the existing
   `operator_evidence_b64` pattern. This branch is an **owner-accepted, attested
   manual precondition — not machine proof that autodeploy is disabled**: it
   cannot rule out a later Git-triggered deployment race, and that residual risk
   is recorded and accepted in ADR-089 and in the run evidence. The attestation
   payload binds: project ID, environment ID, both service IDs, the observed UI
   autodeploy setting per service, capture timestamp, candidate SHA, dispatching
   actor identity, and an evidence hash; a strict schema/codec validates shape
   and enforces an explicit maximum attestation age. Absent, malformed, or stale
   attestation fails closed before any mutation. Selecting this branch touches
   the canonical dispatcher and its pins: `scripts/deploy-production.ps1`
   (constructs the exact dispatch payload, `:172`) gains the parameter, and
   `tests/regressions/ci-fail-closed.test.ts:5263` (pins the workflow's 11-input
   count) is updated in the same commit.
4. Corroboration: the existing read-only deployment observation (the
   `wait-railway-workers.mjs` query surface) verifies during preflight that no
   new deployment exists for the candidate SHA that the workflow did not create
   — corroboration of **current deployment state only**, never proof of the
   autodeploy setting. Attestation and observation are evidence and
   machine-checkable prerequisites, never authorization — authority remains the
   owner dispatch itself (governing policy, production-dispatch issuer rule).

Never use a private/internal Railway endpoint. Never commit attestation content
to the repository.

### External prerequisites (not codebase-provable)

Repository inspection cannot validate provider behavior. These stay explicit
gates — each is either proven during the provider-contract validation phase /
authenticated preflight, or owner-accepted as residual risk in ADR-089:

1. Railway supports the named mutations, argument shapes, and response fields;
   returned deployment IDs identify the exact created/reused deployment;
   `meta.commitHash` is stable and authoritative.
2. Terminal/health/rollback/redeploy semantics (`canRollback`/`canRedeploy`)
   mean what the recovery algorithm assumes.
3. An autodeploy-state readback field exists (else: attestation branch with
   owner-accepted residual risk); autodeploy is actually disabled for both
   services.
4. Production project/environment/service IDs match the repository variables;
   `RAILWAY_TOKEN` holds required read and write permissions.
5. Protected-environment approval and owner-dispatch configuration remain
   correct; live rollback/redeploy behavior is safely characterized at first
   authorized dispatch.

## Implementation Details

### 1. Railway deploy helper

**File**: `scripts/release/deploy-railway-workers.mjs` (new)

Supports exactly `capital-call-status` and `fund-scenario-calc`; names fixed in
code. Project, environment, and service IDs come from the existing GitHub
variables (`vars.RAILWAY_PROJECT_ID`, `vars.RAILWAY_ENVIRONMENT_ID`,
`vars.RAILWAY_FUND_SCENARIO_CALC_SERVICE_ID`,
`vars.RAILWAY_CAPITAL_CALL_STATUS_SERVICE_ID`) and `secrets.RAILWAY_TOKEN`. No
provider framework, service registry, new artifact family, or hardcoded
production IDs.

GraphQL operations (exact):
`serviceInstanceDeployV2(serviceId, environmentId, commitSha)`; `deployment(id)`
reading `id/status/meta/ canRedeploy/canRollback`; `deploymentRollback(id)`;
`deploymentRedeploy(id)`.

Transport: no shared Railway transport module exists today — the endpoint
constant and authenticated POST wrapper are duplicated per script
(`collect-provider-evidence.mjs:14,95-108`,
`wait-railway-workers.mjs:13, 232-244`, plus a third copy in
`capture-release-recovery-context.mjs:26`). Extract a minimal shared module
(endpoint constant + authenticated GraphQL POST helper) under
`scripts/release/`, migrate the two observation scripts and the new deploy
helper to it, and add it to the file inventory. Note the actual regression pin:
`tests/regressions/ci-fail-closed.test.ts:4968` bans the inline Railway URL in
the `staged-provider-identity` job's run-scripts (the workflow must delegate to
scripts) — it is not an endpoint-centralization assertion across `.mjs` files;
the extraction is deduplication, and the workflow-delegation constraint must
keep holding.

The helper owns its own deployment-ID wait loop with its own timeout budget.
`wait-railway-workers.mjs` is not stretched: its ten-minute window is a hard
ceiling (`MAX_TIMEOUT_MS = DEFAULT_TIMEOUT_MS`, `:19-21`) and it remains the
worker-health verifier only.

Dry-run mode: validates arguments and exact operation names, variables, headers,
and request bodies; injected transport or fixture responses; zero network calls;
no credentials; claims nothing about token scope, live topology, autodeploy
state, or deployability.

Token-scope preflight (authenticated mode): a read query proving the token
resolves the expected project/environment and exactly the two expected services,
before any mutation. This proves **read visibility and topology only** — a
successful read query is not proof of mutation permission. If the
provider-contract validation phase finds an official token-scope/permission
readback field, wire it into preflight and claim write-scope proof; otherwise
write capability remains unknown until the first mutation, which is the first
write proof. On a scope-denied first mutation: no deployment is created, the run
records the denial as evidence and returns BLOCKED (consistent with the
edge-case list below).

### 2. Mutation sequence and recovery

Serial, fixed order, re-fencing before each service:

1. Re-fence live `main == expected_sha` (run attempt one, `refs/heads/main`),
   topology, autodeploy gate.
2. If an active successful deployment already has the exact candidate SHA,
   record and reuse its deployment ID.
3. Otherwise call `serviceInstanceDeployV2`.
4. Wait on the exact returned deployment ID for terminal success, healthy
   instances, and matching `meta.commitHash`.
5. Re-fence before the second service.

Failure behavior: if service B fails after service A changed, re-read A's prior
deployment; `deploymentRollback(priorId)` only when it reports
`canRollback: true`, else `deploymentRedeploy(priorId)` when
`canRedeploy: true`; verify the recovery deployment ID, terminal status, and
prior exact commit. If neither capability exists or recovery verification fails,
return `BLOCKED` with every old/new deployment handle; Vercel promotion remains
blocked. Reruns are structurally forbidden (`GITHUB_RUN_ATTEMPT != 1` rejected
at `:83-87`), so recovery continuation is always a fresh, separately authorized
dispatch, which may reuse an already-successful exact-SHA service and mutate
only the missing one. After both Railway services verify, existing Vercel
promotion and exact deployment-ID/SHA verification run; post-promotion rollback
remains a separately authorized rollback dispatch.

## Technical Considerations

- **Pattern usage**: exact-ID verification after every provider action (policy
  consequence-proof floor); evidence never authorizes; fail closed on
  absent/stale/mismatched prerequisites.
- **Concurrency**: non-canceling group means a stuck deploy holds the release
  lane until its own timeout — the deploy job's budget is the backstop.
- **Autodeploy residual risk**: `PRODUCTION_SCRIPTS.md` records a 2026-08-14
  observation where a failed autodeploy left the prior deployment active;
  preflight therefore verifies the _current active_ deployment identity, not
  just absence of new deployments.
- **Edge cases**: exact-SHA reuse path; partial failure between services;
  recovery capability absent; attestation absent/malformed; token lacking write
  scope (fails at first mutation — recorded, workflow returns BLOCKED).
