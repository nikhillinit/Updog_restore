# WS2 — Reachable Transaction Audit → Repair Implementation Plan

Version: F_1.2.4 (child plan B of master
`docs/1-plans/F_1.2.0_v1.4-release-proof-activation.plan.md`; P0 critical path).
Plan-version numbering is decoupled from `package.json` (user-confirmed

## Overview

Vercel production runs the Drizzle neon-http driver (`server/db.ts`), which
cannot execute callback transactions: every `database.transaction(...)` call
reachable from the Vercel surface throws at runtime. This plan (a) audits all
server-side transaction call sites for Vercel reachability and ratifies a
per-path architecture at gate G2, then (b) repairs the three P0
current-forecast/mode paths and the five LP-reporting `withTransaction` helpers,
hardens `server/lib/transaction-support.ts`, and adds a real-Neon integration
test lane so the repair is proven against actual driver semantics (gate G3). The
transaction architecture is user-locked (master plan "Decisions Locked",
2026-08-05): audit-first mixed — per-path classification, P0 paths become atomic
SQL/CTE, a driver switch happens only if the audit shows broad need. This plan
does not reopen that decision.

## Solution Architecture

Two phases mapped to the master plan's gates:

- **Phase 1 (→ G2)**: classify every `.transaction(`/`withTransaction` call path
  by Vercel reachability (route-mount tracing per ARCHI §3 two-surface
  architecture) into (a) atomic-SQL/CTE rewrite, (b) genuinely needs
  multi-statement transaction → escalate driver decision, (c)
  Railway-only/unreachable → documented exclusion. Deliverable: tracked audit
  artifact. G2 = user ratifies the classification.
- **Phase 2 (→ G3)**: execute the ratified repairs — P0 atomic rewrites, LP
  helper repair, transaction-support hardening, guardrail, real-Neon test lane.
  G3 = repaired paths pass real-driver tests including idempotency replay and
  concurrent-writer conflict.

Phase 2 tasks are written now but dispatched only after G2 closes (master-plan
stop condition: no executor handoff until the upstream gate closes).

### 2. P0 atomic rewrites (Phase 2)

**Files**: `server/services/fund-calculation-mode-service.ts` (modify),
`server/services/current-forecast-reference-service.ts` (modify)

Rewrite each P0 callback body as a single atomic SQL/CTE statement with
optimistic-lock guards and idempotency preserved:

**Claim-atomicity invariant (applies to mode update and activation)**: today the
idempotency claim, the mutation, and the ledger completion commit together — a
crash anywhere rolls all of them back. On neon-http a standalone claim statement
followed by a separate guarded write would strand the ledger row `pending` on
mid-sequence failure, and both retry paths reject pending rows
(`FundCalculationModeInProgressError` — mode service `:501`, activation `:640`),
bricking the key forever. Therefore each rewrite MUST either (a) fold claim +
guarded mutation + ledger completion into **one** CTE statement (claim insert as
the first data-modifying CTE; mutation CTEs fenced on the claim having returned
a row AND guards matching; completion update in the same chain), or (b)
introduce an explicitly designed reclaimable claim state (lease/expiry allowing
a same-key retry to re-drive a dead pending claim) — (a) is the default; (b)
requires user sign-off because it changes the ledger state machine. Sequential
claim-then-write without one of these is forbidden.

Under (a), **no execution outcome may leave a fresh claim row `pending`**: the
statement must resolve the claim in the same chain on every path. On guard
failure the claim must be **suppressed** (claim CTE conditioned on the guard
predicates) or **deleted** in a trailing CTE — preserving today's semantics,
where a rolled-back transaction leaves no claim and a same-key retry after the
blocker clears succeeds. Completing a guard-failed claim as a terminal
failed/blocked row would make the error replay permanently — that is a contract
change and is **not** adopted here (it would require explicit user approval).
Retry contract per terminal state: completed success replays 200;
suppressed/deleted claim retries fresh. A same-key retry must never be
permanently rejected by a stranded `pending` row.

- **Mode update (`fund-calculation-mode-service.ts:869`)**: the callback does
  idempotency claim (`claimOrReplay`), version check, accepted-ref load, mode
  upsert, ledger completion. Restructure per the invariant above: one CTE
  statement chaining claim insert → version-checked mode upsert → ledger
  completion, version predicate in the `WHERE` clause so a conflict yields zero
  mutated rows (mapped to the existing `FundCalculationModeVersionConflictError`
  contract; distinguishing guard-fail from claim-conflict via the CTE's returned
  columns). Replay reads stay separate statements (read-only, no atomicity
  need).
- **Pointer advance (`current-forecast-reference-service.ts:342`)**: today locks
  the mode row (`FOR UPDATE`), guards
  (effective-`on`/not-killed/not-superseded), then three writes (supersede-head,
  candidate-flip, mode-row update). The function takes **no expected version and
  no idempotency key** — the existing contract serializes concurrent advances
  via the row lock and lets both succeed (last committed wins the head). The
  rewrite must **preserve that contract**: one CTE chain whose mode-row `UPDATE`
  carries the existing guard predicates only (no invented version check), with
  supersede and flip as data-modifying CTEs fenced on the guarded update
  matching. **CTE ordering must be enforced by data dependency, not lexical
  position, and the guard must lead the chain**: a **leading guard CTE** selects
  the mode row iff all guard predicates hold; the supersede CTE consumes the
  guard's output, the candidate-flip CTE consumes the supersede's `RETURNING`,
  and the final mode-row update consumes the flip's. Guard failure then yields
  zero rows through the whole chain — nothing mutates. Placing the guard-bearing
  update last is forbidden: earlier sibling CTEs would still commit their writes
  even when the final update matches zero rows. **The guard CTE must be
  `SELECT ... FOR UPDATE` on the mode row and must return the current
  `cutover_reference_id`**, with the supersede CTE targeting that returned head
  — a plain `SELECT` guard is insufficient: under read committed a second
  concurrent statement can plan against an old snapshot, wait on the head
  mutation, then miss the newly accepted head or trip the partial unique index.
  The `FOR UPDATE` lock serializes concurrent statements on the mode row and
  (via `READ COMMITTED` lock-wait re-read) re-evaluates against the committed
  head, giving the required serial-order-equivalent both-succeed outcome. If
  implementation shows the locking-CTE semantics cannot deliver this within one
  statement on neon-http, the pointer path escalates to class (b) — it does not
  ship with a racy guard. Net: the pointer path **retains mode-row lock
  serialization** (statement-scoped instead of transaction-scoped); the partial
  unique index is the backstop, and conflict tests must prove the outcome is
  equivalent to some serial order (both succeed, single non-superseded head, no
  constraint violation) — NOT a new 409. Any new concurrency contract
  (expected-version parameter) is out of scope unless the user explicitly routes
  it.
- **Activation latch (`:607`)**: `verifyGreenCandidate` is a read gate that
  cannot join the write statement — restructure as: verification reads first
  (advisory), then **one** CTE statement per the claim-atomicity invariant:
  claim insert → guarded supersede + candidate-flip + mode flip to `on` + ledger
  completion, with `activated_at IS NULL` and version predicates inline so the
  one-way latch is enforced by the statement itself, not by the preceding reads.
  Claim-conflict (existing key) falls to the replay read path exactly as today.
  A blocked activation (guards fail) must leave **no claim row** — the claim CTE
  is conditioned on the guard predicates (suppressed) or the chain deletes it in
  the same statement — preserving today's retry-after-blocked semantics, where
  the same key succeeds once the blocker clears. The guard-leads-the-chain rule
  from the pointer rewrite applies here identically.

Semantics contract for all three: same success/error surface (409 codes, replay
behavior) as today; verified by existing unit suites plus the new real-driver
tests. If any path proves impossible to fence in one statement during
implementation, it escalates to class (b) and returns to the user — it does not
get emulated with sequential autocommit writes.

## Technical Considerations

- **Pattern usage**: guarded single-statement CTEs follow the existing
  idempotent-claim pattern (`ON CONFLICT DO NOTHING RETURNING`,
  `fund_calculation_mode_requests` ledger); optimistic locking stays
  version-predicate-in-WHERE (Zero Tolerance policy). Guardrail mirrors the
  existing `guardrails:check` script shape.
- **Neon semantics**: single statements (including data-modifying CTE chains)
  are atomic on neon-http; each rewrite must prove one-statement fit or
  escalate. Never emulate atomicity with sequential autocommit statements.
- **Concurrency-semantics change**: on the version-guarded paths (mode update,
  activation) lock-then-write becomes conditional-write — interleavings that
  previously blocked now race to the guard predicate, mitigated by version
  predicates, the ledger unique, and mandatory concurrent-writer tests. The
  pointer path is the exception: it retains mode-row lock serialization via its
  `FOR UPDATE` guard CTE (statement- scoped), backstopped by the accepted-head
  partial unique index.
- **Financial-path gates**: mode/forecast/LP paths are calculation-adjacent —
  `npm run phoenix:truth` + `npm run calc-gate` mandatory in Phase 2;
  `phoenix-precision-guardian` sign-off if numeric paths are touched,
  `xirr-fees-validator` for fee-adjacent LP paths (master plan WS2 sign-off).
- **Edge cases**: concurrent pointer advance vs activation; same-key activation
  replay racing a fresh-key attempt; fallback path hit by a future driver
  message change (now loud, not silent); `skipTransaction` callers nested inside
  an outer transaction.

## Performance & Cost Impact

Each statement on neon-http is one HTTP round-trip: collapsing callback
transactions (N statements, which today just throw) into one CTE statement both
fixes correctness and reduces round-trips versus any working multi-statement
alternative. The neon lane adds bounded CI wall-clock (container spin-up
comparable to the testcontainers lane).

## Backward Compatibility

- No schema migration expected (all rewrites target existing tables/indexes; the
  accepted-head partial unique and the request-ledger unique already exist). If
  the audit discovers a missing supporting index/constraint, it is an additive
  journaled migration flagged to the user first.
- External API semantics preserved: same routes, same success/409/404 contracts,
  same idempotency replay behavior. Conflict tests guard this.
- Railway/Docker surface untouched: websocket-driver transactions keep working;
  class-(c) paths are documented, not modified.
