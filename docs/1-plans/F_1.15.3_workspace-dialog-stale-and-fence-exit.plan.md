# Workspace Dialog Stale Recovery and Fence Exit Implementation Plan

**Governing policy:**
`docs/governance/solo-internal-change-and-production-policy.md` (resolve from
`origin/main`). This plan is a client-only defect repair. It has no production,
schema, or release authority. Merge, deploy, and production remain separate
owner actions.

Source: handoff of 2026-10-29 (FundWorkspace stale dialog + fence corrections),
re-verified against `origin/main` at `6a180dc1e` (#1669, F_1.15.2). Line numbers
below refer to that commit. Branch: `fix/f1153-workspace-stale-dialog` from
`origin/main`, worktree `.worktrees/f1153-workspace-stale`.

Owner decisions (discovery, 2026-10-29):

1. **Stale UX: both, user picks.** On a 412 the dialog writes the durable stale
   state, the same writes the hook and Fund Basics make. It then switches to a
   conflict variant with "Discard my changes and start new". The existing "Keep
   editing" opens `/fund-setup?step=1`, where the shell banner offers Load or
   Keep my changes. Nothing navigates automatically.
2. **Fence: adopt CR_w10 Suggestion 1.** Delete `hydrateThenStartNew`. Start the
   new fund directly when nothing is pending, and directly after a confirmed
   replay that reports `needsHydration`.
3. **Fenced session with no pending command: skip the dialog.** No local values
   exist, so New Fund starts directly. The server draft stays resumable from the
   fund list.
4. **Missing draft on save: include.** A `rejected` outcome with `missingDraft`
   routes to the same discard variant, with its own copy.

Prior decisions respected, not re-opened: F_1.15.0 rulings R5 (canonical
newer-edit comparison) and R9 (`superseded` is silent); F_1.15.2 rule that
recovery stays in the shell's stale banner (this plan sends the user there and
adds no second Load/Overwrite UI).

## Overview

The FundWorkspace "Start another fund?" dialog is the third `save_draft` caller
of `saveDraftAndSettle`. F_1.15.2 gave the other two callers, the autosave hook
and the Fund Basics bootstrap save, a durable stale transition. The dialog still
handles `stale` locally. The dialog also has two dead ends where the draft is
gone or the session is fenced. This plan makes the dialog's stale outcome
durable. It adds one discard variant for "your changes cannot be saved" (stale
or missing draft). It removes the pre-start hydration fetch that
`startNewFundSession` throws away. All changes stay in `FundWorkspace.tsx`. The
settlement module, the hook, the shell, and the store do not change.

## Problem Statement

### A. Stale is handled only in the dialog

`FundWorkspace.tsx:395-399`: `case 'stale':` calls only
`setDialogError(outcome.message)`. Settlement has already resolved the command
and cleared the acknowledgement record (`fund-draft-settlement.ts:153-157`), but
it leaves `draftETag` at the rejected revision. Consequences:

- **Retry loop.** "Save draft and start new" stays enabled. A second click
  prepares a fresh command with the same stale ETag, and the server returns 412
  again, every time.
- **No banner after Keep editing.** `draftServerReady` keeps its old value. When
  it is `false` (the dialog opens for `!draftServerReady`, `:308`), the shell's
  recovery effect returns before its fetch (`useFundDraftSync.ts:360`). The user
  reaches the wizard with no stale banner. The conflict comes back only when an
  edit triggers an autosave 412.
- **Known stale is ignored.** If the store is already `stale` (the user left the
  shell's banner and opened the workspace), the dialog still offers the save,
  which is certain to return 412.

### B. Fence branch dead end and wasted fetch (CR_w10 Minor 1, Suggestion 1)

Both fence branches call `hydrateThenStartNew` (`:333-340`): fetch the draft,
apply it, then `startNewFund()`. `startNewFundSession` (`fundStore.ts:913-927`)
replaces the whole store, so the hydrated values are never read.

- **No pending command** (`:341-353`). The fetch is the only action. A 404
  (`NO_ACTIVE_DRAFT`, fund finalized) or any fetch failure leaves the user stuck
  on a dialog error. The "Discard and start new" label never appears, because a
  fenced session always has a `draftFundId` (`:316`).
- **`saved` with `needsHydration`** (`:370-378`). The save is confirmed, but a
  failed fetch blocks the new fund with "Draft saved. Could not refresh…".
- **Misleading copy.** A fenced session with no pending command has no local
  values: the store merge discarded them (`fundStore.ts:1270-1287`), and the
  wizard hides step content while fenced (`fund-setup.tsx:129`, `:461`). The
  dialog still says "Save changes to … before starting a separate fund".
- **Reached while the dialog is open.** A fenced replay that ends `rejected` or
  `stale` resolves the command, but the fence stays (`fundStore.ts:894`). The
  next click goes into the no-pending branch. Without that branch it would hit
  `prepareFundCommand`'s hydration guard (`fundStore.ts:1412-1414`).

### C. Missing draft on save (owner-included)

`:396-398` also handles `rejected`. With `missingDraft` (409 `NO_ACTIVE_DRAFT`,
`fund-workflow-service.ts:199`), every retry returns the same rejection. The
only exit is "Keep editing", and the shell shows its missing-draft alert only if
it fetches.

## Solution Architecture

The dialog's content is a pure function of store state plus two pieces of local
dialog state (`dialogError`, and a new missing-draft fund id). The precedence
is:

| #   | Condition (first match wins)                                                      | Description copy                       | Confirm label                      | Confirm action                                                        |
| --- | --------------------------------------------------------------------------------- | -------------------------------------- | ---------------------------------- | --------------------------------------------------------------------- |
| 1   | `blockedCommand` (pending command that is not `save_draft`)                       | existing "Check the pending command…"  | unchanged, disabled                | none                                                                  |
| 2   | `draftFundId != null`, no `pendingCommand`, `draftSyncStatus === 'stale'`         | new: stale copy                        | "Discard my changes and start new" | close dialog, `startNewFund()`, no PUT                                |
| 3   | `draftFundId != null`, no `pendingCommand`, local missing id equals `draftFundId` | new: missing-draft copy                | "Discard my changes and start new" | close dialog, `startNewFund()`, no PUT                                |
| 4   | `draftFundId != null`                                                             | existing "Save changes to …"           | "Save draft and start new"         | fenced with no pending: start new directly; otherwise settle the save |
| 5   | `draftFundId == null`                                                             | existing "… not been saved … discards" | "Discard and start new"            | `startNewFund()` (unchanged)                                          |

"Saving draft…" keeps overriding the label while a save is in flight (row 4
only). Rows 2 and 3 require no pending command. `startNewFundSession` drops
`pendingCommand`, so a discard must never run over an unsettled command
(`fund-workspace.test.tsx:349` guards the same rule for creations). Under a
pending `save_draft`, row 4 replays the exact command.

**Entry rule (`handleNewFund`).** After the existing `!hasLocalSession` check, a
session with `needsServerHydration` and no `pendingCommand` starts new directly
(decision 3). The existing settled shortcut and the dialog-open path follow
unchanged.

**Outcome handling (`confirmNewFund`).**

- `saved` with `needsHydration`: close the dialog and start new. No fetch.
- `stale`: write `setDraftServerReady(true)` and `setDraftSyncStatus('stale')`.
  These are the same two writes as the hook's stale branch
  (`useFundDraftSync.ts:180-184`). Clear `dialogError`; row 2 takes over.
- `rejected` with `missingDraft`: record the target fund id in the new local
  state; row 3 takes over. No store write. `rejected` without `missingDraft`,
  `retry_same_key`, `not_dispatched`, `uncertain`, and `superseded` keep their
  current handling.
- The no-pending fence branch closes the dialog and starts new. The
  `hydrateThenStartNew` helper and the `fetchFundDraft` and `applyDraftSnapshot`
  imports are deleted.

**Hand-off to the shell (decision 1).** "Keep editing" already navigates to
`/fund-setup?step=1` (`:577-580`). After the stale writes, the shell mounts with
`draftServerReady: true`, an old non-null `draftETag`, and no pending command.
Its recovery effect fetches, sees a different ETag, captures the server ETag for
Overwrite, and shows the banner (`useFundDraftSync.ts:396-401`). A 412 needs an
`If-Match` header: a missing header returns 428 (`fund-workflow-service.ts:63`).
So a non-fenced stale outcome always leaves a non-null `draftETag`, and the
shell never takes its silent-overwrite branch (`:374`) for it.

## Implementation Details

### 1. FundWorkspace dialog and handlers

**File**: `client/src/components/workspace/FundWorkspace.tsx`

**Current state**: `NewFundDialog` (`:193-251`) picks copy and label from
`blocked`, `canSave`, `saving`. `handleNewFund` (`:307-314`) opens the dialog
for any unsettled session. `confirmNewFund` (`:318-410`) holds
`hydrateThenStartNew`, the fence branch, and the outcome switch.

**Modifications**:

- `NewFundDialog`: add one prop for the discard reason
  (`'stale' | 'missing' | null`). Copy and label follow the precedence table.
  The discard label uses the existing destructive outline classes from the
  "Discard and start new" button (`:236`). The description element gets
  `aria-live="polite"`, so a switch to rows 2 or 3 while the dialog is open is
  announced. That switch replaces the `role="alert"` error the user hears today.
  The dialog does not announce twice on open. A live region announces changes to
  content that is already rendered, not its first render. On open, only the
  `aria-describedby` announcement runs; the polite region speaks only when the
  variant text changes later. The description text does not change during a
  save, so the region stays quiet then.
- Stale copy (row 2): "A newer version of {name} is saved on the server, so your
  changes were not saved. Discard them and start a new fund, or keep editing
  this draft." It does not promise a Load/Keep choice, because a fenced session
  hands off to a silent server load (Edge cases).
- Missing copy (row 3): "{name} has no active draft on the server, so your
  changes cannot be saved. Discard them and start a new fund, or keep editing."
- `FundWorkspace`: derive the discard reason from `draftSyncStatus` (already in
  the selector tuple, `:261-272`), `pendingCommand`, `draftFundId`, and the new
  local missing-draft fund id. `handleNewFund` resets the missing id together
  with `dialogError`, because a published fund can later get a new draft
  (`:76`).
- `handleNewFund`: add the fenced-no-pending direct start (Solution
  Architecture, entry rule). Add `needsServerHydration` to the selector tuple.
- `confirmNewFund`: when the discard reason is set, close the dialog and start
  new before any save logic. Replace the no-pending fence branch body and the
  `needsHydration` branch with a direct close-and-start. Apply the `stale` and
  `missingDraft` outcome changes. Delete `hydrateThenStartNew` and its two
  imports.
- Unchanged: `superseded` returns silently (R9). `newerEdits` stays the
  settlement's canonical comparison (R5). The `saved` path without
  `needsHydration`, `uncertain`, `not_dispatched`, and `retry_same_key` keep
  their current behavior.

### 3. Shell hand-off contract test

**File**: `tests/unit/pages/fund-setup-draft-sync.test.tsx`

One test pins the state the dialog leaves behind: `draftServerReady: true`,
`draftSyncStatus: 'stale'`, old ETag, no pending command, local edits. It
follows the existing stale-on-mount test (`:605-640`). Assertion order matters.
The shell renders the banner for any non-`idle` status (`fund-setup.tsx:344`),
so the preset `stale` shows `draft-stale` before the recovery effect runs. The
test therefore first waits for `fetchFundDraft` to be called once for the fund.
Only then does it assert `draft-stale`, the kept local values, and no PUT.
Finally it clicks "Keep my changes", then "Overwrite saved draft", and asserts
that the PUT carries the fetched server ETag. That proves the shell rebuilt
`stale` from ETags rather than reusing the preset. The hook is unchanged, so
this test is expected to pass on main. It pins the cross-component contract and
is not a red-first test.

## Technical Considerations

- **Pattern usage**: callers own status, `draftServerReady`, dialog text, and
  navigation (ARCHI §5, fund draft command settlement). The dialog already
  writes durable status for `uncertain` (`:389-390`). The stale writes mirror
  the hook (`useFundDraftSync.ts:180-184`) and F_1.15.2's Fund Basics change.
- **Readiness semantics**: a 412 proves that an active draft exists, so
  `draftServerReady: true` is truthful (F_1.15.2 rationale). The flag is
  persisted in the envelope (`fundStore.ts:780-797`). `draftSyncStatus` is not
  persisted, and the shell rebuilds `stale` from ETags after a reload.
- **Session safety**: the outcome callback runs in the same turn as the
  settlement fence (session, fund, command key). The new store writes therefore
  need no extra session check, as with `uncertain`. Discard actions run on a
  user click against the current store, and rows 2 and 3 require no pending
  command.
- **No new UI primitives or tokens**: existing `Dialog` and `Button`. The
  destructive style is the existing
  `border-error-dark text-error-dark hover:bg-error/10` outline. The primary
  action stays charcoal (`bg-presson-accent`), per `DESIGN.md`. No Preact-compat
  risk.
- **Edge cases**:
  - **Fenced replay gets 412.** The command resolves, but the fence stays. The
    dialog writes stale and shows row 2. Keep editing reaches the shell, which
    applies the server snapshot without a banner (`useFundDraftSync.ts:374`).
    This is pre-existing hook behavior, and it is correct here: no local values
    exist, and the rejected body has left the journal. The row 2 copy makes no
    "values kept" promise. If the user closes the dialog and clicks New Fund
    again, the entry rule starts new directly.
  - **Fenced replay rejected (not missing).** The error text shows. The next
    click goes through the no-pending fence branch and starts new without a PUT
    or a fetch. In this one path the dialog still shows the row 4 copy and the
    "Save draft and start new" label, but the click saves nothing. This is
    accepted under decision 3. The path needs a fence, a pending replay, and a
    rejection while the dialog is open. No local values exist to save, and
    reopening New Fund skips the dialog through the entry rule.
  - **Stale after a reload on the workspace page.** Status is back to `idle`, so
    row 4 sends one PUT, gets 412, and switches to row 2. One extra request is
    acceptable.
  - **Stale with a pending `save_draft`.** Row 4 replays the exact command. The
    discard rows never drop an unsettled command.
  - **Missing draft, then Keep editing.** The shell shows its missing alert only
    if it fetches (`draftServerReady` already true). Otherwise the alert waits
    for an autosave rejection. This is unchanged; the dialog now offers the
    direct exit.
  - **428 / other 4xx.** These are classified `rejected` without `missingDraft`
    (`fund-workflow.ts:56-70`). The existing error text applies.
- **Risk**: the main regression risk is a discard path that drops recoverable
  data. Mitigations: discard rows require no pending command; the copy names the
  loss; the server keeps its draft in every discard case (stale: server holds
  the newer revision; missing: the fund is finalized; fenced: values are already
  gone).
