## Overview

Three client callers dispatch the same `save_draft` command and settle it by
hand: the wizard autosave hook, the Fund Workspace "save before starting another
fund" dialog, and the Fund Basics bootstrap save that follows fund creation. Two
of them also re-implement server-snapshot hydration. This plan moves command
settlement and snapshot application into one new module,
`client/src/services/fund-draft-settlement.ts`, that sits between the callers
and the existing transport in `client/src/services/fund-drafts.ts`, and leaves
each caller with only its continuation: debounce, edit queueing, dialog text,
navigation, and the explicit stale-draft choice.

Discovery chose to extend `fund-drafts.ts`. Codex round 1 showed that an ES
module's internal call to `saveFundDraft` binds to the local function, so a
helper inside `fund-drafts.ts` would bypass the partial `vi.mock` of
`@/services/fund-drafts` and call real transport in all six caller suites. Other
test seams exist (re-mocking every suite wholesale, or injecting the transport),
but a separate module that imports `saveFundDraft` from `fund-drafts.ts` is the
smallest option that keeps every existing suite's mock shape unchanged. Round 3
confirmed: keep the separate module.

## Problem Statement

`client/src/services/fund-drafts.ts` owns the wire call and its uncertainty
rules. The lifecycle around it leaks into callers:

- `client/src/hooks/useFundDraftSync.ts:130-205` (autosave) prepares the
  command, saves, fences on session/fund/key, advances the ETag, marks the
  server ready, resolves the journal, decides whether hydration must follow,
  detects newer local edits, and classifies stale/uncertain/rejected.
- `client/src/components/workspace/FundWorkspace.tsx:366-433` (dialog) repeats
  every step with `JSON.stringify` signatures instead of canonical JSON, maps
  412 to generic text, and hydrates inline at lines 337-352.
- `client/src/pages/FundBasicsStep.tsx:224-274` (bootstrap) repeats it a third
  time; the review listed only two callers.
- `useFundDraftSync.ts:218-237` and `FundWorkspace.tsx:337-352` both apply a
  fetched snapshot with the same seven-field store patch.

Any change to the settlement rule (for example the ETag null-coalesce, or the
key fence) must land in three places, and recent fixes already landed one caller
at a time: #1568 (`293a88c02`) added the key fence to the workspace
rejected-path `resolveCommand` only, and #1567 (`defd02073`) added
`needsServerHydration` recovery as separate copies in the hook and the
workspace. The callers agree today; the duplication is what let them disagree in
between.

## Solution Architecture

Deepen the existing seam by adding one module above it. `fund-drafts.ts`
(`saveFundDraft`, `fetchFundDraft`, `isMissingDraftError`) is unchanged. New
`fund-draft-settlement.ts` exports:

1. `saveDraftAndSettle(fundId, options, onOutcome)` — reads the store, builds
   the write payload through `fundStoreToDraftWriteV1`, calls
   `prepareFundCommand`, dispatches `saveFundDraft` with the prepared key and
   revision, applies the post-await fence (session id, draft fund id, pending
   command key), settles the journal, and delivers one discriminated outcome
   (see Type Definitions) to `onOutcome` in the same synchronous turn as the
   fence and the settlement. It returns `Promise<void>`, resolved after
   `onOutcome` (and anything `onOutcome` returns) completes. Nothing about the
   outcome is returned. It never writes `draftSyncStatus`, `draftServerReady`,
   hook refs, or UI state.
2. `applyDraftSnapshot(fundId, snapshot)` — the shared store patch: hydration
   patch from `fundDraftWriteV1ToStoreHydrationPatch` plus `draftFundId`,
   `draftServerReady: true`, `needsServerHydration: false`, `draftETag`,
   `pendingCommand: null`. It never writes `draftSyncStatus` (see ruling R1).

Why a callback and not a returned outcome (round-3 F1): a returned outcome is
consumed after one more `await`, and that microtask boundary sits after the
ownership check and the journal release. Another queued continuation (a session
replacement, a hydration snapshot, a newer command) can land in that gap, and
the caller would then act on a verdict computed for state that no longer exists:
reset the wrong session, discard an edit, or navigate and mark ready for a stale
result. Today all three callers check ownership, compare edits, and continue
without an intervening await (`FundWorkspace.tsx:390-409`,
`FundBasicsStep.tsx:249-266`, `useFundDraftSync.ts:160-176`); the callback keeps
that property. Returning nothing removes the tempting second path.

Callers keep everything that differs between them. Interface is the test
surface: the outcome table is exercised once against a mocked `saveFundDraft`
with the callback captured; callers are tested for their continuations only,
through their existing transport mocks.

Import direction stays acyclic: the new module imports `@/services/fund-drafts`,
`@/services/fund-workflow`, `@/stores/fundStore`,
`@/adapters/fund-store-adapters`, `@/lib/queryClient` (for `ApiError`), and
`@shared/lib/canonical-json-serialization`. None of those import
`@/services/fund-draft-settlement`, `@/hooks`, or `@/components` (verified
2026-09-23). The module's unit test runs in the client (jsdom) vitest project so
that `sessionStorage` exists and an actor can be bound (see Test Impact).

## Implementation Details

### 1. Settlement module

**File**: `client/src/services/fund-draft-settlement.ts` (new)

**Modifications** (contents, in prose; no code in this plan):

- `saveDraftAndSettle`. Steps, in order: read state; build `not_dispatched` when
  `draftFundId` differs from `fundId` (message: "The draft changed before
  saving; try again."); build the current payload with
  `includeEconomicsAssumptions` from options; call
  `prepareFundCommand('save_draft', fundId, payload, state.draftETag)` and map a
  thrown error to `not_dispatched` carrying the error message (storage fence,
  hydration fence, foreign pending operation); dispatch `saveFundDraft` with the
  prepared payload (the replayed original when a command was pending, never the
  freshly built one); after the await, in the same turn: when the session id,
  draft fund id, or pending key no longer match, the outcome is `superseded`,
  whether the request succeeded or failed (ruling R9); on success call
  `setDraftETag(saved.etag ?? current.draftETag)` where `current` is the store
  read after the await (the transport guarantees a revision in production, but
  the `autosave-debounce` test double returns a result without one at line 31;
  coalescing against the post-await store revision is what all three callers do
  today), `resolveCommand()`, then compute `newerEdits` as canonical JSON of a
  freshly built payload versus canonical JSON of the dispatched payload, and
  `needsHydration` from `needsServerHydration` read after `resolveCommand`
  (ruling R4); on error classify with `isStaleRevisionError` first, then
  `classifyWorkflowError`: `stale` and `rejected` resolve the command,
  `uncertain` and `retry_same_key` keep it; every failure outcome carries
  `message` (the thrown error's message, or a fixed fallback when the error is
  not an `Error`); `rejected` reports `missingDraft` when the API error code is
  `NO_ACTIVE_DRAFT`.
- Delivery (round-3 F1): once the outcome is built, and outside the try/catch
  that classifies transport errors, call `onOutcome(outcome)` synchronously,
  then `await` whatever it returns before resolving. No `await` may sit between
  the post-await fence and the `onOutcome` call. Every outcome kind is
  delivered, including `superseded` and `not_dispatched`; callers ignore what
  they do not act on. A throw from `onOutcome` propagates to the caller's own
  try/finally and is never reclassified as a save failure, because the save is
  already settled.
- Synchronous prefix (eng review): the helper runs synchronously from entry
  through `prepareFundCommand` to the `saveFundDraft` call; no `await` precedes
  the transport call. `not_dispatched` is therefore delivered in the caller's
  own turn, so the caller's saving state and its `not_dispatched` error land in
  one render (ruling R11), and the caller's pre-checks and `prepareFundCommand`
  read the same store state.
- `not_dispatched` means only that this invocation sent nothing. A command that
  was already pending before the call remains pending with its key, body
  signature, and expected ETag preserved: a foreign operation is refused before
  `beginCommand` and is untouched; a `save_draft` replay refused by the storage
  fence has been re-begun by `prepareFundCommand` (`fundStore.ts:1423`), so only
  its `dispatchedAt` may refresh. The outcome never claims the journal is empty.
  Callers already refuse to start over a foreign pending command; the helper
  reports, it does not release.
- `applyDraftSnapshot`. One `fundStore.setState` call with the seven-field patch
  above. No status write, no ref access.
- No React imports.

## Technical Considerations

- **Pattern usage**: ARCHI.md section 5 hooks and services; ports-and-adapters
  with the existing transport (review "Seam discipline"). No new adapter, no
  command framework, no class, no config. One new file in `client/src/services/`
  beside the two it composes.
- **Preact compat**: helpers are plain functions with no React import; the hook
  keeps its existing React surface.
- **Same-turn continuation** (round-3 F1): the post-await fence, the journal
  settlement, the newer-edit verdict, and the caller's continuation execute in
  one synchronous turn. The helper's only awaits are the transport call and the
  callback's returned promise. Callers must not stash the outcome and act on it
  after a later await; the workspace hydration branch is the one deliberate
  exception, already awaited today with its own error handling.
- **Caller error handling** (eng review): the helper never rejects for
  preparation or transport errors; they arrive as outcomes. The hook and the
  dialog keep their existing `finally` (queued-save re-dispatch;
  `setDialogSaving(false)`) around the helper call and drop their `catch`. The
  bootstrap save branch (`FundBasicsStep.tsx:241-274`, `try/catch` with no
  `finally`) drops its `catch` and gains no `finally`, because every callback
  arm sets the stage itself. The workspace hydration branch keeps its own catch
  inside the callback. Each caller's switch on `outcome.kind` ends in an
  exhaustive `never` default, so a new outcome kind fails `npm run check`
  instead of being ignored.
- **Hydration-fence invariant** (Codex fact-check; extra fence rejected as
  unreachable, owner 2026-09-23): the workspace applies `applyDraftSnapshot`,
  which writes `pendingCommand: null`, after an awaited GET fenced only on
  session and fund. That is safe because `prepareFundCommand` is the sole
  `beginCommand` caller (`fundStore.ts:1423`) and refuses every operation while
  `needsServerHydration` is true and nothing is pending (`fundStore.ts:1412`),
  and both workspace hydration paths run with that flag set. A change that lets
  a command begin during hydration must add a pending-key fence before
  `applyDraftSnapshot`. The hook's snapshot path is unchanged by this plan.
- **Pending-command replay**: `prepareFundCommand` returns the original body
  when a command is pending. The helper must dispatch that body and compare
  newer edits against it, exactly as the hook does at lines 136-141 and 176.
- **Idempotency and optimistic locking**: unchanged. Key and `If-Match` travel
  through `saveFundDraft` as today; `resolveCommand` still fires only on
  definitive outcomes; `uncertain` and `retry_same_key` keep the key;
  `not_dispatched` never releases a pre-existing command.

- **Edge cases the outcome table must cover**: save while a foreign operation is
  pending (`not_dispatched`, foreign command still pending afterwards); storage
  fence with a pre-existing `save_draft` command (`not_dispatched`, that command
  still pending); storage fence with no prior command (`not_dispatched`, journal
  empty, released by the store itself); wrong fund and hydration fence
  (`not_dispatched`, nothing dispatched, journal preserved); session reset
  during the await (`superseded`); newer key dispatched during the await on

## Type Definitions

New exported type in `fund-draft-settlement.ts`, `DraftSaveOutcome`, a
discriminated union on `kind`:

- `not_dispatched` with `message` (this invocation sent nothing; a previously
  pending command keeps its key, body, and expected ETag, with `dispatchedAt`
  possibly refreshed by `prepareFundCommand`).
- `superseded` (session, fund, or key changed during the await; no post-await
  settlement or continuation writes, `dispatchedAt` may already have been
  refreshed by `prepareFundCommand`; no message, per R9).
- `saved` with `dispatchedSignature` (canonical JSON of the sent body),
  `newerEdits`, `needsHydration`. No `etag` field: the helper has already
  advanced the store revision and no caller reads it.
- `stale` with `message` (412; command resolved).
- `uncertain` with `message` (command kept).
- `retry_same_key` with `message` (command kept).
- `rejected` with `message`, `missingDraft` (command resolved).

New exported type
`DraftSaveOutcomeHandler = (outcome: DraftSaveOutcome) => void | Promise<void>`;
`saveDraftAndSettle(fundId, options, onOutcome)` returns `Promise<void>`. New
exported options type `SaveDraftAndSettleOptions` with
`includeEconomicsAssumptions: boolean`. `DraftSnapshot` from `fund-drafts.ts` is
reused as the `applyDraftSnapshot` input. No changes to store types or shared
contracts.
