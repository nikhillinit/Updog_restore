# WS1 Surface Contract Matrix (F_1.2.0 Child Plan A) Implementation Plan

Version: F_1.2.1. Parent:
`docs/1-plans/F_1.2.0_v1.4-release-proof-activation.plan.md` (WS1, gate G1).
Keyed to `main @ d030a803` facts; all counts derived fresh at execution time.

## Overview

Produce the zero-unclassified surface contract matrix that defines "every v1.4
surface" for the release-proof program. The matrix is checked-in structured data
(one row per API endpoint, client route, and worker/scheduler job, grouped by
seam) plus a validator that makes gate G1 machine-checkable: zero unclassified
rows, full coverage against the tracked registries, and a recorded
reconciliation against the knowledge graph. G1 closes when the user signs off
every dormant-surface decision.

User decisions (2026-08-05): structured data + validator (not markdown-only, not
fully generated); per-endpoint granularity grouped by seam.

Review resolutions (2026-08-05): the surface boundary is repository HTTP
listeners, not only Node routes represented by the KG. The matrix therefore
discovers the four FastAPI routes in `ml-service/app.py` and the five routes
registered by `workers/health-server.ts`, using listener-qualified ids so their
`/health` paths cannot collide with the primary API. A source import is
structural evidence, not deployment boot proof: standalone Vercel functions
remain `boot_status: unproven` until inspected from actual Vercel build output.
Finally, the proposal precedence is intentionally total without treating
structurally dormant rows as failed deployments: dormant/quarantined,
development-only, and local-only categories resolve first; then any row with at
least one configured release exposure but zero proven release exposures proposes
`keep-and-prove` before Docker-only or live-reachability rules. These
constraints prevent a closed-but-incomplete matrix and prevent unbooted code
from being labeled reachable.

## Problem Statement

"Every v1.4 surface" is undefined. The knowledge graph counts 390 API endpoints,
43 client routes, and 9 worker jobs at `d030a803` — far larger than the 45-entry
common route manifest. Dormant UI, Docker-only routes (404 on Vercel),
quarantined `pages/v2/`, and flag-gated surfaces are unclassified. Downstream
gates (G2 transaction audit, WS3 closure packs, WS4 canaries) cannot scope their
work until each surface carries an explicit contract decision.

## Solution Architecture

New `audit/surface-contract-matrix/` directory, sibling to
`audit/knowledge-graph/`. **Tracking prerequisite**: `.gitignore` ignores
`audit/` wholesale (line ~49) — the knowledge graph itself is untracked local
tooling. This plan rewrites the rule so re-inclusion actually works (git cannot
re-include files beneath an ignored PARENT directory): `audit/` becomes
`audit/*`, followed by `!audit/surface-contract-matrix/` (+
`!audit/surface-contract-matrix/**` for contents), so the matrix artifacts and
schema ARE tracked; the KG dependency remains authoring-time-only local tooling
(CI never reads it — by design, below). The `.gitignore` change is in the Files
list.

- **`matrix.json`** — the checked-in matrix. Top-level metadata (schema version,
  seed provenance: git HEAD + KG `snapshot_id`; the seed "date" is the KG
  snapshot's own timestamp/commit identity, and all provenance fields are
  preserved unchanged when a re-seed's inputs are identical — no wall-clock
  writes, keeping `seed twice == seed once` literal) plus rows.
- **`source-inventory.json`** — checked-in, generated by `seed-matrix.mjs`: the
  exact canonical row-id sets extracted from the KG + registries + dormant
  inventories, with the KG snapshot_id that produced them, PLUS explicit
  **source-to-row mapping tables** (source ids are NOT row ids: a manifest id
  like `auth` is a seam mapping to many endpoint rows — joined through
  `sourceModule`/mount evidence; a `QUEUE_CATALOG` key can differ from its
  `queueName` (`simulation` → `monte-carlo-simulations`) — joined through
  `queueName`). CI coverage assertions run through these mappings, never by
  string-equating source ids with row ids. This is what makes CI exact-set: CI
  asserts `matrix.json` row ids == inventory row ids (both directions — a
  deleted KG-only row fails CI, an orphan row fails CI). Refreshing the
  inventory is an authoring-time act with KG evidence. **Staleness is
  hash-gated, not trusted**: the inventory records the sha256 of every
  contributing tracked source file (route/router files the KG extraction
  attributed endpoints to; the four registries hashed as BOTH file content AND a
  normalized fingerprint of their runtime EXPORTS (registries import other
  modules — the policy registry imports a route-classification fixture,
  governance imports `app-route-definitions.ts` — so file hashes alone miss
  semantic changes arriving through imports); ALL runtime composition and
  mount-boundary files — `server/app.ts`, `server/server.ts`,
  `server/routes.ts`, `server/routes/mount-common-routes.ts` — plus the complete
  deployment-entrypoint chain that decides which app actually ships:
  `api/[...slug].ts`, `scripts/build-vercel-api.mjs`, `server/bootstrap.ts`,
  `scripts/build-server.mjs`, `scripts/build-workers.mjs`, `Dockerfile*`,
  `railway.toml`, `railway.worker.toml`, `.vercelignore`, `.dockerignore` (both
  change deployed membership; their effective exclusion rules are also APPLIED
  during membership checks), and the entrypoint-selecting `package.json`
  `scripts` block (hashed as its normalized JSON subset) — plus `vercel.json`,
  `workers/`, `client/src/pages/v2/` listing, and the client entry/build chain
  that deploys the router itself (`client/index.html`, `client/src/main.tsx`,
  `client/src/App.tsx`, `vite.config.ts`) so client routes cannot become
  undeployed under a still-green closed matrix). CI recomputes those hashes (and
  membership of each glob), plus `package.json` and `package-lock.json` whole
  (boot proof executes the full built dependency graph; the resolved
  `express`/`router` versions matter for stack-walking, but any dependency drift
  can change boot behavior), plus the AUTHORING TOOLING ITSELF —
  `matrix-schema.mjs` and every `scripts/*.mjs` under the matrix directory — so
  a seed/inspector/merge-logic change stales previously generated closed
  artifacts and forces a re-seed before CI passes, and fails on any mismatch —
  so adding/removing an endpoint inside an existing router (which changes no
  registry id) still breaks CI until the author re-seeds against a fresh KG. To
  close the "new file the old KG never attributed" hole, the hash gate ALSO
  records glob membership + hashes of the full endpoint-source UNIVERSE
  (`server/routes/**/*.ts`, `server/app.ts` direct-mount sources, `api/**/*.ts`,
  `workers/**`, `server/workers/**`, `ml-service/**` — including its Python
  FastAPI source, Dockerfile, compose file, and requirements lock input;
  EXCLUDING test/spec/fixture paths like `__tests__/`/`*.spec.ts`, whose edits
  must not stale the matrix; confirmed-test hashes already guard evidence) — a
  brand-new unmounted route file changes membership and fails CI even though no
  attributed file changed. The BullMQ constructor scan is one deterministic
  function in `matrix-schema.mjs`, reused verbatim by seed AND the CI test
  (fresh run, exact-set compare) — same discipline as dormant-candidate
  discovery. A repo-wide shared scanner, `discoverHttpListenerCandidates()`,
  enumerates TRACKED runtime-capable `.ts`/`.js`/`.mjs`/`.cjs`/`.py` sources and
  detects listener creation/start patterns (`listen`, Node HTTP server
  construction followed by `listen`, FastAPI/Flask app creation, `uvicorn.run`,
  and container commands selecting an HTTP entrypoint). Every candidate must
  have a tracked disposition in `listener-dispositions.json`: `product-surface`
  names either the existing primary composition (`row_namespace: api`) or a
  stable standalone listener id (`row_namespace: listener`) plus an exact
  route-extraction strategy; `non-product-tooling` supplies a one-line rationale
  and approved evidence. Current tooling listeners such as
  `server/observability/metrics-demo.ts`, `scripts/orchestrate.ts`, and
  `scripts/ai-tools/metrics-server.js` therefore cannot vanish silently, but do
  not create product rows after approved exclusion. Product extractors discover
  literal method/path registrations from the resolved listener module graph
  (including `workers/health-server.ts` and `ml-service/app.py`); unsupported
  dynamic registrations are hard failures, not omissions. Seed and CI run the
  same candidate scanner and extractor, exact-set compare candidate dispositions
  and listener-qualified row ids, and fixture-test all nine current product
  routes, known tooling exclusions, a newly added listener candidate, and
  dynamic-registration rejection.
- **`matrix-schema.mjs`** — Zod row/document schema, plain JavaScript (Zod gives
  the runtime typing; deliberately no TypeScript under `audit/` so no
  tsconfig/eslint project changes are needed). Single source of truth for enums
  and for `canonicalRowId()` — the ONE id-normalization function (uppercase
  method, verbatim express path, `api:GET:/api/funds/:id` form; KG
  `api:GET /path` and policy `api:get:/path` forms are normalized through it;
  unmatched ids after normalization are hard failures). Multiple handlers on one
  method+path are REAL in v1.4 (`/api/version` is defined at both
  `server/app.ts:213` and `server/routes/health.ts:526` — the WS5 shadowing bug;
  RUM POST paths chain ingress guards + handlers by design), so same-id
  sightings are NOT collisions: each exposure carries an ordered `definitions[]`
  (handler site `file:line`, role `handler | guard | shadowed`, effective mount
  order). **Ordering derivation is runtime, not static guesswork**: the seed
  instantiates each app in-process and derives order via **registration
  instrumentation** — before importing the app module, it wraps BOTH the Express
  `Router` prototype AND `express.application` registration methods
  (`use`/`get`/`post`/… — top-level `app.use`/`app.get` direct mounts are
  registrations too) to capture, per registration, a monotonically increasing
  sequence number plus the registration call-site `file:line` (from a captured
  `Error().stack`); after construction it walks the app router stack and joins
  layers to the captured registrations by DIRECT LAYER TAGGING — the wrapper
  stamps a non-enumerable marker (registration sequence id) onto each Express
  `Layer`/`Route` object it creates, keyed by owning router + layer identity +
  handler index, so the stack walk reads the tag straight off the layer.
  Function identity/occurrence heuristics are NOT used — shared middleware like
  `requireFundAccess` appears across many routers and module import order
  differs from mount order, so identity joins would misattribute evidence.
  `Router.param` callbacks create NO Express layer (e.g. fund-scope enforcement
  in `allocation-scenarios.ts` lives in a param callback) — the wrapper
  instruments `Router.prototype.param` separately and attaches captured param
  callbacks to their matching routes in execution order (params run before route
  handlers), so guard chains include them. The wrapper is
  **re-entrant-deduplicating**: Express delegates `app.use` into
  `Router.prototype.use` internally, so a registration observed while a wrapped
  call is already on the stack is NOT recorded twice (one registration site =
  one record). This yields flattened mount path, effective order, AND static
  evidence in one pass (the existing route-parity suite's source-scan/probe
  approach cannot produce layer order, hence the instrumentation). Roles are
  assigned from that order plus middleware-vs-terminal-handler shape. The Docker
  surface is inspected via **`createServer()`** — its real composition mounts
  CSP/metrics routes BEFORE the nested `registerRoutes()` phase
  (`server/server.ts`) — never bare `registerRoutes`; the exposures
  `runtime: register_routes` value denotes that nested mount phase within
  `create_server`. **Side-effect containment**: `registerRoutes` starts
  schedulers that can write DB rows, so the inspector runs with `NODE_ENV=test`,
  every starter kill-switch set (`ENABLE_QUARTERLY_ANALYSIS=0` and equivalents;
  a starter lacking a kill-switch is stubbed before import), never calls
  `.listen()`, and stops/cleans up in `finally` — the workstream stays
  read-only. Cleanup must handle **unexported top-level timers** created as
  import side-effects (e.g. `metrics-rum-v2.ts`, `routeNormalizer.ts`
  intervals): the inspector patches global `setInterval`/`setTimeout` for the
  duration of instrumented imports, records every handle, then clears them all
  and restores the patched globals AND Express prototypes in `finally` — the
  process must exit cleanly without `process.exit()`. Because `NODE_ENV=test`
  plus kill-switches SUPPRESSES conditional mounts (flag-gated routers, dev-only
  routes, dev WebSocket), a single profile cannot observe every exposure: the
  inspector runs multiple isolated test-safe profiles — default
  (`NODE_ENV=test`), each registration gate run BOTH individually enabled AND
  individually disabled (gates can default ON — `ENABLE_METRICS` defaults true —
  so enable-only deltas would misattribute them), and an explicit development
  profile (`NODE_ENV=development` with memory/no-op providers and ALL scheduler
  kill-switches set, since dev-only mounts and the dev WebSocket only register
  under `development`) — in separate child processes with **sanitized, hermetic
  environments**: launched via `tsx` with the explicit repo
  `--tsconfig tsconfig.server.json` and ABSOLUTE module paths (path-alias
  resolution must not depend on cwd), then `process.chdir` into an isolated
  temporary cwd immediately BEFORE the config/app import (so no repo `.env*`
  files are found at load time while `@shared/*` aliases still resolve),
  inherited credentials cleared, mock `DATABASE_URL`/`REDIS_URL` values, and the
  config loader's `_EXPLICIT_*` markers set for EVERY overridable setting —
  database (`_EXPLICIT_DATABASE_URL`), Neon, Redis, queues, memory mode,
  `NODE_ENV`, and auth (`server/config/index.ts` otherwise lets `.env*`
  overwrite them). The harness ships a complete synthetic-environment table,
  including a 32+ character synthetic `JWT_SECRET` + `_EXPLICIT_JWT_*` markers —
  `loadEnv()` rejects non-test HS256 without one, so the development profile
  cannot boot on sanitization alone — and no profile may touch a real external
  service. `createServer()` also branches on FILESYSTEM state (static serving
  registers only when `dist/public` exists, else an API-only `GET /` —
  `server/server.ts`), so profiles pin cwd and `dist/public` presence explicitly
  and inspect BOTH `static` and `api-only` variants rather than inheriting
  whatever the checkout happens to contain. **Deployment exposures require BOOT
  PROOF of the built artifact, not source-level construction**: `createServer()`
  inspection yields the mount/order/condition DATA, but a `railway-api` exposure
  is only assigned if the actual built entrypoint provably listens — at planning
  time `server/bootstrap.ts` defines but appears NEVER to invoke `bootstrap()`,
  so `dist/index.js` may start no HTTP listener at all. Boot proof executes the
  EXACT container `ENTRYPOINT` + `CMD` as written (no assumptions in either
  direction about shell/exec form or variable expansion — the proof is running
  it). The seed runs the built artifacts hermetically per a per-deployment proof
  table defined in the README (each deployment names its command, probe, and
  success condition): `railway-api` — run built `dist/index.js`, probe HTTP
  listener; `railway-worker` — run built worker entrypoint, probe queue-consumer
  registration AND all five listener-qualified worker health paths (`/health`,
  `/live`, `/ready`, `/metrics`, `/stats`); `vercel-api` — load the
  `build-vercel-api` bundle and construct `makeApp()` (its function model has no
  standalone listener); `vercel-function` — source-import each enabled `api/**`
  entrypoint and verify it exports a handler as STRUCTURAL evidence, but record
  `boot_status: unproven` unless the handler is loaded and invoked from actual
  Vercel build output (this plan does not add Vercel CLI or equate a source
  import with a deployed artifact); `vercel-web` — `build:web` completes and
  emits the SPA entry HTML referencing the built bundle (Vercel serves static
  output directly); `railway-web` — the SPA build proof PLUS the proven
  `railway-api` listener AND an HTTP probe of an asset and a deep-link route
  through it (Railway serves the SPA through the possibly non-listening
  `dist/index.js` — static output alone proves nothing there);
  `ml-service-local` — optionally build and probe `ml-service/Dockerfile` at its
  four FastAPI paths when Docker is available, while retaining
  non-release/local-only reachability because no tracked production deployment
  selects that service. Boot evidence recorded per exposure; a surface's
  exposures carry `boot_status: proven | failed | unproven` — recorded fact,
  never an assumption. `boot_evidence.observed_at` follows the same
  no-wall-clock discipline as seed provenance: on re-seed the merge compares the
  fresh boot evidence MINUS `observed_at` (`command_or_artifact`, `probe`,
  `result`) plus `boot_status` against the stored exposure; when equal, the
  stored `observed_at` is preserved verbatim — a fresh timestamp is written only
  when the boot outcome actually changed — so `seed twice == seed once` stays
  byte-literal even though boot proofs execute on every seed. No-boot semantics
  are explicit and do NOT deadlock G1: rows with at least one configured release
  exposure but only boot-failed/unproven release exposures keep their
  mount-derived exposure data and propose `keep-and-prove`. Each exposure stores
  its machine-owned `boot_evidence` (command/artifact, probe, result,
  timestamp), while `decision_evidence` remains exclusively human approval
  evidence, preserving its single ownership across re-seeds. Docker-only and
  other reachability-derived proposals are evaluated only after at least one
  release exposure is proven. The aggregate boot findings are stamped into the
  G1 review pack as WS5 inputs. Parent WS5 today covers version, Node pins, and
  WORKER identity — not API entrypoint repair — so the planned parent-plan edit
  at G1 close ALSO extends WS5's scope line with "Railway API entrypoint
  (`dist/index.js`) listener repair + boot proof", standalone Vercel-function
  build-output proof, and every other active `keep-and-prove` release obligation
  discovered by the matrix; alternatively the user may approve a configured
  release surface as explicitly excluded. Each active obligation records
  `closure_owner` and `closure_gate` (`WS5/G3` by default; WS6/G4 only when
  rollout evidence is the missing proof), and G4 cannot close while one remains
  unresolved. Either way the gap is owned, not orphaned. What G1 forbids is
  `boot_status` being UNRECORDED — knowing beats fixed, here. Derivation
  discipline: the row carries BOTH configured `reachability` (derived from
  tracked deployment topology regardless of boot) and `proven_reachability`
  (derived only from exposures with `boot_status: proven`). Failed/unproven
  exposures remain configured mount observations with full evidence, so WS2
  still sees their intended scope, but contribute nothing to
  `proven_reachability`, so WS4 cannot mistake them for canary-ready
  deployments. The Docker-surface harness for mount DATA is the exact production
  composition sequence: load config (hermetic env) → build the DI providers
  (memory/no-op variants) → `createServer(config, providers)` → extract the
  Express app from the returned `http.Server`'s request listener → inspect →
  teardown in `finally` (WebSocket servers, providers, timers, prototypes, AND
  the module-level calc-completion registries — `createServer()` registers a
  persistent handler even under `NODE_ENV=test`, so teardown calls both
  `resetCompletionHandlers()` and `resetCompletionHandlerRegistration()` to
  prevent test-order pollution). The inspector unions the observed registrations
  (conditions attributed from the profile deltas), and reconciles in BOTH
  directions: every runtime-manifest source ends up with an observed or
  explicitly overridden exposure, AND every runtime-OBSERVED terminal route is
  exact-reconciled against a matrix row or an explicit exclusion — an endpoint
  the KG extraction missed cannot silently disappear from the matrix because
  runtime observation is itself a row source. Exclusions have a real artifact:
  terminal catch-all/fallback layers (both apps end in one — `server/app.ts` and
  `server/routes.ts` 404/error handlers) are excluded by a deterministic rule
  (terminal layer matching all paths = infrastructure, not a surface), and
  anything else needs an entry in a tracked, fingerprinted
  `runtime-exclusions.json` (curated, human-owned) — no schema-less "explicit
  exclusion" hand-waving. Ambiguous cases fall back to a curated, fingerprinted
  `definition-overrides.json`. Merge-engine fixtures must cover `/api/version`
  (shadowed pair) and both RUM guard-chained POST paths. A hard failure is
  reserved for two DIFFERENT canonical ids normalizing to the same string.
- **`scripts/seed-matrix.mjs`** — authoring-time extraction: enumerates rows
  from the fresh knowledge graph (APIEndpoint/ClientRoute/WorkerJob nodes;
  MOUNTS **and** EXPOSES/DEFINES edges, so direct `makeApp`/`registerRoutes`
  entrypoints like `/api-docs` that have no MOUNTS edge are captured)
  cross-joined with the tracked registries and dormant inventories; writes
  `source-inventory.json` (with mapping tables) and merges rows into
  `matrix.json` by canonical row id under the field-level merge-ownership rule
  below (machine fields replaced, human fields preserved; new rows arrive
  `unclassified`). **Orphan handling is explicit**: rows whose sources vanished
  move out of `matrix.json` into tracked `orphans.json`; each must be resolved
  `pruned` (acknowledged removal) or `retained` (justified); resolved `retained`
  entries in `orphans.json` are themselves a seed inventory input for ANY
  interface kind (the generic re-entry path — `dormant-inventory.json` stays
  UI-specific). A `retained` entry MUST supply current replacement
  exposure/evidence mappings (machine fields cannot be resurrected from the
  vanished source, and re-entry without them would violate mandatory
  machine-field replacement), and a re-entering row always demotes to `proposed`
  — retention is a new contract claim, not a continuation of the old approval.
  Validator + CI fail on unresolved orphans, so exact-set equality is asserted
  over `matrix.json` after orphan resolution and stays well-defined.
- **`scripts/validate-matrix.mjs`** — full validation incl. KG reconciliation
  (local-only; KG outputs are untracked, so CI cannot run this part).
- **`scripts/render-matrix.mjs`** — regenerates `MATRIX.md`, a seam-grouped
  human summary for the G1 review.
- **CI gate**: `tests/unit/audit/surface-contract-matrix.test.ts` — runs in the
  normal `npm test` server project. Validates from TRACKED sources only.

Two-layer validation (deliberate, because `audit/knowledge-graph/out/` is
untracked and rebuilt per-checkout):

1. **CI (tracked sources)**: two modes keyed off matrix metadata
   `phase: authoring | closed`. The flip is owned by ONE command —
   `approve-matrix.mjs --close-g1` (refuses unless closure checks pass, stamps
   the G1 evidence reference) — and is one-way, enforced twice: (a) in the merge
   engine — re-seed preserves `closed` and writing `authoring` over `closed` is
   a hard failure (merge-engine fixture); (b) in CI — the test compares against
   the correct prior copy of `matrix.json` per event type: on pull requests, the
   PR base SHA (`github.event.pull_request.base.sha`); on pushes, the event
   `before` SHA — NEVER `origin/main` on a main push (that compares the file to
   itself). The ref is passed into the test via env; the blob is read via
   `git show <ref>:<path>`; fails closed if the ref is unavailable. A missing
   prior blob is allowed when the working copy is `authoring` (initial
   introduction) OR when it is `closed` AND every closure check passes (a first
   PR that introduces the matrix already closed is legitimate — the check exists
   to catch downgrades, and with no prior blob there is nothing to downgrade).
   What always fails: prior blob `closed`, working copy `authoring`. The
   canonical unit-CI checkout currently fetches no history, so this plan ALSO
   updates `.github/workflows/ci-unified.yml` (checkout depth + ref plumbing) —
   in the Files list. Fails if the prior copy was `closed` while the working
   copy says `authoring`, so a hand-edited downgrade cannot silently disable the
   closure checks. **Scope**: this monotonicity check runs ONLY when the
   prior-ref env var is provided (CI). Local `npm test` skips just this one
   check (all other structural + closure checks still run), so local runs stay
   green without GitHub event refs. **Structural checks always fail-hard** in
   both phases: schema-parse of `matrix.json` and `source-inventory.json`,
   exact-set equality, unique ids, source hashes, membership checks, fingerprint
   recomputation, orphan/candidate resolution. **Closure checks** — zero
   unclassified, zero proposed, no-unknown — REPORT during `authoring` (visible
   counts, non-failing, so the CI test can land green mid-classification) and
   FAIL-HARD once `closed` (and forever after). The checks: **exact set
   equality** between matrix row ids and inventory ids (both directions); zero
   `unclassified` rows; zero `decision_status: proposed` rows; **zero
   `unknown`/`unassigned` in the downstream-required fields of classified rows**
   (`personas[]`, `persistence`, `destructive`, `environment`, `owner` — a
   G1-passing matrix must be directly usable by the WS2 reachability audit and
   WS4 canary scoping; `unknown` is valid only while
   `classification: unclassified`); **fingerprint recomputation** — CI
   recomputes `contract_fingerprint` from every approved row's current fields
   and fails on mismatch with the stored value (a hand-edited approved row
   cannot carry stale sign-off past CI; demotion is enforced, not promised);
   **requirement mapping** — a tracked `requirements.json` maps every
   master-plan mandatory classification family via one of two implementable
   selector kinds — a PATTERN (defined syntax: either exact `seam` string
   equality or an ANCHORED regex over the canonical row id, `^...$`,
   regex-escaped except declared wildcards — no substring matching) (for route
   families like current-forecast commands or kpi-manager) or an EXPLICIT
   curated id list with an evidence note, validated by SET EQUALITY — every
   declared id must resolve to a matrix row, so a typo'd or vanished id fails
   instead of silently passing on the surviving matches. A family may be
   declared `optional_when_absent` (WP-L4 is "where present" — the repo may
   contain no such routes): such a family is EXEMPT from the non-empty assertion
   when it carries approved absence evidence (the search performed, its empty
   result, and G1 sign-off on the absence) — absence-with-evidence and
   non-empty-match are alternatives, never simultaneously required, and never a
   silent skip (for behavioral families with no self-evident surface id —
   subannual flow-fee and cashless-GP/LP-class map to the specific fee/economics
   endpoints and wizard surfaces that carry the behavior, authored during
   classification). Behavioral CORRECTNESS of those families is explicitly out
   of matrix scope — it is proven by WS2 tests and WS4 canaries; the matrix
   family gate only proves the carrying surfaces are enumerated, classified, and
   approved. Families: current-forecast commands, fee catch-up UI, subannual
   flow-fee, cashless-GP/LP-class, Wave H, WP-L4, kpi-manager, `pages/v2/`,
   Docker-only set. CI asserts each family's selector matches a non-empty row
   set AND every matched row is approved — multi-route families
   (current-forecast has many rows) are covered exhaustively by construction,
   not by one token row. At `--close-g1`, the closure metadata stamps the
   normalized `requirements.json` content hash AND each family's expanded
   matched-id set; afterward CI recomputes both and fails on drift (a narrowed
   selector or a shrunken expansion cannot stay green under a closed matrix
   without re-running closure); **zero unresolved orphans, zero undecided
   dormant candidates, and zero undispositioned repo-wide HTTP listener
   candidates** (see below); unique canonical ids; and live coverage
   re-derivation from importable tracked sources — every
   `COMMON_API_ROUTE_MANIFEST` id (45 at planning time; derived fresh by
   importing the module, never hard-coded), every `API_ROUTE_POLICY_REGISTRY`
   entry, every `ROUTE_GOVERNANCE_REGISTRY` path, every
   `API_RUNTIME_SPECIFIC_MANIFEST` id, every `QUEUE_CATALOG` key, and every
   dormant-inventory entry must map (via `canonicalRowId`) into the matrix,
   while every `discoverHttpListenerCandidates()` result maps either to
   listener-qualified rows or an approved `listener-dispositions.json`
   non-product exclusion, so registry or listener growth without a matrix
   decision fails CI even before the inventory is refreshed. The CI test also
   re-renders `MATRIX.md` deterministically (render function imported directly)
   and fails on drift against the committed file, so the G1 review artifact
   cannot diverge from `matrix.json`. G1 closure additionally requires every
   active configured-release `keep-and-prove` row to carry `closure_owner`,
   `closure_gate`, and `closure_acceptance`; downstream G3/G4 checks consume
   these obligations and fail when an obligation is still open at or beyond its
   declared gate.
2. **Authoring-time (KG)**: `validate-matrix.mjs` reconciles
   `source-inventory.json` and row ids against the freshly rebuilt knowledge
   graph plus a scan of `server/routes.ts` scheduler registrations; the passing
   snapshot_id and counts are recorded in metadata and cited in the G1 review.
   The CI test asserts this metadata block exists and is well-formed, not that
   it is current.

### Row schema (columns per master plan WS1)

Stable canonical `id` (via `canonicalRowId`, one format per interface:
`api:GET:/api/funds/:id`, `client:/portfolio`, `worker:<queueName>` (e.g.
`worker:monte-carlo-simulations` — queueName, not catalog key),
`scheduler:<registration>` (e.g. `scheduler:variance-alert-automation`),
`event:<registration>` (e.g. `event:calc-run-completion-handlers`),
`ws:<server>` (from `setupWebSocketServers`), `api-fn:<METHOD>:<route-path>`
(standalone Vercel functions — same collision rules as `api:` ids),
`listener:<listener-id>:<METHOD>:<route-path>` (standalone HTTP listeners;
current listener ids `worker-health` and `ml-reserve`, so duplicate paths like
`/health` remain distinct from `api:GET:/health`),
`dormant:<repo-relative-path>`), `seam` (machine-seeded grouping key, with an
optional human-owned `seam_override` field so the merge engine can distinguish
and preserve human regrouping without guessing ownership of a single field).
Worker rows additionally carry structured
`queue_roles: {producers[], consumers[]}` — each entry (producer AND consumer
alike) records site `file:line`, deployment/runtime, and for producers the
triggering canonical row id(s) (the HTTP endpoint or scheduler whose exposure
mapping the producer's reachability derives from), reconciled from KG +
`QUEUE_CATALOG` **joined against the actual deployment topology**: in-process
consumers registered via `server/providers.ts` (Railway API process) vs
standalone worker entrypoints selected by `scripts/build-workers.mjs` (Railway
worker process) — a queue consumed in-process gets a `railway-api` exposure. A
built worker entrypoint is ARTIFACT boot proof only — tracked
`railway.worker.toml`/`Dockerfile.worker` provide configured `railway-worker`
reachability intent, while actual service/`WORKER_TYPE` selection lives in
untracked Railway configuration. Therefore `railway-worker` proven reachability
derives only when BOTH artifact boot proof AND deployment-membership proof exist
(the latter recorded as `[UNVERIFIED-EXTERNAL]` evidence from the WS5 Railway
verification when not derivable from the repo); both topology files join the
source-hash gate. `interface`
(`http-api | client-route | worker-job | scheduler | event-handler | websocket | vercel-function | dormant-ui`),
`personas[]`, configured `reachability`
(`vercel | railway | both | client | local | dormant`) plus
`proven_reachability` (`vercel | railway | both | client | local | none`).
`reachability` answers where tracked topology intends the row to run even when
boot fails; `proven_reachability` answers where artifact/probe evidence
succeeded. WS2 scopes from configured `reachability`; WS4 canary selection
scopes from `proven_reachability`. The row also carries an `exposures[]` array —
one entry per configured/observed deployment runtime:
`{ deployment, runtime, mount_evidence, ingresses[], conditions, boot_status, boot_evidence }`.
`deployment` is
`vercel-api | railway-api | railway-worker | vercel-web | railway-web | ml-service-local`;
`runtime` is
`make_app | create_server | register_routes | vercel_function | worker_process | scheduler_poller | event_handler | websocket_server | client_router | service_listener`;
`ingresses[]` items are `{external_path, express_path, rewrite_evidence}`;
`boot_status` is `proven | failed | unproven`; and `boot_evidence` is
`{command_or_artifact, probe, result, observed_at}`. Both release web
deployments can serve the SPA, so client-route exposures name which deployment.
`ingresses[]` is the only ingress representation and is fingerprinted.
Registration `conditions` store flag/env gates. Exposure `conditions` capture
ONLY predicates that gate registration/startup — whether the surface exists at
all on that runtime. In-handler feature branches that alter behavior of an
always-registered endpoint (e.g. `ENABLE_RUM_V2`) are NOT exposure conditions;
they are recorded in a separate informational `behavior_flags[]` field so they
inform WS4 canary design without corrupting reachability. Conditions extraction
is deterministic and traces **registration → implementation → deployment
configuration**, not mount sites alone: gates inside `.start()` implementations
(e.g. `ENABLE_QUARTERLY_ANALYSIS` in `analysis-checkpoint-service.ts`), flag
reads from the generated flag registry (`shared/generated/flag-defaults.ts`),
explicit `process.env` guards, and worker deployment selection
(`Dockerfile.worker`, `scripts/build-workers.mjs`) are all in scope, and every
traced tracked file joins the source-hash gate. An unresolvable nested gate is a
hard seed failure recorded as `{unresolved: file:line}`, counts as `unknown` for
the G1 no-unknown gate, and is resolved via a curated, human-owned,
fingerprinted `condition-overrides.json` — never guessed. Untracked external
runtime config (Railway dashboard variables) cannot be hashed — such
dependencies are recorded as explicit `[UNVERIFIED-EXTERNAL]` evidence entries
with a manual verification note, mirroring WS5's Railway verification work.
Client routes and the separately deployed worker process are first-class
exposures, not shoehorned into the two HTTP surfaces. A single canonical row id
keeps identity stable while `exposures[]` represents per-runtime contract
differences (both reachability fields are derived from it and kept for
readability), `persistence`, `destructive`, `environment`, `owner`, `evidence`
(`file:line` and/or KG node id), `classification` (`classified | unclassified`),
`decision`
(`in-contract | docker-only-excluded | dev-only-excluded | quarantined | keep-and-prove | remove-with-approval`),
`decision_status` (`proposed | approved`) + `decision_evidence` (who/when/where
approved — G1 review reference). Any row with configured release reachability
(`vercel | railway | both`), effective decision `keep-and-prove`, and
`proven_reachability: none` additionally requires `closure_owner`,
`closure_gate`, and an executable `closure_acceptance` statement. Those fields
become the downstream obligation contract; G1 may approve an open obligation,
but G3/G4 cannot close past its declared gate until proof resolves it or a later
approved exclusion changes the decision. Validator distinguishes proposals from
sign-off: G1 close requires zero `proposed` rows, so approval is
machine-checkable, not implied.

**Field semantics** (finalized as Zod enums/descriptions in `matrix-schema.mjs`;
every field has an explicit `unknown` value rather than being omitted, so "not
yet determined" is visible and countable):

- `personas[]`: who exercises the surface — non-empty set over
  `gp | lp | admin | analyst | service | system | public | unknown` (a route
  authorizing several roles carries them all). Seeded through a documented,
  EXHAUSTIVE identity → persona mapping defined once in `matrix-schema.mjs`.
  Role extraction covers HANDLER-LEVEL authorization too, not just middleware
  chains — routes like the planning FMV overrides enforce `admin` inside the
  handler body — via a static scan of handler sources for role-check calls, with
  anything unresolvable recorded in a curated, fingerprinted
  `auth-overrides.json` (human-owned) that must be resolved before closure. The
  persona-mapping canonical source is the UNION of the role enum in
  `shared/schema/user.ts` (`admin`, `partner`→`gp`, `analyst`, `operator`,
  `viewer`, `service`, …) AND every guard-role literal discovered in route
  middleware (live guards use capability roles OUTSIDE the enum — e.g.
  `flag_read`/`flag_admin` in `server/routes/flags.ts`, `reserve_admin` in
  `v1/reserve-approvals.ts` — each requiring a human-approved persona mapping),
  plus the `lpId`-based LP identity (LP surfaces are not role-derived); an auth
  role absent from the mapping is a seed hard-failure, not a silent skip.
  Endpoint-to-role extraction is itself seeded: each http row carries structured
  `auth_roles[]` + guard evidence derived from the route's actual middleware
  chain (role-guard calls observed in `definitions[]` plus the policy-registry
  boundary), with coarse boundaries (`require_auth_and_role` without a
  statically resolvable role list) recorded as `unresolved` — counting as
  `unknown` and blocking G1 until classified. Obvious mappings (`partner`→`gp`,
  `admin`→`admin`, `service`→`service`) ship in the table; roles WITHOUT an
  obvious persona (`operator`, `viewer`) are explicit G1 decisions — the table
  entry records the user's chosen persona plus the G1 evidence reference. During
  authoring, an undecided role maps to `unknown` (rows carrying it stay
  countable and visible in the review pack) — the seed runs; it is `--close-g1`
  that hard-refuses while any role mapping is undecided. No circularity: seed →
  review artifacts → decisions → closure. Human-confirmed.
- `persistence`: does invoking it write durable state —
  `reads-only | writes | unknown` (seeded from policy-registry mutation hints +
  HTTP method; human-confirmed).
- `destructive`: can it destroy/overwrite user data —
  `none | soft | destructive | unknown` (human-assigned; seeded `none` for GET).
- `environment`: where it may be exercised for proof —
  `prod-safe | staged-only | local-only | unknown` (human-assigned; feeds WS4
  canary scoping).
- `owner`: enum derived from the UNION of owner domains actually used by the
  manifest (`ApiRouteOwner`) and the policy registry (which includes `reporting`
  — e.g. `/reports` — beyond the manifest's four values), plus `unassigned`.
  Seeded from manifest first, then policy registry for non-manifest rows;
  `unassigned` remains only until classification and is forbidden at G1.
- `test_evidence`: split storage — `derived[]` (machine, replaced every re-seed
  so removed tests cannot linger) and `manual[]` (human-recorded, preserved).
  Every evidence item is structured:
  `{row target, deployment/runtime exposure it exercises, layer, assertion evidence (test `file:line` making a direct request/route/queue assertion)}`.
  KG TESTS edges are **import-level, not assertion-level** (`extract-tests.mjs`)
  — they seed `derived[]` items flagged `assertion_confirmed: false` and count
  toward NOTHING until the classification pass confirms the assertion site; only
  confirmed items contribute coverage. Every exposure must end classification
  with either at least one confirmed evidence item OR the explicit reviewed
  status `test_coverage: none-reviewed` (a human attested that no test covers
  this exposure) — an exposure with only unconfirmed derived edges and no status
  is an `unknown` that blocks G1, so "counts as nothing" can never silently
  satisfy closure. `none-reviewed` attestations live in a HUMAN-OWNED top-level
  `coverage_review` map INSIDE `matrix.json` (sibling of `rows`), keyed by
  stable exposure identity `<canonical row id>|<deployment>|<runtime>` — never
  inside machine-owned `exposures[]`. Merge rule: preserved verbatim across
  re-seeds (listed among the human-owned fields); each entry stores the
  ROW-level `contract_fingerprint` at attestation time (no separate
  exposure-level fingerprint exists — row-wide invalidation is accepted
  deliberately: any contract change on the row invalidates its coverage
  attestations), and the validator invalidates any entry whose stored
  fingerprint no longer equals the row's current one — the invalidation formula
  is fingerprint equality, nothing subtler. Each CONFIRMED item stores the
  sha256 of its test file at confirmation time; CI recomputes these — a changed
  or deleted test file invalidates the confirmation, the exposure loses its
  coverage claim, and a closed matrix fails until re-confirmed, so deleted
  assertions cannot leave closed rows claiming coverage (test files stay out of
  contract fingerprints; their integrity is enforced by this dedicated check).
  `test_layers[]` (`unit | integration | e2e | smoke`) is DERIVED per-exposure
  from confirmed items at render/validate time (the row-level union is
  render-only display, never a gate input), never stored independently.

**Merge ownership** (prevents stale machine data surviving re-seeds):
`matrix-schema.mjs` enumerates the field split once. Machine-owned —
`exposures[]` (incl. `definitions[]` and `boot_evidence`, with the single
carve-out that `boot_evidence.observed_at` carries forward per the
unchanged-boot-outcome preservation rule above), derived `reachability`, derived
`proven_reachability`, `interface`, seed `evidence`, `test_evidence.derived[]`,
source-mapping data — are ALWAYS replaced on re-seed. Human-owned —
`personas[]`, `persistence`, `destructive`, `environment`, `owner` (non-manifest
rows), `test_evidence.manual[]`, `seam_override`, `classification`,
`closure_owner`, `closure_gate`, and `closure_acceptance` — are preserved by row
id (`seam` itself is machine-owned). Decisions are SPLIT: machine-owned
`decision_suggestion` is RECOMPUTED from exposures on every re-seed (a
failed→proven boot change refreshes the suggestion — no stale `keep-and-prove`
survives), while human `decision_override` +
`decision_status`/`decision_evidence` are preserved; the effective decision is
the override when present, else the suggestion, and (per the fingerprint rule) a
changed effective decision on an approved row demotes it. Approval demotion is
**fingerprint-based, not any-change-based**: each row stores a normalized
`contract_fingerprint` over EVERY approved contract field — exposures
(deployment/runtime/conditions/ingresses/`boot_status`/`boot_evidence`), derived
configured `reachability`, derived `proven_reachability` (an entrypoint repair
flipping `failed`→`proven` changes the contract and must demote — a merge
fixture covers both directions), interface, ordered definition roles,
`queue_roles`, `auth_roles[]`, `behavior_flags[]` (all three machine-owned:
replaced on re-seed, fingerprinted, with merge-test expectations like the other
machine fields), `personas[]`, `persistence`, `destructive`, `environment`,
`owner`, `classification`, `decision`, and downstream closure obligation fields
— EXCLUDING only provenance timestamps, test evidence, and `file:line`
positions. ANY change to a fingerprinted field on an `approved` row (machine
re-seed or human edit) demotes it to `proposed` — stale sign-off can never be
silently reused; line drift and test additions never invalidate a decision.

Behavioral drift is caught separately and COARSELY, by design: each `approved`
row also stores `approved_source_hashes` — the sha256 set of its DIRECT defining
source files (handler/router/service files from its `definitions[]` evidence,
plus the worker topology files for worker rows) captured at approval time.
Re-seed demotes any approved row whose defining-source hash changed, even when
path/exposures are unchanged — a handler rewrite that flips `persistence` or
`destructive` semantics cannot ride an old approval. Additionally each row
archives its `machine_suggestions` snapshot — the seed-derived values for the
human-owned fields (suggested personas from auth roles, persistence hints from
the policy registry, owner seed, etc.). On re-seed, if the freshly derived
suggestions differ from the archived snapshot, the row demotes to `proposed`
even though the human values were preserved — an auth-role or policy-registry
change cannot leave a stale approved `personas[]`/`owner` standing unreviewed.
Precision note: source hashing is whole-file — ANY edit to a defining file
(including comment/line drift within it) demotes its rows; the fingerprint's
line-drift immunity applies to evidence locations in OTHER files. That
coarseness is accepted: bulk re-approval by seam makes benign-edit re-approval
cheap, and erring toward demotion is the safe direction for a release-proof
contract. **Declared limitation**: transitively imported service changes are NOT
hash-tracked — per-field behavioral dependency analysis is disproportionate for
a contract inventory; behavioral correctness proof belongs to WS2 (transaction
audit/tests) and WS4 (canaries), which gate the same release.

**Approval bootstrap**: EVERY row starts `decision_status: proposed`. Proposed
decisions are derived AFTER exposures are merged, from the exposures themselves
— never from which registry a row came from. Full proposal table (implemented in
`matrix-schema.mjs`):

| Interface / reachability                                                                                                    | Proposed decision                                                                                                                  |
| --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| http-api with proven live Vercel exposure                                                                                   | `in-contract`                                                                                                                      |
| http-api, `register_routes`-only exposures with proven Railway boot                                                         | `docker-only-excluded`                                                                                                             |
| client-route on a live routing surface                                                                                      | `in-contract`                                                                                                                      |
| client-route archived-placeholder/legacy                                                                                    | `keep-and-prove`                                                                                                                   |

| worker-job / scheduler / event-handler / websocket with >=1 configured release exposure and zero proven release deployments | `keep-and-prove` (boot finding in machine-owned exposure evidence; closure obligation required)                                    |

The table is exhaustive over interface × configured/proven reachability by
construction: the proposal function in `matrix-schema.mjs` is total AND
deterministic — the rules are evaluated in DECLARED PRECEDENCE ORDER (most
specific first: `pages/v2`/curated dormant disposition → development-only
condition → local/non-release-only listener → archived-placeholder/legacy →
**configured-release-but-zero-proven** (only applicable when at least one
configured release exposure exists; today's unproven Railway boot therefore
cannot mislabel Docker-only rows, while exposureless dormant rows never enter
this branch) → docker-only → zero-ingress → live default), the first matching
rule wins, and a fixture asserts every current row matches at most one rule at
its precedence level (overlaps like an archived route also matching the
live-client rule, or the dev dashboard matching both Docker-only and dev-only,
resolve by that order, never ambiguously). A row matching no rule is a seed
hard-failure, not a silent default, so a future interface value forces an
explicit rule.

(The runtime-specific manifest contains BOTH http-api kinds — nine production
`make_app` entries at planning time stay `in-contract`.) Proposals are seeds for
review, freely overridden row-by-row. The G1 review approves in bulk by seam;
`decision_evidence` records the review reference (session/PR + date) for batch
approvals and a per-row note for individually debated rows. So "zero proposed"
at G1 close is meaningful for all rows, not just disputed ones, and every
approval has evidence of the same shape.

**Merge-engine tests**: the CI test suite includes fixture-based tests of the
merge engine itself (small synthetic matrices): idempotent re-seed (seed twice
== seed once, including byte-identical `boot_evidence` — an unchanged boot
outcome preserves the stored `observed_at`; a companion fixture flips `result`
and asserts the timestamp DOES refresh), human-field preservation, machine-field
replacement, fingerprint-based approval demotion (demotes on contract change;
line drift in files OUTSIDE the hashed defining set never demotes — inside a
defining file, any change demotes via the source-hash rule, and the fixture
expectations encode exactly that split), same-id multiple-definitions handling,
different-id normalization-collision hard failure, orphan emission/resolution,
and `approve-matrix.mjs` stamping. Two more fixture families guard the
derivation functions themselves: **profile-delta attribution** (synthetic
inspector outputs for a default-ON gate like `ENABLE_METRICS`, a default-OFF
gate like portfolio-intelligence, development-only mounts, and the static vs
api-only filesystem variants — asserting the enable/disable delta merge
attributes conditions correctly) and **dormant-candidate discovery** (fixture
client trees covering `React.lazy` routes, aliased/named imports,
wrapper-component reachability, and type-only/test-only imports — asserting each
is classified as reachable vs candidate correctly, since CI's set-comparison
uses the same function and would otherwise never catch its bugs). Final-artifact
validation alone cannot prove the mutation path is safe. Additionally, a
**real-app inspector test** (side-effect-free: uses the SAME inspector harness
as the seed — `makeApp()` and full `createServer()` (never bare
`registerRoutes`, which misses outer middleware/mounts) — without listening,
with the timer/prototype cleanup). Because the harness needs `process.chdir()`
and Node forbids that inside worker threads (vitest runs tests in a thread
pool), the test SPAWNS the inspector as an isolated child process — same entry
the seed uses — and asserts on its JSON output, never running the harness
in-process. It asserts the derived flattened ordering (via
`inspect-runtime.mjs`) and `handler | guard | shadowed` roles for the
known-tricky routes — `/api/version` (shadowed pair) and both RUM guard-chained
POST paths — so the ordering walker itself is tested against reality, not only
via merge fixtures.

Enum values finalized in `matrix-schema.mjs`; adding a value is additive.

Reachability seed rule: exposure = application mount **resolved through ordered
deployment routing**, never mount alone and never bare pattern intersection.
Vercel routing is source→destination with precedence (functions before rewrites;
`/metrics/*` REWRITES to `/api/metrics/*` — the external path differs from the
Express path), so each exposure is derived by resolving the external request
through the function/rewrite precedence chain. Each exposure carries an
`ingresses[]` array — one entry per distinct external route to the same Express
endpoint (`{external_path, express_path, rewrite_evidence}`; Vercel can reach
one endpoint via BOTH `/metrics/*` and `/api/metrics/*`), with mount-site
evidence alongside; normalized `ingresses[]` data is part of the contract
fingerprint, so a routing change demotes approval. A `makeApp`-mounted route no
external path resolves to (e.g. `/api-docs`) is NOT configured Vercel-reachable.
`registerRoutes` mounts resolved through tracked Railway topology contribute
configured `reachability: railway` immediately; they contribute
`proven_reachability: railway` only after the built entrypoint proof succeeds.
Thus a configured-but-failed deployment stays in WS2 scope instead of collapsing
to dormant. Only rows with no configured release topology (or unimported UI)
become `dormant`/`local` as appropriate; configured release rows with
`proven_reachability: none` receive the `keep-and-prove` proposal and downstream
closure obligation. Seeds are hints — classification is a human pass.

### 3. Classification sweeps (the bulk of the work)

Executed seam-by-seam, editing `matrix.json` (re-runs of seed-matrix must not
clobber). Order: common-manifest seams → named direct routers (reserves-v1,
cashflow, calculations, ai, scenario-analysis) → Docker-only set → client routes
(three routing surfaces, ARCHI §5) → worker/scheduler jobs → dormant leftovers.
Each row's `evidence` cites the mounting/registration site. Rows needing a user
scope decision (dormant, remove candidates) are marked
`keep-and-prove`/`remove-with-approval` **proposals** and collected for G1.

### 4. Validator test (CI)

**File**: `tests/unit/audit/surface-contract-matrix.test.ts`

As specified in Solution Architecture layer 1. Imports the registries directly
(they are plain TS modules) so coverage assertions track registry growth
automatically — a new manifest entry with no matrix row fails CI.

### 5. Render + G1 review pack

**Files**: `scripts/render-matrix.mjs`, generated
`audit/surface-contract-matrix/MATRIX.md`

Seam-grouped tables + a dedicated "Decisions required" section listing every
`decision_status: proposed` row with evidence, PLUS every OFF-ROW
exclusion/disposition — `runtime-exclusions.json` entries,
`listener-dispositions.json` entries (BOTH kinds: a `product-surface`
disposition is what mints or maps listener rows, a `non-product-tooling`
disposition is what excludes a real HTTP listener from the matrix — each needs
rendered, evidenced sign-off), `dormant-candidates.json` `not-surface`
dispositions, orphan `pruned` resolutions, and `optional_when_absent` absence
evidence — each carrying the same proposed/approved lifecycle and closure check
as rows, so no real surface can be excluded from the matrix without rendered,
evidenced G1 sign-off. Off-row fingerprints are defined per artifact kind — an
exclusion fingerprints its matched layer identity + rule; a candidate
disposition fingerprints the file path + importer-evidence summary; a listener
disposition fingerprints the candidate's file path + detected listener pattern,
its disposition type (`product-surface | non-product-tooling`), and — for
`product-surface` — the declared `row_namespace` + route-extraction strategy, or
— for `non-product-tooling` — the rationale + approved evidence note; an orphan
resolution fingerprints the vanished row's last `contract_fingerprint`; absence
evidence fingerprints the search selector + result set — and the demotion
trigger is uniform: stored fingerprint no longer equal to the recomputed one
reverts the artifact to `proposed`. G1 review = user walks that section;
approvals are folded back into `matrix.json` as `decision_status: approved` +
`decision_evidence`; validator then enforces zero unclassified AND zero proposed
rows — sign-off is a recorded state change, not an implication.

## Technical Considerations

- **Pattern usage**: mirrors `audit/knowledge-graph/` layout (data + scripts
  under `audit/`); validator lives in the normal unit suite like other
  registry-parity tests (route-mount-parity precedent, ARCHI §3).
- **KG untracked**: CI never reads `audit/knowledge-graph/out/` — the
  false-green risk of a stale KG is bounded to the authoring-time reconcile,
  whose snapshot_id is recorded evidence, not a live gate.
- **Merge-not-clobber seeding**: field-level ownership per the Row schema
  section — machine-owned fields always replaced, human-owned preserved by row
  id; machine changes to approved rows demote them to `proposed`; removed
  sources emit orphans requiring explicit `pruned | retained` resolution.
- **No product code changes**: read-only workstream. The only executable code
  added is audit tooling + one test. No route, schema, or client changes.
- **Edge cases**: routes mounted on both surfaces but flag-gated on one;
  `pages/v2/` quarantine (classify `quarantined`, not dormant); admin-gated
  client routes; the scheduler surface with no HTTP route; policy-registry
  entries for routes that no longer exist (orphan detection catches these).
