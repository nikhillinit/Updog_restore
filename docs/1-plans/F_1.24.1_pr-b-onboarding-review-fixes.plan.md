## Overview

(`POST /api/funds/:fundId/imports/actuals/main-fund`), migration 0062
(`vehicle_onboarding_commands`), an artifact-ownership guard that keeps
declaration evidence out of other financial uses, retention of that evidence,
and the `MainFundOnboardingPanel` client. A review found 8 server findings
(S1-S8) and 3 client findings (C1-C3); Codex round 1 returned REQUEST_CHANGES on
C1. This plan resolves every finding that is code in this PR, records S2 as a
declared merge blocker, and restores the branch to a passing scoped-review dry
run.

## Solution Architecture

### Ownership is a fact, not an access check (S1, S3, S4, S6, S7)

Add one function to 0062:
`public.vehicle_onboarding_artifact_digest(p_fund_id integer, p_artifact_id integer) RETURNS text`.
It returns the declared `source_artifact_sha256` for the onboarding command that
owns `(fund_id, source_artifact_id)`, or NULL. Properties:

- `LANGUAGE sql STABLE SECURITY DEFINER`, `SET search_path = pg_catalog`,
  `SET row_security = off`, table reference fully qualified
  (`public.vehicle_onboarding_commands`). This mirrors the existing 0062 trigger
  function `vehicle_onboarding_refuse_envelope_source`. `row_security = off`
  makes the function fail closed (error, not silent filtering) if its owner were
  ever subject to RLS.
- One name, one signature (the manifest auditor refuses overloads).
- `CREATE OR REPLACE` so the replay-safety re-apply in the storage pg test stays
  green.

Every ownership read uses it:

- `isVehicleOnboardingArtifact`:
  `SELECT public.vehicle_onboarding_artifact_digest(fund, artifact) IS NOT NULL`.
  `bindOwnershipReadScope` is deleted: no `set_config`, no `FOR SHARE`, no grant
  or canary check, no request-scope requirement.
- `purgeVehicleOnboardingArtifacts`: replaces the policy-filtered `EXISTS` with
  `public.vehicle_onboarding_artifact_digest(artifact.fund_id, artifact.id) = artifact.payload_sha256`.
  The consumer `NOT EXISTS` list stays as it is.
- Draft-orphan purge: replaces
  `NOT EXISTS (... vehicle_onboarding_commands ...)` with
  `public.vehicle_onboarding_artifact_digest(artifact.fund_id, artifact.id) IS NULL`.

Probe (S6): `hasVehicleOnboardingCommands` reads, in one statement,
`to_regclass('public.vehicle_onboarding_commands')` and
`to_regprocedure('public.vehicle_onboarding_artifact_digest(integer,integer)')`.
Neither present: returns false (pre-migration deploy; the probe stays because
code deploys before schema application, ADR-103: merge is not migration). Both
present: returns true. Table present without the function: throws 503
`VEHICLE_ONBOARDING_SCHEMA_INCOMPLETE`. That state exists only in a database
that applied an earlier draft of 0062 (for example a local dev database; Drizzle
does not re-run an edited, already-recorded migration). Failing closed there
keeps the guard from silently switching off. Staging and snapshot requests get
the 503; a retention purge aborts its transaction and the sweep logs the
failure, leaving bytes in place. `runRetentionSweep` probes once, before
building ports, and passes the boolean to `createRetentionSweepPorts`,
`purgeBatch`, the draft-orphan purge and `purgeVehicleOnboardingArtifacts` (new
optional parameter; when omitted the function probes once itself, so existing
direct callers and tests keep working). `isVehicleOnboardingArtifact` takes the
same optional boolean. No module-level cache: integration runs use
`isolate: false` and different databases per file. Request paths (staging,
snapshot build) keep one probe per call.

#### EXECUTE grant decision and leak analysis

No migration names an application role or grants anything to one; tests create
their own non-owner role and grant table privileges explicitly. A directly
called function whose EXECUTE is revoked from PUBLIC with no matching grant
fails for exactly the non-owner roles S3 is about. The plan therefore keeps
PostgreSQL's default EXECUTE for PUBLIC (no `REVOKE`), and the pg tests do not
add a function grant: the non-owner test role receives EXECUTE the way a
production non-owner role would.

What a caller learns: for a `(fund_id, artifact_id)` pair, whether that artifact
is onboarding evidence, and its declared SHA-256. The digest equals
`source_artifacts.payload_sha256`, which has no RLS and is readable by any role
with SELECT on `source_artifacts`. The new disclosure is one bit per artifact
("this artifact is a main-fund declaration source"), with no payload, actor,
commitment, or receipt content. The trigger function keeps its existing
`REVOKE ALL ... FROM PUBLIC` (triggers do not need caller EXECUTE).

#### Authorization removed from the predicate (deliberate)

The old guard duplicated route authorization inside a database read. After this
change the ownership check authorizes nothing; every caller is authorized
upstream:

| Caller                                                                                      | Upstream authorization                                                                                                                                              |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `stageImportBatch` (`import-batch-staging-service.ts:367`)                                  | `POST /api/funds/:fundId/imports/batches`: `requireAuth()`, `requireFundAccess`; artifact row already locked `FOR UPDATE` in the same fund                          |
| `buildFinancialFactsSnapshot` opening artifact (`financial-facts-snapshot-service.ts:1910`) | Only `server/routes/financial-facts.ts` passes `openingAccountingStateArtifactId` (`:141-144`), behind `requireAuth()`, `requireFundAccess`, `requireRole('admin')` |
| Retention `purgeBatch`, onboarding purge, draft-orphan purge                                | Background job with no caller; maintenance, not a request                                                                                                           |

Onboarding authority itself (append) is unchanged: `authorizeAndLock` still
requires an active, non-canary, granted administrator, and the RLS INSERT policy
still enforces it. The guard's job is narrower: refuse reuse of declaration
evidence (409 `ARTIFACT_RESERVED_FOR_VEHICLE_ONBOARDING`). Onboarding never
claims a pre-existing artifact (`artifact.replayed` -> 409), so an artifact that
is not onboarding-owned when staging locks it cannot become owned later.

### S5: redacted failure log

The route is a sensitive financial response path (`request-logging.ts`
`isSensitiveFinancialResponsePath`), and PR-B's `with-rls-transaction.ts`
deliberately logs only `{ code: 'VEHICLE_ONBOARDING_TRANSACTION_FAILED' }` for
it, because driver and validation errors can echo request values. The final
catch logs
`{ code: 'VEHICLE_ONBOARDING_FAILED', errorName, sqlState, constraint }` at
error level: `errorName` from `err.name`, `sqlState` only when `err.code` is a
5-character SQLSTATE, `constraint` only when a string. No message, detail,
stack, or body. Logger:
`logger.child({ module: 'routes:lp-reporting:imports' })` from
`server/lib/logger`, the pattern `with-rls-transaction.ts` uses.

### C1: classify refusals by code

A failure proves this declaration did not commit under this key only when the
server emitted it after taking the fund `FOR UPDATE` lock and missing the replay
lookup for this key. Everything emitted earlier says nothing about a previous
uncertain attempt. `IDEMPOTENCY_KEY_REUSE` is the one exception to that
criterion: the key did commit, but for a different request hash, so it can never
replay this declaration. Clearing it is safe for a different reason: a new key
converges onto the existing main fund (Assumption 3). The same convergence is
what makes the C2 discard safe. Accepted cost of both: at most one extra
declaration receipt and one extra evidence artifact, never a second vehicle.

| Code (status)                                                              | Emitted at                                                      | Verdict after a prior uncertain attempt |
| -------------------------------------------------------------------------- | --------------------------------------------------------------- | --------------------------------------- |
| `UNAUTHORIZED` (401)                                                       | `requireAuth`, `requireVerifiedActualsCredential`               | Uncertain                               |
| CSRF / `requireFundAccess` / pilot-grant refusals (403, 404)               | Middleware before the handler                                   | Uncertain                               |
| rate limit (429)                                                           | `actualsPilotLimiter`                                           | Uncertain                               |
| `INVALID_BODY` (415, 400), `INVALID_IDEMPOTENCY_KEY` (400)                 | `requireActualsJson`, route parse, service parse, `sourceBytes` | Uncertain                               |
| `RESOURCE_NOT_FOUND` (404), `INSUFFICIENT_ROLE` (403)                      | Service pilot check, `transaction()`, `authorizeAndLock`        | Uncertain                               |
| `IDEMPOTENCY_REQUEST_MISMATCH` (400)                                       | `assertAuthoritativeFields`, before `loadExisting`              | Uncertain                               |
| `REQUEST_IN_PROGRESS` (409), `COMMAND_RETRY_REQUIRED` (503)                | Lock-timeout mapping                                            | Uncertain                               |
| `IDEMPOTENCY_RACE_UNRESOLVED` (409), any 5xx, 408, network, contract parse | Anywhere                                                        | Uncertain                               |
| `IDEMPOTENCY_KEY_REUSE` (409)                                              | `replayExisting`: key stored for a different request hash       | Definitive                              |
| `SOURCE_IDENTITY_CONFLICT` (409)                                           | Insert closure, after replay miss under the fund lock           | Definitive                              |
| `VEHICLE_IDENTITY_CONFLICT` (409)                                          | Insert closure, after replay miss under the fund lock           | Definitive                              |
| `VEHICLE_DECLARATION_CONFLICT` (409)                                       | Insert closure, after replay miss under the fund lock           | Definitive                              |

Rule in `submit()`:

- First attempt for this key (not previously uncertain): any failure that is not
  `outcomeUnknown` is a definitive refusal. No earlier attempt exists, and this
  one did not commit.
- After an uncertain attempt: only the four definitive codes above clear the
  uncertainty.
- On a definitive refusal: `keys.reset(scope)` (removes the `sessionStorage`
  entry), `unknown = false`, `refused = true`. The frozen declaration stays on
  screen with the refusal message; Edit is visible again.
- Otherwise: keep the key, `unknown = true`, keep "Retry unchanged declaration",
  and show the C2 discard action.

The definitive-code set is a single exported constant beside `outcomeUnknown` in
the panel module, so the table and the code stay in one place.

### C2: explicit discard

When the attempt is uncertain or a pending key was restored (and there is no
receipt and nothing in flight), the panel shows a secondary "Discard pending
attempt" button. It calls `keys.reset(scope)` and clears `frozen`, `unknown`,
`refused`, and `error`, returning the form to editable. Helper text states the
consequence: if the discarded attempt was saved, a new declaration with the same
details confirms the existing main fund, and different details are refused.
Server convergence (Assumption 3) makes this safe: a new key never creates a
second main-fund vehicle.

### C3: hide on 404

If the latest-reference probe fails with status 404, the panel returns `null`.
Other probe failures keep the existing "unavailable" status message.

### S2: declared merge blocker

0062 adds journal idx 63 and manifest 39 (`existing_table_required`). ADR-103's
`apply-journaled-0050-0061` route refuses once the repository holds journal
entries past idx 62 or manifests past 38 (proved by
`run-journaled-0050-0061-migrations.test.mjs` "refuses the live repository with
migration 0062"). Merging PR-B without a successor apply route would make every
later release schema audit fail. This plan does not build that route. PR-B must
not merge until (a) the ADR-103 freeze lifts after the release dispatch and (b)
an owner-approved successor-route ADR and route land. The PR body must state
this.

## Technical Considerations

- **Pattern usage**: SECURITY DEFINER with pinned `search_path` and
  `row_security = off` mirrors the existing 0062 trigger function;
  `IdempotentCommandError` contracts and route mapping are unchanged.
- **Security**: the predicate stops authorizing (see table). Fund isolation for
  staging and snapshots remains at the route. Onboarding append authority is
  unchanged. Disclosure is one ownership bit per artifact.
- **Concurrency**: removing `FOR SHARE` locks removes lock-order coupling
  between staging and user/grant updates. Ownership cannot appear after staging
  locks an artifact (onboarding only uses artifacts it creates).
- **Pre-migration deploys**: probe keeps staging, snapshots, and retention
  working before 0062 is applied.
- **Edge cases**: a restored key plus an identical review still reuses the key;
  a discarded key followed by an identical declaration returns 200 `existing`;
  CONTRACT_PARSE_ERROR (status 200) stays uncertain.
