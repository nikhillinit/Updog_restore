**Governing policy:**
`docs/governance/solo-internal-change-and-production-policy.md` (resolve from
`origin/main`). This plan grants no merge, production, schema, or release

Reviewed checkout: `origin/main` at `72c452caa` on 2026-09-27. Sources: the
September 24 queue (`docs/6-memo/research_2026-09-24_roadmap-reprioritization.md`,
"Recommendations" item 3) and the September 23 stabilize-and-qualify

## Overview

The fund workspace publish flow ships to Vercel on merge, but its only
real-backend browser test (Batch B) runs in no workflow and boots the
Docker/`registerRoutes` surface, not the `makeApp` surface that Vercel serves.
This plan adds a built-artifact Batch B runtime that serves the Vercel build
output, adds six browser cases for the write-path failures the September 23
review listed (stale-ETag 412, lost finalize response, two-session conflict,
double submit, and two actor-isolation variants), and runs Batch B in CI on
every pull request that touches the workspace journey, so the PR that adds it
qualifies itself without a manual dispatch. If the cross-tab actor case fails
on `main`, a one-line client fix lands in the same PR.

## Problem Statement

1. **Batch B runs nowhere in CI.** `.github/workflows/ci-unified.yml:113-119`
   selects `["integration","validate-core"]` for ordinary heavy pull requests
   and adds `e2e` only for `main`, `run_full_suite`, or a schema change. No
   group runs `npm run test:e2e:batch-b`.
2. **Batch B exercises the wrong surface.** `tests/e2e/support/batch-b-server.ts:84`
   boots `server/main.ts`, which runs `requireSecureContext` and
   `withIdempotency()` (`server/server.ts:229,256`). The Vercel surface does
   not: `server/app.ts:226` uses `requireAuth()` and has no `withIdempotency`.
   The dev harness also runs the React client, while the deployed bundle runs
   on Preact (`docs/ARCHI.md` section 1). Batch B evidence therefore covers
   middleware and a client runtime that production does not run.
3. **The write-path failure cases have no browser test.**
   `tests/e2e/fund-workspace-real-backend.spec.ts` has one test (`:139`). Its
   `route.fetch()`/`route.abort()` (`:453-461`) intercepts the draft `PUT`
   (draft-save recovery). No case covers a lost finalize response, a stale
   `If-Match` 412, a two-session conflict, a double submit, or an actor switch.
4. **A stated client invariant is unenforced across tabs.**
   `client/src/lib/queryClient.ts:63-66` states that cached query data belongs
   to the identity that fetched it and, with `staleTime: Infinity`, would be
   served to the next identity. `clearIdentityScopedQueries` runs on logout
   (`client/src/app/app-layout.tsx:201`), login success
   (`client/src/hooks/useLogin.ts:20`), and every unexpected 401
   (`queryClient.ts:74`). Each tab owns its own in-memory `QueryClient`, so a
   tab that did not log out or log in keeps the previous identity's cache after
   another tab switches the shared session cookie.

## Decisions

Owner answers, 2026-09-27:

- **D-A, CI lane: workspace path lane.** A new `batch_b` path filter adds a
  `batch-b` group to `test_full_groups` on heavy pull requests that touch the
  workspace journey. `main`, `run_full_suite`, and schema changes always add it.
  PR2 touches the harness, so its own head runs the lane. This is admission
  protection for the listed paths and post-merge detection (the `main` run) for
  everything else. It replaces the design doc's D3 placement and closes the
  design doc's "Batch B: PR-lane contract" TODO. D12 stays intact: no
  acceptance step needs a manual dispatch.
- **D-B, runtimes: built only in CI.** CI runs the built runtime (D14). The dev
  harness stays for local iteration. This amends the memo's item 3 acceptance
  ("both runtimes green on the exact candidate") to: the built runtime green in
  CI on the exact candidate, the dev runtime green locally, and a failing Batch
  B case fails `CI Gate Status`.
- **D-C, cross-tab fix: one line in PR2, only if the cross-tab case is red on
  `main`.** "Red" is defined in case C6 below. If C6 is green on `main`, no
  client change ships.
- **D-D, held-request actor case: out of scope.** PR2 holds only the finalize
  response (the server executes as actor A). Forwarding the held request after
  the actor switch is recorded as a TODO (see section 10).

Design-doc checks resolved while planning:

- **D14 preview check: rejected.** In the Vercel project, the Preview
  `DATABASE_URL` is scoped to a single unrelated git branch, so a preview built
  from the PR2 branch has no database. The lost-finalize recipe also needs a
  direct database query against the same database the app writes. The target is
  the local listener, labelled "built-artifact local acceptance". It is not
  deployment proof.
- **D4 freshness check: dropped.** The built harness always runs the build
  first, so a stale bundle cannot be served. This replaces D4's mtime check.
- **D4 readiness probe: `/api/health/ready`.** Vercel rewrites `/readyz` to
  `index.html` (`vercel.json:27-28`), so the built listener cannot serve it
  either. `/api/health/ready` (`server/routes/health.ts:246`) goes through the
  API rewrite and is exempt from the rate limiter (`server/app.ts:120`).

## Solution Architecture

Three parts, one pull request:

1. **Built runtime.** `BATCH_B_RUNTIME=built` makes the existing harness run
   the Vercel build command, import `makeApp()` from `api/_app.generated.mjs`,
   and serve it behind one local HTTP listener. The listener applies the
   `vercel.json` rewrite table: `/api/*` goes to `makeApp` with the URL
   unchanged, `/metrics/*` goes to `/api/metrics/*`, and every other path
   serves a file from `dist/public` or falls back to `index.html`. One origin
   serves both the client and the API, as on Vercel.
2. **Cases.** A sibling spec adds six cases that share helpers moved out of the
   existing spec. Every case creates its own funds and asserts by fund ID, fund
   name, and idempotency key, never by global table counts.
3. **CI lane.** A `batch_b` path filter feeds the existing group-selection step.
   The `test-full` matrix gains a `batch-b` leg that installs Chromium and runs
   the built runtime. `CI Gate Status` already requires `needs.test-full.result`
   on heavy pull requests (`ci-unified.yml:1018`), and a matrix job fails when
   any leg fails, so a failing Batch B case fails the gate with no gate change.

### 5. New recovery spec: six cases

**File**: `tests/e2e/fund-workspace-recovery.spec.ts` (new)

The file name sorts after the existing spec, but no case depends on order.
Each case uses unique fund names, fails on any uncaught page error, and asserts
only rows it created. The server's replay header is `Idempotency-Replay: true`
(`server/services/fund-workflow-service.ts:240`), and the server emits 412
`PRECONDITION_FAILED` for any command whose `If-Match` is not the current draft
ETag (`fund-workflow-service.ts:199-205`), which covers both `save_draft` and
`finalize`.

- **C1, two-session draft conflict (`save_draft` 412).** Two browser contexts
  sign in as actor A. Context 1 creates draft F. Context 2 opens F at step 1
  and waits for "Latest draft saved". Context 1 edits the as-of date and saves
  (200). Context 2 edits the as-of date to a different value; its `PUT` carries
  the old ETag and gets 412. Assert: context 2 shows the `draft-stale` alert
  ("A newer draft is available"), context 2 keeps its local value, the database
  draft holds context 1's value, and context 2 sends no further draft `PUT`
  without a user action.
- **C2, stale publish (`finalize` 412).** Context 1 creates draft G and
  advances to the review step. Context 2 opens G and saves an edit (new ETag).
  Context 1 clicks publish; the finalize request carries the old ETag and gets
  412. Assert: the stale-publish message (`STALE_PUBLISH_MESSAGE`,
  `client/src/pages/ReviewStep.tsx:46`) is visible, the URL stays on the review
  step, G has no published `fundconfigs` row, no finalize receipt exists for
  the request's key, and the session envelope holds no pending command.
- **C3, lost finalize response (design doc R4 recipe).** Create draft H and
  advance to review. Route the first `POST /api/funds/finalize`: record its
  `Idempotency-Key`, `If-Match`, and body; call `route.fetch()`; confirm through
  an independent database query that one finalize receipt for that key exists
  and H has one published `fundconfigs` row; then
  `route.abort('connectionreset')`. Assert the `publish-uncertain-alert` shows
  the uncertain-publication message, and the session envelope holds a pending
  `finalize` command with the recorded key. The test never writes the envelope.
  Click "Check publication status". Assert the replayed request carries the same
  key, `If-Match`, and body; the response has `Idempotency-Replay: true`; the
  browser lands on `/fund-model-results/<H>`; and the database still has one
  fund named H, one finalize receipt for the key, and one published
  `fundconfigs` row for H. The pending command is cleared.
- **C4, double submit during an in-flight finalize.** Create draft J and
  advance to review. Route every finalize request and hold it until the test
  releases it. Double-click the publish button (both clicks land before the
  re-render that disables the button, so the second click reaches
  `handleCreate`, whose `submitState` guard reads a stale closure,
  `ReviewStep.tsx:328-329`). Release the held requests. Assert: every finalize
  request carries the same `Idempotency-Key` (`prepareFundCommand` reuses a
  pending command's key, `client/src/stores/fundStore.ts:1401`), the database
  has one fund named J, one finalize receipt for the key, and one published
  `fundconfigs` row for J, and the browser lands on J's results page once. The
  number of requests (one or two) is recorded, not asserted.
- **C5, actor switch by logout and login (design doc actor case).** Actor A
  creates draft K and advances to review. Route the finalize request:
  `route.fetch()` (the server executes as A), then hold the response. Click
  publish. Log A out with the "Log out" button, then sign in as B on the same
  page. Release A's response. Assert: the page stays on B's dashboard (no
  navigation to K's results), `/api/auth/session` returns B, the session
  envelope's actor is B and holds no pending command with A's key, and no later
  request carries A's key. The design doc's "empty before and after proves
  nothing" rule holds: A's command is non-empty and unresolved at the switch.
- **C6, actor switch in another tab (cross-tab variant).** Install
  `page.clock` on page one before its first navigation (time keeps flowing;
  `fastForward` jumps it). Page one signs in as A, opens the workspace (this
  caches `GET /api/funds`), creates draft L, advances to review, and clicks
  publish with the response held after `route.fetch()`, as in C5. Wait for
  "Latest draft saved" before any clock jump, so the autosave debounce has
  nothing pending. Page two, in the same browser context (shared cookie), logs
  A out and signs B in. It cannot sign B in directly: `/login` redirects to `/`
  while a session exists (`client/src/app/app-router.tsx:202-205`). Assert that
  page one sends no request between page two's logout and B's login; such a
  request would get a 401, run `handleUnauthorized`, clear page one's cache, and
  hide the defect. On page one, `fastForward` past the session query's 60-second
  `staleTime` (`client/src/lib/auth-session.ts:48`) and navigate in-app (the
  "Settings" navigation link, no reload) so a new `useAuthSession` observer
  re-fetches the session. Assert that re-fetch returns B. Release A's response.
  Assert the same session, envelope, navigation, and key checks as C5. Then open
  the workspace in-app and assert a `GET /api/funds` response arrives after the
  rebind. **Red on `main` means that last request never arrives within the
  assertion timeout**: page one serves the list cached under A. `GET /api/funds`
  is organization-wide (`server/routes/funds.ts:172-174`), so this is not a
  cross-user data exposure; it is a violation of the invariant at
  `queryClient.ts:63-66` that login, logout, and 401 already enforce in one tab.

## Technical Considerations

- **Pattern usage**: Two deployment surfaces (`docs/ARCHI.md` section 3); the
  built mode targets the `makeApp` surface through the same generated bundle
  and rewrite table as Vercel. No new route, manifest entry, flag, schema, or
  migration.
- **Preact**: The built client is the Preact bundle (`vite build --mode
  preact`). C4's double-click timing depends on the render scheduler, which
  differs between React and Preact; running it in built mode tests the bundle
  that ships.
- **Surface-contract matrix**: `audit/surface-contract-matrix/source-inventory.json:666`
  pins a derived hash of `package.json#scripts`. The plan adds no npm script
  (CI sets `BATCH_B_RUNTIME` in the step environment) so the matrix needs no
  refresh. None of the other files this plan touches appear in the source
  inventory.
- **Migration freeze**: No change under `migrations/` or
  `scripts/prod-schema-manifests/`.
- **Lane wake-ups**: Editing `.github/path-filters.yml` and `ci-unified.yml`
  also matches `neon_lane` (`path-filters.yml:442-451`) and the full `code`
  filter; PR2's own run is heavier than a typical workspace PR.
- **Docker**: The `batch-b` leg needs Docker for the testcontainer. GitHub
  hosted runners provide it; `test:testcontainers` is precedent.
- **Clock control (C6)**: `page.clock.install()` must precede page one's first
  navigation. `fastForward` fires due timers, which is why the case waits for
  "Latest draft saved" first.
- **Edge cases**: C4 may produce one or two finalize requests depending on
  timing; the assertions are on the key and the database, not the request
  count. C5 and C6 depend on `ReviewStep`'s command fence
  (`isCurrentCommand`, `ReviewStep.tsx:130-137`) to ignore A's released
  response. C6's discriminator relies on nothing else invalidating
  `/api/funds` between the rebind and the workspace open; the publish success
  path that does invalidate it never runs in C6.
- **Non-goals**: Batch C (visual, keyboard, zoom), queue-backed paths (the
  scenario release gate owns them), deployed Vercel or Neon behavior, and the
  held-request actor case.

## Performance & Cost Impact

- **`batch-b` leg** (unmeasured estimate): Chromium install about 1 minute,
  Vite Preact build plus API bundle about 2-4 minutes, container start and
