## Overview

Each merge to `main` builds a Vercel deployment of the fund workspace publish
flow; production changes only through release dispatch (`vercel.json` sets
`github.autoAlias: false`). The flow's only real-backend browser test (Batch B)
runs in no workflow and boots the Docker/`registerRoutes` surface, not the
`makeApp` surface that Vercel serves. This plan adds a built-artifact Batch B
runtime that serves the Vercel build output, adds browser cases for the
write-path failures the September 23 review listed (stale-ETag 412, lost
finalize response, two-session conflict, double submit, and two actor-isolation
variants), and runs Batch B in CI on every pull request that touches the
workspace journey, so the PR that adds it qualifies itself without a manual
dispatch. If the cross-tab actor case fails on `main`, a few-line client fix
lands in the same PR. Planning found one server defect (a late finalize response
reinstalls a logged-out actor's session); PR2 characterizes it as an expected
failure and a follow-up plan fixes it.

## Problem Statement

1. **Batch B runs nowhere in CI.** `.github/workflows/ci-unified.yml:113-119`
   selects `["integration","validate-core"]` for ordinary heavy pull requests
   and adds `e2e` only for `main`, `run_full_suite`, or a schema change. No
   group runs `npm run test:e2e:batch-b`.
2. **Batch B exercises the wrong surface.**
   `tests/e2e/support/batch-b-server.ts:84` boots `server/main.ts`, which runs
   `requireSecureContext` and `withIdempotency()` (`server/server.ts:229,256`).
   The Vercel surface does not: `server/app.ts:226` uses `requireAuth()` and has
   no `withIdempotency`. The dev harness also runs the React client, while the
   deployed bundle runs on Preact (`docs/ARCHI.md` section 1). Batch B evidence
   therefore covers middleware and a client runtime that production does not
   run.
3. **The write-path failure cases have no browser test.**
   `tests/e2e/fund-workspace-real-backend.spec.ts` has one test (`:139`). Its
   `route.fetch()`/`route.abort()` (`:453-461`) intercepts the draft `PUT`
   (draft-save recovery). No case covers a lost finalize response, a stale
   `If-Match` 412, a two-session conflict, a double submit, or an actor switch.
4. **A stated client invariant is unenforced across tabs.**
   `client/src/lib/queryClient.ts:63-66` states that cached query data belongs
   to the identity that fetched it and, with `staleTime: Infinity`, would be
   served to the next identity. Logout does not call
   `clearIdentityScopedQueries`; `finishLocalLogout` removes identity-scoped
   queries with an inline `queryClient.removeQueries` predicate
   (`client/src/app/app-layout.tsx:196-205`). `clearIdentityScopedQueries` runs
   on login success (`client/src/hooks/useLogin.ts:20`) and every unexpected 401
   (`queryClient.ts:74`). Each tab owns its own in-memory `QueryClient`, so a
   tab that did not log out or log in keeps the previous identity's cache after
   another tab switches the shared session cookie.

## Decisions

Owner answers, 2026-09-27:

- **D-A, CI lane: workspace path lane.** A new `batch_b` path filter adds a
  `batch-b` group to `test_full_groups` on heavy pull requests that touch the
  workspace journey. `main`, `run_full_suite`, and schema changes always add it.
  PR2 touches the harness, so its own head runs the lane. This is admission
  protection for the listed paths and post-merge detection (the `main` run) for
  everything else. It replaces the design doc's D3 placement and closes the
  design doc's "Batch B: PR-lane contract" TODO. Release dispatch does not
  consume the Batch B result on the candidate. `release-production.yml:366-376`
  calls `release-proof.yml`, whose exact-SHA check (`release-proof.yml:653-695`,
  `scripts/release/verify-exact-sha-checks.mjs`) requires a green
  `CI Gate Status` on the candidate SHA. On a `main` push, however, the gate
  checks `test-full` only for pull requests (`ci-unified.yml:1017-1019`), and
  the exact-SHA allow list has no `Test batch-b` check. A red `Test batch-b` leg
  on `main` therefore leaves the gate green, and a docs-only candidate runs no
  `test-full` leg at all. The `main` run is detection only; section 10 adds the
  owner check TODO. D12 stays intact: no acceptance step needs a manual
  dispatch.
- **D-B, runtimes: built only in CI.** CI runs the built runtime (D14). The dev
  harness stays for local iteration. This amends the memo's item 3 acceptance
  ("both runtimes green on the exact candidate") to: the built runtime green in
  CI on the PR head and on the resulting `main` run (main requires
  rebase-before-merge, so the trees match), the dev runtime green locally, and a
  failing Batch B case fails `CI Gate Status` on the pull request. On `main` the
  leg is visible but not gating, and release dispatch does not read it (D-A).
- **D-C, cross-tab fix: a few-line fix in PR2, only if the cross-tab case is red
  on `main`.** "Red" is defined in case C6 below. If C6 is green on `main`, no
  client change ships.
- **D-D, held-request actor case: out of scope.** PR2 holds only the finalize
  response (the server executes as actor A). An intercepted request keeps the
  headers it was sent with, so forwarding it after the switch would carry A's
  revoked cookie and fail with 401; that case adds nothing. The residual risk is
  recorded as a TODO (section 10).
- **D-E, stale-response credential defect: characterize in PR2, fix next.**
  Codex round 1 found, and source confirms, that a successful finalize renews
  the creator's browser session: `renewCreationCredential`
  (`server/lib/auth/creator-identity.ts:64-104`, called at
  `server/routes/fund-config.ts:142`) sets new session and CSRF cookies for a
  new `jti`. Logout revokes only the `jti` it was sent
  (`server/routes/auth.ts:161-185`, `server/lib/auth/revocation.ts:82-88`), so a
  renewed token minted by an in-flight finalize survives logout. If that
  response reaches the browser after A logs out and B signs in, the browser
  installs A's live session over B's. PR2 adds case C5b as a Playwright expected
  failure scoped to A's session replacing B's, so the defect is reproduced in CI
  and the annotation must be removed when the fix lands. The same
  `renewCreationCredential` call (`server/routes/fund-config.ts:142`) runs after
  the workflow service returns even for a replay, so C3's publication-status
  replay renews credentials too; F_1.19.1 must cover that replay path. The fix
  is a separate plan (F_1.19.1) because the two known designs are an owner
  choice: a per-user revoke-at-logout epoch needs a new column (a migration,
  blocked by the freeze), and moving renewal to a client call made after the
  command fence needs a new route on both surfaces.

Design-doc checks resolved while planning:

- **D14 preview check: rejected.** In the Vercel project, the Preview
  `DATABASE_URL` is scoped to a single unrelated git branch, so a preview built
  from the PR2 branch has no database. The lost-finalize recipe also needs a
  direct database query against the same database the app writes. The target is
  the local listener, labelled "built-artifact local acceptance". It is not
  deployment proof.
- **D4 freshness check: dropped.** The built harness always runs the build
  first, so a stale bundle cannot be served. This replaces D4's mtime check.
- **D4 readiness probe: `/api/health/ready`.** Vercel rewrites `/readyz` to
  `index.html` (`vercel.json:27-28`), so the built listener cannot serve it
  either. `/api/health/ready` (`server/routes/health.ts:246`) goes through the
  API rewrite and is exempt from the rate limiter (`server/app.ts:120`).
  `readinessCheck` checks only the database (`server/health.ts:121-127`), so it
  returns 200 under the harness environment.

## Solution Architecture

Three parts, one pull request:

1. **Built runtime.** `BATCH_B_RUNTIME=built` makes the existing harness read
   `buildCommand`, `rewrites`, and `outputDirectory` from `vercel.json`, run the
   build command as one shell child process, import the default handler from
   `api/[...slug].ts`, and serve it behind one local HTTP listener. That is the
   canonical function entry (`boot-proof.mjs:615-616`); it lazily imports
   `api/_app.generated.mjs`, calls `makeApp()`, and provides the handler's 500
   response path. The listener supports the three current rewrite shapes:
   `/metrics/:path*` to `/api/metrics/:path*`, `/api/:slug*` to the function,
   and `/:path*` to `/index.html`, with static files from the output directory
   taking precedence as on Vercel. Any other rewrite source or destination exits
   nonzero and names it, so rewrite changes cannot pass against a stale copy.
   One origin serves both the client and the API, as on Vercel.
2. **Cases.** A sibling spec adds seven tests (C1-C4, C5a, C5b, C6) that share
   helpers moved out of the existing spec. Every case creates its own funds and
   asserts by fund ID, fund name, and idempotency key, never by global table
   counts.
3. **CI lane.** A `batch_b` path filter feeds the existing group-selection step.
   The `test-full` matrix gains a `batch-b` leg that installs Chromium and runs
   the built runtime. `CI Gate Status` already requires `needs.test-full.result`
   on pull requests (`ci-unified.yml:1017-1019`), and a matrix job fails when
   any leg fails, so a failing Batch B case fails the pull request gate with no
   gate change. The gate does not check `test-full` on `main` pushes (D-A).

## Implementation Details

### 1. Batch B harness: built mode and second user

**File**: `tests/e2e/support/batch-b-server.ts`

**Current state**: Starts a `pgvector/pgvector:pg16` testcontainer, migrates it,
seeds one `partner` user (`:42-47`), writes the runtime JSON, then spawns
`server/main.ts` under `tsx` on port 5087 and the Vite dev server on 5187.

**Modifications**:

- Seed a second `partner` user (actor B) after the first. The runtime JSON gains
  B's username, password, and user ID.
- Read `BATCH_B_RUNTIME`: unset or `dev` keeps today's behavior unchanged;
  `built` selects the built mode; any other value exits nonzero with a message.
- Built mode, in order:
  - Read `buildCommand` from `vercel.json` and run it as one shell child
    process. It is currently
    `npm run build:web && node scripts/build-vercel-api.mjs` (`vercel.json:7`);
    exit nonzero if it fails. Force `VITE_API_BASE_URL` to an empty string in
    the build environment, so `client/src/lib/api-url.ts:2` keeps API calls
    same-origin even if a local `.env` sets it. Do not pass the dev mode's
    `VITE_*` values to this child; leave `VITE_E2E_DEMO_ENABLED` unset because
    `'0'` is truthy and would open the production gate
    (`client/src/core/demo/persona.ts:19-22`).
  - Build the runtime environment from the same values the dev mode uses, with
    these differences: `CLIENT_URL` and `CORS_ORIGIN` equal the built origin
    (`http://localhost:5188`); `RATE_LIMIT_MAX` is raised well above the spec's
    request volume, because `server/app.ts:112` defaults to 60 requests per
    minute; `VERCEL` and `VERCEL_ENV` are never set, because `server/db.ts:72`
    would then select the Neon WebSocket driver against a plain Postgres
    container and `assertQueueRuntimePolicy` (`server/app.ts:38`) would apply
    Vercel rules. `NODE_ENV=test` with `ENABLE_QUEUES=0` and
    `REDIS_URL=memory://` passes the queue policy
    (`server/config/queue-runtime-policy.ts:35`).
  - Apply that environment to the harness process, dynamically import the
    default handler from `api/[...slug].ts` under the existing
    `node --import tsx` web-server command, and serve it on port 5188 behind an
    Express listener (Express is already a dependency). The listener reads and
    validates `rewrites` and `outputDirectory` at start, applies the rewrite
    table in the Solution Architecture, and exits nonzero for unsupported
    shapes. The listener runs in the harness process, so `stop()` closes it with
    the database.
- Record the evidence limits in a header comment: built mode proves the
  `makeApp` route and middleware surface and the built Preact client. It does
  not prove the Neon driver (the `neon-lane` job owns that), Vercel static-tier
  headers (the listener applies no `vercel.json` `headers`, so static responses
  carry no CSP; `helmet` covers only `/api` responses here), a shared rate-limit
  store, or production cookie attributes.

### 5. New recovery spec: cases C1-C6

**File**: `tests/e2e/fund-workspace-recovery.spec.ts` (new)

The file name sorts after the existing spec, but no case depends on order. Every
project in `playwright.config.ts`, `playwright.config.simple.ts`,
`playwright.manual-gp.config.ts`, and `playwright.lp-reporting.config.ts` uses
an explicit `testMatch` list, so the new spec runs only under
`playwright.batch-b.config.ts` and never without its runtime file. Each case
uses unique fund names, fails on any uncaught page error, and asserts only rows
it created. The server's replay header is `Idempotency-Replay: true`
(`server/services/fund-workflow-service.ts:240`), and the server emits 412
`PRECONDITION_FAILED` for any command whose `If-Match` is not the current draft
ETag (`fund-workflow-service.ts:199-205`), which covers both `save_draft` and
`finalize`.

- **C1, two-session draft conflict (`save_draft` 412).** Two browser contexts
  sign in as actor A. Context 1 creates draft F. Context 2 opens F at step 1 and
  waits for "Latest draft saved". Context 1 edits the as-of date and saves
  (200). Context 2 edits the as-of date to a different value; its `PUT` carries
  the old ETag and gets 412. Assert: context 2 shows the `draft-stale` alert ("A
  newer draft is available"), context 2 keeps its local value, the database
  draft holds context 1's value, and context 2 sends no further draft `PUT`
  without a user action.
- **C2, stale publish (`finalize` 412).** Context 1 creates draft G and advances
  to the review step. Context 2 opens G and saves an edit (new ETag). Context 1
  clicks publish; the finalize request carries the old ETag and gets 412.
  Assert: the stale-publish message (`STALE_PUBLISH_MESSAGE`,
  `client/src/pages/ReviewStep.tsx:46`) is visible, the URL stays on the review
  step, G has no published `fundconfigs` row, no finalize receipt exists for the
  request's key, and the session envelope holds no pending command.
- **C3, lost finalize response (design doc R4 recipe).** Create draft H and
  advance to review. Route the first `POST /api/funds/finalize`: record its
  `Idempotency-Key`, `If-Match`, and body; call `route.fetch()`; confirm through
  an independent database query that one finalize receipt for that key exists
  and H has one published `fundconfigs` row; then
  `route.abort('connectionreset')`. Assert the `publish-uncertain-alert` shows
  the uncertain-publication message, and the session envelope holds a pending
  `finalize` command with the recorded key. The test never writes the envelope.
  Reload the page, so recovery comes from the persisted envelope and not from
  in-memory state, and assert the uncertain state renders again
  (`ReviewStep.tsx:111-116` initializes it from the pending finalize). Click
  "Check publication status". Assert the replayed request carries the same key,
  `If-Match`, and body; the response has `Idempotency-Replay: true`; the browser
  lands on `/fund-model-results/<H>`; and the database still has one fund named
  H, one finalize receipt for the key, and one published `fundconfigs` row for
  H. The pending command is cleared.
- **C4, double submit during an in-flight finalize.** Create draft J and advance
  to review. Route every finalize request and hold it until the test releases
  it. Activate the publish button twice inside one `page.evaluate` (two
  synchronous `HTMLElement.click()` calls). Both handlers run before any render,
  so both read `submitState === 'idle'` from their closure
  (`ReviewStep.tsx:328-329`); the second finds the first's pending command,
  takes the replay branch, and `prepareFundCommand` returns the same key
  (`client/src/stores/fundStore.ts:1401`). A Playwright `dblclick()` is not
  used: a render between its two clicks disables the button, and the case would
  pass without reaching the replay branch. Assert two finalize requests with the
  same `Idempotency-Key`. Release the first, wait for its 201, then release the
  second and assert `Idempotency-Replay: true`. Sequential release keeps the
  case deterministic; concurrent execution of one key against the advisory lock
  and `lock_timeout` stays with PR3b, where the design doc assigns it. Assert
  the database has one fund named J, one finalize receipt for the key, and one
  published `fundconfigs` row for J, and the browser lands on J's results page
  once.
- **C5a, actor switch by logout and login: client fence.** Actor A creates draft
  K and advances to review. Route the finalize request and execute it out of
  band with the shared forwarding helper; its forwarded headers include A's
  cookie and CSRF header, and the response is held. `route.fetch()` is not used,
  because Playwright writes its response cookies into the browser context at
  once, before logout, which would let logout revoke A's renewed token and hide
  the D-E defect. The server executes the finalize as A. Click publish. Log A
  out with the "Log out" button, then sign in as B on the same page. The client
  aborts a finalize after `FUND_WORKFLOW_TIMEOUT_MS` (10 seconds,
  `client/src/services/fund-workflow.ts:15,89-92`), so the case times the
  interval from the publish click and fails with a named message if B's sign-in
  has not completed within 8 seconds, instead of silently testing the timeout
  path. Logout resets the fund store (`unbindFundWorkspaceActor`), so
  `ReviewStep`'s command fence ignores A's result on either path. Release A's
  response with every `Set-Cookie` header removed, which isolates the client
  fence from the D-E defect. Assert: the page stays on B's dashboard (no
  navigation to K's results), `/api/auth/session` returns B, the session
  envelope's actor is B and holds no pending command with A's key, and no later
  request carries A's key. The design doc's "empty before and after proves
  nothing" rule holds: A's command is non-empty and unresolved at the switch.
- **C5b, actor switch by logout and login: stale session cookie (expected
  failure).** This is the least-verified mechanic: Chromium must install
  `Set-Cookie` from a `route.fulfill` response. Use the same flow and
  out-of-band execution as C5a, but release A's response with its headers
  unmodified through `route.fulfill`. The ordinary prerequisites must pass: the
  out-of-band response is 201 with a session `Set-Cookie`, B's sign-in completed
  before the release, and one `/api/auth/session` request after the release
  returns 200 with a user ID that is A's or B's. Record that user ID as a test
  annotation of type `observed-session-user`, so the JSON report carries it.
  Also assert that the browser context's session cookie equals the token from
  A's response, proving the release, not a test artifact, installed it. Only
  after those pass does the test call `test.fail()` with the D-E reason and
  assert the recorded session user ID is B's. A 401, a 500, a third user, or any
  other prerequisite failure is a normal red test, never masked by
  `test.fail()`.

  If the cookie-equality prerequisite fails only because Chromium does not
  install the fulfilled `Set-Cookie`, switch to an API-level characterization of
  the same defect: take the renewed token from the out-of-band response's
  `Set-Cookie`, and after A's browser logout call `/api/auth/session` with that
  token through the isolated request context. The prerequisite is that the call
  returns 200 or 401; the test records the status as a test annotation of type
  `observed-renewed-token-status` (this path writes no `observed-session-user`
  annotation). Then call `test.fail()` with the D-E reason and assert 401,
  because the renewed token should die at logout. Record the switch and its
  reason in the PR body. While the defect exists the final assertion fails and
  the test reports as expected; once F_1.19.1 fixes it, the test reports
  "expected to fail, but passed" and the annotation must be removed.

- **C6, actor switch in another tab (cross-tab variant).** Install the context
  clock (`context.clock.install()`; `page.clock` is the same object) on page one
  before its first navigation. It covers page two too, so `fastForward` also
  fires page two's due timers; page two is idle on B's dashboard by then. Page
  one signs in as A, opens the workspace (this caches `GET /api/funds`), creates
  draft L, and waits for "Latest draft saved" so no autosave is pending. Page
  two, in the same browser context (shared cookie), logs A out and signs B in.
  It cannot sign B in directly: `/login` redirects to `/` while a session exists
  (`client/src/app/app-router.tsx:202-205`). Page one sends no request in that
  gap by construction: window-focus refetch is off
  (`client/src/lib/queryClient.ts:193`), no query polls, and nothing is pending.
  The case still counts page one's requests in the gap and fails if any is sent,
  because a request there would get a 401, run `handleUnauthorized`, clear page
  one's cache, and hide the defect. On page one, `fastForward` past the session
  query's 60-second `staleTime` (`client/src/lib/auth-session.ts:48`), then
  trigger a reconnect refetch on page one only: `page.evaluate` dispatches a
  window `offline` event and then an `online` event. TanStack Query 5.101.4
  listens to exactly these events (`@tanstack/query-core`
  `src/onlineManager.ts:21-22`), and on the change back to online the query
  client refetches every active query that is stale (`src/queryClient.ts:88-91`,
  `src/query.ts:342-345`, `src/queryObserver.ts:115-119`). The app keeps the
  default `refetchOnReconnect: true` (`client/src/lib/queryClient.ts:188-197`
  sets no override). The session query, observed by the always-mounted
  `AppRouter` (`client/src/app/app-router.tsx:200`), is stale and refetches. The
  funds list keeps the default `staleTime: Infinity`
  (`client/src/lib/funds-query.ts` sets none), so it is not stale and does not
  refetch. In-app navigation is not used as the trigger: on this path the
  session's only observer is `AppRouter`, which stays mounted, so a navigation
  mounts no new session observer and triggers no refetch. Assert the reconnect's
  `GET /api/auth/session` response returns B, and that the session envelope's
  actor is B with no pending command. Then open the workspace in-app and assert
  a `GET /api/funds` response arrives after the rebind. **Red on `main` means
  that last request never arrives within the assertion timeout**: page one
  serves the list cached under A. `GET /api/funds` is organization-wide
  (`server/routes/funds.ts:172-174`), so this is not a cross-user data exposure;
  it violates the invariant at `queryClient.ts:63-66` that login, logout, and
  401 already enforce in one tab. C6 holds no finalize: the 10-second client
  timeout is a fake timer under the context clock and would fire during the
  61-second jump, so a held response could not outlast it. The finalize fence
  across an actor switch is C5's job.

### 6. Cross-tab identity fix (only if C6 is red on `main`)

**File**: `client/src/app/app-layout.tsx`

**Current state**: The bind effect (`:186-195`) calls
`bindFundWorkspaceActor(session.user.id, ...)` whenever the session user
changes. `bindFundWorkspaceActor` (`client/src/stores/fundStore.ts:1329`) resets

## Technical Considerations

- **Pattern usage**: Two deployment surfaces (`docs/ARCHI.md` section 3); the
  built mode targets the `makeApp` surface through the same generated bundle and
  rewrite table as Vercel. No new route, manifest entry, flag, schema, or
  migration.
- **Preact**: The built client is the Preact bundle
  (`vite build --mode preact`). C4's double-click timing depends on the render
  scheduler, which differs between React and Preact; running it in built mode
  tests the bundle that ships.
- **Surface-contract matrix**:
  `audit/surface-contract-matrix/source-inventory.json:666` pins a derived hash
  of `package.json#scripts`. The plan adds no npm script (CI sets
  `BATCH_B_RUNTIME` in the step environment) so the matrix needs no refresh.
  None of the other files this plan touches appear in the source inventory.
- **Migration freeze**: No change under `migrations/` or
  `scripts/prod-schema-manifests/`.
- **Lane wake-ups**: Editing `.github/path-filters.yml` and `ci-unified.yml`
  also matches `neon_lane` (`path-filters.yml:442-451`) and the full `code`
  filter; PR2's own run is heavier than a typical workspace PR.
- **Docker**: The `batch-b` leg needs Docker for the testcontainer. GitHub
  hosted runners provide it; `test:testcontainers` is precedent.
- **Clock control (C6)**: `context.clock.install()` must precede page one's
  first navigation and applies to every page in the context. `fastForward` fires
  due timers on both pages, which is why the case waits for "Latest draft saved"
  first, leaves page two idle on B's dashboard, and holds no finalize request.
- **Edge cases**: C4 dispatches both clicks in one task, so it always issues two
  requests; it releases them in order so the second is a replay, not a lock
  contender. C5a and C5b depend on `ReviewStep`'s command fence
  (`isCurrentCommand`, `ReviewStep.tsx:130-137`) to ignore A's released
  response, and on B's sign-in finishing inside the 10-second client timeout.
  C6's discriminator relies on nothing else invalidating `/api/funds` between
  the rebind and the workspace open; the publish success path that does
  invalidate it never runs in C6, and the reconnect refetch skips the funds list
  because it is never stale under `staleTime: Infinity`.
- **Non-goals**: Batch C (visual, keyboard, zoom), queue-backed paths (the
  scenario release gate owns them), deployed Vercel or Neon behavior, and the
  held-request actor case.
