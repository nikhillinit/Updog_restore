# Draft Save Acknowledgement and Stale Bootstrap Exit Implementation Plan

**Governing policy:**
`docs/governance/solo-internal-change-and-production-policy.md` (resolve from
`origin/main`). This plan is a client-only defect repair with no production,
schema, or release authority. Merge, deploy, and production remain separate
owner actions.

Source: TRIP-research session of 2026-10-29 against `origin/main` at `86d8002e4`
(#1668), with a Codex fact-check of the three conclusions. Line numbers below
refer to that commit. Branch: `fix/f1152-draft-save-ack-stale-exit` from
`origin/main`. The local branch `codex/bootstrap-save-confirmation`
(`c7a5b4a79`) is superseded by #1576 (`f6ef7d5de`) and is not a base for this
work.

Owner decisions (discovery, 2026-10-29): one PR with two atomic commits (phase 1
= defect A, phase 2 = defect B); on a bootstrap 412 the Fund Basics step shows
only the shell stale banner; the FundWorkspace dialog stale handler is deferred
to a TODO; the two minor UX findings (dead Next click during a hook autosave,
`idle` status during the bootstrap save) are out of scope.

## Overview

F_1.15.0 moved every `save_draft` caller onto `saveDraftAndSettle`, and F_1.15.1
(#1576) added the live-save registry so a live bootstrap save is not reported as
uncertain. Two defects remain on the same path. (A) A direct save leaves the
autosave hook unaware of the acknowledgement, so an armed debounce sends a
second, redundant PUT. (B) A 412 on the direct Fund Basics bootstrap save never
reaches the shell's stale-recovery UI and does not survive a reload, so the user
has no way out of the stale state. Both fixes stay inside the existing
settlement module, the autosave hook, and the Fund Basics step.

## Problem Statement

### A. Duplicate PUT after a fast direct save

`TODOS.md:187` records this but understates it. Reproduced on `86d8002e4` with
the bootstrap suite's `BootstrapWithDraftSync` harness (draft 77,
`draftServerReady: false`): an edit arms the 600 ms debounce, Next dispatches
the direct save, the save is acknowledged, and then the debounce expires. Two
`saveFundDraft` calls result; the second has a new key and the acknowledged
ETag, so it advances the server revision with identical content. A step change
is not required; the step-change flush is only a second way to fire the same
armed timer.

Root cause: the hook's "already saved" baseline is the hook-local
`lastSavedSignatureRef` (`client/src/hooks/useFundDraftSync.ts:82`). It is
written only by hook-owned saves and hydrations (`:161`, `:214`, `:311`,
`:356`). Direct callers of `saveDraftAndSettle` (`FundBasicsStep`,
`FundWorkspace`) never update it, so the skip check at `:130` sees an outdated
or null baseline and prepares a new command.

A second, pre-existing weakness in the same check: the baseline is a content
signature only. If this tab acknowledged content A at ETag e1, another writer
saves B at e2, and the user chooses "Overwrite saved draft" (`keepLocalDraft`,
`:250`, which installs e2 and calls `persistCurrentDraft`), a local A equal to
the old baseline makes `persistCurrentDraft` report `synced` without writing A
over B. Moving the baseline unchanged would keep this weakness.

### B. A stale bootstrap save has no exit

When the direct bootstrap save returns 412 (`draftServerReady: false`, and a
second writer, such as a duplicated tab or another partner, advanced the draft),
`FundBasicsStep` groups `stale` with `rejected` and `retry_same_key`
(`client/src/pages/FundBasicsStep.tsx:262`) and only sets a step-local
`bootstrapError` (the raw server message). Consequences, confirmed by a probe on
`86d8002e4`:

- `draftSyncStatus` never becomes `stale`, so the shell's stale banner with
  "Load server draft" and "Overwrite saved draft"
  (`client/src/pages/fund-setup.tsx:386`) never renders.
- The hook's recovery effect returns early on
  `!draftServerReady && !needsServerHydration` (`useFundDraftSync.ts:335`), so
  nothing fetches the server draft, either now or after a reload.
- Every Next click prepares a new command against the same stale ETag and gets
  412 again. A reload restores `draftServerReady: false` from the envelope and
  the cycle continues.

Hook-owned saves already set `stale` on 412 (`useFundDraftSync.ts:165`), but
leave `draftServerReady` unchanged. Because `draftSyncStatus` is not in the
workspace envelope (`client/src/stores/fundStore.ts:780`), a reload loses that
`stale` status too whenever readiness was still false.

## Solution Architecture

**A: shared acknowledgement record.** Move the hook's baseline into
`client/src/services/fund-draft-settlement.ts`, next to the `inFlightSaves`
registry, and follow the same precedent: a module-local, transient,
non-persisted record. It holds a single slot (the store holds one workspace):
session id, fund id, content signature, and acknowledged ETag.
`saveDraftAndSettle` writes it for every `saved` outcome after the existing
session/fund/command fence accepts the result, regardless of which caller
dispatched. The hook writes it on its hydration paths and clears it when
identity clears. The hook treats current content as already saved only when
session, fund, signature, and the store's current `draftETag` all match the
record. A reload clears the record, the same as the registry.

**B: durable stale transition.** A 412 on the direct bootstrap save becomes the
same durable state as a hook-detected stale draft. Set `draftServerReady: true`
and `draftSyncStatus: 'stale'`, keep local values and the old ETag, and let the
shell's existing stale banner own the resolution. Setting readiness is valid:
the server returns 412 only after it has found an active draft for the fund
(`server/services/fund-workflow-service.ts:194-206`). Persisted readiness lets a
reload reconstruct `stale` through the hook's existing ETag comparison
(`useFundDraftSync.ts:346-370`). Fund Basics Next stays blocked while the shell
shows an unresolved draft state (`stale`, `hydrating`, `uncertain`, or `error`),
because with readiness true an unblocked Next would navigate without saving the
local edits. Only a successful recovery (`synced`) unblocks it. An autosave
debounce armed before the 412 is cancelled and re-checked at fire time, but the
explicit Overwrite action still dispatches.

`needsServerHydration` is not used to trigger recovery. That flag selects the
branch that replaces local values with the server snapshot, which would discard
the user's edits.

## Implementation Details

### 1. Settlement module: acknowledgement record

**File**: `client/src/services/fund-draft-settlement.ts`

**Current state**: module-local `inFlightSaves` registry (`:25`) and
`isDraftSaveInFlight`. `saveDraftAndSettle` fences on session, fund, and command
key (`:91-97`), and its `saved` branch sets the ETag and resolves the command
(`:98-108`). It does not record what was acknowledged.

**Modifications**:

- Add a single module-local acknowledgement slot beside `inFlightSaves`, with a
  short comment in the same style as the registry's ("a reload clears it").
- Export three small functions: record an acknowledgement (session, fund,
  signature, ETag), clear it, and a predicate that answers "is this signature
  acknowledged for this session, fund, and current ETag". The predicate returns
  false when any field differs or the slot is empty.
- In the `saved` branch, after `setDraftETag` and `resolveCommand`, record the
  captured session, `fundId`, `dispatchedSignature`, and the store's resulting
  `draftETag`. Record the dispatched signature even when `newerEdits` is true.
  The `superseded`, `stale`, `rejected`, `uncertain`, and `retry_same_key`
  branches do not record.
- `applyDraftSnapshot` is unchanged: it has no write-options context to compute
  a signature, so hydration recording stays with the hook.

### 2. Autosave hook: read the shared record

**File**: `client/src/hooks/useFundDraftSync.ts`

**Current state**: `lastSavedSignatureRef` (`:82`) is written at `:161`, `:214`,
`:311`, and `:356`, and read at `:130`, `:357`, and `:422`.

**Modifications**:

- Remove `lastSavedSignatureRef`.
- `:161` (hook `saved` callback): delete the write. The settlement module now
  records every accepted save, including hook-owned ones.
- `:214` (`applyServerSnapshot`): record the post-hydration local signature with
  the snapshot ETag for the current session and fund.
- `:311` (identity cleared): clear the record.
- `:356` (recovery, ETag equal): record the snapshot signature with the snapshot
  ETag; the `:357` comparison uses the predicate. This site records
  `canonicalJson(snapshot.config)` while `:214` records `localSignature()`. That
  split already exists on main and is kept as-is; it is not new behaviour.
- `:130` (`persistCurrentDraft` skip): use the predicate against the live
  `draftETag`. The skip still runs only after the existing pending-command and
  operation guards (`:118-126`) and only when there is no pending command. A
  content match must never bypass recovery.
- `:422` (autosave subscriber): use the same predicate, so content that returns
  to the acknowledged state at the acknowledged ETag does not schedule a save.
- Leave the existing designed behaviour alone. Edits made while a direct save is
  in flight are not drained by the hook's queue (`queuedSaveRef` drains only in
  the hook-owned `finally`, `:194-208`). Fund Basics keeps asking for a second
  Next ("Save the newer changes before continuing", asserted by the test at
  `tests/unit/pages/fund-basics-bootstrap.test.tsx:778`).

### 3. Fund Basics: durable stale on bootstrap 412

**File**: `client/src/pages/FundBasicsStep.tsx`

**Current state**: `stale` shares a case with `rejected` and `retry_same_key`
(`:262-267`) and sets a step-local error. Next is disabled only for
`isBootstrapping || draftSyncStatus === 'uncertain'` (`:494`). `handleNext`
returns early only for a live registry save (`:131-137`).

**Modifications**:

- Split `stale` into its own case: set `draftServerReady` true and the store
  status to `stale`, and reset the bootstrap stage to idle. Set no step-local
  error; the shell banner owns the message. This follows #1576's `uncertain`
  pattern at `:258-261`.
- Extend the Next `disabled` condition from `uncertain` to the unresolved set
  `uncertain`, `stale`, `hydrating`, and `error`. `stale` alone is not enough: a
  failed "Load server draft" fetch or a failed Overwrite sets `error`
  (`useFundDraftSync.ts:242-245`, `:272-275`, and the `rejected` and
  `retry_same_key` outcome cases), and with readiness already true, Next would
  then skip the bootstrap save and navigate.
- Add a live-state check at the top of `handleNext` for the same set, reading
  the store's current status. This mirrors the existing live registry check, so
  a click queued before the re-render cannot navigate.
- Every status in the set already has a shell banner action (`error`: Retry;
  `stale`: Load server draft / Overwrite saved draft; `uncertain`: Check save
  status; missing draft: view results / start new fund; `hydrating` resolves on
  its own), so the block cannot become a new dead end.
- `rejected` and `retry_same_key` keep their current step-local handling.

### 4. Autosave hook: stale entry and guarded debounce

**File**: `client/src/hooks/useFundDraftSync.ts`

**Modifications**:

- Hook-owned `stale` outcome (`:165-168`): also set `draftServerReady` true,
  using the same reasoning as section 3, so a reload rebuilds `stale` instead of
  dropping it.
- Cancel the pending debounce when the store status becomes `stale`, from any
  source (direct caller, hook outcome, or recovery comparison). Use a small
  effect keyed on the selected `status` that calls `clearPendingSave`.
- Close the window between the store update and that effect: the debounce
  callbacks (`:360` and `:431`) and the step-change flush (`:456-462`) check the
  live store status when they fire and drop the dispatch when it is `stale` or
  `hydrating`. Explicit callers (`keepLocalDraft` at `:270` and `:282`, `retry`
  at `:302`) keep calling `persistCurrentDraft` directly, so "Overwrite saved
  draft" still dispatches while the status is `stale` or `hydrating`. Do not add
  an unconditional status guard inside `persistCurrentDraft`; it would break the
  Overwrite action.

### 6. Test harness preparation

**Files**: `tests/unit/pages/fund-basics-bootstrap.test.tsx`,
`tests/unit/pages/fund-setup-draft-sync.test.tsx`,
`tests/unit/performance/autosave-debounce.behavior.test.tsx`,

- **Record isolation.** The bootstrap and settlement suites reset through
  `resetFundWorkspace`, which issues a fresh `sessionId`

  That reuses one `sessionId` for every test in the file, so the record could
  leak from one test into the next. Add the exported clear call to the

  the hook already uses; do not add a test-only production seam.
- **Draft fetch in the bootstrap suite.** Its
  `vi.mock('@/services/fund-drafts')` (`:56`) exports only `saveFundDraft`, but
  the phase 2 shell tests drive the hook into `fetchFundDraft` and
  `isMissingDraftError` (Load server draft, Overwrite, rebuild after reload).
  Extend that file-local mock in the pattern of
  `fund-setup-draft-sync.test.tsx:53-57`: spread the original module, add a
  `fetchFundDraft` mock whose default rejects with "no draft fetch expected",
  and reset it in `beforeEach`. Existing bootstrap tests never reach a fetch
  (one would currently throw), so their assertions do not change. Grep the file
  for fetch-dependent assertions before editing, per the pre-action rule for
  shared mocks. The direct-bootstrap tests must stay in this suite, because
  `fund-setup-draft-sync.test.tsx` replaces `FundBasicsStep` with a stub
  (`:26`).
- **Reload simulation.** The hook reads the `fundStore` singleton, so an
  isolated store cannot exercise it. While the actor stays bound, any in-memory
  reset is written back to sessionStorage (`fundStore.ts:831-835`), so the
  envelope must be captured first. Simulate a reload in five steps:
  1. After the 412, read the exact stored envelope string under
     `FUND_WORKSPACE_STORAGE_KEY`.
  2. Unmount the shell.
  3. Replace in-memory state with `getInitialState()` and clear the
     acknowledgement record.
  4. Write the captured string back to sessionStorage.
  5. Await `bindFundWorkspaceActor(TEST_ACTOR_ID)`, which calls
     `fundStore.persist.rehydrate()` (`fundStore.ts:1337`), and remount.

  Then assert that `draftServerReady` and the old ETag were restored, that
  `fetchFundDraft` was called, and that the status rebuilds to `stale`.

## Technical Considerations

- **Pattern usage**: the record copies the `inFlightSaves` precedent
  (module-local, transient, session-keyed). This keeps the six suites that
  `vi.mock('@/services/fund-drafts')` unaffected in shape (ARCHI §5, "Fund draft
  command settlement"). Callers still own status, `draftServerReady`, dialog
  text, and navigation.
- **ETag binding**: the record matches only at the store's current `draftETag`.
  This closes the Overwrite no-op described in the Problem Statement and makes a
  record left over from an earlier revision harmless.
- **Readiness semantics**: `draftServerReady` means the server has an
  authoritative draft for `draftFundId`. A 412 proves that the active draft
  exists. Other consumers of readiness are unaffected while stale: the shell's
  explicit-fund switch treats only `ready && synced` as settled
  (`fund-setup.tsx:172`), and autosave waits for verification when ready
  (`useFundDraftSync.ts:410`). In both 412 flows the recovery effect has already
  verified the fund while the save was pending (`:322-324`), so setting
  readiness does not trigger a fetch in the same mount; only a reload or remount
  fetches.
- **Next gating change (intended)**: on main, a draft that is already
  server-ready can leave Fund Basics while the hook reports `error`. After this
  change it cannot until the shell banner action resolves the state. This
  matches the bootstrap rule from F_1.15.1 (Next waits for a confirmed draft)
  and applies only to step 1.
- **Cross-mount behaviour change (intended)**: on main every hook mount starts
  with a null baseline, so an explicit retry after a remount re-sends content
  that was already acknowledged. With the shared record, the same session at the
  same ETag reports `synced` without a PUT. The implementer must grep the
  hook-mounting suites for `unmount`/`rerender` paired with save-count
  assertions. The one found so far, `fund-setup-draft-sync.test.tsx:752`,
  involves an uncertain save that is never acknowledged, so it should be
  unaffected. Any test that encodes the old re-send must be called out in the
  commit, not silently rewritten.
- **Edge cases**:
  - Superseded acknowledgements: a save that resolves after a session or fund
    change fails the fence and records nothing.
  - An armed debounce plus edits made during a direct save: the timer fires
    after the acknowledgement, sees content that differs from the record, and
    saves the newer edits. This happens on main today; it is not a regression.
  - Duplicated tab: the record lives in memory per page, so a duplicated tab has
    none. Cross-tab safety still depends on server idempotency and the 412
    fence.
  - Reload after phase 2's stale: the envelope restores `draftServerReady: true`
    and the old ETag. The recovery effect fetches, sees a different ETag, and
    sets `stale` with the server ETag captured for Overwrite.
- **Risk**: the main regression risk is a skip that is too broad and silently
  drops a real save. Mitigations: the ETag binding, the guard ordering in
  section 2, and the overwrite regression test in Test Impact.
