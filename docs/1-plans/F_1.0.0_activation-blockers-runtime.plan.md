the Current-Forecast V2 activation critical path documented in ADR-068
(`DECISIONS.md:9779-9788`). It covers six items: `#1325` (retire the last

## Problem Statement

The Current-Forecast V2 system is code-complete but **cannot activate in
production** because:

- **Shadow mode is unreachable.**
  `currentForecastCalculationModeStrategy.validateAccepted`
  (`server/services/fund-calculation-mode-service.ts:691`) unconditionally
  returns `accepted_reconciliation_required`, and the `shadow` branch of
  `updateFundCalculationMode` (`:911-925`) calls it before writing the row — so
  `off → shadow` always throws `FundCalculationModeBlockedError`. No fund can
  enter shadow mode via any production surface, which makes every downstream
  soak/activation step vacuous.
- The shadow-execution path (`current-forecast-shadow-service.ts`) has **zero
  production importers** — `substrate_shadow_reconciliations` rows never get
  written, so the activation gate (`verifyGreenCandidateWithLedger`) always
  raises `shadow_green_required`.
- The shadow trigger as originally sketched was underspecified: the facts
  builder returns no row ID (a bare row-ID or "latest" read would race), the
  financial-facts commit path produces **no pinned V2 receipt to compare
  against** (only the checkpoint path runs `runCurrentForecastV2WithReceipt`),
  raw fire-and-forget can be frozen by Vercel after the response is sent
  (silently losing reconciliation evidence), and one persisted historical failed
  row would block activation forever (`verifyGreenCandidateWithLedger`'s
  fund-wide `substrate_state='failed'` query in
  `server/services/current-forecast-reference-service.ts:501-514` blocks on ANY
  historical failed row).
- Recovery from `held` is currently impossible as described anywhere: pointer
  advance requires effective `on`, rollback only creates a candidate, and
  activation is one-shot — so there is no tested resume/re-arm path, no
  production entrypoint that could invoke one (the mode route 409s every `on`
  request at `server/routes/current-forecast.ts:295-302`), and the kill-switch
  drill cannot safely run until both exist.
- The inert `enable_current_forecast_v2` flag is present in the registry but
  absent from the generated flag-types union — zero production reads, yet tests
  assert against it.
- The legacy `metricsAggregator` facade still has 3 production consumers that
  must be migrated off before the module can be retired.

## Solution Architecture

The solution follows the **Decision A** approach (DB-mode/reference activation
only — flag retired):

- **Facade retirement (#1325):** migrate the 3 remaining production consumers
  off `metricsAggregator` to a named V2-only seam module —
  `server/services/current-forecast-serving-seam.ts` (new) exporting
  `getDualForecast(fundId)`, `getUnifiedMetrics(fundId, opts)`, and
  `invalidateCurrentForecastCache(fundId)`. The seam delegates to the
  `metricsAggregator` singleton, so serving dispatch stays inside
  `metrics-aggregator.ts` and authoritative responses are byte-identical (#1325
  AC). The manifest allowlist shrinks from 3 consumers to **the seam module
  alone — not to empty**: the guard
  (`scripts/guardrails/legacy-calculation-consumers-lib.mjs:91`) errors on any
  non-allowlisted import of the protected module, so an empty allowlist plus a
  delegating seam is contradictory.
- **Shadow-mode reachability (NEW-A, prerequisite):** permit the `off → shadow`
  transition for the current-forecast key without an accepted reconciliation.
  Scoped strategy change in `fund-calculation-mode-service.ts` (a per-strategy
  `shadowRequiresAccepted: false` knob) honored in **both** places that raise
  the blocker: the `shadow` transition branch (`:911-925`) AND
  `buildModePreview` (`:571`, which otherwise reports
  `accepted_reconciliation_required` for every non-off mode) — so `off → shadow`
  succeeds, sets `shadow_started_at`, and returns a clean preview, while `on`
  stays impossible via the mode route (existing 409
  `activation_command_required`) and the activation command's gates are
  untouched.
- **Shadow runtime wiring (NEW-A):** a new trigger module is called from both
  production facts-commit call-sites (`financial-facts.ts` and
  `analysis-checkpoint-service.ts`). It resolves mode via
  `resolveCurrentForecastModeResolution(fundId)`; when `shadow`, it obtains a
  **pinned receipt** for the committed basis (never a bare row ID or a "latest"
  read): the checkpoint path reuses the receipt it already produced via
  `runCurrentForecastV2WithReceipt` (`analysis-checkpoint-service.ts:1412`); the
  financial-facts path performs a hash-based receipt lookup for the committed
  basis and, when none exists, first pins one via the **get-or-create baseline
  execution** defined below. The shadow comparison is then an **exact-basis
  replay** against the pinned receipt's expected hashes, calling
  `runCurrentForecastShadowBase` with explicitly constructed inputs.
- **Trigger lifecycle (single semantics):** the trigger **awaits bounded shadow
  execution with a timeout before the facts-commit response returns**. No
  `waitUntil()`, no outbox/queue, no fire-and-forget. On timeout the trigger
  persists a failed reconciliation row (timeout reason) and lets the response
  proceed; the underlying promise may settle later, but its persistence is
  conflict-tolerant and superseded by later observations (no claim of cancelling
  in-flight engine/DB work).
- **Failure semantics (decision: latest-decisive-observation gating, no
  migration):** shadow failures persist a failed reconciliation row
  (`substrate_state='failed'`) plus structured log. The activation gate's
  failed-row check in `verifyGreenCandidateWithLedger`
  (`current-forecast-reference-service.ts:501-514`) changes from "any historical
  failed row" to **latest-decisive-observation**: define **decisive** =
  `substrate_state='failed'` OR (`substrate_state='available'` AND
  `reconciliation_status` IN (`'match'`,`'mismatch'`)) — state-qualified because
  the writer stamps `reconciliation_status='mismatch'` on every non-value row
  (`unavailable`/`failed` have no third status;
  `current-forecast-shadow-service.ts:166-171`); the gate selects the fund+key's
  most recent decisive observation (ordered by `observed_at`/`id`, served by the
  existing `idx_substrate_shadow_reconciliations_fund_observed` index) and
  blocks unless it is `available`+`match`. Non-decisive rows (`unavailable`,
  `indicative`) are skipped — they neither block nor clear. No decisive rows →
  this check raises no blocker (the candidate-basis `match` requirement above
  still governs green). Each new facts commit produces observations under a NEW
  `input_hash` (facts-snapshot ID and clock change per commit, so per-basis
  grouping could never clear an old-basis failure) — a later `available`+`match`
  observation under any basis unblocks. Failure persistence uses
  **`ON CONFLICT DO NOTHING`** (fixed policy — never a timestamp touch, so a
  repeated same-basis failure after a later success can never resurrect the
  blocker) under the existing partial unique on `(fund, key, input)` for
  null-hash rows. No schema/migration change. The facts commit itself never
  fails on shadow errors. Retry is the next organic facts commit. Soak-window
  failure interpretation (distinct from the gate) stays with
  `evaluateCurrentForecastShadowGreen` and the NEW-B runbook.
- **Bounded idempotency key (pre-existing latent bug):**
  `currentForecastReferenceIdempotencyKey` currently emits
  `cfref:{fundId}:{inputHash}:{resultHash}` — ≥137 chars against the
  `varchar(128)` `idempotency_key` column
  (`shared/schema/current-forecast-references.ts:58`), so candidate creation
  would always fail at insert. The function has zero production callers today
  (only the unwired shadow path), so the fix is a **bounded key**:
  `cfref:{fundId}:{sha256(inputHash + ':' + resultHash)}` (~82 chars) —
  deterministic, dedupe semantics preserved, no column widening, no data
  migration.
- **Idempotent baseline receipt (get-or-create, advisory-lock serialized):** the
  current baseline path (`current-forecast-v2-service.ts:276`) unconditionally
  inserts a new `fund_snapshots` row. The facts-path baseline becomes
  **get-or-create keyed by exact basis** (fundId, factsSnapshotId,
  planVersionId, clock), serialized by a **transaction-scoped Postgres advisory
  lock** (`pg_advisory_xact_lock` on a 64-bit hash of the basis tuple): acquire
  lock → select existing `CURRENT_FORECAST_V2` receipt for the basis →
  run+insert only when absent. The lock makes concurrent get-or-create atomic
  without a unique constraint or serializable isolation; as defense-in-depth,
  any duplicates that predate the lock resolve deterministically to the lowest
  `fund_snapshot` id. No schema change.
- **Recovery (resume/re-arm):** a dedicated, tested resume/re-arm command
  provides recovery from `held` without repeat activation, exposed via a
  production admin entrypoint:
  `POST /api/admin/funds/:fundId/calculation-modes/current-forecast/resume` on
  the existing mounted router in `server/routes/current-forecast.ts`
  (requireAuth + requireFundAccess + requireRole('admin'), `Idempotency-Key`
  header required — 428 when missing, matching the mode route —
  `expectedVersion` optimistic locking, atomic state mutation through the
  `fund_calculation_mode_requests` ledger, plus a route-policy entry in
  `server/route-policy/api-route-policy-registry.ts` and
  `COMMON_API_ROUTE_POLICY_IDS` mapping verified by `npm run policy:verify`).
  **State-transition contract:** `held` already serves the pinned reference head
  named by `cutover_reference_id`
  (`current-forecast-reference-service.ts:238-240`) — resume does NOT "return to
  the pinned reference"; it **re-arms live V2 serving** from every held cause.
  The held causes are the `CurrentForecastHeldReason` union
  (`current-forecast-calc-mode-resolver.ts:35`): `kill_switch`,
  `configured_off`, `configured_shadow`. Contract: require a row-locked
  post-activation state (non-null `cutover_reference_id`, `activated_at`),
  reject pre-cutover funds with 409, then **set `configured_mode='on'` AND
  `kill_switch_active=false`** (one idempotent write covering all three causes)
  while preserving every activation/pointer field. Activation remains a one-way
  latch: a **fresh-key** repeat activation returns 409; a **same-key** replay of
  a completed activation returns 200 with `replayed: true` (existing ledger
  semantics at `current-forecast-reference-service.ts:584`). Pointer advance and
  rollback reference are NOT recovery mechanisms and are never claimed as such.
- **Flag retirement (#1299-R):** delete `enable_current_forecast_v2` from the
  registry and regenerate the flag types/defaults.
- **Soak governance (NEW-B):** a runbook defines the 4×7-day soak windows,
  ADR-057 green criteria, `evaluateCurrentForecastShadowGreen` evaluation,
  failure/retry interpretation under latest-decisive-observation gating, and the
  kill→held drill procedure (gated on the resume/re-arm command). The soak
  itself is executed by the Phase 2 plan after this release deploys.

## Technical Considerations

- **Pattern Usage**: Each item has concrete verification commands, explicit
  invariants, and its own To-dos checkboxes. All file paths and call-sites have
  been verified in-repo.
- **One-way activation latch**: The kill-switch drill can demonstrate
  held-serving, **not** legacy restoration — an accepted consequence of Decision
  A. Fresh-key repeat activation returns 409; same-key replay of a completed
  activation returns 200 with `replayed: true` (ledger semantics at
  `current-forecast-reference-service.ts:584`); recovery from `held` exists only
  via the tested resume/re-arm command and admin route from item 3, never via
  pointer advance or rollback reference.
- **Shadow-mode reachability**: `off → shadow` is currently impossible (strategy
  blocker at `fund-calculation-mode-service.ts:691` invoked by the shadow branch
  at `:911-925`); NEW-A's strategy change is a prerequisite for every other
  runtime item and for the Phase 2 soak.
- **Prompt-drift risk**: Two merges landed on snapshot day (#1333, #1326) — plan
  keyed to origin/main `a3d0a6b6`; re-fence before each dispatch.
- **Broken verification commands**: `test:rls` is broken; "194 audit tests" is
  nonexistent — verification fields above use only collected-and-confirmed
  commands.
- **Shadow failure semantics (decision)**: latest-decisive-observation gating —
  decisive = `failed` OR (`available` AND status IN (`match`,`mismatch`)),
  state-qualified because the writer stamps `mismatch` on every non-value row;
  the gate (`current-forecast-reference-service.ts:501-514`) blocks unless the
  fund+key's most recent decisive observation is `available`+`match`;
  `unavailable`/`indicative` rows are skipped; no decisive rows raises no
  blocker. Per-`input_hash` grouping rejected (each commit changes the hash;
  old-basis failures would never clear). Failure persistence policy fixed to
  `ON CONFLICT DO NOTHING` (no timestamp touch — duplicate failures can never
  resurrect the blocker) under the existing `(fund, key, input)` partial unique
  for null-hash rows. No schema/migration change. Verified by ordering tests:
  failure → later-success unblocks; success→failure→success unblocks;
  failure→success→duplicate-failure stays unblocked; success→unavailable stays
  unblocked; failure→unavailable stays blocked; latest `available`+`mismatch`
  blocks.
- **Bounded idempotency key (latent bug fix)**:
  `currentForecastReferenceIdempotencyKey` output ≥137 chars exceeds
  `varchar(128)` (`shared/schema/current-forecast-references.ts:58`); switch to
  `cfref:{fundId}:{sha256(inputHash + ':' + resultHash)}` — deterministic, ~82
  chars, zero production callers today, no column widening or data migration.
  Real-Postgres candidate-insert test required.
- **Trigger data flow**: pinned-receipt lookup only (full basis + expected
  hashes + engine/methodology versions); never a bare row ID or "latest" read.
  Checkpoint path reuses its `runCurrentForecastV2WithReceipt` receipt;
  financial-facts path get-or-creates a baseline receipt keyed by exact basis,
  serialized by a transaction-scoped `pg_advisory_xact_lock` on the basis-tuple
  hash (pre-lock duplicates resolve to lowest snapshot id), then replays
  exactly.
- **Trigger lifecycle (single semantics)**: bounded await with timeout before
  response return — no `waitUntil()`, no outbox/queue, no fire-and-forget.
  Timeout persists a recorded failure; late settlement of the underlying promise
  is conflict-tolerant and superseded by later observations, so no cooperative
  cancellation is required. The lifecycle test asserts the trigger settles
  (success, recorded failure, or recorded timeout) before the response returns.
- **Resume state-transition contract**: `held` serves the pinned head already;
  resume re-arms live V2 serving from every held cause (`kill_switch`,
  `configured_off`, `configured_shadow` — the `CurrentForecastHeldReason`
  union): set `configured_mode='on'` AND `kill_switch_active=false` in one
  idempotent write, preserve activation/pointer fields, reject pre-cutover with
  409 — it never "restores the pinned reference" (that is what `held` does) and
  never repeats activation.
- **Route-policy surface**: the new admin resume route requires an
  `api-route-policy-registry.ts` entry and `COMMON_API_ROUTE_POLICY_IDS`
  mapping; `npm run policy:verify` added to item 3 verification.
- **Manifest end-state (#1325)**: allowlist shrinks to the single delegating
  seam module, not to empty — the guard errors on any non-allowlisted import of
  `metrics-aggregator.ts`, and the seam must import it by design.
- **Router-index regen**: Use `git add -N` (intent-to-add), not `git add`,
  before `npm run docs:routing:generate`, so the file is visible to the
  tracked-files scan without breaking TRIP delta review over unstaged `git diff`
  (alternatively review both cached and unstaged diffs).
- **Downstream dependency**: The Phase 2 plan
  (`F_1.2.0_deployment-soak-activation.plan.md`, #1298/#1299) hard-gates on this
  release being deployed: `off → shadow` transition available, NEW-A organic
