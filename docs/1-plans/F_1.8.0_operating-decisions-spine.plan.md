# Operating Decisions Spine Implementation Plan (F_1.8.0)

**Status:** PROPOSED
**Baseline:** `origin/main @ aa355aaf75a2f9f1be99783f9633dba6575d97f9`
**Production dispatch:** HOLD — no release, schema apply, or provider action is
authorized by this plan. Merge and any subsequent production step require
separate approval under the governing policy.
**Issue:** #1289 (Wave H, PLAN_61 Task 21 schema slice, re-scoped by the
grilling pass). **Governing ADR:** ADR-067 (lifecycle semantics are already
decided there; this plan conforms to it and does not re-open it).

**Document role:** Proposed plan for the schema + service-layer + tests slice
only. Routes for decisions (#1290) and the operations page (#1293) are separate
follow-on plans.

## Overview

Three additive changes to the operating-objects foundation
(`shared/schema/operating-objects.ts`), one migration, and the thin service
layer over them:

1. **`operating_decisions` table** — the Wave H decision spine with the
   ADR-067 lifecycle: `proposed -> accepted | rejected | deferred`, terminal
   immutability, a supersession chain, recommendation kept separate from a
   recorded outcome (outcome immutable once recorded), and CHECK-enforced
   follow-up owner/date on deferred rows. This table is distinct from
   `allocation_scenario_ic_decisions` (`shared/schema/allocation-scenarios.ts`)
   — see the explicit note in `docs/ARCHI.md` section 4's active-work-area map.
2. **`decision_evidence_links` table** — decision-sourced evidence links only,
   per the accepted ruling in #1289 (ADR-cand-3): exactly one source FK
   (`decision_id`), exactly one target among the existing Task 21 union
   (`analysis_reference` | `internal_economics_run`), same-fund composite FKs,
   immutable rows. It does not duplicate `task_evidence_links` semantics: tasks
   keep linking through the PR4 store, and this table has no `task_id` column
   at all, making task-sourced rows unrepresentable.
3. **Task create-idempotency** — `idempotency_key` + `request_hash` on `tasks`
   via the shared primitive (`server/lib/idempotent-command.ts`), create path
   only. The existing `xmin`-based If-Match optimistic update path in
   `server/services/operating-objects/task-service.ts` is unchanged.

One PR. No new routes are mounted; no manifest, impl-map, group-slice, or
route-policy entries are added. The single permitted route-file touch is the
existing `POST /api/funds/:fundId/tasks` handler in
`server/routes/operating-object-tasks.ts` (an already-mounted module), which
must start parsing the `Idempotency-Key` header to feed the new create path —
without that pass-through the service change would be dead code. One
non-route lib touch accompanies it: a task-create entry in the
database-backed idempotency classifier
(`server/lib/database-backed-idempotency-routes.ts`) so the Railway/Docker
surface's generic in-memory idempotency middleware stands down for this path
(see the tasks create-idempotency section).

## Problem Statement

- Decisions have no operating-object home. The only decision table today is
  `allocation_scenario_ic_decisions`, which is scenario-IC-specific. The Wave H
  context rail (#1293) and decision routes (#1290) need a fund-scoped decision
  spine with the operating standard from ADR-067 (recommendation, approval,
  outcome, follow-up).
- Evidence links exist only task-sourced. `task_evidence_links`
  (`shared/schema/operating-objects.ts:83-152`) owns task-to-evidence links
  immutably and idempotently; there is no way to attach the same evidence kinds
  to a decision, and #1289's accepted ruling forbids widening that table into a
  dual-source store.
- `tasks` (`shared/schema/operating-objects.ts:41-66`) has no
  `idempotency_key`/`request_hash` (verified absent at baseline), so
  `createTask` (`task-service.ts:45`) is a bare insert — a retried POST creates
  a duplicate task. This violates the repo non-negotiable that all mutations
  must be idempotent.

## Solution Architecture

### `operating_decisions` (new table, ADR-067-conforming)

Columns:

- `id serial` PK; `fund_id integer NOT NULL` FK `funds.id` ON DELETE CASCADE.
- `title varchar(200) NOT NULL` with a `btrim` non-empty CHECK (mirrors
  `tasks_title_nonempty_check`).
- `recommendation text NOT NULL` — the proposed course of action. Never
  overwritten by the outcome.
- `status varchar(16) NOT NULL DEFAULT 'proposed'`, CHECK
  `IN ('proposed','accepted','rejected','deferred')`. There is no
  `superseded` status value; supersession is expressed only by the chain
  pointer on the newer row (ADR-067: deferred rows "transition to accepted,
  rejected, or be superseded" — the last via a new row).
- `supersedes_decision_id integer NULL` — same-fund composite FK
  `(supersedes_decision_id, fund_id) -> operating_decisions(id, fund_id)`
  ON DELETE RESTRICT, plus a partial unique index on
  `(fund_id, supersedes_decision_id) WHERE supersedes_decision_id IS NOT NULL`
  so a decision can be superseded at most once (a linear chain, not a tree).
- Outcome, distinct from recommendation: `outcome text NULL`,
  `outcome_recorded_at timestamptz NULL`, `outcome_recorded_by integer NULL`
  FK `users.id`. All-or-none coupling CHECK across the three columns. A second
  CHECK restricts non-NULL outcome to terminal rows
  (`status IN ('accepted','rejected')`). Schema permits NULL outcome on
  accepted rows; per ADR-067 the #1290 service surfaces accepted-without-
  outcome as an explicit outcome-missing state.
- Follow-up: `follow_up_owner_id integer NULL` FK `users.id` (default NO
  ACTION, not SET NULL — SET NULL on user delete would violate the deferred
  CHECK below), `follow_up_date date NULL`. CHECK:
  `status <> 'deferred' OR (follow_up_owner_id IS NOT NULL AND follow_up_date IS NOT NULL)`.
- Create idempotency: `idempotency_key varchar(128) NOT NULL`,
  `request_hash varchar(64) NOT NULL`, unique `(fund_id, idempotency_key)`.
  New table, so the columns are NOT NULL from day one.
- `created_by integer` FK `users.id`; `created_at`/`updated_at timestamptz`
  defaultNow.
- `unique (id, fund_id)` composite — the FK target for both the supersession
  chain and `decision_evidence_links`. This must be a `unique()` constraint,
  not `uniqueIndex()` (drizzle FK-on-uniqueIndex aborts 42830 but exits 0 —
  known repo gotcha, `docs/ARCHI.md` section 9).

Lifecycle enforcement is a `BEFORE UPDATE` trigger
(`operating_decisions_enforce_lifecycle`), the "immutability trigger or
equivalent" the issue requires. Permitted updates, everything else raises:

1. `proposed -> accepted | rejected | deferred` (deferred requires the
   follow-up columns, already CHECK-enforced).
2. `deferred -> accepted | rejected`; while still `deferred`, follow-up
   owner/date may be edited.
3. One-shot outcome recording on a terminal row: `OLD.status` in
   accepted/rejected, `OLD.outcome IS NULL`, the three outcome columns move
   NULL -> NOT NULL together, and every other column except `updated_at` is
   unchanged.
4. Nothing else. In particular: a terminal row with a recorded outcome accepts
   no update at all (changes require a superseding row); `recommendation`,
   `title`, `fund_id`, `supersedes_decision_id`, and `idempotency_key`/
   `request_hash` are frozen after insert; status can never leave
   accepted/rejected.

No DELETE trigger: row deletion is reachable only through the `funds` cascade,
and the service layer exposes no delete. (A BEFORE DELETE trigger would also
block the fund cascade.)

### `decision_evidence_links` (new table, decision-sourced only)

Structural mirror of `task_evidence_links` with `decision_id` as the sole
source FK:

- `id serial` PK; `fund_id integer NOT NULL` FK `funds.id` CASCADE.
- `decision_id integer NOT NULL` — composite FK `(decision_id, fund_id) ->
  operating_decisions(id, fund_id)` ON DELETE CASCADE.
- `target_kind varchar` CHECK
  `IN ('analysis_reference','internal_economics_run')` with
  `analysis_reference_id` / `economics_run_id` columns and the same
  exactly-one-target coupling CHECK as `task_evidence_links` (zero, two,
  mismatched targets unrepresentable).
- Same-fund composite FKs on both targets:
  `(analysis_reference_id, fund_id) -> internal_analysis_references(id, fund_id)`
  and `(economics_run_id, fund_id) -> internal_lp_economics_runs(id, fund_id)`,
  both ON DELETE RESTRICT. Cross-fund evidence is unrepresentable at the
  schema level; the `assertOwnedByFund` service-layer pattern arrives in the
  #1290 slice per the issue.
- `idempotency_key varchar(128) NOT NULL`, `request_hash varchar(64) NOT NULL`,
  unique `(fund_id, decision_id, idempotency_key)`.
- Immutability: reuse the existing `internal_economics_forbid_update` trigger
  function (precedent: `migrations/0047_internal_economics_linkage.sql:463`)
  with a new `decision_evidence_links_forbid_update_trigger`.
- Index `(fund_id, decision_id, id)` for list reads.
- **No `task_id` column.** Task-sourced rows are structurally impossible;
  future task-target kinds extend the `task_evidence_links` union, not this
  table (accepted ruling ADR-cand-3).

### `tasks` create-idempotency (additive columns, existing rows preserved)

- `ALTER TABLE tasks ADD COLUMN idempotency_key varchar(128)` and
  `request_hash varchar(64)`, both NULLABLE — existing rows predate the
  columns; only new creates populate them.
- Partial unique index `(fund_id, idempotency_key) WHERE idempotency_key IS
  NOT NULL`.
- `createTask` (`task-service.ts`) wraps the insert in `runIdempotentCommand`
  (`server/lib/idempotent-command.ts`), following the load-existing /
  conflict-tolerant-insert / reload shape already proven in
  `task-evidence-link-service.ts:126-240`: same key + same request hash
  replays the stored row; same key + different hash raises
  `IdempotentCommandError` (key-conflict, 409-shaped). Implementation note:
  drizzle `onConflictDoNothing` against a partial index needs the
  `targetWhere` clause for index inference — verify the emitted SQL in the
  testcontainers suite, and fall back to catching 23505 if inference fails.
- The `xmin`-pinned optimistic update path (`task-service.ts:102-133`,
  If-Match etag) is byte-untouched. Update idempotency remains the existing
  xmin compare-and-swap; only create gains the key.
- Route pass-through: the existing `POST /api/funds/:fundId/tasks` handler in
  `server/routes/operating-object-tasks.ts:85` adopts the same
  `Idempotency-Key` header parse already used by the evidence-link handler in
  the same file (`parseInternalEconomicsIdempotencyKey`, 428 on missing, 400
  on invalid). No mount-chain or policy-registry changes.
- Typed error mapping in the create handler: the current catch
  (`operating-object-tasks.ts:90`) is a bare `catch {}` that converts every
  throw to 500, so a service-raised `IdempotentCommandError` (409 key-reuse)
  would surface as 500. The handler must adopt the same typed mapping the
  evidence-link handler in this file already uses
  (`operating-object-tasks.ts:200-202`): `IdempotentCommandError ->
  error.status`/`error.code`; replay returns 200 with the stored row's
  representation, first create returns 201 (evidence-link precedent). Header
  pass-through alone is insufficient.
- Middleware classifier entry (dual-surface parity): the Railway/Docker
  surface (`server/server.ts:276`) applies the generic in-memory
  `withIdempotency()` middleware to POST paths containing `/funds` unless the
  path is excluded via `isDatabaseBackedIdempotencyRoute`
  (`server/lib/database-backed-idempotency-routes.ts`). The classifier covers
  the evidence-link path but not the bare task-create path, so without a new
  entry the two surfaces diverge: on Railway the middleware blindly replays
  the first cached response for a reused key regardless of payload (and
  returns 409 `request_in_progress` / 500 `cached_error` in its other
  states), while makeApp (which never mounts this middleware) gets the
  service-layer hash-compared behavior. Add a
  `TASK_CREATION_PATH` (`/api/funds/:fundId/tasks`) POST entry to the
  classifier so task create stores its own key + request hash on the row and
  bypasses the middleware, mirroring the KPI-observation precedent noted in
  that file. Intended uniform outcome on BOTH surfaces: same key + same hash
  replays the stored row (200); same key + different hash returns 409
  `IDEMPOTENCY_KEY_REUSE`; the in-memory middleware never answers for this
  path. Tests: extend
  `tests/unit/middleware/database-backed-idempotency-routes.test.ts` for the
  new classifier entry, and add route-level coverage asserting the 201 /
  200-replay / 409-conflict statuses on the common-route surface.

### Service layer (new files, no routes)

`server/services/operating-objects/`:

- `decision-service.ts` — `createDecision` (idempotent via
  `runIdempotentCommand`), `transitionDecision` (xmin-pinned compare-and-swap
  mirroring `updateTask`; the trigger is the backstop, the service gives the
  412-shaped error), `recordOutcome` (xmin-pinned, one-shot),
  `supersedeDecision` (creates the superseding row idempotently, pointing
  `supersedes_decision_id` at the prior row; rejects a `proposed` source row
  with a 409-shaped service error — see resolved question 2), `loadDecision`,
  `listDecisionsForFund`. Column map + `xmin::text` selection mirrors
  `task-service.ts:21-33`.
- `decision-evidence-link-service.ts` — `createDecisionEvidenceLink` +
  `listDecisionEvidenceLinks`, a structural mirror of
  `task-evidence-link-service.ts` (ports shape, `runIdempotentCommand`,
  `onConflictDoNothing` on the unique triple, typed service errors).

Contracts: `shared/contracts/operating-objects/decision.contract.ts` mirroring
`task.contract.ts` (Zod create/transition/outcome shapes; Drizzle
`$inferSelect`/`$inferInsert` remain the row types — never hand-declare column
types in consumers, per the module header convention).

Request-hash preimages (normative). `runIdempotentCommand`
(`server/lib/idempotent-command.ts:28`) requires authoritative `fundId` and
`contractVersion` inside the hashed request and rejects mismatches with 400
`IDEMPOTENCY_REQUEST_MISMATCH`; the hash is `canonicalSha256` over the
preimage. Follow the `TaskEvidenceCommandPreimage` precedent
(`task-evidence-link-service.ts`: `{ commandKind, contractVersion, fundId,
taskId, target }`). Each command's preimage is exactly:

- Task create: `{ commandKind: 'create_task', contractVersion:
  TASK_CONTRACT_VERSION, fundId }` plus the validated `TaskCreateSchema`
  fields (`title`, `ownerId`, `dueDate`, `description`). `status` is NOT in
  the preimage: `TaskCreateSchema` excludes it (server-controlled, always
  `'open'` — `task.contract.ts:19`), so it carries no discriminating
  information for the hash.
  `TASK_CONTRACT_VERSION` is a new versioned const in `task.contract.ts`
  (shape precedent: `TASK_EVIDENCE_LINK_CONTRACT_VERSION =
  'task-evidence-link/1.0.0'`).
- Decision create: `{ commandKind: 'create_decision', contractVersion:
  DECISION_CONTRACT_VERSION, fundId }` plus the validated decision-create
  fields (`title`, `recommendation`, and the optional follow-up fields when
  supplied).
- Decision supersede: `{ commandKind: 'supersede_decision', contractVersion:
  DECISION_CONTRACT_VERSION, fundId, supersedesDecisionId }` plus the new
  row's validated create fields.
- Decision evidence-link create: `{ commandKind:
  'create_decision_evidence_link', contractVersion:
  DECISION_EVIDENCE_LINK_CONTRACT_VERSION, fundId, decisionId, target }` —
  the structural mirror of the task-evidence preimage.

Actor-inclusion policy: the actor is EXCLUDED from every preimage. It is
stored on the row as `created_by` but never hashed, matching the
task-evidence precedent — a retried create replayed by a different resolved
identity is still the same command. `DECISION_CONTRACT_VERSION` and
`DECISION_EVIDENCE_LINK_CONTRACT_VERSION` live in `decision.contract.ts`.

Schema export: `shared/schema/operating-objects.ts` is already re-exported by
`shared/schema.ts:42` (`export * from './schema/operating-objects'`), so the
new tables flow through the barrel with no wiring.

### Migration (one file, additive, replay-safe)

Journal tail verified at plan-authoring time: 55 entries, tail idx 54, tag
`0053_g3_release_gate_hardening`. **Provisional prefix: `0054`.** The
implementer MUST re-read `migrations/meta/_journal.json` at mint time and take
the real next index — never trust this plan's claimed tail (ARCHI section 4 has
caught exactly this drift twice). Any migration pin or guard test asserts its
own journal entry by tag, never `entries.at(-1)`.

Content, all guarded for replay (`IF NOT EXISTS` / `DROP TRIGGER IF EXISTS`
then `CREATE` / `CREATE OR REPLACE FUNCTION`), preceded by an
absent-or-exact preflight:

1. Preflight `DO` block(s), the 0047 pattern
   (`migrations/0047_internal_economics_linkage.sql:109`): `IF NOT EXISTS`
   guards silently pass when a same-named object already exists with the
   WRONG shape, so before any DDL the migration must verify each guarded
   object is either absent or exactly the expected catalog shape — column
   set/types/nullability AND column defaults/serial-sequence ownership (the
   0047 `required_column` tuple includes `default_kind`, e.g. `'serial'` for
   identity columns — `0047:126`; apply the same to `operating_decisions.id`,
   status/timestamp defaults, and the nullable `tasks` columns) for both new
   tables and the two `tasks` columns, constraint definitions (via
   `pg_get_constraintdef`), and the partial unique index predicates — and
   `RAISE EXCEPTION` on any partial or drifted state rather than record a
   journal entry over it.
2. `CREATE TABLE operating_decisions` with all constraints above.
3. `CREATE OR REPLACE FUNCTION operating_decisions_enforce_lifecycle()` +
   trigger.
4. `CREATE TABLE decision_evidence_links` + forbid-update trigger reusing
   `internal_economics_forbid_update`.
5. `ALTER TABLE tasks ADD COLUMN IF NOT EXISTS ...` x2 + partial unique index
   `IF NOT EXISTS`.
6. Journal entry appended.

Replay testing covers both directions: apply-twice against a scratch
container converges (idempotent replay), AND partial-drift refusal — seed a
same-named object with a deliberately wrong shape (e.g. a
`operating_decisions` table missing a CHECK, or a `tasks.idempotency_key` of
the wrong type) and assert the preflight raises instead of silently
accepting the drifted catalog.

Journaled migrations are additive-only; never `db:push` against prod; nothing
in this plan applies the migration to any production database (dispatch HOLD).

## Test Impact (real PostgreSQL, testcontainers)

New file `tests/integration/operating-decisions/operating-decisions-schema.pg.test.ts`
(pattern: `tests/integration/internal-economics/economics-linkage-schema.pg.test.ts`),
registered in `tests/config/testcontainers-test-paths.mjs` — new testcontainers
tests do NOT auto-run unless registered there, and new integration tests do not
run on their own PR's default lanes, so the local
`npm run test:testcontainers` run is the gate of record. Coverage required:

1. **Lifecycle** — every legal transition succeeds; illegal transitions
   (accepted -> anything, proposed -> proposed edits of frozen columns,
   rejected -> deferred) raise from the trigger; invalid status values fail
   the CHECK; deferred without follow-up owner/date fails the CHECK; follow-up
   edits allowed only while deferred.
2. **Immutability** — terminal row field edits rejected; outcome recorded once
   succeeds; any second outcome write rejected; outcome on a proposed row
   rejected; `decision_evidence_links` UPDATE rejected by the forbid-update
   trigger.
3. **Supersession / same-fund** — cross-fund `supersedes_decision_id`
   rejected by the composite FK; second superseder of the same decision
   rejected by the partial unique; explicit rejection test: `supersedeDecision`
   against a `proposed` source row raises the 409-shaped service error
   (resolved question 2); cross-fund analysis-reference and
   economics-run targets rejected; exactly-one-target CHECK (zero, two,
   mismatched kind/column pairs all rejected).
4. **Replay and key-conflict** — same key + same hash returns the original row
   (decision create, link create, task create); same key + different hash
   raises the key-conflict error; replay after a poisoned first attempt
   (insert raced) still converges to one row.
4b. **Migration drift refusal** — apply-twice converges; a seeded same-named
   object with a wrong shape makes the preflight raise (see Migration
   section).
5. **Concurrency** — two parallel creates with the same key yield exactly one
   row (both callers get the same row back); two parallel xmin-pinned
   transitions from the same snapshot: one wins, one gets the stale-token
   failure.
6. **Guard test (issue AC)** — asserts `decision_evidence_links` has no
   `task_id` column (task-sourced rows unrepresentable) and that
   `task_evidence_links` semantics are untouched (its constraint set is
   unchanged against the 0047 manifest expectations).
7. **Tasks regression** — existing task create/list/update unit tests still
   pass; pre-existing rows with NULL `idempotency_key` are readable and
   updatable.

## Resolved Questions (decided by this plan + ADR-067; do not re-open)

1. **Outcome on rejected rows — RESOLVED: both terminal states.** The
   architecture section already selects the terminal CHECK
   `status IN ('accepted','rejected')`. ADR-067 (DECISIONS.md, "Operating
   Decisions Lifecycle") treats outcome as a property of a decided row —
   "text plus recorded-at and actor, immutable once recorded" — and nowhere
   restricts it to accepted; its accepted-without-outcome language addresses
   the missing-outcome UX, not a rejected-row prohibition. The CHECK stays as
   specified; no narrowing.
2. **Supersession source states — RESOLVED: service-layer check, schema
   permissive.** The plan's proposed default is adopted as the decision.
   ADR-067 names the supersession candidates: "Accepted and rejected remain
   immutable (changes create a superseding row). Deferred is re-openable to
   accepted, rejected, or superseded" — proposed rows are never supersession
   sources (they transition in place). `supersedeDecision` rejects a
   `proposed` source row with a 409-shaped service error; the chain FK keeps
   no status predicate. An explicit rejection test is mandated in Test Impact
   item 3.
