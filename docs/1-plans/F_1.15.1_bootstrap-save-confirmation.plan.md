## Overview

The Fund Basics bootstrap save shows a false "Save not confirmed" alert while a
live `save_draft` is still in flight, and a genuinely lost response leaves the
mounted shell without the recovery alert it needs. This plan finishes the
existing local candidate on refreshed main: keep its module-local live-transport
registry that suppresses the false alert, and add the one missing store
transition in the two direct callers so that a real unknown outcome reaches the
global `draftSyncStatus` in the same mounted UI. Seven source and test files, no
new module, no wire, schema, or public-API change.

## Problem Statement

Two reproduced same-mount gaps (test-spec, 2026-09-24):

1. **False uncertainty during a live save.** The recovery effect in
   `client/src/hooks/useFundDraftSync.ts` (around line 311) treats any pending
   `save_draft` as a command recovered from a reload and reports `uncertain`.
   The bootstrap path in `client/src/pages/FundBasicsStep.tsx` starts that
   command in the same session, so the user sees "Save not confirmed" for a save
   that then succeeds. The candidate already fixes this with an in-memory
   registry of live saves consulted by the effect.
2. **Real uncertainty never reaches the shell.** With the registry in place, the
   effect stays quiet while the transport runs. When the transport then rejects
   with `FundWorkflowUncertainError`, the registry entry is removed in
   `finally`, but registry cleanup is not store state and the effect does not
   rerun. The two direct callers' `uncertain` arms (`FundBasicsStep.tsx` around
   line 252, `client/src/components/workspace/FundWorkspace.tsx` around
   line 389) only write component-local error text. Global `draftSyncStatus`
   stays `idle` or `saving`, so the shell's `draft-uncertain` alert and its
   "Check save status" action never render, and the workspace dialog reports an
   unknown outcome while the store still says `saving`.

The autosave path in the hook already performs the missing transition
(`setStatus('uncertain')` in its outcome switch), which is why only the two
direct callers are wrong. The hook's `status` is the store's `draftSyncStatus`
(selected at hook line 58), so a caller's store write is what the FundSetup
shell renders.

## Solution Architecture

Option A from the consensus PRD. Caller-owned status is the settled contract of
F_1.15.0: `saveDraftAndSettle` owns transport, journal settlement, and the
session/fund/command-key supersession fence; callers own status,
`draftServerReady`, dialog text, and navigation. The repair therefore stays in
the callers:

- Keep the candidate's registry in
  `client/src/services/fund-draft-settlement.ts` (`isDraftSaveInFlight`, exact
  identity match on session, key, operation, target fund, body signature, and
  expected ETag; entry added before transport, removed in `finally`) and the
  guarded effect in the hook, unchanged.
- In both direct callers' `uncertain` outcome arms, write the store's
  `uncertain` status synchronously, before the existing local error update,
  inside the same synchronous outcome callback. No status write for
  `superseded`, no `pendingCommand` clearing, no key/body/ETag replacement, no
  fetch over an unresolved write, and the callback never moves across an
  `await`.

Rejected alternatives, recorded so TRIP-2 does not reopen them: moving the
status write into the helper (Option B) widens settlement into presentation and
changes the closed outcome contract for every caller; making the registry
observable and rerunning the effect on transport end (Option C) adds a
subscription lifecycle and must undo the verified-ref early return. Revisit
centralization only on another demonstrated mismatch.

### 2. Direct caller status transitions

**File**: `client/src/pages/FundBasicsStep.tsx`

**Current state**: the `uncertain` arm (around line 252) sets `bootstrapError`
to `UNCERTAIN_SAVE_MESSAGE` and returns the stage to `idle`. The `saved` arm
already writes `synced` to the store before navigating.

**Modifications**:

- In the `uncertain` arm, write the store's `uncertain` status, then return the
  stage to `idle`. Drop the local `bootstrapError` write and the step-local
  `UNCERTAIN_SAVE_MESSAGE` constant. `FundBasicsStep` renders only inside
  `FundSetup` (via `STEP_COMPONENTS` in `client/src/pages/fund-setup.tsx`), and
  the shell's `draft-uncertain` alert owns uncertainty text: it appears on
  `uncertain` and disappears on every later status, including `stale`,
  `rejected`, or `error` after a replay. A step-local copy would go stale on
  exactly those terminal replays, so it is removed rather than cleared by an
  effect. Keep the exhaustive `switch` and every other arm unchanged.
- The existing test "keeps the pending key when a draft save is uncertain"
  asserts the local alert text; change it to assert `draftSyncStatus` is
  `uncertain` and the pending key is retained (no shell in that render, so no
  alert is expected there).
- Double-dispatch guard: after an uncertain outcome, Next is enabled again (its
  only guard is the local `bootstrapStage`) and the shell's "Check save status"
  is available (its only guard is the hook-local `saveInFlightRef`).
  `prepareFundCommand` reuses the pending key, body, and ETag, so both can
  dispatch the same command concurrently. The shared guard is the candidate's
  registry: the Next handler returns early when `isDraftSaveInFlight` reports
  the pending command live, and the hook's `persistCurrentDraft` does the same
  (setting its queued flag, as it already does for its own in-flight ref).
  Consume the existing pending debounce timer before either in-flight guard
  returns, so a fired timer cannot trigger another PUT on the next step change.
  No new state; one import in each caller.
- Next never replays from `uncertain`: disable the Next button while the store's
  `draftSyncStatus` is `uncertain` (read through the existing
  `useFundSelector`). The shell's "Check save status" is then the only
  dispatcher out of uncertainty, so the hook's outcome arms (which already write
  `stale`, `error`, `synced`, and `uncertain` to the store) own every terminal
  replay outcome. The Fund Basics `stale`, `rejected`, and `retry_same_key` arms
  stay as they are because they can no longer run against an `uncertain` store
  status. Once the replay is acknowledged and status is `synced`, Next is
  enabled and navigates without a new save (see Edge cases).

## Technical Considerations

- **Pattern usage**: follows the F_1.15.0 settlement contract in `docs/ARCHI.md`
  section 5 (helper owns transport and fences, callers own status). The registry
  is a module-local `Set`, not store state, by design: a reload clears it, which
  is exactly the signal that distinguishes a recovered command from a live one.
- **Ordering**: the status write must be synchronous and precede the local error
  write so a test observing the store immediately after the callback sees
  `uncertain` with no intermediate render.
- **Supersession**: when session, fund, or command key changed, the helper
  delivers a `superseded` outcome through the callback; that arm performs no
  status write, so the new transition cannot touch a replacement session.
  Existing ordering regressions assert replacement state unchanged.
- **Preact production bundle**: no new React-specific API; `Set` iteration and a
  store setter only.
- **Edge cases**:
  - After a successful "Check save status" replay from the mounted shell, the
    hook's `saved` arm sets `draftServerReady` and `synced` and does not
    navigate. The expected user path is to press Next again; Fund Basics then
    skips the bootstrap save because `draftServerReady` is true and falls
    through to the plain navigate at the end of its handler (verified around
    line 273). This is intended and must not be "fixed" in TRIP-2.
  - Same-actor rehydration (role change) replaces `pendingCommand` with an
    equal-identity envelope; the registry matches on identity fields, not object
    reference, so the live save stays owned.
  - A real reload empties the registry; a persisted pending `save_draft` is then
    reported `uncertain` and replayable, as today.
