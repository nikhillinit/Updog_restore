# Journaled Schema Apply Route 0050-0061 Implementation Plan

**Governing policy:**
`docs/governance/solo-internal-change-and-production-policy.md` (resolve from
`origin/main`). This plan grants no merge, production, schema, or release
authority. Merge, workflow dispatch, schema apply, rehearsal, and release
dispatch remain separate owner actions.

Reviewed checkout: `origin/main` at `68a53cb49` on 2026-09-26. Revised on
2026-09-27 after a code-grounded red team (see "Red team revisions"). The
repository is public: this plan cites only pushed SHAs and public run IDs, and

## Overview

Production has no usable route to the schema that `main` requires. This plan
adds one bounded apply mode, `apply-journaled-0050-0061`, to
`.github/workflows/prod-schema-reconcile.yml`. The mode validates the exact
production migration ledger, then applies every unapplied journaled migration
from the validated tail through `0061_durable_create_receipts` in journal order,
inside one transaction. It follows the ADR-098 pattern that admitted
`apply-current-forecast-0050-0055`. A matching rehearsal mode runs the same
runner against an isolated Neon branch. The release audit contract does not
change: a release still requires every manifest to report `SKIP`.

The route is valid only while the repository ends at journal index 62 and
manifest 38. The runner refuses before connecting when anything newer exists,
and the owner sequence freezes migration and manifest merges from merge to
release.

## Owner Decisions (2026-09-26, settled)

1. **Linear range.** One mode applies 0050-0061 in order, including the 0056 and
   0057 DDL. The ledger stays linear. The existing modes stay untouched.
2. **ADR-098 recovery posture.** The mode has real apply capability, guarded by
   exact source, first attempt, retention, pinned identities, exact ledger and
   catalog checks, advisory lock, and timeouts. The owner creates a Neon restore
   branch before dispatch as a runbook step. The workflow does not verify that
   branch.
3. **Production ledger read.** Approved and completed (Problem Statement 1).

Decision 1 admits 0056 and 0057 DDL without the actuals recovery program
described in `docs/workflows/PRODUCTION_SCRIPTS.md`. This is a recorded tension
with that document's 72-hour isolated-restore requirement. The owner's choice is
preserved. It is bounded as follows: the admission covers DDL only, both
migrations create empty tables plus parent constraints, `ACTUALS_PILOT_FUND_ID`
stays unset, and `ACTUALS_PILOT_PUBLISH_ENABLED` stays false. Actuals data
actions keep every existing prerequisite. A new ADR and a policy amendment
record the decision (Implementation Details 7). The pilot bound is enforced by
configuration and an owner readback only; no code or workflow gate enforces it
(Technical Considerations, "Pilot configuration").

## Solution Architecture

One new runner, modeled on
`scripts/run-current-forecast-journaled-migrations.mjs`:

1. **Tail guard, before any database connection.** The journal must hold exactly
   63 entries (idx 0-62), and the manifest directory must hold exactly 38
   manifests with orders 1-38. Anything newer refuses. A later migration
   therefore stops the route before mutation, never after commit.
2. **Source identity, before any database connection.** The SQL of journal idx
   51-62 and manifests 27-38 must equal full 64-character pinned hashes
   (Implementation Details 1). Any drift refuses.
3. **Target identity.** Connect through a direct (non-pooler) URL, read the
   database identity, and compute the target fingerprint with the one shared
   serializer (Implementation Details 1). In apply mode it must equal
   `EXPECTED_TARGET_FINGERPRINT`. A missing or different value refuses with a
   constant message, before the lock and before any mutation. Unlike the actuals
   runners, the fingerprint check runs before the lock; only `connect()` and one
   side-effect-free identity `SELECT` run first.
4. **Lock and timeouts.** Take the shared advisory lock and set `lock_timeout` 5
   s and `statement_timeout` 5 min. When `server_version_num` is 170000 or
   higher, also set `transaction_timeout` 10 min, which bounds the whole
   migration transaction.
5. **Classify the ledger.** The expected chain is the baseline (canonical or
   ADR-074 reconciled) followed by the twelve target entries. The ledger must be
   an exact prefix of that chain and must contain the whole baseline. Unknown
   rows, gaps, reorders, duplicates, NULL or later timestamps, and hash
   mismatches refuse.
6. **Validate the catalog** against the ledger state (Technical Considerations,
   "Catalog rule per target").
7. In read-only mode, or when the ledger is complete, return without mutation.
   Read-only mode prints the fixed readback line with the classified state and
   applied count (Implementation Details 1).
8. **Apply.** Build a temporary migrations folder that holds exactly the twelve
   pinned entries and SQL files, and call the Drizzle migrator once. Drizzle
   applies the entries newer than the ledger tail and their ledger rows inside
   one transaction on the lock-holding client, so the apply is all-or-nothing.
   Immediately after `migrate()` returns, print the fixed line
   `journaled-0050-0061: migration transaction committed`. The line is
   diagnostic only: a connection lost while awaiting `COMMIT` can leave the
   transaction committed with no line printed, so the owner branches on the
   workflow's ledger readback (Implementation Details 5), never on this line.
9. **Validate after commit.** Re-read the ledger: it must be complete, and every
   earlier row must be unchanged. Re-audit: manifests 1-38 must all report
   `SKIP` with no deltas.
10. **Emit a result** (pre-state, post-state, applied flag, range, and the two
    backfill counts) for the receipt.

The workflow adds the mode, skips the generic pre-apply decision gate for it
(the runner's tail guard and catalog rules replace it; Technical Considerations,
"Skipped generic gate"), and keeps the generic post-apply audit, which passes
because the schema is complete through manifest 38. Audit mode accepts the new
receipt as historical schema proof, so one apply run proves the whole chain for
a release.

## Technical Considerations

- **Pattern usage**: ADR-098 range runner, ARCHI.md section 4 migration-tail
  rules, section 9 "New DB/schema change".
- **Catalog rule per target**: target k of the twelve (0050 is 1) is ledgered
  when the classifier's applied count is at least k; each reused validator
  receives that state in its own input shape (Implementation Details 1). A
  ledgered migration requires its manifest clean (`SKIP`, zero deltas). An
  unledgered migration requires an exact allowed pre-state:
  - Manifests 1-26: the extracted ADR-074 baseline check, for both baseline
    kinds.
  - Manifests 27-32: the existing Current Forecast assertion, which already
    accepts production's manifest-applied 0050-0053 objects.
  - Manifests 33 and 34: the existing actuals assertions (exact pristine
    absence).
  - Manifests 35-38: exact equality with a pinned full-absence delta set per
    manifest, keyed `${kind}:${name}`, measured at TRIP-2 on disposable
    databases for both baseline kinds. This is an equality check, not the subset
    check that `ALLOWED_NON_SENTINEL_DELTAS` performs
    (`current-forecast-journaled-migration-range.mjs:401-410`): a strict subset
    of the full-absence set means partial residue and refuses. For manifest 35
    the only admitted delta is `missing-constraint` for
    `fund_scenario_variants_override_type_check`. No journaled migration before
    0058 creates that CHECK, so both baseline kinds and production produce
    `missing-constraint`; `constraint-definition-mismatch` is not admitted.
  - Any other delta refuses as partial DDL.
- **Skipped generic gate**: the mode skips
  `Require additive-safe apply decision` (`prod-schema-reconcile.yml:713-786`)
  because manifests 33 and 34 must report `REFUSE-FOR-HUMAN` before their DDL
  exists. The runner is not a line-for-line equivalent. What replaces each gate
  duty:
  - one decision per manifest across the whole directory: the tail guard;
  - no `REFUSE-FOR-HUMAN`: the per-target catalog rules (33 and 34 require it,
    27-32 forbid it, 35-38 exact delta sets);
  - at least one `APPLY-MISSING-DDL`: dropped on purpose, so a replay can still
    produce a receipt;
  - `assertApplyPolicyForManifests`: moved to the apply-policy unit test over
    the pinned SQL ("Apply policy" below);
  - dropObject decision lines: none of manifests 27-38 declares a drop object.
- **Data statements**: eleven of the twelve migrations are DDL only. 0053
  contains one `UPDATE`
  (`migrations/0053_g3_release_gate_hardening.sql:102-120`). It fills
  `fund_scenario_calculation_runs.queued_event_recorded_at` from the earliest
  matching `calculation_queued` event, and only where the column is NULL.
  Production's ledger tail is 0049, so Drizzle replays 0053 and this statement
  runs again. It is idempotent: it never overwrites a value and it derives the
  same value on every run. ADR-098 already admitted this replay for the
  0050-0055 mode. ADR-103 must name the statement as the one data mutation of
  the route. The runner counts the eligible rows (NULL value and a matching
  event) under the lock before the apply and again after it, in production and
  in rehearsal, and the result and receipt carry both counts under the
  two-directional rule in Implementation Details 2. In production the counts are
  recorded evidence and never a gate: a nonzero after-count can only come from
  rows written concurrently after the statement's snapshot. The rehearsal
  requires an after-count of zero when 0053 is replayed, because a rehearsal
  branch has no concurrent writer. Gap rows: the promoted production code writes
  `calculation_queued` events without setting the column, so runs created
  between the apply and the release stay NULL. After release,
  `recordReserveCalculationQueuedEventOnce`
  (`server/services/fund-scenario-calc-queue-service.ts:219-268`) treats NULL as
  "no event recorded yet" and may append a second queued event when such a run
  is reused. Displayed status is not affected (the run row and snapshot take
  precedence). ADR-103 records this as accepted residue; no second backfill is
  part of this plan.
- **Validation after commit**: Drizzle commits the migration transaction before
  step 9 runs. A ledger or catalog validation failure after commit cannot roll
  back. The run then fails without a receipt, the post-apply audit and evidence
  upload still run (`if: always()`), and the always-run ledger readback
  (Implementation Details 5) decides the recovery (owner sequence step 9). The
  admitted 0050-0055 runner has the same property
  (`run-current-forecast-journaled-migrations.mjs:137-161`). Every check that
  can run before the mutation runs before it: the tail guard removes the one
  known post-commit failure (a later manifest), and the exact pre-state rules
  leave only unforeseen catalog drift. Whether the transaction committed is
  never inferred from the committed marker line: Drizzle awaits `commit` and
  treats any error as failure
  (`node_modules/drizzle-orm/node-postgres/session.js:184-191`), so a lost
  `COMMIT` acknowledgement makes `migrate()` throw after the server committed.
  The readback has three outcomes. `ready` with the pre-dispatch count means
  nothing changed. `complete 12/12` means committed and clean, because read-only
  mode validates the catalog of a complete ledger; a fresh dispatch then
  classifies the ledger `complete`, performs no mutation, and emits an
  `applied: false` receipt. A readback refusal after connection (classification
  or catalog) means unknown state and is an incident. A pre-connection refusal
  (tail guard or pin drift: constant text, no connection made) that the readback
  repeats means nothing changed.
- **DDL safety**: 0058 drops the CHECK with `IF EXISTS` and re-adds it, which
  scans `fund_scenario_variants` and fails closed if a stored `override_type` is
  outside the six values. 0060 adds
  `draft_revision bigint NOT NULL DEFAULT 1 CHECK (draft_revision > 0)`
  (`0060:295-296`); the default is metadata-only on PostgreSQL 17, but the
  inline CHECK scans `fundconfigs` without a rewrite. 0061 builds a partial
  unique index without `CONCURRENTLY`, which is required inside a transaction
  and acceptable at this table size. 0059 contains `DROP TRIGGER IF EXISTS` on
  its own new table. The in-migration preflights of 0054 (`0054:42-57`,
  `:540-549`), 0055 (`0055:30-53`), and 0060 (`0060:52-61`) compare parent
  constraints and the `internal_economics_forbid_update` function body
  byte-exact. They cover parents beyond the Problem Statement list, including
  `internal_analysis_references_id_fund_unique`,
  `internal_lp_economics_runs_id_fund_unique`,
  `source_artifacts_id_fund_unique`, `financial_facts_snapshots_id_fund_unique`,
  and the `substrate_shadow_reconciliations` primary key. A mismatch raises
  `P0001` inside the transaction and rolls everything back; only the rehearsal
  proves production matches.
- **Lock footprint**: the single transaction holds each lock until commit. Even
  a replayed `ADD COLUMN IF NOT EXISTS` takes ACCESS EXCLUSIVE before it checks
  for the column. Locked tables include `users`, `funds`, `portfoliocompanies`,
  `fund_scenario_calculation_runs`, `tasks`, `cash_flow_events`,
  `valuation_marks`, `fund_scenario_variants`, and `fundconfigs`. Every
  `REFERENCES` in a new table takes SHARE ROW EXCLUSIVE on its parent. While the
  apply runs, app requests inside a request-context transaction fail after their
  own 2 s lock timeout (`server/db/request-context.ts:52`), and plain pool
  queries wait. App workflow transactions can hold locks for up to 60 s
  (`server/middleware/with-rls-transaction.ts:97`), which is enough to trip the
  apply's 5 s `lock_timeout`; the owner sequence therefore requires a quiet
  window and a stopped worker. The rehearsal measures the apply duration.
- **Apply policy**: the mode skips the generic pre-apply gate, so
  `assertApplyPolicyForManifests` does not run on this path. The pinned SQL
  hashes freeze the exact statements admitted at source review for all twelve
  migrations, so a runtime scan adds nothing. Instead, a unit test runs
  `validateSqlApplyPolicy` over the twelve pinned files and requires the
  violation set to equal a documented exemption list exactly, by violation
  identity, not by count. Measured at `68a53cb49`: ten files report nothing;
  0054 reports nine violations (`drop-table` and `unknown-drop` kinds from its
  DO-block preflight temp tables and `DROP TRIGGER IF EXISTS` replays); 0059
  reports one `unknown-drop` (`DROP TRIGGER IF EXISTS` on its own new table).
  Both dispositions are already recorded in
  `tests/unit/prod-schema-apply-policy.test.ts:315-328`. Any new violation fails
  the test, and any SQL change fails the hash pin.
- **Audit step**: `Run pre-apply audit` stays unconditional. Audit mode returns
  before the refusal check (`reconcile-prod-schema.mjs:2206`), so
  `REFUSE-FOR-HUMAN` rows do not fail that step.
- **Recovery posture (owner decision 2)**: the governing policy says that
  missing backup, restore, custody, or isolation evidence yields zero dispatch,
  and that a restore reference is revalidated immediately before apply. The
  owner declined a machine-verified restore gate for this route. The policy
  amendment therefore states the route-specific substitute and the floors it
  replaces (Implementation Details 7). ADR-103 records this as an accepted risk
  with its bound: one transaction, additive objects, one idempotent NULL-only
  backfill, and a short provider history window that makes the restore branch
  the recovery point. A restore from that branch returns the whole database to
  the branch's creation time and discards every write made after it, which is
  why the branch is created immediately before dispatch and its creation time is
  recorded.
- **Pilot configuration**: `ACTUALS_PILOT_FUND_ID` alone mounts every 0056 and
  0057 writer (`server/routes/lp-reporting/imports.ts:929-1356`). The promoted
  production code predates those routes, so the variable has no effect at apply
  time. It matters at release time. 0056 and 0057 rows are append-only (their
  triggers reject UPDATE and DELETE, `0056:63-65`, `0057:78-84`), so a mis-set
  variable creates rows nobody can delete. The owner sequence includes a
  readback of every Vercel environment that points at the production database,
  confirming the variable is absent and `ACTUALS_PILOT_PUBLISH_ENABLED` is
  absent or false, before the release dispatch. A machine gate belongs to
  `release-production.yml` and is out of scope here; ADR-103 records it as an
  open item.
- **Locks and timeouts**: a lock wait above 5 s, a statement above 5 min, or (on
  PostgreSQL 17) a transaction above 10 min aborts the whole transaction with no
  partial state. `transaction_timeout` does not exist on the PostgreSQL 16
  Testcontainers image, so the runner sets it only when `server_version_num` is
  170000 or higher. The 30-minute job timeout is unchanged.
- **Runtime admission**: the promoted production code predates these objects. It
  writes `fundconfigs`, `portfoliocompanies`, `fund_scenario_variants`, `tasks`,
  `cash_flow_events`, and `valuation_marks`. The added columns are nullable or
  carry a default, the partial unique indexes exclude the new all-NULL columns,
  0057's `UNIQUE (id, fund_id)` sits on serial primary keys, every new trigger
  is on a new table, and the added CHECKs accept every value that code writes
  (its `override_type` contract has five literals, all within 0058's six). No
  flag or configuration change is part of the apply.
- **Identifier length**: every new constraint, index, and trigger name is below
  63 bytes. The integration test asserts this for the manifests 35-38 names.
- **Owner sequence**. Each step is a separate owner action; none is performed by
  this plan or its implementation.
  1. Before starting, confirm the eleven canary cap variables and the TTL are
     set in the GitHub `Production` environment and the Vercel `Production`
     environment (`release-production.yml:272-284`, `:505-576`). Release is
     blocked without them, and the receipt helps only until the next migration
     lands, so the apply-to-release window must be short.
  2. Merge with `CI Gate Status` green.
  3. Freeze: no merge that touches `migrations/` or
     `scripts/prod-schema-manifests/` until the release dispatch completes. A
     merge during the freeze makes the tail guard refuse the route (before
     mutation) or makes the release audit fail (after apply), and it moves
     `main` away from the rehearsed SHA.
  4. Dispatch the rehearsal mode at the `main` HEAD SHA, record that SHA and the
     apply duration, and delete the rehearsal branch (the project has a low
     branch limit).
  5. Derive the target fingerprint with the documented recipe and set the
     `PRODUCTION_SCHEMA_TARGET_FINGERPRINT` environment secret.
  6. Pick a quiet window and stop the Railway worker.
  7. Create a Neon restore branch of the production branch immediately before
     dispatch. Record its creation time and identifier privately, outside the
     repository.
  8. Dispatch `apply-journaled-0050-0061` at the rehearsed SHA. If `main` has
     moved, stop and re-rehearse.
  9. Act on the outcome. The `Read back journaled ledger` line decides the
     branch; the committed marker line is diagnostic only.
     - **Success**: record the artifact ID, digest, and receipt SHA-256 from the
       step summary. Restart the worker.
     - **Failed; the readback reports `ready 0/12` or repeats a pre-connection
       refusal**: nothing changed. Restart the worker. For a lock timeout
       (`SQLSTATE 55P03`) dispatch again fresh through steps 7-8 (a new restore
       branch first); a GitHub re-run is attempt 2 and is refused. For any other
       refusal, stop and revise the plan.
     - **Failed; the readback reports `complete 12/12`**: the transaction
       committed and the catalog is clean. Restart the worker. Obtain the
       receipt with a fresh dispatch through steps 7-8; the runner classifies
       the ledger complete, performs no mutation, and emits an `applied: false`
       receipt.
     - **Failed; the readback refuses after connection**: unknown state. Stop.
       Treat it as an incident. Do not dispatch the apply mode again. Choose
       between a forward fix and a restore from the restore branch, which
       discards every write since its creation time.
     - **No readback line** (the step did not run or could not connect): read
       the ledger with the owner-approved read-only query (Problem Statement 1).
       The unchanged 14 rows mean nothing changed; 26 rows ending at
       `0061_durable_create_receipts` are handled as `complete 12/12` (the fresh
       dispatch re-validates the catalog before it emits a receipt); anything
       else is an incident.
  10. Read back every Vercel environment that points at the production database:
      `ACTUALS_PILOT_FUND_ID` absent and `ACTUALS_PILOT_PUBLISH_ENABLED` absent
      or false.
  11. Dispatch `release-production.yml` with the recorded values as schema apply
      identity. Lift the freeze after the release completes.
- **Edge cases**: replay after success returns `applied: false` and still emits
  a receipt. A `main` advance between apply and release that does not touch
  migrations or manifests does not invalidate the receipt; the release audit
  re-proves the catalog, and the receipt stays the only ledger proof (audit mode
  never reads `drizzle_migrations`). A future migration 0062 or manifest 39
  makes the tail guard refuse before any connection; the route then needs a
  successor, which is the intended fail-closed behavior and is documented in
  ADR-103.
- **R04 collision**: untracked files in local Codex worktrees claim 0060, 0061,
  and manifests 37 and 38. The pins refuse any such content. R04 must renumber
  to 0062 and manifest 39 or later, and must not merge during the freeze.

rehearsal, deleted by the owner afterwards. No runtime cost.

and have no down migration. Containment is a forward correction or a restore
from the owner's restore branch, each a separate owner action.

## Red team revisions (2026-09-27)

A code-grounded red team of the round-6 plan found one blocker and several major
gaps. All revisions are additive. None reopens the owner decisions.

1. Blocker: with the generic gate skipped and the pins keyed by index, a later
   0062 or manifest 39 would commit 0050-0061 and then fail the post-apply
   audit, leaving no receipt. Added the pre-connection tail guard and the merge
   freeze.
2. Owner sequence: the restore branch moved to immediately before dispatch and
   is recorded; added the canary-cap precondition, the quiet window and worker
   stop, the rehearsed-SHA binding, and explicit branches for refusal, lock
   timeout, and failure after commit.
3. Fingerprint: one named serializer, byte-identical to the actuals serializers
   and shared with the rehearsal, which uses it instead of its own `sha256:`
   host hash; an owner recipe; a constant refusal message; no fingerprint in the
   public receipt.
4. Pre-state exactness: real pins for 0054 and 0055 SQL and manifests 31-33;
   exact-equality delta sets for manifests 35-38; the unmeasurable
   `constraint-definition-mismatch` allowance removed (no journaled migration
   before 0058 creates the CHECK).
5. `transaction_timeout` on PostgreSQL 17; SQLSTATE read through
   `DrizzleQueryError.cause`.
6. The two-stage classifier replaced by one call to
   `classifyCurrentForecastLedgerState` with twelve target entries.
7. Two-directional backfill count rule; negative contract cross-binding matrix;
   apply-policy exemptions pinned by identity (nine for 0054, one for 0059).
8. Complete governance amendment list, the governance routing test, and ADR-074
   cited as the restore-posture precedent.
9. Corrected facts: 0060 is not metadata-only; the lock footprint, the 0053 gap
   rows, the pilot-bound enforcement, and the rehearsal identifier exposure are
   now stated.

### Codex round 7 (2026-09-27)

1. Commit state: the committed marker line is diagnostic only. A new always-run
   workflow step reads the ledger back with the runner in read-only mode, and
   "Validation after commit" and owner sequence step 9 branch on that readback:
   `ready` with the pre-dispatch count, `complete 12/12`, or unknown (incident).
   A pre-connection refusal repeated by the readback means nothing changed; a
   missing readback falls back to the owner-approved ledger query. The earlier
   contradiction between a fresh dispatch after a harmless post-commit failure
   and "do not retry" is removed.
2. Catalog validator inputs: each reused validator receives a state derived from
   the one classifier count (Current Forecast `min(n, 6)`, 0056 complete at 7,
   0057 complete at 8, manifests 35-38 ledgered at 9-12), with unit coverage at
   every count and a Testcontainers tail at 0056.
3. Fingerprint wording: the serializer is byte-identical to the actuals
   serializers and shared with the rehearsal. The actuals runners are not
   refactored; their modes are superseded for production and their regression
   suites stay unchanged.
