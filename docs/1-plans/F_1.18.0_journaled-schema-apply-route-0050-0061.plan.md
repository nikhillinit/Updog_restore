Reviewed checkout: `origin/main` at `68a53cb49` on 2026-09-26. The repository is

## Overview

Production has no usable route to the schema that `main` requires. This plan
adds one bounded apply mode, `apply-journaled-0050-0061`, to
`.github/workflows/prod-schema-reconcile.yml`. The mode validates the exact
production migration ledger, then applies every unapplied journaled migration
from the validated tail through `0061_durable_create_receipts` in journal order,
inside one transaction. It follows the ADR-098 pattern that admitted
`apply-current-forecast-0050-0055`. A matching rehearsal mode runs the same
runner against an isolated Neon branch. The release audit contract does not
change: a release still requires every manifest to report `SKIP`.

2. **ADR-098 recovery posture.** The mode has real apply capability, guarded by

   catalog checks, advisory lock, and timeouts. The owner creates a Neon restore

## Solution Architecture

One new runner, modeled on
`scripts/run-current-forecast-journaled-migrations.mjs`:

1. Verify source identity: the journal entries at idx 51-62 and manifests 27-38
   must equal pinned values. Any drift refuses before a database connection.
2. Connect through a direct (non-pooler) URL. Compute the target fingerprint
   (SHA-256 over direct host, port, database, and role, the same shape as the
   actuals runners) and, in apply mode, require it to equal
   `EXPECTED_TARGET_FINGERPRINT`. A missing or different value refuses before
   the lock and before any mutation. Then take the shared advisory lock and set
   `lock_timeout` 5 s and `statement_timeout` 5 min.
3. Classify the ledger. The expected chain is the baseline (canonical or ADR-074
   reconciled) followed by the twelve target entries. The ledger must be an
   exact prefix of that chain and must contain the whole baseline. Unknown rows,
   gaps, reorders, duplicates, and hash mismatches refuse.
4. Validate the catalog against the ledger state (Technical Considerations).
5. In read-only mode, or when the ledger is complete, return without mutation.
6. Otherwise build a temporary migrations folder that holds exactly the twelve
   pinned entries and SQL files, and call the Drizzle migrator once. Drizzle
   applies the entries newer than the ledger tail inside one transaction, so the
   apply is all-or-nothing.
7. Re-read the ledger: it must be complete, and every earlier row must be
   unchanged. Re-audit: manifests 1-38 must all report `SKIP` with no deltas.
8. Emit a result (pre-state, post-state, applied flag, range, target
   fingerprint, and the two backfill counts) for the receipt.

The workflow adds the mode, skips the generic pre-apply decision gate for it
(the runner performs the exact equivalent under the lock), and keeps the generic
post-apply audit, which passes because the schema is complete through
manifest 38. Audit mode accepts the new receipt as historical schema proof, so
one apply run proves the whole chain for a release.

## Technical Considerations

- **Pattern usage**: ADR-098 range runner, ARCHI.md section 4 migration-tail
  rules, section 9 "New DB/schema change".
- **Catalog rule per target**: a ledgered migration requires its manifest clean
  (`SKIP`, zero deltas). An unledgered migration requires an allowed pre-state.
  Manifests 27-32 use the existing Current Forecast assertion, which already
  accepts production's manifest-applied 0050-0053 objects. Manifests 33 and 34
  use the existing actuals assertions (pristine absence). Manifests 35-38 use a
  pinned allowlist of delta identities, in the style of
  `ALLOWED_NON_SENTINEL_DELTAS`, measured at TRIP-2 on disposable databases for
  both baseline kinds. Manifest 35 must allow both `missing-constraint` (the
  production state) and `constraint-definition-mismatch` (a journal-linear
  database that holds the five-value CHECK) for
  `fund_scenario_variants_override_type_check`. Any other delta refuses as
  partial DDL.
- **Data statements**: eleven of the twelve migrations are DDL only. 0053
  contains one `UPDATE`
  (`migrations/0053_g3_release_gate_hardening.sql:102-120`). It fills
  `fund_scenario_calculation_runs.queued_event_recorded_at` from the earliest
  matching `calculation_queued` event, and only where the column is NULL.
  Production's ledger tail is 0049, so Drizzle replays 0053 and this statement
  runs again. It is idempotent: it never overwrites a value and it derives the
  same value on every run. Rows created after 2026-08-18 that have a matching
  event receive a value. ADR-098 already admitted this replay for the 0050-0055
  mode. ADR-103 must name the statement as the one data mutation of the route.
  The runner counts the eligible rows (NULL value and a matching event) under
  the lock before the apply and again after it, in production and in rehearsal.
  The result carries both counts as `backfillEligibleBefore` and
  `backfillEligibleAfter`. Both counts are null when 0053 is already ledgered,
  because the statement does not run then. The before-count is also null when
  the column does not exist yet. In production the counts are recorded evidence
  and never a gate: a nonzero after-count can only come from rows written
  concurrently after the statement's snapshot, and those rows stay NULL exactly
  as they are today. The receipt schema carries the same two fields. The
  rehearsal script parses the result file. When 0053 is replayed it requires an
  after-count of zero, because a rehearsal branch has no concurrent writer and a
  failure there has no production consequence. Otherwise it requires both counts
  null.
- **Validation after commit**: Drizzle commits the migration transaction before
  step 7 runs. A ledger or catalog validation failure after commit cannot roll
  back. The run then fails without a receipt, the post-apply audit and evidence
  upload still run (`if: always()`), and recovery is a separate owner action.
  The admitted 0050-0055 runner has the same property
  (`run-current-forecast-journaled-migrations.mjs:145-160`). Every check that
  can run before the mutation runs before it, which is why the pre-state catalog
  rule is exact. The Testcontainers suite proves both halves: a NULL row with a
  matching event is filled, and a row that already holds a value is unchanged.
- **DDL safety**: 0058 adds a CHECK that scans `fund_scenario_variants` and
  fails closed if a stored `override_type` is outside the six values. 0060 adds
  `draft_revision bigint NOT NULL DEFAULT 1`, a metadata-only change on
  PostgreSQL 17. 0061 builds a partial unique index without `CONCURRENTLY`,
  which is required inside a transaction and acceptable at this table size. 0059
  contains `DROP TRIGGER IF EXISTS` on its own new table. The runner uses the
  Drizzle migrator, not the manifest apply policy, so that statement is not
  evaluated by `prod-schema-apply-policy.mjs`.
- **Apply policy**: the mode skips the generic pre-apply gate, so
  `assertApplyPolicyForManifests` does not run on this path. The pinned SQL
  hashes freeze the exact statements admitted at source review, so a runtime
  scan adds nothing. Instead, a unit test runs `validateSqlApplyPolicy` over the
  twelve pinned files and requires the violation set to equal a documented
  exemption list exactly. Measured at `68a53cb49`: ten files are clean; 0054
  reports its DO-block preflight and two `DROP TRIGGER IF EXISTS` statements on
  its own tables; 0059 reports one `DROP TRIGGER IF EXISTS` on its own new
  table. Both dispositions are already recorded in
  `tests/unit/prod-schema-apply-policy.test.ts:315-328`. Any new violation fails
  the test, and any SQL change fails the hash pin.
- **Audit step**: `Run pre-apply audit` stays unconditional. Audit mode returns
  before the refusal check (`reconcile-prod-schema.mjs:2206`), so
  `REFUSE-FOR-HUMAN` rows do not fail that step.
- **Recovery posture (owner decision 2)**: the governing policy says that
  missing backup, restore, custody, or isolation evidence yields zero dispatch,
  and that a restore reference is revalidated before apply. The owner declined a
  machine-verified restore gate for this route. The policy amendment must
  therefore say more than the route's name. It must state that, for this route,
  the restore reference is a Neon restore branch that the owner creates and
  confirms immediately before dispatch, that the workflow does not verify it,
  and that the owner, as sole dispatch issuer, withholds dispatch when it is
  absent. ADR-103 records this as an accepted risk with its bound: one
  transaction, additive objects, one idempotent NULL-only backfill, and a short
  provider history window that makes the restore branch the recovery point.
- **Pilot configuration**: `ACTUALS_PILOT_FUND_ID` alone mounts the draft-write
  routes (`server/routes/lp-reporting/imports.ts:929`). The promoted production
  code predates those routes, so the variable has no effect at apply time. It
  matters at release time. The owner sequence includes a readback of the Vercel
  Production environment that confirms the variable is absent and
  `ACTUALS_PILOT_PUBLISH_ENABLED` is absent or false, before the release
  dispatch. A machine gate for this belongs to `release-production.yml` and is
  out of scope here; ADR-103 records it as an open item.
- **Locks and timeouts**: a lock wait above 5 s aborts the whole transaction
  with no partial state. The 30-minute job timeout is unchanged.
- **Runtime admission**: the promoted production code predates these objects. It
  writes `fundconfigs`, `portfoliocompanies`, and `fund_scenario_variants`. The
  added columns are nullable or carry a default, and the added CHECKs accept
  every value that code writes, so its writes stay valid. No flag or
  configuration change is part of the apply.
- **Identifier length**: every new constraint, index, and trigger name is below
  63 bytes. The integration test asserts this for the manifests 35-38 names.
- **Owner sequence** (each step is a separate owner action; none is performed by
  this plan or its implementation): merge with `CI Gate Status` green; create a
  Neon restore branch of the production branch (history retention is short, so
  the branch is the recovery point); dispatch the rehearsal mode and delete the
  rehearsal branch afterwards (the project has a low branch limit); set the
  `PRODUCTION_SCHEMA_TARGET_FINGERPRINT` environment secret; dispatch
  `apply-journaled-0050-0061` at the exact `main` SHA; record artifact ID,
  digest, and receipt SHA-256 from the step summary; confirm the pilot
  configuration readback; dispatch `release-production.yml` with those values as
  schema apply identity.
- **Edge cases**: replay after success returns `applied: false` and still emits
  a receipt. A `main` advance between apply and release does not invalidate the
  receipt; the release audit re-proves the catalog. A future migration 0062 adds
  manifest 39, which makes the post-apply audit fail for this mode until a new
  route exists. That is the intended fail-closed behavior and is documented in
  ADR-103.
- **R04 collision**: untracked files in local Codex worktrees claim 0060, 0061,
  and manifests 37 and 38. The pins refuse any such content. R04 must renumber
  to 0062 and manifest 39 or later. Coordination item only.

## Type Definitions

`JournaledRangeMigrationResultV1` and `SchemaReconcileJournaledRangeReceiptV1`,
inferred from the Zod schemas in item 2. No database schema or Drizzle type
changes.

## Performance & Cost Impact

One short transaction of DDL plus one bounded backfill on small tables. One
rehearsal branch per rehearsal, deleted by the owner afterwards. No runtime
cost.

## Backward Compatibility

All six existing modes, their receipts, and their tests stay unchanged.
Historical receipts stay valid for their exact SHA. The migrations are additive
and have no down migration. Containment is a forward correction or a restore
from the owner's restore branch, each a separate owner action.
