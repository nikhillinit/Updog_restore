# Planning-Document Lineage Corrections Implementation Plan (F_1.3.3)

## Overview

Eight plan documents under `docs/1-plans/` carry uncommitted lineage annotations
dated 2026-08-28 (status frontmatter, "Current state" / "Plan disposition"
headers, document-role and operational-state disclaimers), plus the matching
regenerated `docs/_generated/router-index.json` and
`docs/_generated/staleness-report.md`. This plan verifies every factual claim in
those annotations against git truth, corrects any that are wrong, regenerates
the routing artifacts, and ships the result as a docs-only chore PR with no
version bump.

## Problem Statement

- The annotations exist only in the working tree of the main checkout. Their
  provenance is a prior session; none of the claims (PR numbers, merge SHAs,
  supersession links, "not on origin/main" negatives) have been independently
  verified. Repo policy treats unverified agent output as untrusted until
  checked.
- Until committed, the corrections are one `git reset`/checkout away from loss,
  and the staleness report on `main` still reports the eight documents as
  missing frontmatter.
- Scope decision (owner, 2026-08-28): verify and commit the eight annotated
  documents only. The remaining plan documents without `status:` frontmatter are
  explicitly out of scope.

## Solution Architecture

Single-phase docs chore. No application code, schema, routes, flags, or
calculation changes. Three steps: (1) verify each annotation claim against git
evidence; (2) apply minimal corrective edits where a claim fails verification;
(3) regenerate routing artifacts and ship one docs-only PR containing exactly
the eight plan docs, the two generated files, and this plan document.

Verification outcome is recorded per claim as pass/fail in the PR body (one line
per file). A failed claim gets a minimal in-place correction (right PR number,
right SHA, or removal of the unverifiable sentence) — nothing else in the
document is rewritten.

### 2. Corrective edits (only where verification fails)

**Files**: the eight documents above.

Edits are constrained to the annotation blocks added in the working tree.
Pre-existing document bodies are untouched except the one F_1.7.0 checkbox
already flipped in the working tree (kept if #1429 verification passes). Header
shape is intentionally NOT normalized across the eight ("Current state" vs "Plan
disposition" variants both stay) — format unification is churn outside this
plan's purpose.

### 3. Regenerate routing artifacts

**Files**: `docs/_generated/router-index.json`,
`docs/_generated/staleness-report.md`

After any corrective edits, run `npm run docs:routing:generate` and commit the
regenerated outputs in the same commit as the doc edits. The already-modified
working-tree copies are superseded by this regen (expected deltas:
missing-frontmatter count down 8, HISTORICAL +7, ACTIVE +1, DRAFT +1 for
this plan document).

### 4. Commit vehicle

Branch from `origin/main` (never local main — release-branch rule), e.g.
`docs/plan-lineage-corrections-2026-08-28`. One commit, conventional type
`docs:`. PR contains exactly 11 files (the eight annotated docs, the two
generated outputs, and this plan document, tracked in the same PR).
Untracked `.agents/research/` and
`.playwright-mcp/` are radioactive agent-state dirs — never staged; stage files
by explicit path, no `git add -A` / `git add .`. Owner merges manually per usual
flow.

## Technical Considerations

- **Pattern usage**: status frontmatter follows the existing generator
  vocabulary observed in `staleness-report.md` (ACTIVE / HISTORICAL / DEPRECATED
  are all already-recognized values).
- **Governance**:
  `docs/governance/solo-internal-change-and-production-policy.md` must be read
  from `origin/main` before the merge action (routing rule in `CLAUDE.md`).
  Marking a plan DEPRECATED is a frontmatter status change, not an archive move
  — the archive-guard (`docs/archive/**`) is not triggered.
- **CI expectations**: docs-only PR produces a short, mostly-vacuous CI run;
  that green proves formatting only, not repo health — do not cite it as a
  baseline. The diff is narrow, so no dormant path-filtered lanes activate.
- **Working-tree safety**: the corrections currently exist only as uncommitted
  edits in the main checkout, which is also the tree used for other work. First
  implementation action is to create the branch and commit the (verified) state
  before anything else touches the tree.
- **Edge cases**: a claim that verifies to a _different_ PR/SHA than annotated
  is corrected in place; a claim that cannot be mapped to any merged PR is
  deleted and the deletion noted in the PR body. If verification shows a
  document's `status:` value itself is wrong (e.g. ACTIVE work actually merged),
  the status is corrected and the staleness regen picks it up.
