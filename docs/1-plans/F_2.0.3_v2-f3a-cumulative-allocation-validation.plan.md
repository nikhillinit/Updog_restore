## Overview

Close the F3a repeated-row and ignored-refusal defects in the V2 internal
economics event-stream engine without widening public V2 capability. The change
adds cumulative (per-lot aggregate) validation for repeated cash-source
allocation and investment-lot relief rows, exact event-total validation, and
propagation of refusal-capable processor results through the existing
chronology switch. F2 public event admission remains refused; no contract,
receipt, or public behavior changes.

## Problem Statement

Three defects in the current V2 event-stream engine:

1. Repeated allocation rows referencing the same cash lot (or investment lot)
   can each pass individually while cumulatively overdrawing the lot's
   remaining balance (or remaining cost basis).
2. Event `amountUsd` is not checked against the sum of its allocation rows
   (deployment/fund-expense cash allocations; realization allocated proceeds),
   so a total mismatch is silently accepted.
3. The existing chronology switch in `derive-composite-v2.ts` drops returned
   refusals from refusal-capable processors instead of propagating the first
   refusal.

## Solution Architecture

Internal Economics V2, Current Forecast V2, and marginal reserve MOIC remain
separate seams. F3a keeps the existing chronology switch and the
validation-before-mutation processor pattern; no dispatcher or generic
transition framework is introduced.

Design principles (from the ralplan RALPLAN-DR):

1. Validate all fallible conditions before the first write.
2. Repair shared validators and the existing chronology loop, not callers.
3. Admit capability only with versioned consumer-backed proof.
4. Evidence never grants merge or production authority.

Rejected alternatives: a new dispatcher/transition framework (duplicates the
existing switch, broadens scope); landing `sourceCashLotId`/eventful
receipt/persistence/queue now (needs consumer and durable-state decisions —
deferred to later gates); per-caller guards (miss shared behavior).

## Implementation Details

Exact three-file scope. Any additional path is a stop condition.

### 1. Event-stream engine validators and processors

**File**: `shared/lib/internal-economics/v2/event-stream-engine-v2.ts`

**Current state**: `validateCashSourceAllocations` and `validateReliefRows`
check rows individually; `processDeployment`, `processFundExpense`, and
`processRealization` do not compare row sums against event `amountUsd`.

**Modifications**:

- `validateCashSourceAllocations`: scan all references; reject any allocation
  row with a negative amount (existing family
  `CASH_SOURCE_ALLOCATION_VIOLATION` at provenance) before aggregation;
  aggregate amount by `lotId`; compare each aggregate against the lot's
  `remainingBalance`.
- `validateReliefRows`: scan all references; reject any row with a negative
  `relievedCostBasis` or negative `allocatedProceeds` (existing family
  `INVESTMENT_LOT_RELIEF_VIOLATION` at provenance) before aggregation;
  aggregate `relievedCostBasis` by `investmentLotId`; compare each aggregate
  against remaining cost basis.
- `processDeployment` / `processFundExpense`: after cash validation and before
  `applyCashSourceAllocations`, compare the allocation-row sum with
  `amountUsd`; on mismatch construct the existing-family refusal
  (`CASH_SOURCE_ALLOCATION_VIOLATION`, provenance stage) with the literal
  message and contextDetails specified below.
- `processRealization`: after relief validation and before `applyReliefRows`,
  compare the `allocatedProceeds` sum with `amountUsd`; on mismatch construct
  the existing-family refusal (`INVESTMENT_LOT_RELIEF_VIOLATION`, provenance
  stage) with the literal message and contextDetails specified below.
- Preserve existing code/stage values and existing missing-reference and
  cumulative behavior. Do not change contracts, receipts, opening state, or
  unsupported-event policy. `processSettledContribution` remains non-refusing.

### 2. Chronology loop exposure and refusal propagation

**File**: `shared/lib/internal-economics/v2/derive-composite-v2.ts`

**Current state**: `runLane` contains the `processEvents` chronology switch
inline; processor return values are not captured, so returned refusals are
dropped.

**Modifications**:

- Rename/expose the existing `processEvents` loop as `processEventsV2ForTest`
  without changing chronology order. No dispatcher.
- Keep the switch; capture and return the first refusal-capable processor
  output (assign per case, return on first non-null refusal).
- `runLane` calls `processEventsV2ForTest`.
- Keep `checkAdmissionGuard` and the F2 public refusal unchanged. Leave
  public-refusal/no-`sourceCashLotId` tests untouched unless a red run proves
  regression.

### 3. Tests

**File**: `tests/unit/internal-economics/v2/event-stream-engine-v2.test.ts`

See Test Impact and the To-dos (1A/1B) for the exact case list. Snapshots
capture mutable event-lane maps/ledgers/ending cash in stable key order with
Decimal values at six places.

### Required Refusal Semantics

| Event | Validation sequence | Refusal |
| --- | --- | --- |
| `deployment`, `fund_expense_payment` | all source refs; no negative allocation row; aggregate per lot vs `remainingBalance`; allocation sum equals `amountUsd`; apply | `CASH_SOURCE_ALLOCATION_VIOLATION`, provenance |
| `realization` | all investment refs; no negative `relievedCostBasis` or `allocatedProceeds` row; aggregate `relievedCostBasis` vs remaining basis; `allocatedProceeds` sum equals `amountUsd`; apply | `INVESTMENT_LOT_RELIEF_VIOLATION`, provenance |

Deterministic precedence: missing reference wins over negative row; negative
row wins over cumulative balance/basis; cumulative wins over total mismatch;
total mismatch wins over mutation. (Negative-row rejection is a row-level
validity check and therefore sits with reference validity, before any
aggregate math.)

Deployment/fund-expense total-mismatch diagnostics contain `eventId` and this
byte-exact, no-whitespace contextDetails JSON text:

~~~json
{"expectedEventAmountUsd":"<six-place>","actualCashSourceAllocationTotalUsd":"<six-place>"}
~~~

Literal message:

~~~text
Event <eventId>: event amount <amountUsd six-place> must equal cash source allocation total <sum six-place>.
~~~

Realization total-mismatch diagnostics contain `eventId` and this byte-exact,
no-whitespace contextDetails JSON text:

~~~json
{"expectedEventAmountUsd":"<six-place>","actualAllocatedProceedsTotalUsd":"<six-place>"}
~~~

Literal message:

~~~text
Event <eventId>: event amount <amountUsd six-place> must equal allocated proceeds total <sum six-place>.
~~~

ContextDetails is deterministic JSON text of exact six-place strings. Tests
assert the complete byte-exact string. No new contract field and no cents
conversion.

## Technical Considerations

- **Pattern usage**: follows the established V2 refusal-first
  validation-before-mutation pattern (ARCHI.md section 8, item 6). Reuses the
  two existing refusal families; no new refusal family or code.
- **Execution isolation**: implementation runs only in a fresh linked worktree
  created from `origin/main` — never in the current dirty main checkout:

  ~~~sh
  set -euo pipefail
  git fetch origin main
  SOURCE_SHA="$(git rev-parse origin/main)"
  test "$(printf %s "$SOURCE_SHA" | wc -c | tr -d ' ')" -eq 40
  git cat-file -e "$SOURCE_SHA^{commit}"
  if test -e /Users/nikhil/code/Updog_restore-f3a || git show-ref --verify --quiet refs/heads/codex/f3a-transition-kernel; then
    printf '%s\n' 'existing F3a worktree or branch; stop' >&2
    exit 1
  fi
  git worktree add -b codex/f3a-transition-kernel /Users/nikhil/code/Updog_restore-f3a "$SOURCE_SHA"
  cd /Users/nikhil/code/Updog_restore-f3a
  npm ci
  test -z "$(git status --porcelain)"
  ~~~

  Record `SOURCE_SHA` before the first edit. Dependency bootstrap is
  lockfile-backed; any tracked change stops execution before edits. Read the
  governing policy (`docs/governance/solo-internal-change-and-production-policy.md`)
  from `origin/main` in the linked worktree and confirm the F2/F3 boundary
  before editing.
- **Authority boundaries**: local candidate SHA is the terminal deliverable
  without separate GitHub write authority — no push, no PR. After separate
  GitHub write authority only, execution may push, create a PR, and obtain
  exact-candidate CI Gate Status. CI Gate Status is a merge gate only; merge
  authority and production authority remain separate.
- **Non-negotiable rules preserved by construction**: idempotency, optimistic
  locking, cursor validation, and queue timeouts are preserved by touching no
  durable, routed, or queued surface. TZ=UTC for all test runs. Financial
  proof includes `npm run phoenix:truth`.
- **Edge cases**: repeated rows against the same lot that are individually
  valid but cumulatively overdraw; negative rows that offset within an event
  so both the cumulative and total checks would pass while corrupting
  balances (the decimal-string schema permits `-`; rejected at row level);
  total-mismatch refusal raised after validation but before any apply (state
  must be byte-identical before/after); later-event refusal after an earlier
  committed event (earlier effect retained, later effect zero).

## ADR (to be recorded in DECISIONS.md at implementation)

**Decision**: F3a repairs validation order, repeated-row aggregation, exact
totals, and refusal propagation through the existing chronology switch before
source lineage, receipts, persistence, or queues.

**Drivers**: financial safety; smallest root-cause patch; exact-SHA isolation;
independent consumer/evidence seams.

**Alternatives**: dispatcher/framework (duplicates existing switch);
`sourceCashLotId`/eventful receipt (needs a named consumer); persistence/BullMQ
(needs durable-state decisions); caller guards (miss shared behavior).

**Consequences**: no public event result; future execution isolated from dirty
main; a post-write refusal need would require new design.

**Follow-ups**: reopen source-lineage work only after F3a exact-SHA green plus
a named consumer; evaluate correction/write-off/conversion and
persistence/BullMQ independently.

## Out of Scope (later gates — not part of this plan's implementation)

- **2A `sourceCashLotId` and eventful receipt**: only after F3a exact-SHA
  green, a named consumer, and approved versioned semantics. Source lineage
  explicit; never inferred from `sourceRef`, `investmentLotId`, owner, deal,
  or security.
- **2B correction, write-off, conversion**: separate consumer-backed
  extensions; explicit refusal remains correct until independent truth proof.
- **2C persistence / BullMQ**: a later proposal must define durable consumer,
  idempotency, optimistic version, retries, timeout, recovery, schema
  ownership, and real-database proof. Queue de-duplication never replaces
  domain idempotency.
- **Evidence lanes E1 (Current Forecast shadow soak) and E2 (marginal-MOIC
  soak)**: read-only runbook-driven evidence under separate authority;
  documented in the source ralplan procedure; not part of the F3a code slice.
