**Status:** DRAFT — proposed scope; not an accepted amendment or execution
authority

## Outcome

Complete the narrow F2 success surface before F3 introduces event transitions:

- accept a zero-event, deal-by-deal opening state with explicit investment
  provenance;
- deeply seal normalized input before hydration and hashing;
- hydrate explicit runtime opening-position types;
- emit balance-forward journal entries without inventing period cash flows;
- return one closed internal-economics-receipt/2.1.0 shape;
- bind the receipt to one exact result-hash preimage and one closed component
  manifest;
- enforce deterministic output-row and serialized-output-byte limits;
- freeze a complete V2-S-0100 input and expected receipt;
- regenerate V2-S-0101 under 2.1.0 and prove its changed-case manifest is
  consumed.

F2 remains zero-event. processEvents repair, event-stream atomicity,
callable-commitment event processing, cumulative event-allocation validation,
and sourceCashLotId event lineage move entirely to F3.

## Assurance boundary

This project is an internal fund-management decision-guidance tool maintained by
one developer. Required rigor is proportional:

- preserve deterministic financial calculations, explicit provenance,
  refusal-on-invalid-input behavior, exact truth fixtures, and reproducible
  hashes;
- keep changes small, local, dependency-free, and reviewable;
- use existing repository CI and financial-truth gates;
- do not add regulatory compliance mappings, audit-grade attestations,

  controls, new release orchestration, or production operating ceremony.

Receipts are reproducibility and debugging evidence for internal decisions. They
are not accounting books, legal records, regulatory filings, or independent

## Problem statement

The F_2.0.1 entry seam admitted V2-S-0101, a paid-in cash-only zero-event
success. F2 completion remains blocked because:

1. V2-S-0100 is described only as a proposition, not as one literal input and
   receipt.
2. Opening positions are mixed conceptually with transaction cash flows.
3. Runtime state cannot represent opening owners, source references, entitlement
   pools, or entitlement values.
4. investmentLotId is currently unique per input row, while future
   sourceCashLotId lineage is unspecified.
5. Receipt 2.0.0 is summary-only and componentVersions is open and empty.
6. Current result-hash descriptions use incompatible preimages.
7. entitlementAmount is positive and accepted independently of cost basis, but
   the prior plan implied an unsupported economic equality.
8. processEvents repair is partial and cannot provide whole-stream atomicity.
9. MAX_OUTPUT_ROWS exists but is not enforced; output expansion can exceed it.
10. Normalized input is only shallow-frozen.
11. Initializer revalidation would duplicate the normalizer and widen results
    without a second trust boundary.
12. Prior governance wording claimed an accepted erratum and possible ADR-085
    addendum that neither the plan nor a draft can authorize.

## Architecture decisions

### 1. Normalization owns validation and deep sealing

verifyAndNormalizeInternalEconomicsInputV2 remains the only validation boundary:

1. strict parse produces a detached wire object;
2. canonical row ordering is applied;
3. all schema, reconciliation, provenance, and admission-limit checks run;
4. normalizedInputHash is computed from canonical wire fields only, excluding
   normalization metadata;
5. the full normalized object graph, including arrays and nested owner objects,
   is recursively frozen;
6. the normalized brand and hash metadata are attached and the graph is handed
   to hydration.

The current canonical input-hash behavior remains unchanged: absent optional
wire fields are absent, not emitted as undefined.

### 2. Hydration is infallible over sealed normalized input

initializeEventStreamState accepts only NormalizedInternalEconomicsInputV2 and
returns EventStreamState directly.

It does not:

- re-run schema or provenance validation;
- widen to a Result;
- mutate normalized input;
- use “state fingerprint” wording;
- partially apply rows and then refuse.

Invalid opening rows are rejected before hydration by the normalizer. Hydration
creates fresh Decimal-backed runtime state from the sealed value.

### 3. Opening positions are not period cash flows

Opening cash lots and investment slices are positions at cutoverInstant. They
are disclosed under openingPositions and represented by balance-forward journal
entries.

CashFlowEntryV2 remains reserved for actual events. Because F2 admits
events.length === 0:

- every partner cashFlowVector is [];
- every class cashFlowVector is [];
- opening journal entries are excluded from IRR, XIRR, event-flow, contribution,
  deployment, realization, fee, expense, and distribution vectors.

### 4. Journal role is deliberately narrow

The opening journal is the sole source for journal-derived balance aggregates
and posting conservation.

The deeply sealed normalized state remains the source for:

- partner and class identities;
- commitments and opening ledger disclosures;
- sourceRef values;
- entitlement-pool identity and metadata;
- entitlementAmount disclosure;
- selected lane and input lineage.

No claim is made that the journal alone contains every receipt disclosure.

### 5. Closed balance-forward accounts

F2 uses exactly three journal accounts:

- cash
- invested_basis
- opening_unreturned_capital

For each opening cash lot, one entry posts:

- positive remainingBalance to cash;
- negative remainingBalance to opening_unreturned_capital.

For each opening investment slice, one entry posts:

- positive remainingBasis to invested_basis;
- negative remainingBasis to opening_unreturned_capital.

Entitlement pools create disclosure rows only. They do not create journal
entries.

### 6. Investment identity and F3 lineage boundary

For receipt 2.1.0, investmentLotId is the unique identity of one input
investment-slice row. Duplicate investmentLotId values remain refused. It is not
a shared parent-lot identifier.

sourceRef remains an opaque disclosure reference. F2 does not infer acquisition
cash lineage.

F3 must introduce sourceCashLotId explicitly through a versioned input and
receipt change before any deployment, realization, correction, or relief
semantics are admitted. F3 must not derive sourceCashLotId from sourceRef,
investmentLotId, owner, dealId, or securityId.

### 7. entitlementAmount is opaque in F2

entitlementAmount must be a positive six-decimal string because the current
strict normalizer requires that shape.

In F2 it is:

- disclosed unchanged;
- summed arithmetically into entitlementTotal for its pool;
- excluded from cash, basis, unreturned-capital, ownership-percentage,
  waterfall-allocation, and conservation equations.

No equality or ratio between entitlementAmount and costBasis, remainingBasis,
paid-in capital, or distributions is asserted. F3 requires a successor economic
invariant before using entitlementAmount for allocations.

### 8. processEvents moves to F3

F2 makes no processEvents change and creates no test-only export.

F3 owns one complete event-processing design that covers:

- whole-stream atomic prepare/apply behavior;
- rollback or non-mutation on any refusal;
- callable-commitment consumption and restoration;
- cumulative cash-source allocation validation;
- cumulative investment-basis relief validation;
- explicit sourceCashLotId lineage;
- event-derived journal and cash-flow semantics.

## Receipt 2.1.0 closed contract

### Scalar and container rules

- Every interface field is readonly.
- Every returned object and array is deeply frozen.
- Money and signed posting amounts are base-10 strings with exactly six
  fractional digits.
- Ratio configuration remains twelve fractional digits in input; receipt
  allocations are money strings.
- Every top-level field is required.
- Empty optional lineage is emitted as [].
- undefined, Decimal instances, Map, Set, Date, bigint, functions, and non-plain
  objects are forbidden in the receipt.
- Object key order is irrelevant because canonical JSON sorts keys.

## Hash contracts

### Normalized input hash

normalizedInputHash remains SHA-256 of canonical JSON over the normalized wire
fields only. Normalization metadata is excluded. The value is computed before
attaching the brand and then the full graph is deeply frozen.

### Result hash

There is one result-hash preimage:

**InternalEconomicsReceiptV2ResultHashPreimage = InternalEconomicsReceiptV2 with
only resultHash omitted.**

Formula:

**resultHash = sha256CanonicalJson(receipt without resultHash)**

This includes receiptVersion, the closed component manifest, selectedLane,
hashAlgorithm, normalizedInputHash, and every immutable receipt payload field.
There is no second wrapper, domain tag, summary-only payload, or
implementation-identity side object.

Production and independent-oracle canonicalizers must:

- sort every plain-object key;
- preserve normative array order;
- reject undefined instead of dropping it;
- reject non-JSON-safe values;
- produce identical bytes and digest for every valid receipt shape.

## Conservation and consistency invariants

All arithmetic uses the repository Decimal configuration and ROUND_HALF_UP.

1. **Entry balance:** each journal entry’s signed postings sum to 0.000000.
2. **Cash:** sum opening cash-lot remainingBalance equals openingCash, opening
   cash classification total, journal cash debit total,
   fundCashEquation.openingCash, and fundCashEquation.endingCash for zero
   events.
3. **Basis:** each slice has relievedAmount === 0.000000 and remainingBasis ===
   costBasis; sum remainingBasis equals journal invested_basis debit total.
4. **Partner unreturned capital:** for each partner, owned opening cash
   remainingBalance plus owned investment remainingBasis equals both:
   - the positive balance-forward asset total from that owner’s cash and
     invested_basis postings;
   - partnerLedger.unreturnedSettledCashCapital.
5. **Opening ledger ordering:** nonnegative balances;
   unreturnedSettledCashCapital <= paidInCapital; paidInCapital ===
   settledCapital; settledCapital <= calledCapital; calledCapital <=
   committedCapital; remaining callable equals committed minus called.
6. **Class aggregation:** for each LP class, every monetary ClassLedgerV2 field
   equals the sum of the same PartnerLedgerV2 field for LP partners in that
   class; class cashFlowVector is the canonical merge of member vectors.
7. **Pool identity:** every investment slice resolves one matching pool with the
   same dealId and securityId.
8. **Entitlement arithmetic only:** entitlementTotal equals the sum of positive
   member entitlementAmount values. No further economic invariant is asserted in
   F2.
9. **Tier conservation:** sum tier totalAllocated equals
   fundCashEquation.distributions; each tier totalAllocated equals gpShare plus
   lpShare. All are zero for V2-S-0100.
10. **No opening flows:** every F2 partner and class cashFlowVector is empty.

Any violation refuses with existing RECEIPT_CONSERVATION_VIOLATION at stage
receipt. No new refusal code is needed for conservation.

## Output limits

Reuse ADMISSION_LIMIT_EXCEEDED and stage receipt.

### Row limit

Enforce V2_ADMISSION_LIMITS.MAX_OUTPUT_ROWS prospectively before allocating
receipt arrays.

The row count includes:

- one receipt root;
- one row per component manifest entry;
- one fund-cash-equation row;
- every opening cash lot, investment slice, and entitlement pool;
- every journal entry and posting;
- every tier allocation;
- every partner and class ledger;
- every partner and class cash-flow entry;
- every sourceRef and upstreamReceiptId.

Tests cover the exact limit and one row over it. The helper that computes the
count is tested directly so boundary tests do not need to allocate a 100,000-row
receipt.

### Byte limit

Add V2_ADMISSION_LIMITS.MAX_SERIALIZED_OUTPUT_BYTES = 16 * 1024 * 1024.

The measured object is the complete final receipt with resultHash attached —
never the preimage. After building the detached plain-object candidate,
computing resultHash, and attaching it, compute the canonical JSON UTF-8 byte
length of that complete receipt; refuse when it exceeds the limit. Measurement
happens after resultHash attachment and before deep-freeze and return. For
V2-S-0100 the measured size is 4,206 bytes; the 4,126-byte preimage is not the
measured object. Tests cover the exact byte limit and one byte over using the
byte-count helper, not a large persisted artifact.

These are memory-safety bounds for an internal tool, not throughput or
service-level guarantees.

## Runtime opening-state types

event-stream-engine-v2.ts must define explicit runtime types:

- HydratedOpeningCashLot: full cash-lot identity, owner, classification,
  sourceRef, Decimal originalAmount, mutable runtime remainingBalance.
- HydratedOpeningInvestmentSlice: unique investmentLotId row identity,
  sourceRef, pool/deal/security identity, owner, Decimal costBasis,
  relievedAmount, remainingBasis, and entitlementAmount.
- HydratedOpeningEntitlementPool: pool/source/deal/security identity and Decimal
  entitlementTotal.
- OpeningJournalEntry and OpeningJournalPosting: detached balance-forward
  records using the closed accounts.
- EventStreamState: the existing event-lane properties — cashSourceLots,
  investmentLots, callableTrackers, partnerLedgers, derivedEvents, and
  endingCash — keep their current types and semantics and are not replaced,
  unioned, or repurposed. Hydration adds four new readonly properties that sit
  beside them: openingCashLots (Map keyed by lotId), openingInvestmentSlices
  (Map keyed by investmentLotId), openingEntitlementPools (Map keyed by
  entitlementPoolId), and openingJournal (an OpeningJournalEntry array in
  canonical entryId order).

Consumers are fixed:

- Event processors and the deal-by-deal waterfall read only the existing
  event-lane maps. Opening rows are never inserted into cashSourceLots or
  investmentLots, so processor and waterfall behavior over those maps is
  byte-identical to today.
- The receipt builder is the sole consumer of the four opening* properties.
- Hydration of the existing properties is unchanged; the initializer only
  additionally constructs the opening* properties from the sealed normalized
  input.

The types contain no sourceCashLotId in F2.
